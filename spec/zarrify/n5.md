# Part 1. The convention

This convention gives a layout only to the containers that meet its
requirements. Where it says that "the input is rejected", or that
something MUST hold, a container that fails has no layout under this
convention, and the profile rejects it.

An N5 container (the N5 specification, version 4.0.0 and the 2.x versions
before it) is a hierarchy of groups and datasets. Each may have an
`attributes.json` document; a dataset's holds its shape, block size, data
type and compression. A dataset's blocks are objects at keys
`<dataset>/<i0>/<i1>/…`, each a header (mode, number of dimensions and the
block's size along each) followed by the elements in column-major (first
index fastest) order, big-endian, compressed as a whole.

The output is a Zarr v3 hierarchy with a node at the path of every N5 node.
Each N5 dataset becomes an array that reads the blocks with the
**`n5_default`** codec of the zarr-extensions registry
(`codecs/n5_default`), and each chunk holds a whole block object, header
included: the codec parses the header, so a block that is smaller than the
block size (the truncated edge blocks Java N5 writes) or larger (padded
ones) reads correctly. Every object of the container that is neither a
node's document nor a block is kept whole ([§6](#6-other-objects)).

## 1. Declaration

The root and `refkv_source` declare the convention
([conventions §11.2](../conventions.md#112-declaration)), the root with its source
metadata ([§5](#5-source-metadata)), if it has any, as the member `"n5"`. Every other
node that has source metadata ([§5](#5-source-metadata)) declares it with `{"n5": S}`.
Its CMO is:

```json
{
  "uuid": "ad5d4c39-c69e-48f7-a3ef-4cc8c607d416",
  "schema_url": "https://raw.githubusercontent.com/d-v-b/refkv/refs/heads/main/spec/zarrify/n5/schema.json",
  "spec_url": "https://github.com/d-v-b/refkv/blob/main/spec/zarrify/n5.md",
  "name": "refkv_zarrified",
  "description": "The Zarr layout of a N5 source zarrified by refkv, and the source's metadata"
}
```

`refkv_source`'s source metadata also holds the recorded ignored keys
([§5.1](#51-the-ir-mirror)).

## 2. Nodes

The **candidates** are the directories `D` (the root included) for which
the store has an object `D/attributes.json` (`attributes.json` for the
root). Each candidate's document is read ([spec/zarrify.md §1.6](../zarrify.md#16-json-documents)) and MUST be a JSON object;
otherwise the input is rejected.

Candidates are classified from the root down (in order of their number of
segments):

- a candidate inside a dataset (a proper descendant of a directory that is
  a dataset) is **not a node**, and its document is neither read nor
  checked: it, and the blocks of such a nested dataset, are other objects
  ([§6](#6-other-objects));
- otherwise, a candidate whose document has a member `dimensions` is a
  **dataset**;
- otherwise, it is an **explicit group**.

Every directory that is a proper ancestor of a dataset or an explicit
group, and is not one itself, is an **implicit group** (N5 has no document
for a group without attributes; any directory on a file system is a group,
and an object store has directories only as key prefixes). No other
directory is a node: a directory that leads to no `attributes.json` (for
example a directory of other files) is not a node, and its objects are
other objects ([§6](#6-other-objects)).

The hierarchy has one `zarr.json` per node, at `<path>/zarr.json`
(`zarr.json` for the root). A dataset's is [§3](#3-datasets)'s
[`N5Array`](#type-n5array); a group's is
`{"zarr_format": 3, "node_type": "group", "attributes": A}`:

<a id="type-n5group"></a>**`N5Group`**, a group's `zarr.json`:

| member | type | presence | value |
|---|---|---|---|
| `zarr_format` | integer | required | `3` |
| `node_type` | string | required | `"group"` |
| `attributes` | object | required | for an implicit group, `{}` (the root's has the declaration of [§1](#1-declaration)); for an explicit group, `A`, which holds the member `ome`, an [`N5Ome`](#type-n5ome), when [§4](#4-multiscale-images) applies, and then the members of a [`Declaration`](../conventions.md#type-declaration), the declaration of [§1](#1-declaration) (on the root, and on a group that has source metadata) |

## 3. Datasets

A dataset's document MUST have these members, or the input is rejected:

| member | value |
|---|---|
| `dimensions` | an array of `n` integers ([spec/zarrify.md §1.6](../zarrify.md#16-json-documents)), `1 ≤ n ≤ 32`, each from 0 to 2^53 − 1: the size along each dimension |
| `blockSize` | an array of `n` integers, each from 1 to 2^31 − 1 |
| `dataType` | one of the strings in the table below |
| `compression`, or else `compressionType` (below) | the compression: an object whose member `type` is a string |
| `compressionType`, if there is no member `compression` | the compression: a string `t`, which is read as the object `{"type": t}` (N5 before version 1.0.0) |

| `dataType` | Zarr `data_type` | bytes per element `b` |
|---|---|---|
| `uint8`, `int8` | `uint8`, `int8` | 1 |
| `uint16`, `int16` | `uint16`, `int16` | 2 |
| `uint32`, `int32`, `float32` | `uint32`, `int32`, `float32` | 4 |
| `uint64`, `int64`, `float64` | `uint64`, `int64`, `float64` | 8 |

Any other `dataType` (such as `string` or `object`) rejects the input.

**Dimension order.** The array's axes are the N5 dimensions in the order
`dimensions` lists them: the shape is `dimensions` and the chunk shape is
`blockSize`, neither reversed. N5 stores a block's elements with the first
dimension fastest; the `transpose` codec inside `n5_default` (order
`[n−1, …, 0]`) turns that layout into the array's. This is the convention of
the `n5_default` README's example (`examples/zstd_array`, where
`dimensions [256, 128]` becomes `shape [256, 128]`) and of `zarr-n5`, and it
is what makes block keys and chunk keys agree: the block at `i0/i1/…/i(n−1)`
is the chunk whose index along dimension `k` is `ik`.

**Compression.** The compression object's `type` selects the bytes-to-bytes
codec `C`, or none:

| `type` | `C` | members `C` carries |
|---|---|---|
| `raw` | none | `type` |
| `gzip` | `{"name": "gzip", "configuration": {"level": L}}` if the member `useZlib` is absent or `false`; `{"name": "numcodecs.zlib", "configuration": {"level": L}}` if it is `true` | `type`, `useZlib`, `level` |
| `zstd` | `{"name": "zstd", "configuration": {"level": L, "checksum": false}}` | `type`, `level` |
| `blosc` | `{"name": "blosc", "configuration": {"cname": c, "clevel": l, "shuffle": s, "typesize": b, "blocksize": k}}`, see below | `type`, `cname`, `clevel`, `shuffle`, `blocksize` |
| anything else, among them `lz4`, `xz`, `bzip2` and `jpeg` | rejected | |

The values of the codecs, from the compression object's members:

| value | member | MUST be | when the member is absent |
|---|---|---|---|
| `C`'s name, for `gzip` | `useZlib` | a boolean: `numcodecs.zlib` if it is `true`, `gzip` if it is `false`. Java N5 writes a gzip stream (RFC 1952) unless `useZlib` is true, when it writes a zlib stream (RFC 1950) | `gzip` |
| `L`, for `gzip` | `level` | an integer from −1 to 9; `L` is that integer, except that −1 (the default of Java's `Deflater`, which Java N5 writes) is 6, the level it stands for (the Zarr v3 `gzip` and `numcodecs.zlib` codecs take 0 to 9) | 6 |
| `L`, for `zstd` | `level` | an integer from −131072 to 22 (zstd's levels, which the Zarr v3 `zstd` codec takes); `L` is that integer | 3, the default of n5-zstandard |
| `c`, for `blosc` | `cname` | one of `blosclz`, `lz4`, `lz4hc`, `snappy`, `zlib` and `zstd` | rejected |
| `l`, for `blosc` | `clevel` | an integer from 0 to 9 | rejected |
| `s`, for `blosc` | `shuffle` | an integer 0, 1 or 2, for which `s` is `"noshuffle"`, `"shuffle"` or `"bitshuffle"` | rejected |
| `k`, for `blosc` | `blocksize` | an integer from 0 to 2^31 − 1 | 0 |
| `b`, for `blosc` | | the bytes per element | |

Any other value rejects the input. (A level only matters when encoding; the codec carries it
so that the compression can be recovered.) `blosc` is the n5-blosc compression. (A blosc
stream describes itself, so every n5-blosc block decodes with the Zarr `blosc` codec; these
checks make its configuration exactly the compressor's.)

The compression object's members that `C` does not carry (such as
n5-blosc's `nthreads`) are not read here; they are kept in the source
metadata ([§5](#5-source-metadata)).

**The array.** The dataset's `zarr.json` is the object

```json
{
  "zarr_format": 3,
  "node_type": "array",
  "shape": dimensions,
  "data_type": "...",
  "chunk_grid": {"name": "regular", "configuration": {"chunk_shape": blockSize}},
  "chunk_key_encoding": {"name": "v2", "configuration": {"separator": "/"}},
  "fill_value": 0,
  "codecs": [{"name": "n5_default", "configuration": {"codecs": [T, B, C]}}],
  "attributes": A
}
```

with the member `"dimension_names"` only when [§4](#4-multiscale-images) gives the array axis
names, and no other members:

<a id="type-n5array"></a>**`N5Array`**, a dataset's `zarr.json`: an
[`ArrayDocument`](../conventions.md#type-arraydocument) with these members:

| member | type | presence | value |
|---|---|---|---|
| `shape` | array of integer | required | `dimensions` |
| `data_type` | string | required | from `dataType`, by the table of data types above |
| `chunk_grid` | object | required | regular, its chunk shape `blockSize` |
| `chunk_key_encoding` | object | required | `{"name": "v2", "configuration": {"separator": "/"}}` |
| `codecs` | array of object | required | `[{"name": "n5_default", "configuration": {"codecs": [T, B, C]}}]`, the codecs of `n5_default` below |
| `dimension_names` | array of string | optional | only when [§4](#4-multiscale-images) gives the array axis names: those names, in array order |
| `attributes` | object | required | `A`: the members of a [`Declaration`](../conventions.md#type-declaration), the declaration of [§1](#1-declaration), with the dataset's source metadata ([§5](#5-source-metadata)), when it has any (and on the root, which always declares the convention); otherwise `{}` |

The codecs of `n5_default`, in this order:

| codec | value | when |
|---|---|---|
| `T` | `{"name": "transpose", "configuration": {"order": [n−1, …, 1, 0]}}` | always |
| `B` | `{"name": "bytes", "configuration": {"endian": "big"}}` | `b > 1` |
| `B` | `{"name": "bytes"}` | `b = 1` |
| `C` | the compression codec | when there is one; it is left out (the list is `[T, B]`) when there is none |

N5 has no fill value; blocks that do not exist read as 0.

### 3.1 Chunks

The **chunk keys** of a dataset at path `D` are `D/i0/i1/…/i(n−1)` (or
`i0/…/i(n−1)` for a dataset at the root), where each `ik` is the decimal
form of an integer with `0 ≤ ik < ceil(dimensions[k] / blockSize[k])`,
without leading zeros (`0` itself is the only form of zero). A dataset with
a zero in `dimensions` has no chunk keys. Its chunk objects ([spec/zarrify.md §1.4](../zarrify.md#14-store-inputs)) are the
store's objects with these keys, whatever their size; every other object
under `D` (an object whose name is not a chunk key, or whose index is
outside the grid) is an other object ([§6](#6-other-objects)).

Each chunk is present when its object is (and is not empty): its bytes
are the whole block object, header included, which the `n5_default` codec
decodes. Every other chunk is absent and reads as 0. An empty chunk object
is one of [§6](#6-other-objects)'s empty objects, whose key is kept there. (N5 readers fail on
an empty block, which an interrupted write can leave behind, rather than
read it as absent; the key records that the object was there.)

<a id="type-n5object"></a>**`N5Object`**, a present chunk, or an other object
([§6](#6-other-objects)): the whole of an object of the store, of size `s > 0`:

| part | range | presence | value |
|---|---|---|---|
| the object | source range `(i, 0, s)` | required | every byte of the object (for a chunk, the block, header included), `i` its own `url` source ([spec/zarrify.md §1.4](../zarrify.md#14-store-inputs)) |

An N5 block declares its **mode** in its header:

| mode | value |
|---|---|
| default | 0 |
| varlength | 1 |
| object | 2 |

Only default-mode blocks hold an array of the dataset's
shape, and nothing in a dataset's attributes says which mode its blocks
use, so the zarrifier, which reads no block ([spec/zarrify.md §1.4](../zarrify.md#14-store-inputs)), cannot know it. The
output always uses `n5_default`. A reader decoding a block whose mode is
not default, or whose header's number of dimensions is not `n`, fails on
that chunk (the `n5_default` codec rejects it, as its README requires);
the rest of the array reads normally.

## 4. Multiscale images

A group may describe a multiscale image in one of two widely used N5
conventions: COSEM (as on OpenOrganelle) and n5-viewer (as written by
BigDataViewer, Fiji's N5 plugins and Paintera). For each explicit group `G`
whose document has no member `ome`, the zarrifier tries COSEM first and
then n5-viewer; the first that **recognizes** `G` gives the OME-NGFF 0.5
object `M`, and `G`'s attributes get the member `"ome": M`. If neither
does, `G` has no `ome`. (A group recognized by both, such as
OpenOrganelle's, which have COSEM `multiscales` and n5-viewer `scales`,
uses COSEM.) Whatever is recognized, the N5 attributes themselves are in the source metadata ([§5](#5-source-metadata)).

**Levels.** A **level path** is a string of one or more segments separated
by `/`, none of them empty, `.` or `..`. It names the node at `G`'s path
joined with it, which MUST be a dataset.

**Axis types.** An axis named `x`, `y` or `z` is a space axis, `t` a time
axis, and `c` a channel axis; any other name is a custom axis (no type).
The axes are **valid** when their names are nonempty and distinct and, in
array order, they are at most one time axis, then at most one channel or
custom axis, then two or three space axes, as OME-NGFF 0.5 requires.

**Units.** A unit string maps by [conventions §5](../conventions.md#5-units)'s table; a string that is already one
of that table's unit names (`micrometer`, `nanometer`, …, `hour`) is kept
as it is. Any other string gives no unit.

**COSEM.** `G` is recognized when all of these hold:

- its member `multiscales` is a nonempty array whose first element `m` is
  an object whose member `datasets` is a nonempty array of objects (only
  `m` is read);
- every element `d` of `datasets` has a member `path` that is a level path,
  and its **transform** is `d`'s member `transform` if `d` has one, and
  otherwise the member `transform` of the level's dataset document; the
  transform is an object with the members of the table below, where `n` is
  the level's number of dimensions;
- every level has the same `n`, and after the reordering below the same
  axes and the same units;
- the axes are valid.

| member | value |
|---|---|
| `axes` | an array of `n` strings |
| `scale` | an array of `n` numbers, each positive |
| `translate` | an array of `n` numbers, or absent (zeros) |
| `units` | an array of `n` strings, or absent (no units) |
| `order` | the string `"C"` or `"F"`, or absent (`"C"`) |

COSEM lists a transform's values in C order, the reverse of N5's dimension
order (OpenOrganelle's `fibsem-uint16/s0` has `dimensions` `[12000, 1600,
6368]` in the order x, y, z, and the transform `"axes": ["z", "y", "x"]`),
unless its `order` is `"F"`. So, for order `"C"`, `axes`, `scale`,
`translate` and `units` are each reversed onto the dimension order; for
`"F"` they are used as they are. Then `M` is

```json
{"version": "0.5", "multiscales": [{
  "name": ...,
  "axes": [{"name": a, "type": ..., "unit": ...}, ...],
  "datasets": [{"path": path, "coordinateTransformations": [
    {"type": "scale", "scale": [...]},
    {"type": "translation", "translation": [...]}]}, ...]
}]}
```

with `name` only when `m`'s member `name` is a string (it is that string);
each axis with `type` only when it has one and `unit` only when its unit
maps; and the datasets in `datasets`' order, each with its path as written
and the scale and translation of its transform (the translation always
present, zeros when `translate` is absent). Its types:

<a id="type-n5ome"></a>**`N5Ome`**, `M`, a recognized group's `ome`:

| member | type | presence | value |
|---|---|---|---|
| `version` | string | required | `"0.5"` |
| `multiscales` | array of [`N5Multiscale`](#type-n5multiscale) | required | one multiscale |

<a id="type-n5multiscale"></a>**`N5Multiscale`**:

| member | type | presence | value |
|---|---|---|---|
| `name` | string | optional | COSEM only: `m`'s member `name`, present only when it is a string |
| `axes` | array of [`N5Axis`](#type-n5axis) | required | one per dimension, in array order (the dimension order) |
| `datasets` | array of [`N5Dataset`](#type-n5dataset) | required | the levels: for COSEM in `datasets`' order, for n5-viewer `s0`, …, `s(k−1)` |

<a id="type-n5axis"></a>**`N5Axis`**:

| member | type | presence | value |
|---|---|---|---|
| `name` | string | required | the axis's name |
| `type` | string | optional | present only when the axis has a type (**Axis types**): `"space"` for `x`, `y` and `z`, `"time"` for `t`, `"channel"` for `c`; a custom axis has none |
| `unit` | string | optional | present only when the axis's unit maps (**Units**): for n5-viewer, the unit of every space axis |

<a id="type-n5dataset"></a>**`N5Dataset`**, a level:

| member | type | presence | value |
|---|---|---|---|
| `path` | string | required | the level path, as written (COSEM), or `s<i>` (n5-viewer) |
| `coordinateTransformations` | array of object | required | a [`Scale`](../conventions.md#type-scale), then a [`Translation`](../conventions.md#type-translation), always present |

**n5-viewer.** `G` is recognized when all of these hold:

- the **levels** are found by the first of these that applies:
  - `G` has a member `scales`: it is a nonempty array of `k` arrays, each of
    `n` positive numbers, the **factors** of level `i`; the levels are the
    datasets `s0`, …, `s(k−1)` (level paths), each with `n` dimensions;
  - otherwise: `s0` and `s1` are datasets, and the levels are `s0`, `s1`,
    …, `s(k−1)` for the largest `k` such that each of them is a dataset;
    the factors of `s0` are its member `downsamplingFactors` if it has one,
    else `n` ones; the factors of each later level are its member
    `downsamplingFactors`, which it MUST have; each `downsamplingFactors` is
    an array of `n` positive numbers, and every level has the `n`
    dimensions of `s0`;
- the **resolution** `r` and the **unit**: the member `pixelResolution` of
  `G`, or, if `G` has none, of `s0`'s document. It is either an object with
  `dimensions`, an array of `n` positive numbers (`r`), and optionally
  `unit`, a string; or an array of `n` positive numbers (`r`, no unit). If
  neither document has `pixelResolution`, `r` is `n` ones and there is no
  unit. (`pixelResolution` is in dimension order.)
- the **axes**: `G`'s member `axes`, an array of `n` strings, if it has
  one; else `["x", "y"]` for `n = 2` and `["x", "y", "z"]` for `n = 3`
  (for any other `n`, `G` is not recognized). The axes are valid.

Any member above that is present but not of the stated form means `G` is
not recognized. Then `M` is as for COSEM, without `name`, with the datasets
`s0`, …, `s(k−1)`, each with a scale and a translation: along dimension
`j`, level `i`'s scale is `r[j] × factors_i[j]` and its translation is
`((factors_i[j] − 1) / 2) × r[j]`, since N5's downsampling (as BigDataViewer
and the N5 tools do it) centers a downsampled voxel on the voxels it
averages. The unit, if it maps, is the unit of every space axis.

**Dimension names.** OME-NGFF 0.5 requires every level array to have
`dimension_names` equal to its image's axis names. Groups are considered in
ascending order of path (compared as UTF-8). A group that is recognized,
but one of whose levels is already a level of an earlier recognized group
with different axis names, is not recognized after all: it gets no `ome`. (An array can only have one set of
`dimension_names`, so the later image could not be valid 0.5.) Each level of
each recognized group then gets `"dimension_names"`: the axis names in
array order.

## 5. Source metadata

A node's source metadata `S` ([conventions §2](../conventions.md#2-attributes)) is
the object

```json
{"attributes": A, "metadata": M}
```

where each member is present only when its value is not empty, and
the node has source metadata only when `S` has a member. An implicit group,
which has no document, has none. Each node's document is also kept whole,
byte for byte, with the store's listing, on `refkv_source`, the store's **IR
mirror** ([§5.1](#51-the-ir-mirror)).

<a id="type-n5node"></a>**`N5Node`**, a node's `S`:

| member | type | presence | value |
|---|---|---|---|
| `attributes` | object | optional | `A`, present when not empty: the node's `attributes.json` document without its **layout members**, the container's version `n5`, and, for a dataset, `dimensions`, `blockSize`, `dataType`, `compression` and `compressionType`. It is the user's attributes and those of the multiscale conventions (`pixelResolution`, `transform`, `scales`, ...), unchanged. (A group's `dataType` or `compression` is not a layout member: it describes no dataset.) Every member is under the key, so none can collide with `ome` or with the conventions of the Zarr v3 hierarchy; a document that has its own `refkv_zarrified` or `zarr_conventions` nests them there |
| `metadata` | [`N5Metadata`](#type-n5metadata) | optional | `M`, present when not empty |

<a id="type-n5metadata"></a>**`N5Metadata`**, `M`: the layout members that the Zarr v3
metadata does not reproduce, in this order:

| member | type | presence | value |
|---|---|---|---|
| `n5` | any JSON value | optional | the member as written, when the document has it |
| `compression` | object | optional | for a dataset: the object of the compression object's members that its codec does not carry ([§3](#3-datasets)), when there is any |
| `compressionType` | any JSON value | optional | for a dataset whose document has both `compression` and `compressionType`: the member as written ([§3](#3-datasets) reads only `compression`) |

What `S` leaves out, the Zarr v3 metadata holds: `dimensions`, `blockSize`,
`dataType`, and the compression's `type` and the members its codec
carries. What neither keeps is layout: whether a default level was written
(or was −1 rather than 6), whether `useZlib` was `false` or absent, and
whether an old container wrote `compressionType` rather than `compression`.
So a node's document is recovered from its `zarr.json`: the members that [§3](#3-datasets)
reads back from the Zarr v3 metadata (`dimensions` the shape, `blockSize`
the chunk shape, `dataType` the data type, `compression` from the codec),
then those of `A`, and those of `M` set over them (the members of
`M.compression` over the compression object).

Members are copied as [spec/zarrify.md §1.6](../zarrify.md#16-json-documents)
reads them, except that a number written as an integer (a JSON number
with no fraction and no exponent) is kept exactly, every digit, beyond
2^53 − 1 too, and is written back so. Any other number is its binary64
value, and a number whose binary64 value is infinite still rejects the
input. Where [§3](#3-datasets) and [§4](#4-multiscale-images) use a number (a size, a level, a scale), they use
its binary64 value.

### 5.1 The IR mirror

`refkv_source` is the store's **IR mirror**
([conventions §8.9](../conventions.md#89-stores)): its table, from which every
node's `attributes.json` is rebuilt byte for byte and the listing (every
object's key and size) is read back, and its view, `refkv_source/tree`. Its
source metadata is `{"ir": I, "ignored": K}` (not a node's `S` of [§5](#5-source-metadata)): `I` the mirror's
description ([conventions §8.2](../conventions.md#82-the-table), with
`objects`), and `K` the recorded ignored keys of
[spec/zarrify.md §1.4](../zarrify.md#14-store-inputs) in ascending order of their UTF-8
bytes, present only when there is one (they are not objects, so the IR does
not hold them). The IR's elements (the N5 **source model**) are below:
the documents the profile reads are held, and every other object (blocks,
other objects, documents it does not read) is referenced, or empty.

<a id="type-n5mirror"></a>**`N5Mirror`**, `refkv_source`'s source metadata: a
[`Mirror`](../conventions.md#type-mirror) with these members, and no `empty_dirs`:

| member | type | presence | value |
|---|---|---|---|
| `ir` | [`IrDescription`](../conventions.md#type-irdescription) | required | `I`, the mirror's description, a store IR's, with `objects` ([conventions §8.2](../conventions.md#82-the-table), [§8.9](../conventions.md#89-stores)) |
| `ignored` | array of string | optional | `K`, the recorded ignored keys of [spec/zarrify.md §1.4](../zarrify.md#14-store-inputs), in ascending order of their UTF-8 bytes; present only when there is one |

### 5.2 Elements

Paths are relative to the IR's root, whose path is `""`; the root and the
directories are the listing's ([conventions §8.9](../conventions.md#89-stores)),
so the path of an object is its key, each segment named by that section's
rule. `<D>` is a node's path (`""` for the root), `<m>` a member's name and
`<o>` a decimal name index.

| path | kind | type | what |
|---|---|---|---|
| `""` | struct | | the root: the store's root directory (no extent) |
| a directory's path | struct | | each directory of the store (no extent) |
| `<D>/attributes.json` | object | | the document of a node (an explicit group or a dataset, [§2](#2-nodes)): held, extent `(0, s)` |
| `<D>/attributes.json/<m>` | value | `ascii[n]` | the value of the document's top-level member named `<m>` (below), its bytes as written: the member's JSON text |
| `<D>/attributes.json/gaps/<o>` | gap | | the rest of the document at offset `<o>`: braces, member names, colons, commas and whitespace (the whole document when it has no member) |
| `<D>/attributes.json/json` | value | `ascii[s]` | in place of the members and gaps, the whole document, when it has more than 4096 top-level members (so that a document's rows stay few) |
| any other key | object | | every other object: a block, an other object ([§6](#6-other-objects)), a candidate's document that is not read ([§2](#2-nodes)); referenced (one leaf, its whole source) when its size is not 0, empty otherwise |

**Members.** A document's top-level members are its values' elements in the
order the document writes them, a member written twice being two elements
(the hierarchy reads the last, [spec/zarrify.md §1.6](../zarrify.md#16-json-documents)). They are named by
the rule of [ND2 §5.3](nd2.md#53-elements), with `gaps` and `json` the fixed
names: among the members, in order, one whose name `t` is not empty, holds no
`/` or `~`, is neither `gaps` nor `json` and is the first with name `t` is named `t`, with no
name index; any other is named `t` with `%`, `/` and `~` percent-encoded,
then `~`, with the number of earlier members named `t` as its name index. A
name read from an escape that leaves a surrogate unpaired has U+FFFD in
place of that surrogate (the bytes of the document keep the escape). The
view ([conventions §8.7](../conventions.md#87-the-view)) shows each member whose
value is at most 1024 bytes as its JSON text, a string.

### 5.3 Equivalence

Hierarchies of one store are compared entry for entry, `refkv_source` included
([conventions §11.4](../conventions.md#114-equivalence)).

## 6. Other objects

An **other object** is an object of the store
([spec/zarrify.md §1.4](../zarrify.md#14-store-inputs)) whose size is not
0 and which is neither the `attributes.json` of a node (an explicit group
or a dataset, [§2](#2-nodes)) nor a chunk object of a dataset ([§3.1](#31-chunks)), whatever its
size. Among them are READMEs and other files a writer put next to the
data, the objects of directories that are not nodes, the objects under a
dataset that are not chunk keys, and a dataset nested in a dataset (its
`attributes.json` and its blocks), which is not a node ([§2](#2-nodes)). Each is kept
whole: the hierarchy has the key `refkv_source/objects/<k>`, where `k` is the
object's key, escaped, and its bytes are the object's. (An empty object
holds nothing, and has no key: the mirror's listing has it, [§5.1](#51-the-ir-mirror).)

**Escaping.** A last segment that a Zarr reader would take for a node's
document must not end a key under `refkv_source/objects/`: when the last
segment of `k` is `zarr.json`, `.zarray` or `.zgroup` followed by any
number (zero included) of `~`, one `~` is appended to it. So `zarr.json`
is kept at `refkv_source/objects/zarr.json~`, `a/.zgroup` at
`refkv_source/objects/a/.zgroup~`, and `zarr.json~` at
`refkv_source/objects/zarr.json~~`. The escape is one to one: a key whose
last segment is one of these names followed by at least one `~` is the
object's key with one `~` removed, and every other key is the object's.
No Zarr v3 or Zarr v2 reader then opens a node under `refkv_source/objects/`.

**Empty objects.** The **empty objects** are the store's objects of size
0, the empty chunk objects ([§3.1](#31-chunks)) among them. They are objects of the
mirror's listing ([§5.1](#51-the-ir-mirror)), with no extent, and have no key in
the hierarchy; the recorded **ignored keys** of
[spec/zarrify.md §1.4](../zarrify.md#14-store-inputs) are the member
`ignored` of `refkv_source`'s source metadata.

**`refkv_source`.** The hierarchy always has `refkv_source`, the mirror. When
the root is a group, it is the group `refkv_source`, a child of the root (the
source metadata node of [conventions §2](../conventions.md#2-attributes)), whose
`zarr.json` is `{"zarr_format": 3, "node_type": "group", "attributes": A}`,
`A` declaring the convention ([§1](#1-declaration)) with the source metadata of
[§5.1](#51-the-ir-mirror); the mirror's groups and arrays, and the other objects'
keys, are below it, and the directories between it and the objects are not
nodes and have no `zarr.json`. A hierarchy that then has a node ([§2](#2-nodes)) at
the path `refkv_source`, or below it, is rejected, since its keys would mix
with these. When the root is an array, which can have no children, the
same keys (the mirror's documents and arrays, and the objects' keys) are
plain keys of the archive under `refkv_source/`, which a Zarr reader that
opens the root never reads as nodes.

# Part 2. The profile

The N5 profile of [spec/zarrify.md](../zarrify.md) is [§8](#8-n5-profile) of this document. What every profile's Part 2 shares is in
[spec/zarrify.md, Profiles](../zarrify.md#profiles).

## 8. N5 profile

The profile was chosen because the store's root has an `attributes.json`
([§1.4](../zarrify.md#14-store-inputs)). The store is listed ([§1.5](../zarrify.md#15-listing-a-store)), and its documents are read as JSON
([§1.6](../zarrify.md#16-json-documents)): the `attributes.json` of each candidate of
[the convention §2](#2-nodes), which MUST be a
JSON object. They are read in rounds
([conventions §8.9](../conventions.md#89-stores), producers): each round is
every candidate not read yet whose candidates above it are read and are
groups, read concurrently, each document once and whole; a candidate inside
a dataset is never read. Their integer literals are kept exactly where the convention
copies them ([its §5](#5-source-metadata)),
beyond 2^53 − 1 too, in place of [§1.6](../zarrify.md#16-json-documents)'s last paragraph; every number the
convention uses is its binary64 value, as [§1.6](../zarrify.md#16-json-documents) says.

### 8.1 Rejection

The input is rejected when a rule of [§1.4](../zarrify.md#14-store-inputs)–[§1.6](../zarrify.md#16-json-documents) fails, and when the
convention gives it no layout: wherever it says that the input is
rejected, or that something MUST hold and it does not.

### 8.2 Chunks and other objects

Each chunk object is a chunk entry referencing the whole object ([§1.4](../zarrify.md#14-store-inputs)); an
object of size 0 has no entry, and its key is one of [the convention §6](#6-other-objects)'s
empty objects' keys. The block's header is not read: the output
depends only on the keys and sizes in the listing.

Every other object of [the convention §6](#6-other-objects)
is referenced whole in the same way, by an entry under the key
`refkv_source/objects/<k>` (with a `~` appended when [the convention §6](#6-other-objects)
escapes `k`'s last segment) whose `url` source is the URL of the object `k`
([§1.4](../zarrify.md#14-store-inputs)). (This is the one place where an entry's key is not its object's
key; [§1.4](../zarrify.md#14-store-inputs)'s rules otherwise apply: the sources are in ascending order of
their entries' keys, each entry referencing its object's whole range.)
The documents under `refkv_source/` (the mirror's, [the convention §5.1](#51-the-ir-mirror))
are deflated and, like the chunks, not among the documents a reader fetches
when it opens the archive ([conventions §2](../conventions.md#2-attributes)).

### 8.3 Summary

This section is informative. Both implementations print a one-line JSON
summary, with these members:

| member | value |
|---|---|
| `groups` | the groups, explicit and implicit |
| `arrays` | the arrays |
| `chunks` | the number of chunk entries |
| `emptyChunks` | the chunk objects of size 0 |
| `objects` | the store's objects |
| `otherObjects` | the entries under `refkv_source/objects/` |
| `images` | the recognized groups, each `{"path", "convention"}` |
| `listingRequests` | the listing's requests |
| `format` | from the Rust core |
| `reads` | from the Rust core, the store run's counts: the objects read, the batches, the ranges asked and their bytes, the requests, spans and bytes read, the objects listed |
| `elements` | from the Rust core: the IR's elements |
| `folded` | from the Rust core: what the mirror's table folded |

The members are the implementations', not the convention's.
