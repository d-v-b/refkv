FLAC¶

The Zarr layout of a FLAC file (Free Lossless Audio Codec, .flac, RFC 9639), and the translation of its metadata blocks and tags into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the FLAC profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: e9108d07-b24b-432f-a8ce-09d80c8073b4 · Schema: schema.json

Changes: changes/flac/, one file per change.

Added 2026-10-25.

This document has two parts (conventions §11.1).

Like MP3’s, the hierarchy holds decoded audio, with no OME-NGFF metadata. The samples stay in the file as FLAC frames; the array’s codecs decode them when a chunk is read. FLAC is lossless: the array holds the recording’s own integer samples, exactly.

The footer’s CRC-16 (polynomial x^16 + x^15 + x^2 + 1, initial 0) covers the frame’s bytes before it, so that the CRC-16 of the whole frame is 0. A frame’s header gives no length: its subframes end where their bits do.

A frame decodes alone: unlike MP3’s or AAC’s, its samples depend on no other frame. Its block size B is the samples per channel it decodes to. In a fixed block size stream every frame but the last has the same block size, and the last may have fewer.

3. Tags¶

FLAC has no tags of its own beyond its Vorbis comments, but other tools add MP3’s: ID3v2 tags at the start of the file, before fLaC, and an ID3v1 tag, the last 128 bytes of the file when they start with TAG, measured as mp3.md §3 says. The convention does not decode an ID3v2 tag’s frames.

4. The layout¶

The hierarchy is a group at the root with an array at path samples and, when the file has PICTURE blocks with data, a group pictures of arrays: the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A}, where A has zarr_conventions and refkv_zarrified (§1) and nothing else.

4.1 The array¶

The stream’s frames are numbered from 0 in file order; N is their count, B the first frame’s block size, C the channel count, b the bits per sample and T the samples per channel, the frames’ block sizes summed. The array is a sharded array (spec/zarrify.md §2.1): each frame is an inner chunk, and each run of F frames a shard, one key of the store. The inner chunk shape is [B, C]: inner chunk j is frame j. The shard shape is [F, 1] inner chunks, with F = min(512, N) frames per shard: shard q, at samples/c/<q>/0, holds the frames q × F to min(N, (q + 1) × F) − 1. The inner codecs are [{"name": "refkv.stream", "configuration": {"format": "flac", "setup": S}}] (a StreamConfiguration), where S is the base64 of the setup: fLaC, then the 4-byte header 80 00 00 22 (the last block, STREAMINFO, 34 bytes), then the file’s STREAMINFO body (conventions §10).

FlacArray, the array’s zarr.json: a ShardedArray, sharded as spec/zarrify.md §2.1 says, of an unsharded array that is otherwise conventions §3’s (ArrayDocument, its fill value 0); these are its members that differ from an ArrayDocument’s:

Inner chunk j of the array, [j × B, (j + 1) × B) along time, is frame j as a refkv.stream chunk of one frame (conventions §10, a FlacInnerChunk): the header 01, the frame’s length as a varint and 02 (its position 0, less −1, as a zigzag varint), then the frame’s bytes. Its samples fill its first rows: the last frame’s, when it holds fewer than B, are followed by the fill value, past the array’s end. A shard is its frames’ inner chunks, one after the other, then the shard index, whose entries past the last frame (in the last shard only) are empty (spec/zarrify.md §2.1, a Shard).

So a reader that reads a few samples reads the shard index and the frames that hold them, and nothing else; the store holds one key per F frames. Since frames decode alone, no inner chunk needs another’s frames.

4.2 The pictures¶

The pictures group, {"zarr_format": 3, "node_type": "group", "attributes": {}}, present only when some PICTURE block’s data is not empty, holds for the i-th PICTURE block of the file, counted from 0, whose picture data is not empty, the array pictures/<i>: the data, as bytes (conventions §7: uint8, dimension byte; a SourceArray of the bytes form). Its fields are in pictures of §5.1. A picture whose media type is --> holds a URI, as text, in place of an image; its array holds the URI’s bytes.

4.3 The samples¶

Sample i of channel c is the ith sample of channel c that a FLAC decoder (RFC 9639) gives decoding the frames one after the other: an integer of b bits, the recording’s own, after the stereo decorrelation is undone, as a signed integer of the array’s data type. A decoder that gives the samples in the high bits of a wider integer (ffmpeg’s: a 24-bit sample in the top 24 bits of 32) is shifted back. FLAC is lossless, and decoding is exact: every conforming decoder gives these values, and STREAMINFO’s MD5, when it is not 0, is the MD5 of the array’s samples, interleaved, each little-endian in ceil(b / 8) bytes, sign-extended (RFC 9639 §8.2).

The sample rate is sample_rate of §5.1; sample i is at i / sample_rate seconds from the stream’s start.

The view (conventions §8.7) shows each ID3v2 header, the marker, each block’s header, STREAMINFO, an application’s ID, a seek table of at most 56 points, and the ID3v1 tag; opaque bytes are not shown.

5.4 Equivalence¶

Hierarchies of one file are compared entry for entry, refkv_source included (conventions §11.4).

7. What the layout does not express¶

This section is informative.

  • Variable block sizes. A stream whose frames hold different sample counts has no regular grid of frames; the profile rejects it (§8.1).

  • The channel layout. The channels are in the order of the frames’ channel assignment (RFC 9639 §9.1.3), or as a WAVEFORMATEXTENSIBLE_CHANNEL_MASK Vorbis comment says; the convention keeps the comment and does not apply it.

  • The seek table’s points, the reserved bytes of a cue sheet and the frames’ per-frame coding (channel decorrelation, predictors) are in the mirror, not in the root.

  • Pictures as images. A picture is kept as its bytes, not decoded.

Part 2. The profile¶

The FLAC profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

8. FLAC profile¶

8.1 The stream¶

The input is a FLAC file, which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/flac.json) chose: H holds the bytes 66 4C 61 43 (fLaC) at the offset A after the ID3v2 tags at its start (0 without one), each tag ID3, its size bytes each below 80, measured as the convention §3 says. Its precedence, 95, is before MP3’s, whose signature also takes a file that starts with ID3. A FLAC file whose ID3v2 tags end past H (552 bytes) does not match: the MP3 profile’s signature then takes it, and that profile rejects it; naming the FLAC profile (FlacSource, spec/zarrify.md §1.7) reads it.

Reads. A frame’s header gives no length, and no index records every frame’s offset: a SEEKTABLE holds a few points, a frame in each run of seconds, and a file need not have one. So the profile reads every frame’s bytes, as the MP3 profile does, and finds each frame’s end by its CRC-16 (below). It reads in rounds, so that it holds at most 16 MiB of frames at a time: the file’s first 64 KiB and its last 128 bytes; then, while the metadata blocks run past what it holds, the 64 KiB from each block header it does not hold, and of each block’s body what the profile decodes (STREAMINFO, SEEKTABLE, VORBIS_COMMENT and CUESHEET whole, an APPLICATION block’s ID, a PICTURE block’s fields up to its data); then the frames, 16 MiB at a time. Bytes read per file: every frame, the metadata blocks but the data of pictures, padding and applications past the 64 KiB windows, the ID3v2 headers, and the last 128 bytes; in 1 + k + ceil(M / 16 MiB) rounds at most, k the block headers past the 64 KiB windows read before them and M the frames’ bytes. A 3-minute stereo track at 44.1 kHz, about 20 MiB of frames after a 1 MiB cover picture, is read in 4 rounds, its picture’s data unread but the first 64 KiB.

Checks. A zarrifier MUST reject the input unless all of these hold, checked in this order:

  • ID3v2 tags: for each tag at the start, as mp3.md §8.1 checks them (its header within the file, syncsafe size bytes, the tag within the file), with its messages.

  • Marker: fLaC at A, before E, where E is the file’s size, or its size less 128 when the last 128 bytes, at or after A, start with TAG (the ID3v1 tag): no fLaC marker at <A>.

  • Metadata blocks: from A + 4, each block, up to the one whose header has bit 7 set: its header is before E; its type is not 127; the first block is STREAMINFO, and no STREAMINFO, SEEKTABLE or VORBIS_COMMENT block follows one of its type; a STREAMINFO body is 34 bytes, a SEEKTABLE body a multiple of 18, an APPLICATION body at least 4; the block ends at or before E; STREAMINFO’s bits per sample are at least 4; and a VORBIS_COMMENT, CUESHEET or PICTURE body is its fields exactly, no length past its end and no byte after its last field (the PICTURE block at 42 is malformed: its fields and data do not fit its body).

  • The first frame: the frames start right after the last block, at P0: P0 < E (no audio frames: ...), and a valid frame header starts there (the frame header at 42 is not valid: no frame sync code; ...: a CRC-8 that does not match): the sync code, no reserved or forbidden code (the convention §2), a coded number of the extended UTF-8 form, and its CRC-8.

  • Each frame: its blocking strategy is fixed (a variable block size (the frame at 42) is not supported: only a fixed block size stream is); its sample rate, channel count and bit depth, each its own or, for code 0, STREAMINFO’s, are STREAMINFO’s (the frame at 180 changes the sample rate from 8000 to 16000); its coded number is its index; it holds no more samples than the first frame; and a frame that another follows holds as many as the first (only the last frame may hold fewer).

  • Each frame’s end (below) is found within 16 MiB of its start (the frame at 3939 (frame 3) has no end: ...).

  • Total: when STREAMINFO’s total samples are not 0, the frames hold that many samples per channel (the frames hold 5120 samples per channel, not STREAMINFO's 8000: a stream cut at a frame’s end).

Frames. Frame 0 starts at P0. Frame j, starting at p, ends at the first q > p + h + 2 (h its header’s length) at which the CRC-16 of the bytes [p, q) is 0 and either q = E or a valid frame header starts at q; frame j + 1 starts at q, and its checks (above) require its number to be j + 1. The last frame is the one that ends at E. A frame that has no such q (a byte of it changed, the stream cut inside it, the next header’s CRC-8 broken) rejects the input.

So a frame is found by two checks at once: a CRC-16 of 0 over the frame (the chance that a wrong end passes it is 2^−16) and a valid header after it, its sync code and its CRC-8 (2^−8): a sync code inside a frame’s audio data, which FLAC does not prevent, is not taken for a frame. Since the CRC-16 of a run of whole frames is 0 at the end of each, a header numbered wrongly ends the frame before it (and rejects the input) rather than making it run on to the next header that matches. There are no bytes between frames, nor after the last but the ID3v1 tag: a stream with junk there has no last frame. The frames’ bytes are read to find the frames and check their CRCs, not decoded: the output is the frames’ offsets and lengths, which are the stream’s structure (spec/zarrify.md §1.2), and a stream whose CRCs fail is rejected, as a decoder would stop.

Why fixed block sizes only. Zarr’s chunk grids are regular, and sharding’s inner chunks are of one shape: a frame is an inner chunk only when every frame holds B samples. Chunks of whole frames (the MP3 profile’s layout) need that too: a chunk of k frames covers k × B samples only when the frames hold B each, and a frame across a chunk boundary would be decoded by two chunks and placed by neither. So a variable block size stream, rare (libFLAC and ffmpeg write fixed block sizes), is rejected by name rather than given another layout.

8.2 Shards¶

Inner chunk j (the convention §4.1), frame j of length L at o, is the reference of two ranges: a literal range of its refkv.stream header (01, varint(L), 02) and the frame’s range of source 0, (o, L):

FlacInnerChunk, inner chunk j, frame j of length L at o:

part

range

presence

value

the header

literal

required

the StreamChunk header of one frame: 01, varint(L), 02 (its position 0, less −1, as a zigzag varint)

the frame

source range (0, o, L)

required

the frame’s bytes

The array is sharded as spec/zarrify.md §2.1 says, F = min(512, N) inner chunks a shard: the array has ceil(N / F) shards, each present, and shard q’s reference, a Shard of the shard shape [F, 1], is the headers and ranges of its frames in order, then the literal index, 16 × F + 4 bytes. No ranges are joined, with or without checksums: a header lies between each two frames.

A shard’s payload is at most 41 × F + 12 bytes for frames of less than 2^28 bytes at offsets below 2^49 (each frame’s literal header part at most 10 bytes, its source range part at most 15 and its index entry 16, and the index’s part at most 12 bytes besides its entries): 21 004 bytes for F = 512, and with checksums, each source range part up to 6 bytes longer, 24 076, within the 32 KiB that shards are sized to and the 65 519 that a reference may hold (spec/zarrify.md §1.2). A reader of a few frames reads the shard’s index, 8 KiB, and those frames.

The pictures’ arrays (the convention §4.2) are cut as bytes are (conventions §7), each chunk a range of source 0 (the last chunk’s zero padding a literal range):

The ranges lie within the file. The output has no data sources: its source table is source 0 alone. refkv_source is the IR mirror (the convention §5.2). The archive has no other entries than the root’s, the array’s and the pictures’ zarr.json, the shards, the pictures’ chunks, and the mirror’s.

8.4 The description¶

This section is not part of the convention: nothing it specifies is written in an output. The parser returns, beside the IR, a description of the file: what it found of the source, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7). It holds none of an output’s decisions: the frames of a shard (§8.2), and the array’s data type, shape, chunks and codecs (§4.1) are the projection’s. Its JSON Schema is flac/description.json. The root’s source metadata of §5.1 follows from the description: sample_rate, channels and bits_per_sample from streaminfo, duration from samples and the sample rate, and the other members as the description gives them, each optional one absent when it is null or empty; and the refkv.stream setup from the bytes of the streaminfo element (§4.1). The projection reads them so, and makes refkv’s plan of the file from the description alone: shard_frames, F (§8.2), and data_type, the array’s data type, from bits_per_sample (§4.1). The plan belongs to refkv’s convention, not to the IR.
