# phkv benchmark results

Method, files and caveats: [README.md](README.md). Tables are generated by `report.py` from `results.json`,
and the parameter tables by `sweep.py`. A request is one read of the archive (a `Range` request over HTTP,
a `pread` on a file). "http 20 ms" is loopback with 20 ms added to each request.

These are the results after two changes to the first run: a hybrid store's superblock is found from the
ZIP end of central directory record instead of by probing, and the reader reads the window before it in
one request ([§17.2](../../../spec/bindings/phkv.md#172-finding-the-superblock)). The central directory
therefore starts where the superblock ends, and the hybrid file no longer has padding.

## What they show

For a lookup in a cold store (open plus one lookup), over HTTP with 20 ms per request, `refs` workload:

| keys | vzip | vzip, paged | phkv | hybrid, as vzip | hybrid, as phkv (before the change) | hybrid, as phkv |
|---|---|---|---|---|---|---|
| 1,000 | 3 req, 68 KiB | 4 req, 68 KiB | 1 req, 33 KiB | 4 req, 68 KiB | 8 req, 168 ms | 4 req, 84 ms |
| 10,000 | 3 req, 691 KiB | 4 req, 70 KiB | 2 req, 65 KiB | 4 req, 70 KiB | 11 req, 230 ms | 5 req, 106 ms |
| 100,000 | 3 req, 6.8 MiB | 4 req, 81 KiB | 3 req, 65 KiB | 4 req, 81 KiB | 14 req, 292 ms | 5 req, 105 ms |
| 1,000,000 | 3 req, 69 MiB | 4 req, 200 KiB | 5 req, 345 KiB | 4 req, 200 KiB | 18 req, 378 ms | 7 req, 148 ms |

1. **The unpaged vzip archive's open cost grows with the key count**: it reads the whole central
   directory (69 MiB, 3.9 s at 10^6 keys, in Python). Paged vzip and phkv do not.
2. **For a cold store, phkv and paged vzip are close.** phkv's open reads its PTRHASH and PAGES
   sections whole: they fit in the first read below about 10^4 keys, and are about 280 KiB beyond
   it at 10^6, so phkv takes 1 to 5 requests. Paged vzip takes 4 at every size. In time, phkv is ahead at
   every size (21 to 107 ms against 88 to 184 ms at 20 ms per request), but the vzip times include the
   Python reader's own work, which is 92 ms at 10^6 keys even on a local file.
3. **A lookup in an opened phkv store is two requests, not one**: the slot table gives the record's
   offset, then the record is read. With 1 KiB inline values it is three, because the first read of a
   record is 512 B (`Limits::record_read`). Paged vzip fetches a page and the entry's body (about 2,
   fewer when the page is cached); unpaged vzip needs 1 once its whole central directory is in memory.
   At 20 ms: 42 ms per lookup for phkv, 44 ms for paged vzip, 22 ms for unpaged vzip.
4. **A hybrid archive read as phkv now opens in 4 to 7 requests, not 8 to 18.** The superblock is
   found from the end of central directory record, which is in the first read, and the window before
   the superblock holds the directory and most sections. The probing it replaces cost a request for
   each probe distance from 128 KiB up to the central directory's size rounded up to a power of two,
   128 MiB at 10^6 keys (the superblock was 134,217,728 bytes from the end, with 61.6 MB of zero padding before the central directory
   to get it there). The hybrid file is also smaller: 157 to 164 B per key at 10^4 keys and over,
   against 172 to 225 B.
5. **`list` with phkv reads one page per request** ([Tuning](#tuning) has the writer's `page_size`). Pages are 4 KiB. For `refs`, 100 keys fit in 1 to 2
   pages. For `bytes` with 1 KiB values inline, the same 100 keys span 26 pages: 26
   requests and 546 ms at 20 ms, against 4 requests and 75 ms for paged vzip. The pages are adjacent,
   so one request would do. A hybrid store does not have this: its values are in the ZIP entries, so
   its records are small (2 requests, 42 ms).
6. **Size.** For `refs`, per key: standalone phkv 34 B at 10^3 and 38 B at 10^6; vzip 119 to 125 B; hybrid
   153 to 164 B. For `bytes` the 1 KiB values dominate: phkv is 6% smaller than vzip.

## Tuning

Which of these costs can a parameter remove? Over HTTP with 20 ms per request (`sweep.py`).

**Reader `Limits::tail`**, the bytes read first (default 64 KiB + 64 B), at 10^6 references, open and one lookup:

| tail | 64 KiB | 128 KiB | 256 KiB | 512 KiB | 1 MiB |
|---|---|---|---|---|---|
| standalone | 5 req, 345 KiB, 108 ms | 5 req, 409 KiB, 107 ms | 4 req, 299 KiB, 87 ms | 3 req, 512 KiB, 65 ms | 3 req, 1.0 MiB, 66 ms |
| hybrid | 7 req, 408 KiB, 148 ms | 7 req, 536 KiB, 150 ms | 6 req, 555 KiB, 129 ms | 5 req, 1.0 MiB, 109 ms | 5 req, 2.0 MiB, 112 ms |

A tail of 512 KiB takes the 10^6-key open from 5 requests to 3 (108 ms to 65 ms), because PTRHASH and
PAGES (about 280 KiB) then arrive with it. Beyond that it only reads more bytes. For a hybrid store the
tail is read twice (the end of the file, and the window before the superblock), so its bytes double.
Under 10^4 keys the default already reads the whole store's index.

**Reader `Limits::record_read`**, the bytes read at a record first (default 512 B), 10^5 keys of 1 KiB inline values:

| record_read | 512 B | 1 KiB | 2 KiB | 4 KiB |
|---|---|---|---|---|
| later lookup | 3.00 req, 1.5 KiB, 63 ms | 3.00 req, 2.0 KiB, 62 ms | 2.00 req, 2.0 KiB, 42 ms | 2.00 req, 4.0 KiB, 42 ms |

A record read as long as the record (2 KiB for a 1 KiB value and its key) takes the lookup from 3
requests to 2 (63 ms to 42 ms) at 0.5 KiB more. Reading more than the record costs bytes and no
requests. A store of references has records of tens of bytes, which 512 B already holds.

**Writer `page_size` and `inline_max`**, 10^5 keys of 1 KiB values (these are the writer's, recorded in the file; a reader cannot change them):

| page_size, inline_max | file | later lookup (record_read 512) | later lookup (record_read 4 KiB) | list of 100 keys |
|---|---|---|---|---|
| 4 KiB, 4 KiB (default) | 101.2 MiB | 3.00 req, 1.5 KiB, 63 ms | 2.00 req, 4.0 KiB, 42 ms | 26 req, 107 KiB, 546 ms |
| 16 KiB, 4 KiB | 101.1 MiB | 3.00 req, 1.5 KiB, 62 ms | 2.00 req, 4.0 KiB, 42 ms | 7 req, 115 KiB, 146 ms |
| 64 KiB, 4 KiB | 101.1 MiB | 2.97 req, 1.5 KiB, 62 ms | 1.97 req, 4.0 KiB, 42 ms | 3 req, 194 KiB, 63 ms |
| 4 KiB, none | 101.5 MiB | 2.96 req, 1.5 KiB, 63 ms | 2.96 req, 5.0 KiB, 63 ms | 2 req, 8.0 KiB, 42 ms |

A larger `page_size` cuts the `list` requests (26 to 3 at 64 KiB) by reading more bytes per page; it costs
lookups nothing, since a lookup reads a record, not a page. Values not inline (`inline_max` 0) make
records small, so a `list` is 2 requests, but every lookup is 3 (slot, record, value).

What the parameters do not fix: the lookup's two dependent reads (slot, then record) stay; `list`
still takes one request per page, only fewer pages; and a bigger `tail` is bytes read at every open.
