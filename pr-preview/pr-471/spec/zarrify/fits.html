FITS¶

The Zarr layout of a FITS file (.fits, .fits.gz, .fits.bz2): its images, its tables and its headers, and the translation of its headers into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the FITS profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 4b0d3a7e-1c52-4f6a-9b8e-2d7f0c6a1e93 · Schema: schema.json

Changes: changes/fits/, one file per change.

Added 2026-10-24.

This document has two parts (conventions §11.1).

Draft. This revision covers uncompressed images, multi-extension files, tables and tile-compressed images (ZIMAGE = T, the .fz files fpack writes) with the RICE_1, GZIP_1, GZIP_2 and NOCOMPRESS algorithms; HCOMPRESS_1 and PLIO_1 are rejected (§9.3). The design is design/plans/fits.md.

Part 1. The convention¶

A FITS file is a sequence of HDUs (header-data units), each an integral number of 2880-byte blocks: a header of 80-byte cards, 36 per block, ending with END and padded with spaces to a block boundary, then the data, padded with zero bytes to a block boundary. The first HDU is the primary; each other is an extension named by its XTENSION card: IMAGE, TABLE (an ASCII table) or BINTABLE (a binary table). FITS is the FITS Standard 4.0 (IAU FITS Working Group, 2016/2018); card and keyword names below are the standard’s.

Unlike most of refkv’s conventions, the hierarchy has no OME-NGFF metadata: FITS axes are sky coordinates under projections, spectral axes and table rows, not microscopy axes, and the world coordinate system is a header convention that viewers and libraries interpret for themselves. This section extends conventions §2 (“Nothing else”): a node’s attributes are zarr_conventions and refkv_zarrified alone.

2. HDUs and nodes¶

The file’s HDUs are numbered from 0 in file order. HDU i is the node at the path <i> (0, 1, …), a child of the root. EXTNAME and EXTVER are metadata, not paths: EXTNAME is optional and repeats (SCI four times in a WFPC2 file, 144 times in a Euclid frame, with EXTVER or a dotted name telling them apart), so a reader finds SCI,2 in the root’s table of HDUs (§5.1).

An HDU’s kind, by its mandatory cards (§9.3):

Random groups (GROUPS = T), tile-compressed tables (ZTABLE = T) and extensions of any other XTENSION are rejected by the profile.

2.1 A compressed file¶

A compressed file is a FITS file compressed whole: one or more gzip members (RFC 1952, .fits.gz) or bzip2 streams (.fits.bz2, as SDSS serves its frames), with nothing after them. No byte range of it reaches a value: gzip’s and bzip2’s blocks start at bit offsets that only decoding the stream finds, and a reader has to decode from a block’s start to reach a value in it. So every array with data has one chunk, of the array’s shape, and that chunk is the whole file, whichever of the file’s HDUs the array holds. Decoding it gives the FITS file: the HDUs before the array’s, the array’s bytes, its padding, and the HDUs after it. The chunk’s codecs then keep the array’s bytes alone:

codec, in the array’s codecs

what it does in decoding

{"name": "gzip", "configuration": {"level": 1}}, or {"name": "numcodecs.bz2", "configuration": {"level": 1}} for bzip2

decodes the file; decoding does not use the level

{"name": "refkv.skip", "configuration": {"length": k, "keep": n}} (npy §4.4)

keeps the n bytes at k of that: k the array’s first byte in the decoded file, n its bytes

the bytes codec of §3.1 or §4

decodes those bytes, as in an uncompressed file

keep is what several HDUs need, and any one image needs too: an array’s data is followed by its padding to a block, so even a file of one image decodes to more than the image’s bytes unless they fill a block, and bytes takes exactly its array’s size. The other way to stop at an array’s end, a chunk of its own per HDU, has no ranges to cut: the stream is usually one gzip member, so an HDU has no stream of its own. Offsets in the source metadata (offset, data_offset, §5.1) are of the decoded file, and the member stream says the file is compressed.

Everything else of the layout is as for the decoded file: the same nodes and arrays, the same metadata, with this one chunk in place of the cut of conventions §7. A tile-compressed image’s tiles are in the decoded file’s heap, out of a reference’s reach, and a chunk of them needs a literal prefix (§3.3) that a whole stream cannot carry: a compressed file with one is rejected (§9.3), and decompressing it first leaves a .fz file this layout reads well.

What it costs a reader. Reading any value of an array fetches the whole file and decodes it into memory, each time, as a gzip NRRD and a deflated .npz member’s reads do; and in a file of many HDUs, reading each array does so again, since each chunk is the same stream. A reader that wants one chip of a large mosaic should decompress the file first. What the layout gives such a file is a Zarr hierarchy, its metadata in the archive without a read, and its values in any reader of Zarr.

Chunks (conventions §7, contiguous values): the data is the row-major array V of the array’s shape, with elements of |BITPIX| / 8 bytes, at the HDU’s data offset. It is cut as contiguous values with the chunk limit L = 2^20 bytes (1 MiB): whole planes when they are small, else bands of rows, else runs of a row; an edge chunk along the cut axis is followed by zero bytes up to the whole chunk.

For example, a 10272 × 4755 float32 plane (a JWST mosaic’s SCI) has rows of 41088 bytes, so floor(2^20 / 41088) = 25 rows per chunk and k = ceil(4755 / 25) = 191. That count would pad its last chunk with 20 rows, over the 1024 bytes conventions §7 allows, so the plane is cut at the first larger count within them: 317 chunks of shape [15, 10272], with no padding. A 1100 × 1000 uint8 plane of 1100000 bytes, over L, is cut along its rows into 2 chunks of 550 rows, [550, 1000]; a 20-plane stack of 128 × 256 int16 (64 KiB planes) into 2 chunks of 10 planes, [10, 128, 256].

3.2 Value scaling¶

The array holds the stored values. FITS’s value scaling, physical = BZERO + BSCALE × stored, is not applied; BSCALE, BZERO, BLANK (the stored value of an undefined integer pixel) and BUNIT are recorded in the node’s source metadata (§5.2). That includes the unsigned convention: a BITPIX = 16 image with BZERO = 32768 and BSCALE = 1 is uint16 data stored as int16, and its array is int16.

3.3 Tile-compressed images¶

A tile-compressed image (the FITS tiled image compression convention, FITS Standard 4.0 section 10) is a BINTABLE with ZIMAGE = T whose rows are the tiles of an image of shape [ZNAXISn, …, ZNAXIS1] and ZBITPIX, each tile of shape [ZTILEn, …, ZTILE1] (ZTILE1 = ZNAXIS1 and the others 1 when absent: a row per tile), numbered in storage order (the tile index along axis 1 fastest). A row’s COMPRESSED_DATA descriptor gives the tile’s stream in the heap, coded with ZCMPTYPE, or its GZIP_COMPRESSED_DATA descriptor a gzip member of the tile’s raw values instead (the writer’s fallback); a row with both null has no tile. A float image (ZBITPIX < 0) whose table has ZSCALE and ZZERO columns is quantized: each tile’s stream codes 32-bit integers I, and its values are `(I − R + 0.5) × ZSCALE

  • ZZERO for the subtractive dithers (ZQUANTIZ), I × ZSCALE + ZZEROwithout one, in binary64 with each operation rounded ([spec/zarrify.md §1.3](../zarrify.md#13-arithmetic)), then the array's type;Ris the dither's random value, from cfitsio's table of 10,000 values (the Park–Miller generator from seed 1, each value as a binary32), which tiletenters at((t + ZDITHER0 − 1) mod 10000) and walks as cfitsio does (unquantize.c: the start int(R_0 × 500), one value per pixel, NaN pixels included, the index wrapping at 10,000); an integer equal to ZBLANK(the row's, or the header's) is NaN, and−2147483646is 0 underSUBTRACTIVE_DITHER_2`. The tiles of an integer image, and a float image’s fallback tiles, are the values as stored.

4. Tables¶

A binary table is rows of NAXIS1 bytes, NAXIS2 of them, each a concatenation of its TFIELDS columns’ fields with no padding, then, after THEAP bytes from the start of the data (NAXIS1 × NAXIS2 when the card is absent), the heap of variable-length arrays, the last of the PCOUNT supplemental bytes. An ASCII table is rows of text and has no heap. A table’s group holds the arrays <i>/rows and <i>/heap, and the column definitions are in the group’s source metadata (§5.2).

4.1 Rows as a struct¶

A binary table’s rows are an array of one struct element per row, the columns its fields, as the HDF5 convention presents a compound (hdf5 §3.1). A chunk is whole rows of the file, big-endian, as an image’s are; nothing is copied. A column’s TFORMn is rTa: a repeat count r (1 when absent), a letter T, and text a that no field depends on.

A column of r values of a type other than A, with r above 1, has a nested struct of the fields 0, 1, … r − 1, since a field of a Zarr struct has no shape (TDIMn is metadata, in the column’s dim). A logical is not bool because a bool is the byte 0 or 1, and F is neither. A column with r = 0 has no bytes and no field. The values are the stored ones: TSCALn, TZEROn and TNULLn are recorded in the column’s source metadata and not applied, as §3.2 says of an image’s.

A column’s name. A field is named TTYPEn, its spaces trimmed, or col<n> when that card is absent or blank. A column’s field (FitsColumn) gives the name.

Variable-length columns stay out. The field of a P or Q column holds its descriptor, not its values, which stay in the heap array as bytes. A row’s elements are of one size, and a variable-length array’s values are of a size that differs by row, outside the row; no Zarr data type holds them by reference to the file’s bytes, without copying them or their offsets out of the heap. A reader finds row k’s values at o bytes into heap, n values of the column’s type, big-endian.

When the rows stay bytes. The rows are bytes when a field cannot be written, and the node’s not_struct (§5.2) gives the first of these that holds, in this order:

not_struct

when

ascii

the table is an ASCII table: a column is text a reader parses by its TFORMn

form

a TFORMn is not of the table above (no letter, another letter, or a P or Q of r above 1)

names

two columns have one name (FITS forbids it, case aside; a struct cannot hold it)

empty

no column has a field, or NAXIS1 is 0

width

the fields’ bytes do not sum to NAXIS1: the columns do not tile the row

fields

the leaf fields number more than 4096 (an A column has one, a descriptor two): past that, a zarr.json of a nested field per value is too long to be of use

row_size

NAXIS1 is over the chunk limit 2^20, which a row has to fit

A tile-compressed image’s table (§3.3) is not a table here.

8. What the layout does not express¶

This section is informative. The layout keeps everything in the file but gives some of it no Zarr expression:

  • World coordinates. The WCS cards (CTYPEn, CRPIXn, CRVALn, CDi_j or PCi_j and CDELTn, CUNITn, alternates A–Z, SIP, TPV and lookup distortions) are kept as cards, not interpreted: placing a pixel on the sky is a library’s job (astropy.wcs, wcslib), and the hierarchy has no OME-NGFF coordinate metadata.

  • Value scaling. BSCALE, BZERO and BLANK are recorded, not applied (§3.2).

  • Table columns. A column is a field of its table’s struct, not an array of its own, since its values are strided through the rows (§4); a reader of one column reads whole rows. ASCII tables, and the binary tables §4.1 leaves as bytes, are described and not decoded.

  • Variable-length columns. A P or Q column’s values are bytes of the heap, by the descriptor in its row (§4.1).

  • Checksums. CHECKSUM and DATASUM are cards; nothing verifies them.

  • ASDF and JSON trees (JWST’s ASDF extension, Rubin’s JSON HDU) are the bytes of a one-row table.

  • Random groups and tile-compressed tables are rejected.

  • Partial reads of a compressed file. Any read decodes the whole stream (§2.1).

Part 2. The profile¶

9. FITS profile¶

9.1 Choosing the profile¶

The input is a FITS file, which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/fits.json) chose, one of:

  • bytes 0–8 of H are SIMPLE  = and byte 29 is T (the fixed-format logical of the standard’s first card);

  • H begins a gzip member (1F 8B 08), and the bytes it decodes to begin as the first case says;

  • H begins a bzip2 stream at its first block (BZh, a digit from 1 to 9, then the block’s magic number 31 41 59 26 53 59). A block decodes only whole, so H cannot say more: a bzip2 file of anything else is rejected once read (§9.3), as not a FITS file.

A file whose first card is SIMPLE = F (a non-conforming file) and a file whose first card is XTENSION (an extension written alone), compressed or not, match no profile’s signature and are rejected.

9.2 Reading¶

The profile reads headers and the main tables of tile-compressed images, never data, but for a compressed file. A compressed file is read whole, in one range, and decoded twice, as its decoded size is needed before the first header, and the file holds the decoded file’s size nowhere it can be trusted (gzip’s is modulo 2^32 and per member, bzip2 has none): once to its end, keeping nothing, then along with the walk below, whose “file” is the decoded file, keeping only the windows. The output depends on the stream’s structure and the headers, not on a value of the data (Structure only). For each HDU in turn, from its first byte: a window of at most 2^16 bytes, extended by such windows until the header’s END card is in it; the bytes of the window past the header are the next HDU’s first bytes when they reach them. A header MUST end within 2^24 bytes of its first byte, else the input is rejected (§9.3). A tile-compressed image’s main table (NAXIS1 × NAXIS2 bytes at its data offset, at most 2^26 bytes) is read in one range, requested with the next HDU’s window when the current window does not reach it.

9.3 Checks¶

The input is rejected unless all of these hold, checked in this order, HDU by HDU, every check applying whatever the other cards hold. A rejection names the HDU by its number.

  • Compression: a compressed file is at most 2^31 bytes, since it is held while it is walked and any reader would hold it whole; it decodes to its end, and each gzip member’s or bzip2 block’s checksum holds. Nothing may follow its last member or stream.

  • File: the file’s size (a compressed file’s decoded size, as in every check below) is at least 2880; a file that does not begin with SIMPLE  = and a T at byte 29 is not a FITS file.

  • Header: every card scanned, up to and including END, is 80 bytes of printable ASCII (bytes 32–126); an END card is found within the lesser of the file’s remaining bytes and 2^24.

  • Mandatory cards, at these positions, each with the keyword the standard requires there and an integer value where one is required ('sixteen' as a BITPIX is rejected): card 0 SIMPLE (the primary) or XTENSION; 1 BITPIX, in {8, 16, 32, 64, −32, −64}; 2 NAXIS, in 0 … 999; 3 to 2 + NAXIS: NAXIS1 … NAXISn, each at least 0; for an extension, then PCOUNT (at least 0) and GCOUNT (at least 1). An extension’s XTENSION is IMAGE, TABLE or BINTABLE (trailing spaces trimmed); any other is rejected and named. A card GROUPS = T (random groups) is rejected.

  • Data size: D = |BITPIX| / 8 × GCOUNT × (PCOUNT + NAXIS1 × … × NAXISn) computed exactly (0 when NAXIS = 0, with PCOUNT = 0 and GCOUNT = 1 for the primary) is at most 2^53 − 1, and data_offset + D is at most the file’s size, where data_offset is the HDU’s first byte plus its header’s blocks. The data’s padding MAY be short (a truncated final block); the next HDU, if any, starts at the next block boundary.

  • Tables (TABLE and BINTABLE): after GCOUNT, the card TFIELDS, an integer in 0 … 999; BITPIX is 8 and NAXIS is 2 (named in the rejection with the extension’s type); a card TFORMn exists for each n in 1 … TFIELDS; THEAP (an integer when present; NAXIS1 × NAXIS2 when absent) is at least NAXIS1 × NAXIS2 and at most NAXIS1 × NAXIS2 + PCOUNT; a card ZTABLE = T (a tile-compressed table) is rejected.

  • Tile-compressed images (BINTABLE with ZIMAGE = T), in this order: the file is not compressed (§2.1); the table is at most 2^26 bytes; ZCMPTYPE is RICE_1, RICE_ONE, GZIP_1, GZIP_2 or NOCOMPRESS (HCOMPRESS_1 and PLIO_1 are rejected and named; any other is rejected); ZBITPIX is a BITPIX value; ZNAXIS in 1 … 999; each ZNAXISn at least 0 and ZTILEn (defaulted) in 1 … ZNAXISn (1 when ZNAXISn is 0); for RICE_1, BLOCKSIZE is 16 or 32 and BYTEPIX 1, 2 or 4; ZQUANTIZ (when present) is NO_DITHER, SUBTRACTIVE_DITHER_1 or SUBTRACTIVE_DITHER_2, and a dither has ZDITHER0 in 1 … 10000; every column is COMPRESSED_DATA (1PB or 1QB), GZIP_COMPRESSED_DATA (1PB or 1QB), ZSCALE (1D), ZZERO (1D) or ZBLANK (1J) with that TFORM (UNCOMPRESSED_DATA and NULL_PIXEL_MASK are rejected and named; any other column is rejected); COMPRESSED_DATA is a column, and ZSCALE and ZZERO both or neither; the row count is the tile count. Then, from the table: no tile has both descriptors non-null; each tile’s stream lies within the heap; the present tiles are in storage order in the heap (a tile starting before the previous present tile ends is rejected). Every integer card named here is an integer.

  • Count: at most 65536 HDUs.

After an HDU, if the next block boundary is within the file and the file has at least 80 bytes from it that begin XTENSION=, they start the next HDU; otherwise the remaining bytes are special records (§6.1), described and never read, and the walk ends. No other card is checked: the values the layout uses change the output only as the convention says, and never reject the input.

9.4 Chunks¶

An image’s data is D contiguous bytes at data_offset, NAXIS1 varying fastest: the array V of the convention §3.1, row-major at that offset. Every chunk of the array is present. The chunk with coords c, at <i>/c/<coords>, is the chunk of V with those coords, referenced as conventions §7 references a chunk of contiguous values with the chunk limit 2^20: one range of source 0, followed for an edge chunk by its zero padding. Where conventions §7 makes that padding a literal range, it is instead the range (1, 0, p) of the output’s zero data source (spec/zarrify.md §1.2), p the padding’s bytes. compression

a tile-compressed image’s (§3.3), else null: type, its ZCMPTYPE; parameters, its BLOCKSIZE and BYTEPIX; zbitpix; shape and tile, its ZNAXISn and ZTILEn, the slowest axis first; quantize and dither_seed; zblank, its ZBLANK card’s value; columns, the offsets in a row of its COMPRESSED_DATA and GZIP_COMPRESSED_DATA descriptors (with q, whether a descriptor is 64-bit) and of its ZSCALE, ZZERO and ZBLANK columns; row_bytes and rows; tiles, the tiles its table describes, and present, those that hold data

elements

the ids of its IR elements (§6.1) by name: header, and, as it has them, data, table, gap, rows, heap and pad

The header element keys the HDU’s stored arrays where the HDU has an axis. The projection reads an image’s data type from bitpix (§3.1), a binary table’s struct from its header’s TFORMn and TTYPEn (§4.1), and a tile-compressed image’s data type and chunks from zbitpix, shape and tile (§3.3, §9.4).

The parser still makes a decision of the output: the elements of a tile-compressed image’s heap (hdus/<i>/heap/<j>) are its chunks (§9.4), one per chunk that holds a tile, and the IR’s data element’s form names its Zarr data type (§6.1).
