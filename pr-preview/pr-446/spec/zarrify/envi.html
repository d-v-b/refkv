ENVI¶

The Zarr layout of an ENVI raster (an “ENVI Standard” file: a flat binary data file and the text header file beside it, .hdr, that says how its values are laid out), and the translation of its header into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, which files it reads and which inputs it rejects, is the ENVI profile, Part 2 below. The format is NV5 Geospatial’s ENVI Header Files, cited here as “the ENVI documentation”.

Convention version: 0 (until release, conventions §1) · UUID: e9428528-2fe3-43f2-8c02-3850cfed2f62 · Schema: schema.json

Changes: changes/envi/, one file per change.

Added 2026-11-20.

This document has two parts (conventions §11.1).

2. The header¶

An ENVI input is one array, of bands bands, each of lines lines of samples samples. Its header is the whole header file: text, in lines, each ended by a LF (0A), a CR (0D) before the LF being part of the line end. A line’s text is its bytes without its line end; the last line may end at the file’s end, without a LF. The first line is the magic: its text, without the spaces and tabs around it, is ENVI, in any case. Each later line is, in this order of tests (the first row that matches it applies):

A name given twice keeps its last value, at its first place. A value open at the end of the header holds the lines to the end. These are the rules of VirtualiZarr’s ENVIParser (its source, newer than VirtualiZarr’s releases; cited here as “ENVIParser” throughout), whose reading of a header this profile follows; GDAL’s ENVI driver reads the same fields of real files.

4. The image¶

The hierarchy is one image at the root (conventions §4), without a name, with one array at path "0": the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A} (an ImageGroup), where A has ome (M, an OmeImage, its axes c of type channel, y and x of type space, its one dataset of scale [1, 1, 1]), zarr_conventions and refkv_zarrified (§1).

No chunk is padded. For a gzip file, the one chunk is the stream (EnviGzipChunk).

The array holds the data’s values; nothing the header says about them (data ignore value, default stretch, data gain values, …) is applied. They are in the source metadata (§5).

4.2 Gzip files¶

With file compression 1, the data file is a gzip stream (RFC 1952) whose inflated bytes are what a raw data file would hold: the header offset’s bytes, then V. GDAL’s ENVI driver reads such a file as that inflated file, so the header offset counts inflated bytes, which the refkv.skip codec passes over. (VirtualiZarr’s ENVIParser instead references the stream from the header offset on; the two agree when the offset is 0, as it is in the files gzip makes of ENVI’s.)

A deflate stream has no index, so, as for NRRD’s gzip encoding (nrrd.md §4.2), the layout keeps the stream as it is: one chunk of the whole array, a reference to the whole file, which Zarr’s gzip codec decodes. A reader decompresses the whole stream to read any value. The profile does not decompress the stream, so a stream that does not inflate to the header offset and B bytes (a damaged file, or one whose header is wrong) is not detected: reading its chunk fails.

The data file, which the chunks reference, is described in place: its bytes stay in the file, which is a source of the archive (§8.5). The header file, which no chunk references, is held: the table holds its bytes (refkv_source/ir/held), so that the mirror alone rebuilds it.

7. What the layout does not express¶

  • Georeferencing. map info, projection info and coordinate system string place the image on the earth, and x start and y start give its first pixel’s position. They are recorded, not applied: the image has scale 1 and no translation.

  • Wavelengths and band names are recorded, not made coordinates or channel labels.

  • Other file types: spectral libraries, classification images, and the TIFF, HDF and other files ENVI reads under a header of their own, whose data is not one flat array as this layout reads it, and framed data (major frame offsets, minor frame offsets), whose lines have bytes between them. Such inputs are rejected, as VirtualiZarr’s ENVIParser rejects them.

  • Data files of other sizes. A raw data file must hold the header offset and the array’s bytes, and nothing else: ENVI writes a file of that size, and one of another size usually means a field that changes the layout is not read. VirtualiZarr’s ENVIParser rejects such a file too.

  • Large bands. A chunk of a raw file is a whole band or line, however large, as VirtualiZarr’s ENVIParser cuts it, so that both tools reference the same byte ranges.

Part 2. The profile¶

The ENVI profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles. The input is the header file and the data file beside it, and the profile also says which of them are read.

8. ENVI profile¶

The input is a file input that names the header file (a URL, or a local path), which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/envi.json) chose: the bytes tested hold a LF, and the text before the first, less a CR that ends it and the spaces and tabs around it, is ENVI in any case. The data file has no signature, so it cannot be named: an application that has the data file’s name (VirtualiZarr’s ENVIParser takes it) names the header beside it instead, <name>.hdr or the data file’s name with its extension replaced by .hdr, which are the names §8.3 probes back. The profile reads the input as a file read as a store (spec/zarrify.md §1.8): the store URL is the header file’s directory, its objects are the header file, at its key, and the data file, which the profile probes for (§8.3), and the root’s source.url is the header file’s object URL.

Siblings (spec/zarrify.md §1.9):

what

it says

form

always: every input is a file read as a store

names

derived keys, from the header file’s key k less its last four characters .hdr (in any case): §8.3

probes

one key a batch, in §8.3’s order, until one exists; each optional, so one outside the scope is absent. When none exists, the input is rejected

identity

the format records nothing that says which files belong together. So the profile checks what it can: that a raw data file is exactly the header offset and the array’s bytes

order

first use: the data file is source 0

the header file whole, of at most 2^24 bytes, which the mirror holds; of the data file, only the first three bytes of a gzip file. The mirror’s store IR describes the data file in place

8.1 The header file¶

The header file is checked to be at most 2^24 bytes (the ENVI header file is <size> bytes, more than 16777216) and its key is checked (§8.3) before it is read, whole, in one request. Its first line must be the magic (§2): not an ENVI header: its first line is not ENVI. No other line is rejected: a line that is no field, comment or blank line is not read (§2).

8.2 The fields¶

The fields are checked in this order. A value is read as one integer when it is an optional sign and decimal digits.

  • file type, when present, is ENVI Standard, in any case: the ENVI file type "<value>" is not supported: only an ENVI Standard file is a flat binary array.

  • major frame offsets and minor frame offsets are absent: the header has a <field> field: the data is in frames, which the profile does not read.

  • samples, lines and bands, each required (the header has no <field> field), are integers from 1 to 2^53 − 1.

  • interleave is required, and bsq, bil or bip, in any case.

  • data type is required, and a code of §3’s table.

  • byte order, when present, is 0 or 1.

  • header offset, when present, is an integer from 0 to 2^53 − 1.

  • file compression, when present, is 0 or 1.

A value that is not as these require is rejected: the <field> field "<value>" .... No other field is checked: they are recorded as written (§5.1).

8.3 The data file¶

The header file’s key k MUST end in .hdr, in any case, after at least one other character: the ENVI header "<k>" is not named <name>.hdr, so its data file cannot be found. With s, k less those four characters, the data file is the first of these keys that exists, each probed in turn, as the NRRD profile probes its data file (nrrd.md §8.3): the host says whether the object at the key exists, and its size (a 404 is absent, any other failure a failure, not a rejection):

  1. s (scene.img for the header scene.img.hdr, scene for scene.hdr, ENVI’s own name);

  2. s followed by each of .img, .dat, .raw, .bin, .bsq, .bil and .bip, in that order, in capitals when the header’s suffix is .HDR.

These are the names VirtualiZarr’s ENVIParser finds a header by, read back: it looks for <data file>.hdr, then the data file’s name with its extension replaced by .hdr. When none exists, the input is rejected: no data file beside the ENVI header "<k>": none of "<key>", ... exists, naming each key probed.

8.4 The data¶

With Z the data file’s size, o the header offset and B the array’s bytes (§4.1), the input is rejected unless all of these hold:

  • B is at most 2^53 − 1;

  • for a raw file, o is at most Z (the header offset <o> is past the end of the <Z>-byte data file "<key>"), and o + B is Z (the <Z>-byte data file "<key>" does not hold the header offset <o> and the array's <B> bytes, and nothing else);

  • for a gzip file, Z is at least 18 (a gzip member’s header and trailer), and the file’s first three bytes are 1F 8B 08 (a gzip member of deflate data). The stream is not otherwise read: the output does not depend on the pixel data (spec/zarrify.md §1.2).

8.5 Chunks¶

Every chunk of the convention’s array (§4.1) is present, at 0/c/<c>/<y>/<x>, and references the data file; the output copies no data.

part

range

presence

value

the values

8.7 The description¶

This section is not part of the convention: nothing it specifies is written in an output. The parser returns, beside the IR, a description of the raster: what it found of the two files, for a projection to read with the IR and its stored array (spec/stored-array.md §7). It holds none of an output’s decisions: the Zarr data type (§3), the axes’ names, the transpose order, the codecs, the chunk shape and the fill value (§4.1) and the root’s source metadata (§5.1) are the projection’s. It is a JSON object with these members:

member

value

header_file, data_file

each file’s key in the store and its size in bytes: the header file the input names, and the data file §8.3 found

fields

every field of the header (§2), in its order, by its name, its value as written, a text value (conventions §6)

comments

the comments, in order, each a text value

samples, lines, bands

the fields’ integers (§8.2)

interleave

the field’s value in lower case: bsq, bil or bip

data_type

the data type field’s code, an integer of §3’s table

byte_order, header_offset, file_compression

the fields’ integers, each 0 where the header has no such field

data_range

[start, length], the data’s range in the data file (§8.4): [o, B] for a raw file, [0, Z] for a gzip file

elements

the ids of IR elements (§5.3): header, the header file’s object, which keys the stored array, and data, the data file’s data element, its one unit

The projection reads the data type and its bytes from data_type by §3’s table, the axes’ stored order and the transpose order from interleave, the bytes codec’s endianness from byte_order, the gzip codecs from file_compression and header_offset, and the chunks from the sizes and data_range (§4.1, §8.5).

The parser still makes one decision of the output: the IR’s data element’s form names the Zarr data type (§5.3).
