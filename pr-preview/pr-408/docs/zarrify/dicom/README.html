DICOM, including whole-slide images¶

refkv turns an image file into an OME-Zarr dataset by writing a small archive of references to the file’s bytes, without copying the pixels (overview). This page is about DICOM files.

Who this is for¶

DICOM is the format of clinical imaging: CT and MR series from hospital PACS, and, increasingly, digital pathology, where a whole-slide image is stored as one DICOM file per pyramid level. Large public collections, such as the NCI Imaging Data Commons (IDC), serve these files from cloud buckets (storage.googleapis.com/idc-open-data/...). Researchers who want to analyze a slide or a volume with Zarr tools, or put it next to OME-Zarr data, would otherwise have to decode and rewrite every frame.

refkv reads the DICOM header and the frame table and writes an archive in which every Zarr chunk is one frame (or one tile of a slide) of the file, still JPEG, lossless JPEG, JPEG 2000 or raw as stored. A 60 MB whole-slide level from the IDC became a 704 KB archive (at spec/zarrify.md revision 16, before the archive kept every element of the file).

A series¶

A CT or MR series, or a slide’s pyramid, is many files. Give refkv the prefix that holds them, in Python or with python -m refkv.zarrify, and it zarrifies each .dcm file there and joins them with refkv.compose, into one group per Series Instance UID:

from refkv.zarrify import zarrify

store = zarrify("https://storage.googleapis.com/idc-open-data/96d032cf-ab4f-45c1-ba51-d9523d076747/")
store.save_vzip("series.vzip")

  • Slices become one z, y, x array, sorted by position along the slice normal, or by Instance Number when a file has none. z has a scale in millimeters when the gaps are uniform.

  • A whole-slide image becomes multiscales, 0 the largest level; thumbnails and labels stay out of them.

  • Each file stays too, under instances/<j>, with its own attributes and mirror. Nothing is copied: both views reference the same bytes.

A series that cannot be joined keeps its files under instances/ with its reason: positions that repeat (a 4D series), files of different shapes, or a slide’s optical paths in files of their own. A file that is not a DICOM image is listed with its reason, and does not fail the store.

The form is Python-only, because refkv.compose is. The CLI of the Rust binding and the browser code reject a store of DICOM files.

What you get¶

One OME-Zarr 0.5 image at the archive root, with one array, 0. A DICOM file is one level: a whole-slide pyramid is one file per level, and each file gives its own archive, unless you zarrify their prefix (a series).

  • Axes: c for RGB; for a multi-frame image that is not a slide, its frames along t when the Frame Increment Pointer names Frame Time or Frame Time Vector (cine ultrasound, angiography, fluoroscopy), else along z, whatever they are; y, x.

  • Whole-slide images (VL Whole Slide Microscopy, TILED_FULL): the frames are the tiles of the total pixel matrix, so the array has the full slide’s shape and one tile per chunk.

  • Palette images (PALETTE COLOR): 0 holds the stored indices, and the array palette the red, green and blue lookup tables, shape [3, entries], with the first mapped value in the root’s refkv_zarrified.dicom.palette, unless the tables are segmented: they then stay in the mirror. No color is applied.

  • Native and RLE YBR_FULL: channels Y, Cb and Cr, as stored, not converted.

  • Data types: uint8, int8, uint16, int16, uint32, int32 (the stored cells, not rescaled), and bool for Bits Allocated 1, as segmentations store them.

  • Codecs: bytes (either byte order) for native pixel data, packbits (zarr-extensions’ bit packing, not TIFF’s PackBits) for Bits Allocated 1, imagecodecs_dicomrle for RLE Lossless, imagecodecs_jpegls for JPEG-LS, imagecodecs_htj2k for HTJ2K (readable in Python; the Neuroglancer fork has no decoder for it yet), imagecodecs_jpeg for JPEG Baseline, imagecodecs_ljpeg for JPEG Lossless, imagecodecs_jpeg2k for JPEG 2000; transpose first for interleaved RGB. JPEG frames get a color marker prepended so they decode to RGB.

  • Scale: Pixel Spacing and Spacing Between Slices, in millimeters (including from the shared functional groups of enhanced and slide files), and Frame Time, in seconds, for frames along t.

  • No translation: DICOM positions an image in the patient’s or the slide’s frame, which is in general rotated against the image axes.

  • omero: a gray or R, G, B channel with the stored value range; for grayscale images, the Window Center and Width, converted to stored values. MONOCHROME1 is marked inverted.

  • Metadata: the file’s elements, private ones included, in the DICOM JSON Model under the root’s refkv_zarrified.dicom, but for those the convention omits (group lengths and trailing padding, for example); the whole file, and the members that would make the root large, are on refkv_source, its IR mirror.

Try it¶

example.py zarrifies a public file and plots it with matplotlib. Its dependencies are in its header (PEP 723), so it runs on its own, with refkv from PyPI:

uv run docs/zarrify/dicom/example.py

A CT slice from pydicom’s test data (39 KB), from corpus_dicom.txt:

uv run refkv zarrify https://raw.githubusercontent.com/pydicom/pydicom/v3.0.1/src/pydicom/data/test_files/CT_small.dcm CT_small.vzip

{"format": "dicom", "axes": ["y", "x"], "shape": [128, 128], "dataType": "int16", "transferSyntax": "1.2.840.10008.1.2.1", "photometric": "MONOCHROME2", "frames": 1, "wholeSlide": false, "references": 1, ...}

import zarr
import refkv.zarr

g = zarr.open_group(refkv.zarr.open("CT_small.vzip"), mode="r")

print(ome["omero"]["channels"])

In the browser. Not on the live demo yet: it zarrifies only TIFF, NDPI and ND2. A local build of the demo (see the overview) zarrifies CT_small.dcm and shows it in Neuroglancer. The IDC’s bucket sends no CORS headers, so its slides cannot be read from a browser at all; use the command line.

Viewing¶

The Neuroglancer fork (https://github.com/d-v-b/neuroglancer, branch vzip) reads every data type and codec this profile writes: integers of up to 32 bits, imagecodecs_jpeg for uint8, and imagecodecs_jpeg2k for 8- and 16-bit data; imagecodecs_ljpeg (JPEG Lossless) needs its lossless JPEG decoder, d-v-b/neuroglancer#15. CT_small.dcm renders through a local build of the demo. The default view uses the stored value range, so a CT looks flat until you adjust the contrast. For IDC slides the obstacle is the host, not the viewer: the chunks are read from a bucket without CORS.

Supported and not supported¶

Supported:

  • DICOM Part 10 files in Implicit VR Little Endian, Explicit VR Little or Big Endian, JPEG Baseline (1.2.840.10008.1.2.4.50), JPEG Lossless (.4.57, and .4.70, its first-order prediction, common in CT, MR and CR) and JPEG 2000 (.4.90, .4.91).

  • Single- and multi-frame images; MONOCHROME1, MONOCHROME2, RGB, and the YBR forms that JPEG and JPEG 2000 decode to RGB.

  • Encapsulated frames over several fragments, with or without a Basic or Extended Offset Table.

  • Whole-slide images organized TILED_FULL, one level per file.

Rejected, with the message the command prints:

  • Other transfer syntaxes, among them deflate: unsupported transfer syntax 1.2.840.10008.1.2.1.99.

  • Signed JPEG-LS frames whose precision is less than Bits Allocated, as for JPEG Lossless below.

  • RLE frames whose segments are not one per byte of each sample.

  • JPEG Lossless frames with a point transform or restart intervals, which the imagecodecs_ljpeg codec’s decoder reads wrongly (frame 0 has the point transform 1, frame 0 has the restart interval 8), and signed ones whose precision is less than Bits Allocated. None of the public JPEG Lossless files refkv was checked with has these.

  • Subsampled native YBR_* images.

  • JPEG 2000 frames labeled YBR_FULL_422 whose chroma is not half width.

  • TILED_SPARSE slides, and slides with several focal planes or optical paths.

  • Encapsulated multi-frame files with an empty offset table and neither one fragment nor one fragment per frame (refkv does not split fragments by reading the JPEG data).

Not applied to the pixels: Rescale Slope and Intercept, modality and VOI LUTs, palettes and overlays. The values are the stored ones.

In the browser¶

The browser code (js/) reads DICOM (Part 10 files):

  • Native pixel data in implicit or explicit VR, little or big endian, and RLE, JPEG Baseline, JPEG Lossless, JPEG-LS, JPEG 2000 or HTJ2K frames, including frames split over several fragments, with or without a Basic or Extended Offset Table.

  • Multi-frame images along z, or t for a cine (Frame Time or Frame Time Vector); whole-slide images (TILED_FULL) as one pyramid level per file, with frames as tiles.

  • Pixel spacing as scale; window center and width in omero.

Not supported, and refused with HTTP 422: other transfer syntaxes (deflate), TILED_SPARSE slides, and slides with several focal planes or optical paths.

Performance¶

  • Large encapsulated files without an Extended Offset Table are slow to zarrify. The frame boundaries are found by reading every fragment’s 8-byte item header, one small read per frame. The 4230-frame IDC level above took 5.4 minutes from storage.googleapis.com. With an Extended Offset Table, or native pixel data, nothing past the header is read, but for JPEG Lossless, whose frames’ first 512 bytes are read for their markers.

  • Reading a chunk is one range request (one per fragment, merged when they are adjacent).

  • A pyramid needs one archive per level file; the archives are independent.

How it’s verified¶

js/test/dicom/verify.py zarrifies 81 synthetic DICOM files (including inputs to reject) with the browser code, reads them back through python/src/refkv and zarr-python, and compares the pixels with pydicom. compare.py checks that the Python and browser outputs are equivalent on those files and on the 21 public files of corpus_dicom.txt: pydicom’s test files, four JPEG Lossless files from pydicom’s pylibjpeg-data, and six whole-slide levels from the IDC, with JPEG, JPEG 2000 and native tiles. python/tests/ir/test_dicom.py compares the lossless JPEG fixtures’ pixels, read through zarr-python, with their frames decoded by libjpeg-turbo.
