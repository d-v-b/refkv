refkv’s Zarr conventions¶

A Zarr hierarchy made from a source in another format (a TIFF, an ND2 file, an N5 store, …) looks like any other Zarr hierarchy. These conventions make it describe itself: which source it presents, which format that source is in, and everything the source’s own header or metadata says. There is one convention per source format, each specified in zarrify/<format>.md next to its JSON Schema zarrify/<format>/schema.json. Its changes are in zarrify/changes/conventions/, one file per change.

A format’s convention specifies the hierarchy’s whole Zarr layout: which groups and arrays it has and where, each array’s metadata (shape, data type, chunk grid, codecs, dimension names), the OME-NGFF metadata, and the attributes under the convention’s key, including the translation of the source’s header into JSON. It says what each chunk holds in terms of the source (for example, “the chunk at 0/c/t/0/z/0/0 is frame f”), but not how a store produces those bytes. refkv produces these hierarchies as reference stores whose chunks are byte ranges of the source; that is specified separately, in spec/zarrify.md and its profiles, which refer to these conventions for the layout.

Every convention is held to two requirements:

  1. Reconstruction. A reader of the hierarchy can recover all the information of the source. This means its data, and its metadata, and every other value it holds, whether or not the layout uses it. What may be left out is only what can be derived from the rest, or that holds nothing:

    • the layout: where the bytes are and how they are framed (offsets, byte counts, chunk maps, block headers, the encoding tables a chunk already carries);

    • dead space: padding and unused bytes.

    Byte-for-byte reconstruction of the file is not required.

  2. Efficiency. The hierarchy reads well:

    • Small typed metadata is JSON, in attributes.

    • Metadata that is large, or that grows with the data, is in arrays (§7), or on the source metadata node (§2), which a reader only opens when it wants it.

    • Values are referenced where the source holds them. They are copied only when they are scattered or must be reordered.

This document holds what every convention shares. The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119. Numbers follow spec/zarrify.md §1.3 (IEEE 754 binary64, correctly rounded).

1. Conventions¶

Each convention follows the Zarr conventions framework.

Versions. Each convention has a version, an integer stated in its document’s header.

  • Until refkv 1.0, every convention is at version 0, in the 0.x releases too. Version 0 promises nothing: any change may change a layout; a convention’s document records its changes.

  • At refkv 1.0, every convention becomes version 1, tagged zarrify-<p>-v1 in the refkv repository. From then on a convention’s version increases by 1 whenever the layout it specifies, or the reference store that refkv’s profile for that format specifies, changes for some source, including whether the source is accepted (a breaking change); an editorial change, or a change to another format, leaves it as it is. Version N of the convention for format p is tagged zarrify-<p>-v<N>.

  • A reader that relies on a convention MUST reject a hierarchy whose version it does not know, as each convention’s JSON Schema does.

The convention metadata object. Format p at version N is declared by the Convention Metadata Object (CMO)

{
  "uuid": "<the UUID above>",
  "schema_url": "https://raw.githubusercontent.com/d-v-b/refkv/refs/tags/zarrify-<p>-v<N>/spec/zarrify/<p>/schema.json",
  "spec_url": "https://github.com/d-v-b/refkv/blob/zarrify-<p>-v<N>/spec/zarrify/<p>.md",
  "name": "refkv_zarrified",
  "description": "The Zarr layout of a <T> source zarrified by refkv, and the source's metadata"
}

with no other members. At version 0, which has no tag, the URLs name the development branch instead: .../refs/heads/main/spec/zarrify/<p>/schema.json and .../blob/main/spec/zarrify/<p>.md. T is the format’s title, the title of its entry in the profile registry (zarrify/profiles/<p>.json: TIFF, Zarr v2, Sentinel-2 SAFE, …). The UUID is the same for every version; the version is in the URLs. All conventions nest their property under one key, refkv_zarrified, which is also their name: the framework asks a nesting convention’s name to be its key, and a key without a colon is not mistaken for a namespace prefix.

2. Attributes¶

Which nodes. The root node of the hierarchy (the document zarr.json) always declares its format’s convention, in an output refkv’s profiles write. In an output a plugin wrote (spec/layout.md) the root is the plugin’s, and a declaration a node of it holds, one kept from the base among them, is the plugin’s claim, which refkv neither checks nor vouches for. Any other node declares it when, and only when, the node has source metadata (below). A node that declares it has, in its attributes, the members of a Declaration:

A separate convention records the program, on the root only: spec/provenance.md, whose member and CMO are not part of the output.

Other attributes. A node’s attributes MAY hold members of other conventions beside a Declaration, and their CMOs in zarr_conventions, also where a format’s layout says the node’s attributes are a Declaration and nothing else; that layout is what a producer of the format writes. A reader ignores the members it does not know, and each convention’s JSON Schema accepts them without checking them.

The source metadata node. A file format’s metadata that grows with the data (one item per frame, plane or channel), and the source’s values kept as arrays (§7), are on the group refkv_source, a child of the root. It declares the convention, with its own source metadata, when it has any, and holds the arrays at paths the format’s convention gives. OME-NGFF readers ignore it. Producers SHOULD store its documents so that a reader fetches them only when it opens the node (refkv writes them with the chunks, not with the documents read when an archive is opened). The node exists only when it has source metadata or arrays, or, for the store conventions, other objects of the store, which it holds whole under refkv_source/objects/, or the recorded ignored keys. For a file’s convention, refkv_source is the source’s IR mirror (§8), from which the source is rebuilt byte for byte; for a store’s, the store’s (§8.9), from which the listing and the documents read are rebuilt: always present (under a root array, as plain keys of the archive). A FLAC file’s pictures, source values kept as arrays, are outside it, under the root’s pictures (flac §4.2).

Everything taken from the source goes under the key, on the node it belongs to, including attributes a source store had (and the conventions they declare), so it can neither collide with nor masquerade as the target formats’ metadata. A source that is itself such a hierarchy therefore nests its own record. The HDF5 and Zarr v3 conventions depart from this: a node’s attributes are the source’s own, beside the key (hdf5 §2.1, zarr3 §4).

3. Arrays¶

Unless the format’s convention says otherwise, every array’s zarr.json is the JSON object below. The conventions that say otherwise:

Delta. imagecodecs_delta is an array-to-array codec, so in decoding it applies to the array bytes gives, in stored order, before transpose reorders it. It replaces each value by the sum of it and every value before it along axis axis, the other indices fixed (with dist 1, a cumulative sum), in the data type’s integer arithmetic: modulo 2^bits, as two’s complement for int. It undoes TIFF’s horizontal differencing (Predictor 2, tiff §4.3), which starts again at each row of a tile or strip, and differences each of a pixel’s interleaved samples with the same sample of the pixel before: the samples are an axis of their own, so a sum along x runs over each apart. It decodes as imagecodecs.delta_decode(chunk, axis=axis, dist=1) does. (zarr-python’s numcodecs.delta, numcodecs’ Delta, differences the chunk flattened, across its rows and samples, so it does not undo a horizontal predictor.)

Floatpred. imagecodecs_floatpred is an array-to-bytes codec, in the place of bytes, so in decoding it gives the array transpose then reorders. It undoes TIFF’s floating-point predictor (Predictor 3, tiff §4.3). Each row along axis axis holds the most significant bytes of its values, then their next bytes and so on, whatever the byte order, each byte stored less the byte one sample before it, modulo 256. A chunk with an axis after axis has that axis’s length of samples a pixel, and the step is that length. It decodes as imagecodecs.floatpred_decode(chunk, axis=axis, dist=1) does, to values in the platform’s byte order (a dist of the sample count is not what interleaved samples need, and imagecodecs refuses one of 3).

JPEG 2000 decoding follows OpenJPEG, as imagecodecs does: a 3-component codestream whose first component is at full resolution and whose other two are subsampled holds YCbCr, and decodes to RGB (as in Aperio’s compression 33003).

An Integer past 2^53 − 1 in magnitude has more digits than a binary64 value holds, so a consumer that needs its exact value parses integers as big integers. In JavaScript, JSON.parse with a reviver that turns into a BigInt only a number whose source text (context.source) matches ^-?(0|[1-9][0-9]*)$ and that lies outside −(2^53 − 1) to 2^53 − 1 (any other number, one with a fraction or an exponent among them, stays a binary64); an engine whose JSON.parse gives a reviver no source text needs a lossless JSON parser instead. Python’s json module reads every integer exactly. An integer of the source’s binary fields is within its field’s width.

These rules apply to values the convention translates from the source’s bytes. Members copied from a JSON document of the source (a store’s attributes) are copied as JSON values, not translated: their numbers are read as spec/zarrify.md §1.6 says. A number written as an integer (no fraction or exponent) is copied exactly, every digit, even beyond 2^53 − 1, and written back so; any other number is its binary64 value. Where a convention uses a number in the layout, it uses the binary64 value.

8. The IR mirror¶

Every format’s convention keeps the source’s metadata as one format-free structure on refkv_source: the source’s IR (intermediate representation), a tree of elements whose leaves partition the source’s bytes, stored as a table (the mirror) and shown as JSON (the view). A reader rebuilds the source byte for byte from the table and the bytes of source 0, with no knowledge of the format; the format’s convention says what the elements are (its source model). Sections 8.1 to 8.7 are all a reader needs to read the table, check it, and rebuild the source; 8.8 is how a producer writes it, one way only, so that the mirror of a source is the same whoever writes it. A store (an N5, Zarr v2, Zarr v3, OME-Zarr or Precomputed store, a SAFE directory, a safetensors store) is many objects, and so is a file that its profile reads as a store (VSI, NRRD and GRIB always, and others when the file names more files; the table of spec/zarrify.md §1.8 lists them): its IR has many sources, one per object, and §8.9 says how 8.1 to 8.8 apply to it. Any other file’s IR is the special case of one source, source 0, which 8.1 to 8.8 describe as they stand.

8.1 Elements¶

An element has a kind: 0 struct (a container), 1 value (a field, of a declared type, 8.6), 2 data (a decodable unit: a tile, a frame, a subblock’s pixels, with a form, 8.5), 3 derived (bytes that exist only after a transform, such as a deflated record, with a form that names the transform and may give their size), 4 alias (a second name for an element already described, its target; it claims no bytes), 5 gap (bytes no other element claims) or 6 object (an object of a store, a source of its own, only in a store’s IR: §8.9). It has a parent (every element but the root, which is element 0), a name and an optional name index (the element’s full name is the name followed by the index in decimal, so tags/ with index 256 is tags/256), a type (values), a space (0: its extent is in the source; d: in the derived bytes of element d), and an extent (start, length; length 0: none). An element’s path is the full names of its ancestors below the root and its own, joined by /; the root’s path is "".

The root. Element 0, the root, is a struct with the name "", no name index, space 0 and the extent (0, Z), Z the source’s size (8.2): its path, "", denotes the whole source, as "" is the whole document in JSON Pointer (RFC 6901) and the root node in Zarr. The root is not a run. Its extent states the range the leaves partition; it claims nothing itself, since a struct is not a leaf, so coverage and injectivity (below) concern the leaves alone and are unchanged by it. (When Z is 0 the root’s length is 0, so it has no extent.) The empty path is an IR path only: archive keys stay non-empty (spec/refkv.md §2.1).

Names. Every element but the root has a full name that is not empty. Among the children of one element (each member of a run being one child), no full name equals another’s, and none equals another’s followed by / and more characters (so tags/256 and tags/256~1 may be siblings, but not a and a/0). Hence every element’s path is its own, and no element but the root has the path "": two elements with one path would have, at the first depth where their chains from the root differ, two siblings (ancestors, or the elements themselves) whose full names are equal or one of which continues the other with /. A table that breaks these rules is invalid (8.3). A path therefore names one element; the view (8.7) gives an alias’s target by its path. A format whose names come from the source (a chunk’s name, a record’s key, an XML tag), which may be empty, repeat, or hold /, names those elements so that this holds; ND2 §5.3 gives one rule for that, which any format may adopt.

These rules are those of every file profile’s IR (a .SAFE.zip included), and of any format added later, without restating them. A format’s convention lists its elements by their paths below the root.

The leaves are the elements of kinds 1, 2, 3 and 5 with a length, in space 0. The invariants: coverage, the leaves’ extents partition [0, size) of the source (they cover it and none overlap); injectivity, no byte is claimed by two leaves (two names for the same bytes are an alias and its target); every parent precedes its children; every alias’s target chain ends at an element that is not an alias, within 64 steps; for each derived element whose form is a JSON object with a member size, the leaves in its space partition [0, size) of its derived bytes; and the root and the names are as above.

A table (8.2) may leave out what canonical form leaves out, and these invariants allow for it: a derived element with no descendants in a table had them left out (8.8, step 3), so its leaves need not partition its derived bytes, and an alias’s target chain in a table may end at -1 (8.8, step 7). The IR a parser builds leaves nothing out.

A run is an element whose subtree stands for count copies of itself (its members): member j has every extent of the subtree shifted by j × stride and the run’s root’s name index increased by j. A run’s leaves are its members’ leaves. The leaves of one member lie within stride bytes, from the first one’s start to the last one’s end, so that no two members’ leaves overlap. Runs do not nest. A run holds no derived element, no alias and no element in a derived space: its members copy member 0’s elements into space 0, and copy no alias’s target. A parser may fold its IR into runs; the canonical table (8.8) expands them, and a reader accepts them.

Canonical form (§8.8, step 1) names every gap gaps/, with the gap’s offset as its name index (gaps/<offset>; in a store’s IR, the offset in the gap’s object; in a derived space, the offset in its derived bytes), whatever name the producer gave it. A producer may name the gaps it folds into a run otherwise: refkv’s names a gap that repeats inside each member of a run gaps/<offset>/, <offset> the first one’s, with the name indexes 0, 1, … for the members it repeats in, and canonical form renames each by its own offset.

8.3 Column runs¶

Consecutive siblings of one shape fold into a column run: count members of size rows each, a member being one to four consecutive sibling subtrees (so that, for example, a directory’s alternating entries and dimensions fold together). Member 0 is stored as ordinary rows starting at its first row; members 1 to count − 1 are not stored: their size rows follow member 0 in the expanded order, member j at ids first + j × size to first + (j + 1) × size − 1. Member j’s rows are member 0’s, except:

  • parent: a row whose parent in member 0 is the first row’s parent (a sibling at the member’s top) has that parent; any other row’s parent is shifted by j × size;

  • fields with a column (a table row of code 4 for this column run and row offset o, the row at first + o of member 0) take the column’s value for member j. Fields: 0 name index, 1 type, 2 start (absolute), 3 length, 4 form (-1: none), 5 alias target (-1: none), 6 start relative to the member’s first row (the member’s first row’s start plus the value). Encodings, for member j:

    • 0: x + j × y (wrapping 64-bit arithmetic);

    • 1: column_values[x] + … + column_values[x + j] (the column stored as differences from the previous member’s value; column_values[x] is member 0’s);

    • 2: entry y + j of the array of unsigned integers that row x holds: row x MUST be a value (kind 1) in space 0, with a length, of a type that is a one-dimensional array of unsigned integers (<u2[n], >u4[n], …, 8.6), not in a column run that has a column of encoding 2; its bytes are those of source 0 at its extent, and the column is entries y to y + count − 1 (so a TIFF’s tiles take their offsets and byte counts from its TileOffsets and TileByteCounts, which the source holds);

    • 3 (name index only): the row’s start;

    • 4: the column as y arithmetic pieces, each three values of column_values from x on, (v, d, c): the next c members’ values are v, v + d, …, v + (c − 1) × d (wrapping); each c is at least 1, and the pieces’ c sum to count.

  • start, without a column: a row with a length, in a member whose first row has a length, is shifted as its member’s first row is (its start plus member j’s first-row start minus member 0’s); any other row keeps member 0’s.

Forms and alias targets without a column are member 0’s. A reader expands the column runs that have no column of encoding 2 first, then the others.

Limits. The expanded table, with every run (code 0) expanded as well, has at most 2^22 + floor(Z / 4) rows; a table that would have more is invalid (budget: more than N rows, N that limit in decimal). A producer rejects a source whose canonical mirror (8.8: runs expanded, derived spaces left out) would have more than N = 2^22 + floor(Z / 4) rows, with the message budget: the mirror would have more than N rows (N in decimal), and may do so before expanding when the elements outside derived spaces, every run expanded, are already more than N. While it parses, refkv’s producer also rejects a source whose IR holds more than N elements as the parser stores them (a run counted once, the derived spaces and the gaps it adds included), with the message budget: more than N IR records, and one whose elements, every run expanded, are more than M = 2^30 + Z, with that message or budget: more than M IR elements (M in decimal). These are that producer’s budgets, and this section does not list every one. (A source can describe more than one element per four bytes, as a TIFF of many small IFDs does, so floor(Z / 4) alone does not admit every source; the limit bounds what a reader must expand.) So is one whose columns’ lengths differ, whose column refers to values past column_values or entries past its array, whose column of encoding 4 has a piece of no member or pieces that are not its column run’s members, whose column run’s member 0 is not size rows of sibling subtrees (every row’s parent is the first row’s parent or an earlier row of the member), whose up is 0 for a row other than the root or larger than the row’s id, or whose kinds, names, types or forms are out of range. So is one whose expanded rows break the rules of the root or of the names (8.1): a root that is not a struct named "" with no name index in space 0 with the extent (0, Z); an element other than the root with an empty full name; or siblings whose full names are equal, or one of which is another’s followed by / and more. So is one whose runs (code 0) break the rules of runs (§8.1): for the first expanded row i in a run’s subtree that is a derived element, an alias or in a derived space, r its run’s root, the message is the run at row r holds a derived element (row i), the run at row r holds an alias (row i) or, for an element of another kind, the run at row r holds an element in a derived space (row i) (r and i in decimal). A reader rejects such a table (8.4) and a validator flags it as invalid.

8.4 Reading the source back¶

A reader that rebuilds the source:

  1. reads rows and tables, and expands the column runs (8.3);

  2. checks the invariants of 8.1, with the runs expanded member by member (a run whose members’ leaves overlap one another is invalid), the root and the names among them;

  3. concatenates, for the leaves in order of their start, the bytes of source 0 at their extents.

The result is the source, byte for byte: its length is Z, which source 0 pins (spec/zarrify.md §1.2), and a range checksum, when the archive carries one, checks each range read. The extents index source 0 directly; there is no array of the source’s bytes. (A store’s IR rebuilds each of its held objects from the table alone: §8.9.)

8.5 Forms and recipes¶

A form is a JSON object: for a data element, recipe and, as its format gives them, geometry (the format’s description of the unit, such as its shape and data type) and codec (a SAFE tile part has no geometry, and a FITS table’s rows and heap have no codec), each in the source’s own terms: never an output’s data type, codec or other metadata, which are a projection’s (stored-array.md §1; python/tests/test_ir_has_no_zarr.py checks every fixture); for a derived element, transform and, when known, size, with skip for nd2-lv-zlib (the bytes of the element before its zlib stream), and, for a deflate element whose space holds values, prefix: the number of bytes, from the start of what its stream inflates to, that hold them (a deflated .npz member’s preamble and header, npy.md §5.3), a value of the source alone, never of how much of the stream a parser read; for an object of a store described in place, {"bytes":"source"} (§8.9). A recipe is the bytes of the unit as a list of parts: ["src", o, n], the n bytes (null: up to the element’s end) at offset o from the element’s start; ["shared", k], shared data source k (8.2); and ["rows", o, s, n, c], c runs of n bytes each, the first at offset o from the element’s start and each s bytes after the one before, the bytes between them not being part of the unit (an ND2 frame’s padded rows, nd2.md §5.3). The hierarchy’s chunks are references built from recipes, except ND2’s, which its profile builds from the frame’s layout (nd2.md §7.3); the rebuild does not need forms.

8.6 Types¶

A value’s type is a string of this grammar, and its value is its bytes decoded by it:

type  = base ["[" n {"," n} "]"]
base  = ["<" | ">"] num | "ascii" | "cstr" | "bytes" | "utf16" | "guid" | "{" field {"," field} "}"
num   = "u1" | "i1" | "u2" | "i2" | "u4" | "i4" | "u8" | "i8" | "f4" | "f8"
field = name ":" type

< and > are little- and big-endian (default little); [n, m] makes an array (row-major) of a number or record type, and gives the length of ascii, cstr, bytes and utf16. ascii[n] is text (UTF-8 when valid, else its bytes); cstr[n] is the text up to the first NUL, or, when bytes after it are not all NUL, the record {text, after}; bytes[n] and utf16[n] are bytes; guid is 16 bytes, written xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx from a little-endian u32, two u16 and eight bytes; a record is its fields in order. The types xml and xml:<runtype> are the UTF-8 text of an XML attribute value (in a derived space).

8.7 The view¶

refkv_source/tree and the groups under it show the canonical IR (8.8) as JSON. Each is a group whose source metadata S (§2) is a struct’s view document, so it declares the convention when the document has a member. The document of the root, the element whose path is "" (8.1), is tree’s. Sizes are those of the JSON text ECMAScript’s JSON.stringify writes (no whitespace), in UTF-8 bytes.

A document has a member per child, in canonical order, by the child’s full name, where a name that starts with $ gets another $ in front (so the members $vz, $form and $partial below are never a child’s):

  • a value is shown when its type is a number type, a record type, guid, xml, or a text type (ascii[n], cstr[n] or utf16[n]; bytes[n] is not text), its length is at most 1024 bytes, and, for ND2, it is not a frame’s timestamp (frames/<f>/timestamp, which an ND2 parser need not read). A producer reads every shown value (its parser holds those it reads; the others are read after it). A shown value is, as JSON:

    • of a text type, its §6 text value T: for ascii and cstr, its bytes up to the first NUL (all of them if there is none), the JSON string they encode when they are UTF-8, else {"latin1": L} with each byte b the code point U+00bb; for utf16, its 16-bit little-endian units up to the first 0 unit, the string they encode when they are UTF-16, else {"$vz": "utf16", "b64": B} of those bytes.     • of any other type, its decoded value (a record whose field v is its value shown as that field; a v of type utf16[n], its last two bytes dropped, as its text);

    when that JSON is at most 4096 bytes; any other value is the spill form {"$vz": "element", "id": i}, row i of the expanded table, whose bytes the source holds;

  • a struct or a derived element: its own document, inline when at most 16384 bytes; else {"$vz": "group", "path": p}, the group refkv_source/p holding it, while there are fewer than 4096 such groups, the documents stored so far and this one total at most 2^24 bytes, and no group has the path p yet (paths are the escaped names, each segment percent-encoded outside [A-Za-z0-9._~-], an empty one as %); else the spill form. 8.8 Canonical form¶

A producer writes the canonical mirror: the one table, description and view this section derives from the source’s IR (its elements, and the decoded bytes of the values the view shows), whatever order the producer found the elements in and however it folded them. Two conforming producers therefore write identical ir/rows, ir/tables and ir/shared, the same description in refkv_source’s source metadata and the same view for one source, and spec/zarrify.md §1.1 compares mirrors entry for entry. In order:

  1. Runs. Every run (8.1) is expanded into its members: member j’s root has the run root’s name index plus j, and each element of member j the extent of member 0’s shifted by j × stride (the same length), and its type, value and form. The table has no row of code 0. Then every gap is named gaps/, with its start as its name index (§8.1), and the root and the names of §8.1 must hold of the elements so named: an IR whose renamed gaps break them has no canonical form, and a producer rejects it with the message of the rule broken.

  2. Order. The elements are numbered depth first from the root (id 0), a parent before its children, each subtree contiguous. An element’s first byte is its start when it has a length, else the least first byte of its children (none when no element of its subtree has a length; none comes after every byte; siblings share a space, so their starts compare). The siblings of one name form a name group, whose first byte is the least of its members’. Siblings are ordered by

    1. their name group: the groups by first byte, then by name (its UTF-8 bytes);

    2. then, within a group, by name index, as an unsigned integer, with no index last;

    3. then by first byte.

    So differently named siblings follow the source’s layout, and a family (tiles/0, tiles/1, …) its indexes, wherever its members lie. No two siblings tie: siblings of one name differ in name index, since their full names differ (8.1), so this order is total and depends on the IR alone. Where leaves claim one byte, they are taken in order of their start, and in this order among those that start at one byte: a leaf that overlaps the last one kept becomes an alias of it and claims nothing, and any other is kept (8.1, injectivity).

  3. Derived spaces. The derived elements are taken in order, skipping those inside another derived element. Each keeps its descendants when they, with the descendants kept so far, number at most 2^20; otherwise its descendants are left out (it stays, with its extent and form). The kept elements are numbered again in the same order.

  4. Strings. names and types are the distinct names and types of the elements, sorted by their UTF-8 bytes (so "" is first). The shared data sources are numbered by first use: for each element in order that has a form, each part ["shared",k] of its recipe in order (as the form’s text writes it, without spaces) gives source k the next number when it has none yet. Each form’s text is the producer’s with every such k replaced by its number, nothing else changed; forms are the distinct texts, sorted by their UTF-8 bytes, and ir/shared holds the sources by number.

  5. Column runs. The elements are taken in order; for each element that is in no member of a column run found so far, its children c_0, …, c_{k−1} (in order) are folded from a = 0:

    • a child is eligible when its subtree has no derived element and no element in a derived space; two subtrees have one shape when they have the same number of elements and, element by element in order, the same kind, the same name, both or neither a length, and (all but the first) the same parent relative to the subtree’s first element;

    • for each period p from 1 to 4, while c_a … c_{a+p−1} exist and are eligible: r is the largest count such that for every member q < r and every t < p, c_{a+q·p+t} exists, is eligible and has c_{a+t}’s shape;

    • the period with the largest r × p among those with r ≥ 3 wins (the smaller period on a tie): children c_a … c_{a+r·p−1} are a column run of r members of p siblings each, and a moves past them; with none, a moves to the next child.

    Members’ subtrees are not searched for column runs of their own: a column run found folds whole subtrees, outermost first. Column runs are listed in order of their first row.

  6. Columns. For each column run, for each row offset o of a member, the fields are, in this order: name index (0), type (1), start (6, relative to the member’s first row, when o > 0 and both row o and the member’s first row have a length; else 2), length (3), form (4) and alias target (5). Member j’s value v_j is the row’s field (-1 for no form or target; field 6 its start minus its member’s first row’s start, wrapping). When every v_j is v_0, there is no column; otherwise the column takes the first encoding that applies:

    • 3, for a name index: every member’s row has a length and v_j is its start;

    • 0: v_j = v_0 + j × (v_1 − v_0) for every j (wrapping), with x = v_0 and y = v_1 − v_0;

    • 2, when one of the profile’s named array rules (below) gives, for this column, a value row x and an index y, and entries y to y + count − 1 of the array x holds are v_0 to v_{count−1};

    • 4, when its pieces are fewer than a third of the members (3 × y < count): x is the length of column_values so far, and the pieces are taken from member 0 on, each as long as it can be: a piece starts at member a with v = v_a; with no member after it, it is (v_a, 0, 1); else d = v_{a+1} − v_a (wrapping), and it holds every member from a on while each value is the one before it plus d. Its (v, d, c) are appended to column_values, and y is the number of pieces (a column of a source’s units in runs of one stride, such as an audio track’s samples, chunk by chunk, costs three values a run instead of one a member);

    • 1: x is the length of column_values so far, y = 0, and v_0, v_1 − v_0, …, v_{count−1} − v_{count−2} (wrapping) are appended to it.

    Columns are listed by column run, then row offset, then field, in that order.

    Named array rules. Encoding 2 reads a column from an array the source holds, which pays only where a format’s layout keeps such arrays; each profile lists its rules, and a column takes encoding 2 only under one of them. A rule has a name and says, for a column run and a field: the conditions on the column run (at least 16 members, so that reading the array costs less than storing the column), the value row x (a value in space 0, with a length, of a one-dimensional unsigned integer array type, 8.6) and the index y.   7. Rows and tables. The stored rows are every row but those of members 1 and later of column runs, in id order. tables holds, in this order: an alias row (code 1) for each stored alias, in id order (target -1 when the target was left out, step 3); a form row (code 2) for each stored row with a form, in id order; the column runs (code 3) and the columns (code 4) as above; and column_values (code 5), padded with zeros to a multiple of six.

  8. Arrays. The chunk shapes are those of 8.2, and the codecs bytes (little-endian) alone: no numcodecs.zlib. The archive’s own entry compression (spec/bindings/vzip.md) does the work, and is not part of the output.

  9. Description and view. S is {"ir": I} of 8.2 with version 2, and the view is 8.7’s, from the elements in this order.

Readers accept, validators flag. A reader MUST NOT reject a valid table (8.2 to 8.4) for not being canonical, and a validator SHOULD flag one that is not. Canonical form serves producers: it makes outputs comparable entry for entry and the archive of a source reproducible. It adds nothing a reader needs: the rebuild, the elements and the view are read the same from any valid table. Checking it means folding the whole table again and, for the columns of encoding 2, reading arrays from the source, a cost a reader that wants one value or a rebuild should not pay; and a reader that rejected a valid but non-canonical table would turn a producer’s defect into a reader’s loss of the data. So the check belongs where producers are checked: conformance/zarrify/compare.py loads each mirror, folds it again and compares the result with what is stored, flagging the first difference (a run row, a compressed chunk, unsorted strings, rows out of order, a fold or an encoding other than the one this section gives, a different entry). A canonical table is a fixed point: loaded and folded again, it is the same, byte for byte. The validator also rebuilds the view (8.7) from the table and the source: each shown value’s bytes from source 0 at its extent, or, in a derived space, from that space’s bytes, which it derives again by the derived element’s transform (nd2-lv-zlib: the record inflated; gunzip, bunzip2: the file decoded; deflate with a prefix (8.5): the first prefix bytes its raw deflate stream inflates to, of which the validator need read no more than they take; xml-variant: the chunk; an xml value is then its span with its references decoded); it compares the rebuilt view with the stored one group by group and member by member, and flags the first group or member missing, extra or different. So a derived transform may hold shown values only if validators can derive it again from source 0: of the transforms the parsers emit, nd2-lv-zlib, xml-variant, and gunzip and bunzip2 (a compressed FITS file, fits §2.1: the file decoded) can; deflate with a prefix (a deflated .npz member, npy.md §5.3) can for the values that end at or before its prefix, and a shown value past it is flagged as one past its derived space; and gzip (a CZI’s compressed attachment) and deflate without a prefix (a SAFE zip entry’s raw deflate stream), whose spaces hold nothing, may hold none. A new transform that would hold shown values comes with its re-derivation, in a revision of this section.

8.9 Stores¶

A store input (spec/zarrify.md §1.4) is a set of objects named by keys. Its IR, a store IR, has many sources: each object of the store is one. A file read as a store (spec/zarrify.md §1.8) has a store IR too, even when it is the only object: the objects are the files its profile read, which are then the store’s listing. Sections §8.1 to §8.8 hold for a store IR with the changes this section gives. An IR without objects, a file IR, is the special case of one source, source 0: this section changes nothing in it, its table or its view.

Objects and directories. An element of kind 6 is an object: one object of the store, and a source of its own. Its extent is (0, s), where s is the object’s listed size (no extent when s is 0), in space 0. The extents in space 0 of its descendants are ranges of that object’s bytes, so an element names its source by the object it is in, its nearest ancestor of kind 6. Objects do not nest, and an object is not a run. The root is the store’s root directory: a struct named "" with no name index, in space 0, with no extent (in place of 8.1’s (0, Z)). Every other element outside every object is a directory: a struct with no extent, in space 0, that is not a run, one per directory of the store (spec/zarrify.md §1.4). An object’s parent is the root or a directory. The path of an object or a directory is its key: the full name of each is its key’s segment, by the rule below. So the tree is the listing: the paths of the objects are the store’s keys, and the lengths of their extents its sizes. A key the listing does not have (a chunk an array does not store) has no element. The keys a store reader ignores (spec/zarrify.md §1.4) are not objects: the store conventions record them as they do without an IR.

Names. A key segment t has the name and name index:

  • when t holds no ~ and is not the key of an object that is also a directory’s (S3 allows the keys a and a/b together): let d be the digits that end t (as many as there are). When there are none, the name is t, with no index. Otherwise the leading zeros of d but its last digit stay in the name: the index is the value of the rest of d, and the name is t without that rest. When that value is 2^64 − 1 or more, the name is t, with no index;

  • otherwise the name is t with %, / and ~ written %25, %2F and %7E, then ~, and the index 0, or 1 for an object whose key is also a directory’s.

So 0 is ("", 0), a.12 is (a., 12), 007 is (00, 7), .zarray is (.zarray, none), c~d is (c%7Ed~, 0), and the object a beside the directory a is (a~, 1). A full name without ~ is its segment; one with ~ is a segment the escape gives back. Siblings’ full names are therefore distinct, and hold no /: 8.1’s rules for names hold. The rule makes the chunk keys of one array siblings of one name with consecutive indexes (0, 1, … in a nested directory, 3.0, 3.1, … after a .), which canonical form folds (below).

Held, referenced and empty objects. An object that has children and a length is held: the leaves among its descendants partition [0, s) of its bytes, as the leaves of a file IR partition its source (8.1’s coverage and injectivity, for each object), and the table holds its bytes (ir/held, below), so the mirror alone rebuilds it. A store’s documents (an N5 attributes.json, a Zarr .zarray, .zgroup or .zattrs, a SAFE manifest) are held. An object with a length and no children is referenced: it is a leaf, which claims its whole source; the hierarchy references it whole (its convention says at which key, such as a chunk object at its own key), and the mirror does not rebuild it. An object whose size is 0 is empty: no element in it has a length.

Described in place. A held object’s bytes are copied into the archive, which suits documents, read whole and small. An object that a format reads in ranges (a SAFE band file: its boxes, main header and tile-part headers, a few kilobytes of a file of up to 160 MB) can be described without being held: an object that has children and whose form (§8.5) is {"bytes":"source"} is described in place. Its leaves partition [0, s) of its bytes, as a held object’s do, but the table does not hold its bytes: they are its own source’s, which a reader reads at the object’s URL (spec/zarrify.md §1.4), as it reads a file IR’s source 0 (§8.4). A producer reads every value the view shows in such an object (its parser holds them). A held object is then an object with children and a length that is not described in place.

The invariants of 8.1 then become, for a store IR: the elements outside every object are the root and the directories above; each object’s leaves (a referenced object being its one leaf) partition [0, s) of that object, every member of a run inside it included; and the objects number o, the description’s (below). A checker MAY check them at once on virtual offsets: byte x of object j at b_j + x, where b_j is the sum of the sizes of the objects before j in id order. The leaves then partition [0, Z), as a file’s do, once each leaf is checked to end within its object.

The table (changes to §8.2). The description I has the member "objects": o after size, o the number of objects; its presence is what makes the IR a store’s. Z is the sum of the objects’ sizes. An object row’s start (column 6) is stored as it is (0, since its extent is (0, s)), and the next row with a length codes its start from the object’s start (its distance from 0), as if the object row were a row of length 0 ending there: an object’s descendants’ starts count from the start of their own source. The kinds of rows go to 6. When the IR has held objects, refkv_source/ir/held is a group of two arrays holding their bytes, offsets and data, as refkv_source/ir/shared holds the shared data sources (§8.2): one byte string per held object, in id order, each the object’s s bytes. An object described in place has its form row (code 2) and no byte string in ir/held. A column of encoding 2 (§8.3) is invalid in a store IR (no profile has a named array rule for stores).

Limits (changes to §8.3). A store IR has at most 2^24 objects, and its expanded table at most N = 2^22 + floor(Z / 4) + 4 × o rows; the distinct names (the description holds them) total at most 2^24 UTF-8 bytes. A producer rejects a store past one of these with the message budget: more than 16777216 objects, budget: the mirror would have more than N rows (N in decimal) or budget: the mirror's names would total more than 16777216 bytes, and a reader rejects such a table. While it parses, refkv’s producer allows a store N elements as the parser stores them, and M = 2^30 + floor(Z / 4) + 4 × o with every run expanded, and rejects a store past either with the messages of §8.3’s limits, budget: more than N IR records and budget: more than M IR elements (in decimal). A reader also rejects a table whose held objects (objects with children and a length, not described in place) are not as many as ir/held’s byte strings, or one of whose byte strings is not as long as its object.

Reading the store back (in place of §8.4). A reader reads rows, tables and held, expands the column runs, checks the invariants above, and then has:

  • the listing: every object’s path, its key, and the length of its extent, its size;

  • every held object, byte for byte: the bytes of its leaves, in order of their start, from its byte string in ir/held. (The byte string is the object; the leaves say what each of its bytes is.)

  • every object described in place, by its elements: its leaves, which partition it, say what each of its bytes is; its bytes are its source’s.

It reads no source to do so: a referenced object is not rebuilt, since the hierarchy references it (a chunk’s bytes are the archive’s references to the store), and an object described in place is its own source (the hierarchy references its ranges; reading it rebuilds it).

The view (changes to §8.7). Referenced and empty objects are neither shown nor visited (a store’s chunk objects would fill the view’s budget of visits); a held object is shown as a struct is, by its own document; a directory whose document would be empty is not shown. A shown value of a held object is read from that object’s bytes in ir/held, so a validator rebuilds the view from the archive alone; one of an object described in place, from that object’s source.

Canonical form (changes to §8.8). An object’s first byte is 0, the start of its source, whether or not it has a length, so the first byte of a directory is 0 too: the objects and directories of one directory are ordered by name, then by name index, which is the order of the keys’ segments with each family of chunk keys in the order of its indexes. Within an object, 8.8’s order holds, its first bytes being those of that object’s source. The rest of 8.8 is unchanged. In particular, column runs fold sibling subtrees of one shape: the chunk objects of one array, siblings of one name with consecutive indexes, fold into a column run of one stored row whose columns are the name index (encoding 0) and, when the chunks’ sizes differ, the length (encoding 0 when each size differs from the one before by the same amount, 4 when the sizes fall in few such runs, else 1; chunks all of one size have no length column). Nested chunk keys (i/j/k) fold whole directories at once, one column run for a full grid; flat keys (i.j.k) fold one column run per name (i.j.). The held objects’ byte strings are in id order.

Producers. A producer lists the store (spec/zarrify.md §1.5), builds the directories and objects from the listing, then reads the objects its format names, whole, in as few rounds as the format’s structure allows: a round is the documents whose keys the listing and the documents read so far name (every .zarray, .zgroup and .zattrs of a Zarr v2 store is one round), read concurrently, each read once. A held object is an object it read whole.

9. Dataset layouts¶

A source whose image layout (§4) serves viewers can also be presented, in the same hierarchy, as a dataset: a group that xarray and other labeled-array readers open as a dataset, whose arrays are its data variables and coordinate variables, with dimensions named by dimension_names and coordinates that give each index a position. The two layouts reference the same bytes of the source; neither copies the other’s chunks. A format has a dataset layout when its dataset convention exists: a convention of its own, named <p>-dataset for the format p, with its own UUID, schema and document (zarrify/<p>-dataset.md), which specifies the layout’s variables and where each comes from. This section holds what every dataset layout shares.

The node. The dataset is a child group of the root, at the path the dataset convention gives (dataset unless it says otherwise). The root names it in layouts (§2). The group declares the dataset convention as a root declares its format’s (§2): its refkv_zarrified has profile (<p>-dataset), version, source and the source metadata member "<p>-dataset", so that the group describes itself when it is copied out of the hierarchy. OME-NGFF readers ignore it, as they do refkv_source. The group has no source metadata node of its own: the source’s mirror (§8) is the root’s refkv_source, which a copied-out group no longer has.

Variables. Every array of the group is as in §3, with dimension_names, and is a data variable or a coordinate variable:

  • A data variable holds the source’s values. Its shape, data type, chunk grid and codecs are those of the image layout’s array for the same values, its dimensions are named as the dataset convention says (a stack’s index dimension by what it indexes, section or volume, not by an image axis type), and its chunks are the same references as that array’s chunks, range for range (an edge chunk’s copy is copied again). A data variable’s attributes hold, when the convention gives them, the CF attributes long_name and actual_range ([min, max], two numbers).

  • A coordinate variable gives the positions along one dimension: a 1-D array named as the dimension, of that dimension’s length n, with the attribute units, a UDUNITS symbol or name (angstrom, micrometer, second), and the chunk shape [min(n, 2^17)]. Its values are derived from the source’s header (the source holds no such bytes), so its chunks are bytes entries, in one of two forms:

    • regular steps o + i × s, the common case, are stored as the index: a uint32 array of the values 0 … n − 1 with the CF attributes scale_factor (s) and add_offset (o), both binary64, which a CF-decoding reader (xarray) turns into i × s + o in binary64 (the product first), and the codecs [{"name": "numcodecs.delta", "configuration": {"dtype": "<u4"}}, {"name": "bytes", "configuration": {"endian": "little"}}, {"name": "gzip", "configuration": {"level": 6}}]. A chunk’s bytes are its indexes delta-coded (the first as it is, each other less the one before: q × c, 1, 1, …, the ramp going on past n into the last chunk’s padding), as little-endian uint32, then one gzip member (RFC 1952, no name, time or extra field) of a deflate stream at level 6. A ramp of a million positions is then a few kilobytes.

    • irregular positions are stored as they are: float64 values in little-endian byte order ([{"name": "bytes", "configuration": {"endian": "little"}}]), the last chunk padded with zero bytes.

    A dimension without a coordinate variable is allowed, and is how a dataset convention leaves out a position it cannot give (an axis with no valid voxel size, a stack’s index).

10. Coded streams¶

Audio and video formats code each frame (an MP3 or AAC frame, an H.264 or HEVC picture) into a run of bytes that a decoder can only decode after the frames it depends on: an MP3 frame’s bit reservoir reaches into the frames before it, an AAC frame overlaps the one before it, and an H.264 or HEVC picture is predicted from other pictures, back to the last keyframe. A chunk of such a stream’s samples therefore holds the frames it decodes to and the frames before them that a decoder must decode first, its lead-in. The array-to-bytes codec refkv.stream decodes such a chunk.

A varint is an unsigned integer as protobuf encodes it, 7 bits a byte, the least significant first, the high bit set on every byte but the last; a zigzag varint is the varint of 2d for d ≥ 0 and of −2d − 1 for d < 0. So a lead-in frame (−1 after −1) costs one byte for its position, and a frame whose output follows the one before it (s samples on, or one picture on) one or two. A header that ends inside a varint, or whose sizes do not add up to the bytes after it, is an error.

Decoding a chunk. A decoder of the format, set up with setup and in its initial state, is given the frames in order, one frame each time. Each frame decodes to some outputs: for audio, s samples of each channel; for video, one picture. The output of frame k goes to the chunk’s row position[k] on, along the array’s first axis: for audio, the s rows from position[k], [s, channels]; for video, the one row position[k], [1, height, width] of the plane. A frame of position −1 is decoded and its output dropped: it is the chunk’s lead-in. Every row no frame fills is the fill value: the rows past the array’s end in its last chunk, and the rows of a frame the decoder gives no output for. An output that does not fit its rows, or whose shape is not the array’s, is an error, and so is a plane of "u" or "v" of a stream whose pictures are 4:0:0, which have no such plane. The outputs are the decoder’s own samples, with no conversion: float32 for MP3 and AAC, the stream’s integer samples for FLAC (of the bits per sample the setup gives, in the array’s signed integer type: a decoder that gives them in the high bits of a wider integer is shifted back), and the planes of a 4:2:0 or 4:2:2 picture for H.264, HEVC, AV1 and VP9 (u and v half the size of y along each axis, or along x alone for 4:2:2, rounded up), or the y plane alone of a 4:0:0 HEVC picture, uint8 for 8 bits a sample and uint16 for 10 or 12, the sample’s value (from 0 to 2^bits − 1, not scaled to the type’s range).

The outputs are placed by the frame each comes from, whatever order the decoder gives them in: an H.264 or HEVC decoder outputs pictures in presentation order, after a delay, and may emit nothing for a frame it cannot decode (an HEVC decoder skips the RASL pictures of the CRA picture it starts from, and those of a BLA picture). A decoder that cannot say which frame an output comes from does not decode this codec. Nor does one whose output for a frame depends on more than a bounded run of the frames before it, such as ffmpeg’s fixed-point MP3 decoder, which carries its rounding error from frame to frame, so a chunk it decodes from the lead-in differs from the stream by a unit here and there. ffmpeg’s float MP3 decoder, its AAC decoder, its FLAC decoder, its H.264, HEVC and VP9 decoders and libdav1d for AV1 (the implementations’ decoders, through PyAV) decode it.

Determinism. A chunk decodes to the same values every time, and, for MP3, FLAC, H.264, HEVC, AV1 and VP9, to the values a decoder of the whole stream gives (FLAC, H.264, HEVC, AV1 and VP9 decoding is exact by their standards; a FLAC frame depends on no other, so it needs no lead-in). AAC’s perceptual noise substitution fills a band with noise from a pseudo-random generator whose state runs on from frame to frame, so a chunk’s noise bands differ from those of a decoder of the whole stream; every other value is the same. So does HE-AAC’s SBR, whose added noise and tones run on likewise, in every band it fills: the top half of the spectrum. A chunk’s values are its own there, of the stream’s level, and the low band’s are the stream’s less the error the SBR’s filter banks leave (about 70 dB below a tone, measured with ffmpeg’s decoder, a lead-in of at least 32 frames reaching HE-AAC v2’s parametric stereo headers).

Producing a chunk. A convention says which frames are a chunk’s own, where each one’s output goes, and which frames before them are its lead-in (zarrify/mp3.md §8.2, zarrify/mp4.md §8.3, zarrify/flac.md §8.2). A zarrifier writes the header as a literal range, then the frames as ranges of the source, a frame that starts where the one before it ends extending that one’s range. The bytes between two frames of the source are in no range, so a decoder never sees them: one that looked for a run of frames to lock onto would drop the frames before them, and one that reset its state would decode the frame after them from nothing. The header holds the frames’ sizes and positions, which are the source’s structure, not its samples (spec/zarrify.md §1.2).

11. Format documents¶

What every format’s document, zarrify/<p>.md, would otherwise say in the same words is stated here once, and each document cites it.

11.1 Parts¶

A format’s document has two parts. Part 1 is the format’s convention: the Zarr layout, which Part 2 cites as “the convention §n”. Part 2 is the format’s profile (spec/zarrify.md, Profiles): how refkv reads the source, which inputs it rejects, and how each chunk references the source. The document is numbered on its own, Part 2 after Part 1, and other documents cite it by name. A dataset layout’s document (§9) is a convention alone.

11.2 Declaration¶

A format’s convention starts with its declaration (§2), its section 1, which shows its CMO (§1) at the version its header states. Unless the declaration says otherwise:

  • the root declares the convention with "profile": "<p>", the convention’s version as version, and the input’s URL as source.url (a file’s URL, or a store’s, ending in /);

  • refkv_source declares it too, with the IR mirror’s description (§8.2; a store’s, §8.9), and so does each group of the mirror’s view that has a member (§8.7); the mirror’s arrays have no attributes.

The declaration names what is the format’s own: the root’s source metadata, the member "<p>", when the root has any, the other nodes that declare the convention, and the other arrays that have no attributes. A dataset layout’s declaration is §9’s.

11.3 The IR mirror¶

For a file’s convention, refkv_source is the file’s IR mirror (§8): its table, from which the file is rebuilt byte for byte, and its view, refkv_source/tree; for a store’s, and for a file that its profile reads as a store (spec/zarrify.md §1.8), it is a store IR’s (§8.9). The format’s convention lists the IR’s elements, the format’s source model.

11.4 Equivalence¶

The elements are determined by the source (a file, or a store’s listing and the documents the profile reads), and the mirror by its elements (§8.8: one order, one folding, one encoding): hierarchies of one source are compared entry for entry, refkv_source included (spec/zarrify.md §1.1).

Every entry the format writes matches exactly one row of type group, array, chunk, object or subtree, except that the format’s own entries under refkv_source (its arrays, §7, and a store convention’s kept objects) match both the subtree refkv_source/** and rows of their own, which say what they are. The mirror is one row, refkv_source/**, a subtree, which links the mirror’s entries (§8.2); a collection’s entries are §4’s table.

Type tables. A structured value (a node’s document, an attribute, an object of the source metadata) is defined once, by a type table: a line naming the type in bold, **Name**, preceded by the anchor []{#type-<name>} (<name> the name in lower case), then a table of its members:

column

holds

member

the member’s name; "<p>" and other placeholders for a name the value column gives; a description in words for a family of members (one per field of the header)

type

a JSON type (string, integer, number, boolean, null, object, array of T, object of T for an object whose members are all T), a type of §6 (Integer, Float, Text, Name, Base64), or a link to another type table; A or B for either

presence

required or optional: an optional member’s condition is in its value

value

the member’s meaning and constraints: a constant, the values it may take, its order

The members are in the order the producer writes them, which the reader need not keep (§6). A format’s types are named with its own prefix (Nifti…); the types of this document and of spec/zarrify.md are shared, and each format’s document links them rather than repeating them. A type that is a shared one but for some members (an array’s ArrayDocument) lists those members only, and says so. A type table stands where the prose defines the type, in place of a list of its members.

Chunk tables. A chunk is a reference to the source’s bytes, or bytes that the archive holds (spec/zarrify.md §1.1). A chunk type lists the ranges of the reference, in order, with these columns:

column

holds

part

what the range holds

range

a source range (i, offset, length) of source i as spec/zarrify.md’s Range numbers it, a literal range, a range of a data source, or bytes, when the chunk is a bytes entry

presence

required or optional: an optional range’s condition is in its value

value

its offset and length, or its bytes, and their constraints

A shard’s composition is spec/zarrify.md §2.1’s Shard, of the inner chunks a format’s chunk type gives.

Unions and tuples. A type that is one of several forms is a table with the columns form and when, one row per form, as §8.7’s ViewValue. A JSON array whose elements differ by position is a table with the columns element, type and value, one row per position.

Binary layouts. Bytes whose structure a type gives (a chunk’s header, a record of the source) are a table with the columns part, encoding and value, its rows in the order of the bytes, as §10’s StreamChunk.

Placeholders and other lists. A table of placeholders has the columns placeholder and value. A list whose items share the same parts (a code’s meanings, the members of an object) is a table, one row per item and one column per part.

12. GRIB messages¶

The codec refkv.grib, which decodes a field of a GRIB edition 2 message, is GRIB’s own and is specified with its convention, in grib §3.4.
