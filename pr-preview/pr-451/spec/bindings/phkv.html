phkv: the perfect-hash binding of refkv¶

Format version: 0 (provisional, a draft’s: §1.3) · Specification revision: 11.3 · Part 3 status: draft

This document is Part 3 of the refkv specification: the perfect-hash binding, which keeps a store in a single file, a phkv store, whose keys are found through a perfect hash in one hop. Part 1, in spec/refkv.md, specifies the reference value type, and its introduction (§1) covers every part: the conventions, the conformance of readers and writers, and the revisions. This part’s format version 0 is a draft’s, which promises nothing yet (§1.3). The sections are numbered as one specification, so this part starts at §16.

Part 3 is a draft: unlike Parts 1 and 2, anything in it may still change, and no conformance suite tests it yet.

A phkv store is either a file of its own (the standalone profile) or a vzip archive (Part 2) that also carries a phkv container in a hidden entry (the hybrid profile, §21). A hybrid store is a valid vzip archive, which readers that know only vzip read as before.

Part 3. The perfect-hash binding¶

16. What the phkv binding defines¶

A phkv store is a store kept in a single file, indexed by a perfect hash of its keys. The phkv binding answers the three questions of §3.1 as follows:

in a phkv store

marking

each key has a record (§19); its kind field says whether the value is bytes, or a reference whose payload is a Range or a Concat. The record holds the reference payload itself.

source table

the SOURCES section (§17.4), found through the section directory, which the superblock locates (§17.1). The superblock starts with the magic PHKV and records the format version. The binding’s auxiliary data are its other sections: the records, the page index, the perfect hash, the slot table, properties and metadata.

names

a key is stored as its UTF-8 bytes, exactly. A standalone store reserves no names. A hybrid store reserves vzip’s __vz__/ prefix (§21).

What a phkv store adds over the ZIP binding:

  • One-hop lookup. A reader holds the perfect hash’s pilots in memory. To find a key it computes a slot, reads that slot’s 12 bytes (the record’s offset and length) from the slot table, and reads the record, whose key it compares with the one asked for (§19.5).

  • Sorted keys. Records are stored in UTF-8 order with a page index, so list(prefix) and binary search work as in a paged vzip archive (§19.4).

  • Properties. Optional typed columns, such as modification times, hold data about keys outside the values (§20). They never change the result of a refkv operation.

  • Compression. A bytes value may be stored as is, or compressed with DEFLATE or Zstandard (§19.2).

16.1 Notation¶

All multi-byte integers are unsigned and little-endian unless stated otherwise. u8, u16, u32, u64 are unsigned integers of 8, 16, 32 and 64 bits. A varint is an unsigned LEB128 integer, as protobuf’s VARINT (§4.1): at most 10 bytes, with a value below 2^64. Writers write minimal varints; readers accept non-minimal ones.

  • XXH64 is the 64-bit xxHash of the xxHash specification, with a 64-bit seed.

  • CRC-32C is the checksum of §4.2.

  • mulhi(a, m) is floor(a × m / 2^64) for 64-bit a and m: the high 64 bits of their 128-bit product. It maps a from [0, 2^64) to [0, m).

  • ×, + and ⊕ (exclusive or) on 64-bit values wrap modulo 2^64 unless stated otherwise.

16.2 Profiles¶

  • Standalone: the file holds only the store. Its layout is up to the writer, within the rules of §17; §23.2 recommends one.

  • Hybrid: the file is a valid vzip archive, and the phkv container is the body of its hidden entry __vz__/phkv (§21). Bytes values and the source table are the ZIP entries’ bodies, which the container’s records and directory point at, so nothing is stored twice.

Readers open both profiles the same way (§22.1). The superblock’s hybrid flag tells them which one a file is.

Which to write:

  • vzip, for the widest compatibility, and when the archive will be read by ZIP tools or by readers that know only vzip.

  • standalone phkv, for the fastest lookups and the smallest file, when every reader knows phkv: about a third the size of the vzip archive above, with one hop per key instead of a page read.

17.2 Finding the superblock¶

The superblock ends D bytes before the end of the file: it occupies [file_size − D − 64, file_size − D). The bytes after it do not belong to the store, and readers do not read them. D is the superblock’s distance, and a store is one of two kinds:

  • A hybrid store (§21) has the hybrid flag, and its superblock ends where the ZIP central directory starts. D is the size of the central directory and the end records, so it is any number.

  • A standalone store has D at one of the probe distances: 0, and 2^k for each k from 10 to 30 (1 KiB, 2 KiB, 4 KiB, …, 1 GiB). A writer usually writes the superblock last (D = 0), but may reserve D bytes after it for data that is not the store’s, such as a signature added later. In the manner of HDF5’s user block, this lets a store live where its last bytes are not its own.

A reader finds the superblock as follows. A candidate at distance D is a match if the 64 bytes at file_size − D − 64:

  1. start with the magic PHKV;

  2. hold in bytes 60–63 the CRC-32C of bytes 0–59; and

  3. have a distance equal to D.

Step 1 is for hybrid stores. If the file ends with a vzip end of central directory record (vzip §10.4: it is 44 or 60 bytes from the end, and its comment starts with vzip/), let C be the central directory’s offset: the record’s own offset field, or the offset in the zip64 end of central directory record when that field is 0xFFFFFFFF (vzip §10.2). The candidate at D = file_size − C is a match if it has the hybrid flag too. If there is no such record, or the candidate is not a match, go to step 2.

Step 2 is for standalone stores. For each probe distance D, in increasing order, with D + 64 ≤ file_size, test the candidate at D.

The first match is the superblock. If none matches, the file is not a phkv store. Once a match is found, a reader does not look further: if its version is not one the reader implements, or flags has a bit set other than bit 0, the store is of an unsupported version. Either way, opening fails with an archive error (§6.4).

The three conditions together make a false match vanishingly rare: random bytes match with probability about 2^-64 per candidate, and a superblock written for another distance does not match at this one. A reader reads at least the last 64 KiB + 64 bytes first, which holds the end records and every probe candidate up to 64 KiB, and reads 64 bytes per larger candidate. (The reference reader reads 512 KiB + 64 bytes, which holds the PTRHASH and PAGES sections of about 10^6 keys as well.) A hybrid store’s superblock takes one such read when the central directory is larger than that, however large it is; a standalone store’s takes one per probe distance beyond the tail it needs to reach.

17.5 Codecs¶

A codec says how stored bytes encode a sequence of size bytes:

codec

name

0

Codecs 3 to 255 are reserved. Stored bytes decode cleanly if they are exactly as the table says and decode to exactly size bytes. As for a vzip DEFLATE body (§13.1), readers must check explicitly that nothing follows the stream, and SHOULD stop decoding once the output passes size. A Zstandard frame MAY omit its content size; a reader then relies on size.

The codecs apply both to sections (§17.3) and to bytes values (§19.2).

18. Perfect hash¶

A store with n ≥ 1 keys has a perfect hash: a function, computed from the key and the PTRHASH section, that gives every key of the store a slot of its own. It is PtrHash’s query (Groot Koerkamp, 2025) with three choices fixed: XXH64 as the key hash, one byte of pilot per bucket, and a slot table in place of PtrHash’s remap, so that the hash need not be minimal.

18.2 SLOTS section¶

The SLOTS section is P × S slots of 12 bytes. Slot i is:

offset

field

type

value

0

offset

u64

the record’s offset from the start of the RECORDS section

8

length

u32

the record’s length in bytes (§19.1), or 0 or 0xFFFFFFFF

  • A length of 0 is an empty slot: no key has a record here. Its offset MUST be 0, so a section of zero bytes is empty.

  • A length of 0xFFFFFFFF says that the record is 2^32 − 1 bytes long or longer, and gives no more.

  • Any other length is exactly the record’s length. It is at least 6, the size of the smallest record (§19.1).

A writer MUST give the exact length of every record shorter than 2^32 − 1 bytes. An offset of 0 is a record, not an empty slot, since its length is not 0. For example, a record 28 bytes long and 1,234 bytes into RECORDS has the slot D2 04 00 00 00 00 00 00 1C 00 00 00. The section’s length MUST be 12 × P × S, else it is an archive error. A slot is not 8-byte aligned in general, so a reader that maps the file reads it as bytes.

18.3 Query¶

The slot of a key k, a sequence of UTF-8 bytes, is computed as follows:

  1. h = XXH64(k, seed).

  2. p = mulhi(h, P): the part.

  3. b = mulhi(h × P, B), where h × P is taken modulo 2^64: the bucket within the part. (h × P mod 2^64 is the fraction of h that mulhi left over, so b is independent of p.)

  4. pilot = pilots[p × B + b].

  5. x = fmix64(h ⊕ (pilot × 0x517CC1B727220A95)), where fmix64 is MurmurHash3’s 64-bit finalizer:

    x ^= x >> 33;  x *= 0xFF51AFD7ED558CCD;
x ^= x >> 33;  x *= 0xC4CEB9FE1A85EC53;
x ^= x >> 33

  6. s = mulhi(x, S): the slot within the part.

  7. The key’s slot is p × S + s.

In a valid store, the slot of every record’s key holds that record’s offset, and every other slot is empty. Appendix C gives test vectors.

18.4 Construction (informative)¶

The specification requires only the property of §18.3; how a writer finds a seed and pilots is its own choice. The reference writer (rust/refkv-phkv) does as PtrHash does:

  • Parameters. P = ceil(n / 65536). Then with m the number of keys in the fullest part, S = ceil(m / 0.98) and B = ceil(m / 3): about 2.7 bits of pilot per key, and about 2–3% of slots empty.

  • Search. It tries seeds 0, 1, 2, … in turn. For each part, it places buckets largest first. A bucket takes the first pilot, from 0 to 255, that puts its keys in distinct free slots. If no pilot does, it takes the pilot that collides with the fewest keys, counting a bucket of c keys as c², and evicts the buckets it collides with, which go back in the queue. It never evicts any of the 16 buckets it placed most recently. If the evictions pass a bound, it gives up on that seed.

With these parameters seed 0 almost always succeeds. Two equal keys can never be placed, but a writer rejects duplicate keys first (§23.1).

The fields come in this order. The fixed part comes before the key, so a reader that reads a few hundred bytes at a record’s offset usually gets the whole record, and can compare its key and find its value in one read. A record is self-contained: its key is never compressed against another record’s, so any record decodes from its own offset.

inline, crc32c and codec are for bytes records only: a reference record with inline or crc32c set is malformed. hidden is for the hybrid profile only (§21): a standalone store has no hidden record.

A record is malformed if a field does not decode (a truncated or overlong varint), it extends past the end of the RECORDS section, kind or codec is not one of the values above, flags breaks the rules above, key_length is 0, or the key is not valid UTF-8.

19.2 Bytes records¶

The value of a kind-0 record is its stored bytes, decoded with its codec. The stored bytes are the record’s data if inline is set, and otherwise the stored_length bytes at offset, which MUST lie within the file. A writer places them where it likes: in the standalone profile, typically before the RECORDS section; in the hybrid profile, in the body of the key’s ZIP entry.

If crc32c is set, the record’s crc32c field is the CRC-32C of the value. A reader MUST check it whenever it has the whole value: on decoding a compressed value (always whole), and on reading the whole of a codec-0 value. A reader that reads only part of a codec-0 value does not check it.

Writers SHOULD set crc32c and SHOULD inline small values that readers fetch together with their keys, such as Zarr metadata documents.

19.3 Reference records¶

The value of a kind-1 or kind-2 record is described by its payload, a Range (kind 1) or a Concat (kind 2), and resolved by §6.3. Writers MUST use kind 1 when a reference has exactly one range (§4.4).

A payload MUST NOT exceed 16,777,216 bytes (2^24); a reader treats a longer one as malformed (a payload error).

The pages partition the RECORDS section: the first page starts at the section’s offset, each later page starts where the previous one ends, and the last ends where the section ends. Each page holds whole records. Writers SHOULD make pages of about 4 KiB.

The page index is malformed, an archive error, if it does not decode, a first_key or length is 0, the pages are not contiguous from the start of RECORDS to its end, or the first_key values are not strictly increasing in UTF-8 order.

A page cannot be parsed if it is not a sequence of whole, well-formed records that exactly fills it, or its first record’s key is not its first_key.

19.5 Lookup¶

A reader determines whether a key k has a record as follows:

  1. If n = 0, k has none.

  2. Compute k’s slot (§18.3) and read the slot’s 12 bytes. If the slot is empty (its length is 0), k has no record.

  3. The slot’s offset, from the start of the RECORDS section, MUST lie within it, and the record there MUST be well-formed (§19.1) and, if the slot gives a length (any length but 0xFFFFFFFF), exactly that long, and that length MUST be at least 6; otherwise it is an entry error for k, since the reader cannot tell whether k is present. A reader can read a record whose slot gives its length in one read of that many bytes, but need not: it may read only the start of a long record and the rest of it as it needs it. It reads a record whose slot does not give its length (0xFFFFFFFF) as its encoding says.

  4. If the record’s key is k, that is k’s record. Otherwise k has none.

A reader MAY instead find k through the page index, by selecting the last page whose first_key is at most k and searching it, as in a paged vzip archive (§12.2). In a valid store both give the same result.

20. Properties¶

Properties are data about keys that are not part of their values, such as modification times. They are optional, a reader need not support them, and they never change the result of classify, get, list or raw.

20.3 METADATA section¶

The METADATA section holds data about the store as a whole. Decoded, it is a sequence of entries, each a varint name length, the name (UTF-8, at least one byte, named as in §20.2), a varint value length and the value’s bytes, in strictly increasing UTF-8 order of name. This part registers one name, writer: the name and version of the program that wrote the store, in UTF-8. A METADATA section that does not decode, or breaks these rules, is an archive error.

21. Hybrid profile¶

A hybrid store is a vzip archive (Part 2) that is also a phkv store:

  1. The entry. The archive has a hidden STORED entry __vz__/phkv, the last entry before the central directory. Its body is the container region: the phkv sections that are not other entries’ bodies, the directory and the superblock, which ends the region. region_offset and region_length are its body offset and size.

  2. Distance. The superblock ends where the central directory starts, so D is the size of the central directory and the end records, and has the hybrid flag. A phkv reader finds the superblock from the end of central directory record (§17.2), which is the one place where it reads a ZIP structure; the container is otherwise read alone.

  3. Records. The store has one record for every entry of the archive except __vz__/phkv, so its n counts hidden entries too. A record has hidden set if and only if its key starts with __vz__/.

    • A bytes entry has a kind-0 record, not inline, with codec 0 (method 0) or 1 (method 8), whose offset, stored_length and size are the entry’s body offset, compressed size and uncompressed size.

    • A reference entry has a kind-1 (extra field 0x7A76) or kind-2 (0x7A77) record with the same payload. Its body MUST be byte-identical to the payload (§11.3 allows an empty body; this profile does not).

  4. The source table. The SOURCES section is the body of __vz__/sources: its directory entry has codec 1 and the entry’s body offset and compressed size.

  5. Agreement. The phkv operations (§22.2) give the same results as vzip’s (§13.2) for every key.

A reader that knows only vzip sees __vz__/phkv as one more hidden entry, and reads the archive as before. A phkv reader reads no ZIP structure but the end of central directory record.

Bytes values cannot use codec 2 (Zstandard) in a hybrid store, since a vzip archive allows only methods 0 and 8 (§10.1).

22. Reading a phkv store¶

22.1 Opening¶

Opening a phkv store (§6.1) reads and checks the following. Any failure is an archive error:

  • the superblock, found as in §17.2, of format version 0 with no unknown flags;

  • the directory: within the file, matching directory_crc32c, a whole number of 40-byte entries with reserved fields 0 and no unknown flags, and no unknown section with must_understand set;

  • the sections, as §17.4 requires them by type, count and codec, each within the file;

  • the sections read whole (SOURCES, PAGES, PTRHASH and METADATA): their stored bytes match crc32c and decode cleanly to size bytes (§17.5), within the limit for data read at open (§6.7 rule 6);

  • the source table, valid as §5 requires; the page index and the PTRHASH section, not malformed (§19.4, §18.1); the SLOTS section’s length (§18.2); and the METADATA section, if there is one (§20.3).

A reader MAY read more, but MUST NOT report an error at open that this section and §6.1 do not list. In particular, records and PROPERTY sections are not read at open. A reader MAY read the SLOTS section whole and keep it, which saves a read per lookup at the cost of about 12 bytes per key read at open and held.

22.2 Operations¶

On a phkv store, the operations of §6.2 work as follows.

  • classify(key) finds the key’s record (§19.5), and returns its kind: bytes for kind 0, reference for kinds 1 and 2. A key without a record, or whose record is hidden, is missing.

  • get(key, request), for a bytes record, returns the requested window of its value (§19.2). A codec-0 value is read only within the window; a compressed one is decoded whole. A reference is resolved (§6.3). A key without a record, or whose record is hidden, is missing.

  • list(prefix) returns the keys of the records that are not hidden and start with prefix, in UTF-8 order. It reads the pages whose key range may hold such a key, with the rule of §13.2, and fails with an entry error if one of them cannot be parsed (§19.4).

  • raw(key), in a standalone store, returns a bytes record’s stored bytes, not decoded, and a reference record’s payload. It does not decode the stored bytes, so the only body errors it reports are stored bytes outside the file and, for a codec-0 value with crc32c set, a checksum mismatch. In a hybrid store it returns what vzip’s raw view returns (§13.2): a bytes record’s value, decoded; a reference record’s payload (which is its entry’s body, §21); the same for hidden records; and for __vz__/phkv, the container region. In either profile a key without a record is missing.

A phkv reader also provides two operations of its own, which are not refkv operations and look up keys as raw does, hidden records included:

  • entry_info(key) → missing, or the record’s kind; for a bytes record, also its codec, stored_length, size, and crc32c if present; for a reference, its payload_length. With it, a caller can interpret what raw returns.

  • property(key, name) → missing (no such key), absent (no PROPERTY section named name, or no value for this record), or the record’s value, typed by the section’s value_type. It fails if the section is malformed (§20.1) or the record’s rank is not less than n.

22.3 Errors¶

In a phkv store, the error classes of §6.4 have these causes, besides those of Part 1:

class

causes in a phkv store

archive error

everything §22.1 checks

entry error

the slot of the key points outside the RECORDS section, or at a malformed record (§19.5); for list, a page that cannot be parsed (§19.4)

body error

a bytes value’s stored bytes lie outside the file (judged as a whole, even for a small window); compressed stored bytes do not decode cleanly (§17.5); a codec-0 value whose stored_length and size differ; a crc32c mismatch (§19.2)

payload error

a payload longer than 2^24 bytes (§19.3)

In the order of checks of §6.4, step 3 is the lookup of §19.5 and the record’s entry error, and step 4 reads the stored bytes.

22.4 Violations readers need not detect¶

For stores that break these writer requirements, reader results are unspecified (besides those of §6.6):

  • §17.3: the crc32c of a section the reader does not read whole.

  • §18.3 and §19.1: whether the slot table matches the records (a key that only the page index finds, or two slots with one record); whether records are sorted and their ranks are their positions.

  • §19.4: whether the pages match the records beyond the checks there.

  • §20: duplicate PROPERTY names, and whether a value matches its registered meaning.

  • §21: whether a hybrid store’s container matches its ZIP structures. A phkv reader reads only the container; a vzip reader only the ZIP structures.

  • §17.1: region_offset and region_length, except in raw("__vz__/phkv").

23. Writing a phkv store¶

23.1 Requirements¶

A writer of a phkv store follows §7. It MUST also reject its input, producing no store, if:

  • a reference payload exceeds 2^24 bytes (§19.3);

  • in the hybrid profile, a key is __vz__/phkv, or the input breaks a requirement of the ZIP binding (§14.1);

  • in the hybrid profile, a bytes value would use codec 2 (§21).

It writes the perfect hash of §18 for every store with a key; a writer that finds no seed and pilots for its keys fails.

23.2 Recommended layout (informative)¶

[bytes values]          not inline, in key order
[RECORDS]               in key order
[SLOTS]                 8-byte aligned
[PROPERTY sections]     8-byte aligned
[PAGES]
[PTRHASH]
[SOURCES]
[METADATA]
[section directory]
[superblock]            D = 0

With this layout, what a reader reads at open is at the end of the file. It reads the last bytes of the file (64 KiB or more), which hold the superblock and directory, and then the range from PAGES to the directory, if the first read did not cover it. Each get then reads one slot and one record, plus the value if it is not inline. A reader that keeps the slots it reads, a block at a time, reads no slot for a later get whose slot is in a block it has.

23.3 File names¶

A standalone store SHOULD be named with the extension .phkv. A hybrid store is a vzip archive, and SHOULD be named .vzip (§14.3). Readers MUST NOT depend on the file name.

24. Security considerations for phkv¶

  • Every offset and length in a phkv store comes from the file. Readers MUST check that each region lies within the file before reading it, and MUST NOT allocate for a section, record or value more than the limits of §6.7 and §8 allow. In particular, the PTRHASH section is read at open, so its size is bounded by rule 6, which also bounds the number of keys whose store a reader will open.

  • A compressed value can expand greatly. Readers stop decoding at its size (§17.5).

  • A key’s slot is computed from its bytes with a public hash and a seed stored in the file. Someone who chooses the keys can make construction slow (by choosing keys that collide), but cannot make lookup slower than one slot and one record.
