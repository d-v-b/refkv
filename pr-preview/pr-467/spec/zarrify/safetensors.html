safetensors¶

The Zarr layout of a safetensors file: the named tensors of a machine learning model’s weights, as Hugging Face’s safetensors library writes them (model.safetensors). What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the safetensors profile, Part 2 below. The format is the one the library’s README defines (huggingface/safetensors), cited here as “the format”; where the README is silent, the library’s reader (safetensors/src/tensor.rs, version 0.7) decides.

Convention version: 0 (until release, conventions §1) · UUID: 15e7ce39-d4ca-4514-8144-6e19d2a0341b · Schema: schema.json

Changes: changes/safetensors/, one file per change.

Added 2026-11-01.

This document has two parts (conventions §11.1).

Like NumPy’s, a safetensors file’s tensors are not images: the hierarchy holds each tensor as a plain Zarr array, with no OME-NGFF metadata. The values stay in the file: each chunk is a range of it.

The root and refkv_source declare the convention (conventions §11.2), the root with its source metadata of §5.1 as the member "safetensors". Its CMO is:

The root’s attributes are zarr_conventions and refkv_zarrified and nothing else: there is no ome member, since the hierarchy is not an image. The arrays and the other groups have no attributes.

2. The safetensors format¶

A safetensors file is a length, then a header, then the buffer:

bytes

field

type

value

0–7

length

u64, little-endian

N, the header’s length in bytes

8 to 8 + N − 1

header

UTF-8 text

a JSON object, which starts with {; spaces (0x20) may pad it at its end

8 + N to the end

the buffer

bytes

the tensors’ data, one after another, with no gap

The library writes N as a multiple of 8, padding the header with spaces; real files that other writers made have other lengths (the survey of §7 found N of 14283 and 10830).

The header’s members are the tensors, each a tensor’s name and its entry, and optionally the member __metadata__, an object of string values (the file’s free-form metadata, often {"format": "pt"}). Their order is the writer’s: the library writes __metadata__ first and the tensors by data type and name, so a tensor’s place in the header is not its data’s place in the buffer. A tensor’s entry is an object with these members:

member

type

value

dtype

string

the tensor’s data type (§3)

shape

array of integer

the tensor’s size along each of its axes, [] for a scalar (rank 0)

data_offsets

array of two integers

[begin, end]: its data is the bytes [begin, end) of the buffer, 8 + N + begin to 8 + N + end of the file

An entry’s other members, which the library ignores, are kept in the source metadata (§5.1). A tensor’s elements are in C order (the last index varying fastest), each in little-endian byte order. Its data is B = ⌈e · k / 8⌉ bytes, e the product of its shape (1 for []) and k its data type’s bits; e · k is a multiple of 8. Sorted by data_offsets, the tensors’ data covers the buffer from its start to the end of the file, with no gap and no overlap (§8.2).

A Zarr data type of zarr-extensions is used only where its definition is the library’s type bit for bit, as the library reads it into PyTorch (safetensors/torch.py): F8_E5M2 is torch.float8_e5m2, which has infinities, as zarr-extensions’ float8_e5m2 has. The fill value is the data type’s zero: false for bool, 0 for a number (a float’s too), [0, 0] for complex64; float8_e8m0fnu, a power of two with no zero, has "NaN". No chunk of a tensor is missing, but those of a tensor of size 0.

3.1 The refkv.float8_e4m3fn data type¶

refkv.float8_e4m3fn is an 8-bit floating-point data type, the E4M3 format of the OCP 8-bit floating point specification (OFP8, 2023), which ml_dtypes and PyTorch call float8_e4m3fn (“finite”):

  • Name: "refkv.float8_e4m3fn", with no configuration.

  • Bits: 0bSEEEEMMM: a sign bit, 4 exponent bits with a bias of 7, and 3 mantissa bits. A biased exponent of 0 is a subnormal number, (−1)^S · 2^−6 · M / 8; otherwise the number is (−1)^S · 2^(E − 7) · (1 + M / 8). There are no infinities: 0x7F and 0xFF (S.1111.111) are NaN, and the largest finite number is 448 (0x7E).

  • Fill value: as Zarr v3 core’s floating-point types: a JSON number, which MUST be exactly representable; "NaN", the bits 0x7F; or a hexadecimal string "0xNN", the bits. The strings "Infinity" and "-Infinity" are not allowed, since there is no such value.

  • Codecs: with bytes, each element is one byte and endian has no effect; with packbits, it is 8 bits.

  • Readers: a Python reader maps it to ml_dtypes.float8_e4m3fn, as refkv’s zarr extra does (refkv.zarr.dtypes). TensorStore has the same type under the name float8_e4m3fn, which zarr-extensions does not define; zarr-extensions’ float8_e4m3 is the IEEE-style E4M3, with infinities, a different type.

3.2 Packed data types¶

F4, F6_E2M3 and F6_E3M2 have k of 4 and 6 bits: the buffer holds a tensor’s elements as one sequence of bits, element i its bits [i · k, (i + 1) · k), and bit j of the sequence is bit j mod 8 (from the least significant) of the data’s byte ⌊j / 8⌋. For F4 this is PyTorch’s float4_e2m1fn_x2, two elements a byte with the first in bits 3 to 0, which the library writes (its header’s shape counts elements, not bytes). It is the order of zarr-extensions’ packbits codec with padding_encoding "none", which decodes such a tensor’s chunks (§4.2). No writer of F6_E2M3 or F6_E3M2 tensors was found; the library defines their bits, and this order is the one it gives F4.

4. The hierarchy¶

The hierarchy is a group at the root: the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A}, where A has zarr_conventions and refkv_zarrified (§1) and nothing else. Each presented tensor is an array at its path.

4.1 Paths¶

A tensor’s path is its name, its / separating Zarr node names: model.layers.0.weight is the root’s child of that name, and encoder/conv/kernel the array kernel of the group encoder/conv. A tensor is presented unless:

  • its name is not a path of node names: a part between two / (or before the first, or after the last) is empty, . or .., starts with __, or is zarr.json (reason name);

  • its path’s first node name is refkv_source (reason reserved);

  • its path is a proper prefix, ending before a /, of another tensor’s name, which makes it a group (reason path).

Every proper prefix of a presented tensor’s path that ends before a / is a group, with the attributes {}. A tensor that is not presented is in the root’s source metadata, with its reason (§5.1), and its data is in the mirror.

7. What the layout does not express¶

This section is informative.

  • Sharded checkpoints. A large model is several files, model-00001-of-00004.safetensors and so on, with a model.safetensors.index.json that maps each tensor’s name to its file. The file form zarrifies one of them; the store form (§9) zarrifies a store of them as one group, a group per shard. A model’s tensors are not also gathered by name across its shards: the index, which the store form checks and keeps, says which shard holds each.

  • Readers of the data types. zarr-python 3.4 has no bfloat16, float8_*, float4_* or float6_* data types, and no packbits codec: refkv’s zarr extra registers them, through ml_dtypes (refkv.zarr.dtypes, refkv.zarr.codecs.packbits). TensorStore 0.1.86 reads bfloat16, the float8_* types of zarr-extensions and float4_e2m1fn with the bytes codec, but not refkv.float8_e4m3fn (it names that type float8_e4m3fn), the float6_* types, or packbits. A tensor’s data type is also in the root’s source metadata, as the file names it.

  • The header’s text. Its spacing, its padding, its members’ order and the place of __metadata__ are in the mirror (header), not in the layout.

  • Model structure. The names’ dots (model.layers.0.mlp.up_proj.weight) are a framework’s module path; the layout keeps each name whole, as one node, rather than guess a hierarchy from them.

  • Survey. The design was checked against the headers of ten public files on the Hugging Face Hub (2026-11-01, over range reads): GPT-2, Qwen2.5-0.5B (BF16), a FP8 checkpoint of it (BF16 and F8_E4M3), BERT, all-MiniLM-L6-v2, DINOv2, Whisper, a VAE and a timm ResNet. Their headers start with {", two have an N that is not a multiple of 8, one lists its tensors in no order of their data, one has scalars (shape []), and none names a tensor with a /.

Part 2. The profile¶

The safetensors profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

8. safetensors profile¶

8.1 Signature¶

The input is a safetensors file, which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/safetensors.json, before the TIFF profile’s) chose: H has at least 10 bytes; the u64 at byte 0, little-endian, is at least 2 and at most 100000000; byte 8 is { (0x7B); and byte 9 is ", }, or a space, tab, line feed or carriage return. (Its precedence is before TIFF’s because a header of 2771273 bytes starts with II*\0, TIFF’s signature; a TIFF file, whose first IFD is not at offset 0, never has byte 8 { with bytes 4–7 zero.)

The profile reads the file’s first min(size, 65536) bytes, which hold the length and, in every file of the survey, the header; then the rest of a longer header. It reads no tensor’s data, but for the edge chunks it copies (§8.3).

8.2 Checks¶

The input is rejected unless all of these hold, checked in this order:

  • Length: the file has at least 8 bytes.

  • Limit: N is at most 100000000, the library’s limit (MAX_HEADER_SIZE).

  • Header: 8 + N is at most the file’s size.

  • Text: the header is UTF-8.

  • Start: the header starts with {.

  • JSON: the header is JSON (RFC 8259, with its trailing spaces), whose objects have no member twice (“Duplicate keys are disallowed”, the format), and it is an object.

  • Metadata: __metadata__, when present, is an object whose values are strings.

  • Entries: every other member’s value is an object with the members dtype, a string; shape, an array of integers from 0 to 2^53 − 1; and data_offsets, an array of two such integers.

  • Data types: each tensor’s dtype is one of §3’s.

  • Offsets: taken in the order of their data_offsets, [begin, end] (and of the header, for equal ones), each tensor’s end is at least its begin, and its begin is the previous tensor’s end (0 for the first): no overlap, and no gap.

  • Size: in the same order, each tensor’s e · k is a multiple of 8, and end − begin is e · k / 8, computed exactly.

  • Buffer: the last tensor’s end (0 for none) is the buffer’s size, size − 8 − N.

The library’s reader checks the same, but for three rules its README states and its reader does not test: Start (it reads a header that starts with spaces, which the signature never chooses); a member written twice, of which it keeps the last; and the limit of 2^53 − 1 on integers, where it takes any 64-bit one (no file can hold a buffer that large). A file with no tensors is accepted: its hierarchy is the root alone.

8.3 Chunks¶

A presented tensor’s data is B contiguous bytes at offset v = 8 + N + begin, its elements in C order. Every chunk of the tensor is present. A tensor of k ≥ 8 bits is cut as conventions §7 cuts contiguous values of its shape, with elements of k / 8 bytes and the chunk limit 2^20 bytes (1 MiB). A tensor of rank 0 is one chunk, <path>/c, the range (0, v, k / 8); a tensor of size 0 has none.

A packed tensor (§3.2) is cut as contiguous values of its shape with elements of one byte, the same limit: each chunk is a run of the elements [s, s + m) of the tensor, of a chunk shape of C elements. When s · k is a multiple of 8 for every chunk, the chunk is the bytes [v + s · k / 8, v + (s + m) · k / 8), padded with zero bytes to ⌈C · k / 8⌉. Otherwise the tensor is one chunk, its whole data, of the chunk shape shape (each size at least 1).

8.5 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the file: what it found of the header, in the format’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7), which give each tensor’s bytes. Its JSON Schema is safetensors/description.json. It holds none of an output’s decisions: which tensors are presented and why the others are not, their paths and the groups they make (§4.1), each array’s data type, fill value, chunks and codecs (§3, §4.2, §8.3) and the source metadata (§5) are the projection’s. Those decisions are refkv’s plan of the file, made from the description alone by the function the convention’s projection calls (safetensors::plan::plan in the Rust core); a layout that wants another hierarchy makes its own from the description. It is a JSON object with these members:

value

header_length

the header’s length N, the file’s first 8 bytes (§2)

the header’s __metadata__, its strings as written; null without one

tensors

each tensor in the order the header writes them: name, its member’s name; dtype, shape and data_offsets, its entry’s; and extra, its entry’s other members, where it has any

the IR’s elements: length, header, and tensors, each tensor’s data element in the order of tensors, null for a tensor of no bytes

Every tensor of the header is there, those §4.1 does not present among them: a header that fails a check of §8.2 rejects the file before the description.

9. The store form¶

The store form zarrifies a store input (spec/zarrify.md §1.4) of safetensors files, such as a model’s repository: its shards (the objects whose keys end in .safetensors, at any depth), the indexes of sharded checkpoints (keys ending in .safetensors.index.json), and the configurations beside them (an object config.json in a directory that holds a shard). The store chooses it when its root has none of the other store profiles’ keys and some key ends in .safetensors (“Choosing the profile”).

9.1 The hierarchy¶

The root is a group, which declares the convention (§1) with the store’s source metadata of §9.2 as "safetensors", and source.url the store URL. Each presented shard is a group at its key: model-00001-of-00048.safetensors, or unet/diffusion_pytorch_model.safetensors, below a group per directory above it (attributes {}). A shard’s group declares the convention with the shard’s own source metadata, its SafetensorsRoot, and holds its tensors at their paths, as the file form lays them out at the root (§4): the array of the tensor layers.0.w of the shard model-00001-of-00048.safetensors is model-00001-of-00048.safetensors/layers.0.w.

A shard is presented unless:

  • its header fails one of §8.2’s checks: its reason is the check’s message;

  • a segment of its key starts with __ or is zarr.json, or its first segment is refkv_source: its reason starts name: or reserved:;

  • its key is another shard’s directory (a store may hold the keys a and a/b): its reason starts path:.

The store is not rejected for a shard that is not presented: the shard is listed with its reason, and referenced whole, as an other object (§9.4).

9.3 Reading and checks¶

The store form reads, in one batch, every shard’s first min(size, 65536) bytes and every index and configuration whole (one longer than 16 MiB is not read, and has a problem); then, in a second batch, the rest of every header longer than the first read. Each shard’s header is checked as §8.2 checks a file’s, each failure the shard’s reason. A shard’s tensors’ data is never read.

9.4 Chunks and sources¶

A presented shard’s tensors are cut into chunks as §8.3 cuts a file’s, each chunk a range of the shard’s object (its offsets the file form’s), its padding a range of the output’s zero data source; no chunk is copied. Every other object of the store that is not empty (an object the hierarchy does not hold: a shard not presented, a configuration or index that is not a JSON document, and every other file, such as a tokenizer, a README or code) is referenced whole at refkv_source/objects/<k>, as spec/zarrify.md §1.4 says. As the SAFE profile’s, the url sources are one per object that some reference uses, and the zero data source follows them.

9.5 The IR mirror¶

The store IR (conventions §8.9) lists every object. A shard whose header passes §8.2’s checks is described in place, whether or not it is presented: its elements are the file form’s (§5.3), at its offsets, and its bytes stay at its URL. Which objects the IR describes does not depend on the hierarchy. An index or configuration that is a JSON document is held: its members’ values are its elements (spec/zarrify.md §1.6), and the mirror rebuilds it. Every other object is referenced.

9.6 Summary¶

This section is informative. The summary has shards (each presented shard’s {"key", "tensors"}), unpresented (the shards not presented), chunks and others (the objects referenced whole).
