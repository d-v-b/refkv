VSI¶

The Zarr layout of an Olympus VSI slide (a cellSens .vsi file and the tile files beside it), and the translation of its metadata tree into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, which files it reads and which inputs it rejects, is the VSI profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: c0a1d4e6-5b7f-4f3a-9c2d-8e1f6a7b3c45 · Schema: schema.json

Changes: changes/vsi/, one file per change.

Added 2026-10-21.

This document has two parts (conventions §11.1).

1. Declaration¶

The root and refkv_source declare the convention (conventions §11.2), the root with the .vsi file’s URL as source.url (the object URL of its key in the store, spec/zarrify.md §1.4) and its source metadata of §6.1 as the member "vsi". Its CMO is:

{
  "uuid": "c0a1d4e6-5b7f-4f3a-9c2d-8e1f6a7b3c45",
  "schema_url": "https://d-v-b.github.io/refkv/conventions/vsi/schema.json",
  "spec_url": "https://d-v-b.github.io/refkv/conventions/vsi/",
  "name": "refkv_zarrified",
  "description": "The Zarr layout of a VSI source zarrified by refkv, and the source's metadata"
}

Each image’s group (§4) declares it too, with the image’s source metadata (§6.1) as "vsi" and no profile, version or source (a node property, conventions §2, a NodeProperty). The arrays and the OME group have no attributes.

2. The .vsi file¶

A slide is a .vsi file and a directory beside it, _<name>_ for the file <name>.vsi, holding one directory per stack with a tile file (§3). The .vsi file is a little-endian classic TIFF (II, 42, the first IFD’s offset) whose byte 8 starts the metadata tree: a container of fields that fills the rest of the file, and inside whose regions the TIFF IFDs lie (§2.3). All integers are little-endian. The types:

type

value

i32, i64

a two’s complement integer of that width

u32

an unsigned integer of that width

f64

an IEEE 754 binary64 number

A plain (not extended, not inline) field is a value: its data is one value, or an array of values, of its field type. A volume’s data is one container, with the region [q, data end). Tags are reused in different containers with different meanings (2003 is Dimension size in a stack’s volume and Display limits in a property set; 2018 is RWC frame origin in the stack properties and the External file properties set in a frame volume; 2019 RWC frame scale and Coarse frame IFD). The table tag_names of the schema names the tags as Bio-Formats’ CellSensReader does; a tag it does not name is still a field.

2.3 The TIFF images¶

The TIFF chain starts at the header’s first IFD offset: each IFD is an entry count (u16), 12-byte entries (tag, type, count, value or offset) and the next IFD’s offset (u32), as classic TIFF; IFD k of the chain has the index k. An IFD whose entry of tag 34665 (ExifIFD, type LONG, IFD or SHORT) is not 0 also has an EXIF IFD at that offset, which is not in the chain. Every IFD, main or EXIF, lies inside a TIFF region of the tree (§2.1); its elements go under that region’s field (§6.3).

An IFD used as an image (the macro image, §4.3, or a stack’s default sample IFD) is one of ImageWidth (256) × ImageLength (257) pixels, with these tags; a tag that is absent has its TIFF default:

A tile’s coordinates are its column (coordinate[0]) and row (coordinate[1]) in the level’s grid of tw × th tiles, then the stack’s dimensions in coordinate order (§2.2), and, when use_pyramid is set, the level last (coordinate[n − 1]). A PNG or BMP file says what order its samples are in, whatever component_order says.

4. The images¶

The hierarchy is a bioformats2raw layout of images (conventions §4, its entries; this convention’s are in Layout): the root zarr.json (CollectionRoot) has "ome": {"version": "0.5", "bioformats2raw.layout": 3} beside zarr_conventions and refkv_zarrified (§1), the group OME has {"version": "0.5", "series": ["0", "1", ...]}, and image k is the group k, one OME-Zarr 0.5 image named by its stack. The images are, in this order: each stack of the tree (§2.2) that has a tile file (§4.1) or else a default sample IFD (§4.3), in the tree’s order; then the macro image (§4.3), when the collection volume has a Default sample IFD field (2016). A stack with neither is no image (it is listed in stacks, §6.1), and nor is an IFD image the layout cannot present (§4.4). Without any image, the root has no ome member and there is no OME group.

4.1 The pyramid¶

A stack with a tile file is an image whose levels are the tile file’s: L levels, L being 1 past the greatest level coordinate among the tiles when use_pyramid is set, else 1. Level 0 is W × H (§2.2). Level l > 0 is w_l × h_l from the level before, as Bio-Formats computes it: with mx = tw × (1 + max column coordinate at level l) and my likewise for the rows, w_l = floor(w_{l−1} / 2), plus 1 when w_{l−1} is odd and that quotient is less than mx, else capped at mx when it is greater; h_l the same from h_{l−1} and my. A tile whose column is ceil(w_l / tw) or more, or whose row is ceil(h_l / th) or more, is outside its level and is no chunk (the count is recorded, §6.1).

Axes: t when the t dimension’s size T is over 1; c when the c dimension’s size C is over 1 or the samples per pixel S are over 1; z when the z dimension’s size Z is over 1; then y, x. (A dimension is the stack’s dimension of that meaning whose coordinate is a tile record’s and not the level’s; without one, its size is 1. A dimension of another meaning has the size 1, §9.3.) t is time, c channel, z, y and x space.

Arrays: one per level, at the path l.

Each channel has "active": true and, for a data type of at most 32 bits, a window: min 0 and max the type’s largest value (for a signed type, its least and largest), start and end the display limits, clamped to [min, max], when they are finite and end > start, else min and max. The limits are the channel’s own (§2.2), else the stack’s. A 64-bit or float type has no window.

6.2 The IR mirror¶

refkv_source is the input’s IR mirror (conventions §8), a store IR (conventions §8.9) whose objects are the files the profile read: the .vsi file, at its key, and each stack’s tile file, at its key under the directories _<name>_ and stack<N>. Every object is described in place: its leaves partition it, and its bytes stay in the file (the table holds none of them). The view, refkv_source/tree, shows the headers, the tree’s fields and values, the IFDs’ entries and the tile directories; tiles, strips and gaps are not shown. A tile file the profile did not probe (a frame_t_0.ets beside a frame_t.ets, §9.2) is not an object.

8. What the layout does not express¶

This section is informative. The layout keeps what OME-NGFF 0.5 can place: each stack’s pixels with a pixel size, a position and channel colors. The rest of what cellSens records is in tree, in each image’s source metadata, or in the mirror.

  • The relation between stacks. An overview (type 1), the default image (type 0) it was the preview of, a focus map (type 4), a sample mask (2) and the EFI maps (8, 16, 32) are separate images, placed by their origins on one stage; the layout does not say which overview belongs to which scan. type and type_name say what each is.

  • The coordinate values of a dimension: Z start, Time start and the per-plane values a dimension description holds are not applied (the z scale is the z step alone, t has none); the channel wavelengths are recorded, not expressed.

  • Dimensions the axes cannot hold. A lambda, phase or unknown dimension is accepted only when its size is 1 (§9.3).

  • The IFD images it cannot present (§4.4): recorded with their reasons, their bytes in the mirror.

  • The thumbnails. Each stack’s coarse frame IFD (a small JPEG of the stack) is in the mirror but is no image: the pyramid’s levels serve.

  • Display. The stack’s and channels’ display limits become windows; the LUT itself (a 256-entry colormap, of which the layout keeps the last entry as the channel’s color), the default background color (2034, the stack’s) and the magnification are recorded only.

  • Document properties: the name, author, creation time, the product and its version, the objective and camera settings, and every other tag: in tree, by number and, where Bio-Formats names them, by name.

  • The tile index of each record and the file’s colorspace and quality: in the mirror and ets.

Part 2. The profile¶

The VSI profile of spec/zarrify.md is §9 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles. The input is the slide’s files, and the profile also says which of them are read.

9. VSI profile¶

The input is a file input that names the .vsi file (a URL, or a local path), which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/vsi.json) chose: bytes 0–3 of H are 49 49 2A 00 (a little-endian classic TIFF) and bytes 8 to 11 18 00 49 53 (a container header’s size, 24, and version, 21321; the convention §2.1), tested before the TIFF profile’s. The profile reads it as a file read as a store (spec/zarrify.md §1.8): the store URL is the .vsi file’s directory, its objects are the .vsi file, at its key, and the tile files the profile probes for (§9.2), and the root’s source.url is the .vsi file’s object URL. The .vsi file’s key MUST end in .vsi (in any case), or the input is rejected.

9.1 The .vsi file¶

The .vsi file is read whole, in one request. It is rejected when it is shorter than 32 bytes or larger than 2^28 bytes (256 MiB; a slide’s metadata is a few megabytes), when its byte order mark is not II or its magic not 42, or when its first IFD offset plus 6 exceeds its size.

The tree (the convention §2.1) is parsed from offset 8 to the file’s end, every container and field checked in order:

  • a container is rejected when its 24-byte header does not fit its region, when header_size is not 24 or version not 21321, when containers nest more than 64 deep, when its field count is over 2^20, when data_offset is not 24 (or 0 with no fields), or when its fields’ headers (16 bytes each) do not fit before its region’s end;

  • a field is rejected when its header runs past the container’s region; when next is 0 and it is not the last field, or not 0 and it is; when fp + next is before the field’s header’s end or past the container’s region; when its data ends before its header or past its own region; when it is extended and its type is not 0, 1, 2 or 10 (the schema’s extended_types); or when it is a property set or an mdim volume whose size is not 0 (their containers fill their regions).

The chain (the convention §2.3) is read from the first IFD offset: an IFD whose entries and next-offset word do not fit in the file is rejected, as are more than 65536 IFDs (EXIF IFDs counted) and a chain that returns to an IFD already read (a next offset or an EXIF offset seen before). An entry’s out-of-line value that lies outside the file is not an element (the entry’s 12 bytes are). An IFD that lies in no TIFF region of the tree is read but has no elements; when the profile would use such an IFD as an image, that image is not presented.

An IFD image that cannot be presented (the convention §4.4) does not reject the input: what is lost is that image, and the rest of the slide is presented. What the chain’s own checks reject is the file’s structure, whichever IFD they meet, and a tile file is rejected as §9.2 and §9.3 say: it holds a stack’s pixels.

The stacks are found as the convention §2.2 says. A stack that has a tile file but no image boundary (a width and height of at least

  1. is rejected. A stack of the collection volume that is not a volume field of tag 2001 is not a stack; a stack whose dimension descriptions name coordinates the tile records lack is accepted (those dimensions have the size 1, §9.3).

9.2 The tile files¶

For each stack that has a tile file, in the tree’s order, the profile probes two keys, in this order: _<base>_/stack<id>/frame_t.ets and _<base>_/stack<id>/frame_t_0.ets, where <base> is the .vsi file’s key without its last four characters and <id> the stack’s id in decimal. The first keys of all stacks are one batch; the second keys of the stacks whose first key is absent are a second batch, left out when there are none. A key is not probed once an earlier key of its stack is found, so a host is never asked for a file beside a tile file it has: a host may answer for a missing file in a way a reader cannot tell from a failure, such as a 404 without CORS headers, which a browser reports as a network error. A probe asks the host whether the object exists and how large it is: a local file that is there, or an HTTP object whose response to the first request is not a 404 (a HEAD or a ranged GET under the reader policy; a 404 is absent; any other failure is a failure, not a rejection). The first candidate found, in the order above, is the stack’s tile file, an object of the store at that key. A stack none of whose candidates exists is rejected: stack <id> (<name>) has no tile file: neither _<base>_/stack<id>/frame_t.ets nor _<base>_/stack<id>/frame_t_0.ets exists.

The hosts drive this through the core’s store run: the run’s poll returns an empty read list while probes are pending, the host answers each key with its size or none (probes and found of the Python, TypeScript and Rust bindings), and the run goes on. Both implementations open each object through a transport of its own (a mapped local file, or an http(s) object under the reader policy), reading ranges from then on.

Each tile file is then read in two batches across every file: its first 64 bytes (the SIS header), then its ETS header (ets_size bytes at ets_offset) and its tile directory (tiles × (20 + 4n) bytes at tiles_offset), both in one batch. A tile file shorter than 64 bytes is rejected, and so is one whose SIS magic is not SIS, whose header_size is not 64, whose coordinates are fewer than 2 or more than 16, whose ETS header is outside the file or shorter than 228 bytes, whose tile count is negative or over 2^24, or whose directory is outside the file. Its ETS header is rejected when its magic is not ETS, its pixel type is not in pixel_types, its channels are not 1, 3 or 4, its compression is any other value than 0, 2, 3, 5, 8 or 9, its compression is 8 (PNG) and its pixel type not uint8 or uint16, or 9 (BMP) and its pixel type not uint8 (a stream of those formats holds no other, and could not decode to the array’s data type), its tiles are not 1 to 65535 pixels on each side, its tile_depth is not 1, or its dimensions are 1 or more than coordinates (0, as a version 0x30003 header has, lists no sizes: every coordinate but the column, the row and the level then has the size 1).

9.3 Tiles and levels¶

The coordinates of a tile record are read as the convention §3 says: the column, the row, the stack’s dimensions by coordinate, and the level last when use_pyramid is set. Each dimension of the stack (the convention §2.2) is checked: its size (the ETS header’s for its coordinate; 1 for a coordinate the records lack or the level’s) is at least 1, and its meaning is z, t or c, or its size is 1 (a lambda, phase or unknown dimension of several values is rejected: the layout cannot place it). A stack with several samples per pixel and a c dimension of several channels is rejected.

Each tile is checked: its size is at least 1 and it lies within the file; each coordinate is 0 or more and, for a coordinate that is not the column, the row or the level, less than its dimension’s size; no earlier tile has the same coordinates; and an uncompressed tile has exactly tw × th × channels × bytes bytes. A compressed tile’s codestream is not read: the output does not depend on pixel data (§1.2).

The levels and their sizes are those of the convention §4.1; a tile outside its level is no chunk, and counted. A tile the directory lacks is no chunk: the array’s fill value stands for it.

9.4 Chunks¶

Every image’s chunk (the convention §4.1, §4.3) references the files; the output copies no pixels. A pyramid’s chunk is one range of its tile file’s object: the tile’s size bytes at its offset, referenced as conventions §7 references a chunk of a store’s object. An IFD image’s chunk is, for JPEG, three parts (the strip’s first 2 bytes, the prefix as a data source, the rest of the strip), or the strip alone, and for an uncompressed image one range per run of contiguous strips, of the .vsi file’s object. An uncompressed IFD image whose runs do not fit in a reference’s payload (§1.2), one of thousands of strips apart, is not presented (the convention §4.4). The output’s data sources are the distinct JPEG prefixes (one per IFD image with a prefix, shared when equal). The output’s source table is one url source per object a reference uses (its object URL, with a size pin), in order of first use, then the data sources in order of first use (the references taken in the order of their keys). A file no reference uses, such as a .vsi file whose IFD images are all left out, has no source: the mirror’s reader reads it at its object URL (conventions §8.9).

9.6 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the slide: what it found of the .vsi file’s and the tile files’ known structures, in Olympus’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7). Its JSON Schema is vsi/description.json. It holds none of an output’s decisions: which stacks and IFDs are images and in what order (§4), and which IFD images are not presented (§4.4); the levels, axes, data types, fill values and codecs (§4.1, §4.3); the channels’ labels, colors and windows (§4.2); the units, scales and translations (§5); and the source metadata (§6) are the projection’s.
