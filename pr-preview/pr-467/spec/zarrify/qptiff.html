QPTIFF¶

The Zarr layout of an Akoya Biosciences (formerly PerkinElmer) QPTIFF file: the whole-slide scans of the Vectra and Vectra Polaris scanners (.qptiff), and the unmixed component data inForm writes (.tif). QPTIFF is a TIFF whose images each carry a PerkinElmer-QPI-ImageDescription XML; this convention builds on the TIFF convention, and its source model is the TIFF source model. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store is the QPTIFF profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 329ea136-2f55-4c27-b6f4-8e60ca2109b8 · Schema: schema.json

Changes: changes/qptiff/, one file per change.

Added 2026-10-21.

This document has two parts (conventions §11.1).

The format is described by Akoya’s “PerkinElmer image format” note (PKI_Image Format.docx, 2015, with its public sample files at https://downloads.openmicroscopy.org/images/Vectra-QPTIFF/), which this convention follows where the samples do.

Part 1. The convention¶

This convention gives a layout only to the files that meet its requirements. Where it says that “the input is rejected”, or that something MUST hold, a file that fails has no layout under this convention, and the profile rejects it.

2. The source¶

The file is a TIFF (magic 42) or BigTIFF (magic 43), in either byte order, whose first IFD’s Software tag (305) is ASCII text starting with PerkinElmer-QPI (§7 says how that is tested). Its IFDs are the image file directories of its main chain, which starts at the header’s first-IFD offset and ends at a next-IFD offset of 0, and MUST have at least one IFD; IFD 0 is its first. The SubIFDs of an IFD (tag 330) are read as the TIFF convention §2 says, for the source metadata only: the layout uses the main chain alone. Of duplicate tags in an IFD, the first is used.

The layout uses the tags of the TIFF convention’s table (with their defaults, the strip tags included; field types and counts as the profile checks them), and these:

tag

name

kind

default

286, 287

XPosition, YPosition

scalar (RATIONAL)

An IFD’s format is the tuple of the TIFF convention §2 (BitsPerSample, SamplesPerPixel, SampleFormat, PlanarConfiguration, Compression, Predictor, and PhotometricInterpretation when Compression is 7), computed as it says, for IFD 0 and for every IFD that becomes part of a level (§3); a failure rejects the input.

The QPI description. An IFD’s QPI description is read from its ImageDescription (270) when that has field type ASCII (2): let D be its bytes up to the first NUL; if D is valid UTF-8, its text X is read with the tag scan of the TIFF convention §3 (skipped sections, tags, attribute values and the decoding of references as there), tracking depth: a start tag that is not self-closing opens an element, and an end tag closes one. The description is the first start tag named PerkinElmer-QPI-ImageDescription found at depth 0 (outside every element); without one, or when D is not UTF-8 or the tag is not ASCII, the IFD has no QPI description. Within it, the layout reads the direct children (the start tags at depth 1, inside the root element and no other) named ImageType, Name, Color and SlideID: of each name, the first that is not self-closing. A child’s text is the characters of X from the end of its start tag to the start of the next tag, with skipped sections removed, references decoded as attribute values are, and leading and trailing whitespace removed. Elements nested deeper (the Name inside a ScanProfile, a Responsivity filter’s) are not read. The description’s XML declaration says encoding="utf-16", but the bytes are ASCII; the declaration is a skipped section.

An IFD’s kind is its ImageType text: FullResolution, ReducedResolution, Thumbnail, Overview, Label, another string, or none (no QPI description, or no ImageType child). Only the first two shape the layout; the others, and any IFD whose kind is none or unknown, are kept in the source metadata and otherwise ignored.

3. Images and channels¶

  • Channels. IFD 0 MUST have a QPI description, and its kind MUST be FullResolution. The channels are the main-chain IFDs from IFD 0 to the last of the FullResolution IFDs that start the chain; their count N is at least 1. Channel c (from 0) is the IFD at index c. A FullResolution IFD later in the chain, after an IFD of another kind, rejects the input. When N > 1, IFD 0’s SamplesPerPixel MUST be 1 (several RGB channels are not supported).

  • Levels. Level 0 is the channels. The ReducedResolution IFDs of the chain, in chain order, are taken N at a time: each run of N is the next level, its c-th IFD the level’s image of channel c. Their count MUST be a multiple of N. IFDs of other kinds between them (the Thumbnail between level 0 and level 1) are skipped. The levels are numbered 0, 1, … in that order.

  • Within a level, every IFD MUST have ImageWidth and ImageLength, both at least 1, and all the IFDs MUST have the same width, length, format and tiling (§4.2: tiled with the same TileWidth and TileLength, or in strips with the same RowsPerStrip). Every IFD of every level MUST have IFD 0’s format. A level after the first MUST be strictly smaller than the level before in both width and length.

  • A channel’s name is the Name text of its FullResolution IFD, and its color the Color text; the image’s name is IFD 0’s SlideID text. The ReducedResolution IFDs’ names are not used (the scanners’ brightfield levels have none).

4. The image¶

4.1 Data types and codecs¶

The data type and codecs are those of the TIFF convention §4.3, including its requirements on JPEG, FillOrder and YCbCr subsampling, its LZW row (bytes, refkv.tiff_lzw: the scanners’ default), its Predictor 2 (imagecodecs_delta before bytes), its Predictor 3 (imagecodecs_floatpred in place of bytes) and its rejection of other predictors.

4.2 Tiles and strips¶

An IFD is tiled or in strips as the TIFF convention §2 says (an IFD with TileWidth and TileLength is tiled, and MUST have both of its tile tables, TileOffsets and TileByteCounts or, in an IFD with neither, StripOffsets and StripByteCounts, with TileWidth and TileLength at least 1), and a level in strips has the rows per strip R, the chunks of R rows and the padding of a short last strip of the TIFF convention §4.5 (its limits on the padding and on the bytes an LZW tail reads included, which reject the input whatever the level), with one difference: a level whose short last strip cannot be padded (a compression other than uncompressed and LZW) is not a level, and its images stay in the source metadata. If level 0 would be left out, the input is rejected. (The scanners write 512 × 512 tiles for images larger than about 2K × 2K, and strips of 16 rows for smaller ones, so the smallest levels of a pyramid, and inForm’s component data, are in strips.)

  • Pixel size. PX, PY and the units of x, y are those of the TIFF convention §4.4’s resolution-tag rule (its third rule, from IFD 0’s XResolution, YResolution and ResolutionUnit, 2 or 3, when the pixel is under 25.4 µm): the scanners write ResolutionUnit 3 and the pixels per centimeter, and 96 dots per inch when the resolution is unknown. Otherwise PX, PY are 1 with no unit. c has no unit.

  • Position. The image has a translation (conventions §5), the same at every level, when x and y have units and IFD 0 has XPosition n / d and YPosition n' / d' with d and d' not 0: the translation is x = (n / d) × u, y = (n' / d') × u, where u is 25400 for ResolutionUnit 2 and 10000 for 3 (the positions are in ResolutionUnits, and name the image’s upper-left corner), and 0 for c. The translation MUST be finite.

  • Name: IFD 0’s SlideID text, if present and not empty.

  • Chunks: for channel c of a level, its IFD’s tiles (or strips) are numbered k = s × T + j, where T is the number of tiles (strips) per sample plane (ceil(H / TileLength) × ceil(W / TileWidth), or the strip count), j runs row-major over the tile grid (down the strips), and s is the sample when spp > 1 and planar (else 0). Both offset and byte count tables MUST have T times the number of sample planes values. The chunk with coords c (the channel, or the sample s, or 0 when interleaved; only when c is present), then the tile row and column (the strip index and 0), is tile k. It is present when its byte count is more than 0, and absent (the fill value) otherwise. Its bytes are the tile’s or strip’s, encoded as the codecs say (a short last strip’s, with its padding, §4.2); for JPEG, as the TIFF convention §4.4 says of a tile: a complete stream with the IFD’s JPEGTables and an explicit color transform, with the same requirements on JPEGTables and on the tile’s length. Its reference is a QptiffChunk (§7).

Every channel has "active": true and, but for a float32 channel without a sampled window, a window, as in the TIFF convention §4.4: a QPTIFF records no display range (SMinSampleValue and SMaxSampleValue, when present, are the data’s extremes, not a display setting), so the window is sampled from the middle chunk of each channel of the last level, there in steps 1 to 3, when spp is not 3 (an RGB image, whose samples keep the type’s range) and Compression is 1, 5 (LZW, decoded as §4.1 says, into the chunk’s size) or 8 or 32946 (Deflate), with Predictor 2’s differences summed back and Predictor 3 undone; a level in strips has the chunk shape above, and a padded last strip’s rows past the image are not values. 5. Source metadata¶

The root’s source metadata S is a TiffRoot ({"byte_order": "little" | "big", "bigtiff": true | false}), as the TIFF convention’s. Everything else the file holds is on refkv_source, which is the file’s IR mirror (conventions §11.3). The QPTIFF source model is the TIFF source model (its elements, which IFDs, its values), and with the TIFF convention’s named array rule (“layout tables”, conventions §8.8), so that a level’s thousands of tiles fold into one row of the table, whose extents are read from the TIFF’s own TileOffsets and TileByteCounts (or StripOffsets and StripByteCounts). Every QPI description, the ScanProfile included, is a value of its IFD’s ImageDescription, held in the mirror; the channel names and colors the layout reads are also in omero.

Hierarchies of one file are compared entry for entry, refkv_source included (conventions §11.4).

Part 2. The profile¶

The QPTIFF profile of spec/zarrify.md is §7 of this document. It builds on the TIFF profile (tiff.md §7, tiff.md). What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

7. QPTIFF profile¶

No signature. A file’s first bytes never choose this profile (spec/zarrify.md §1.2): a file the TIFF profile’s signature chose is read by it when it passes the detection test below.

Akoya QPTIFF files are TIFFs or BigTIFFs, in either byte order, whose images each carry a QPI description. They are read by tiff.md §7.1 (tiff.md) with the changes below, with the tags of the convention §2 (the TIFF table and the two it adds) as the checked tags.

Detection. After the header is read (and the NDPI test, ndpi.md §7, has failed), let O be the header’s first-IFD offset. The file is a QPTIFF if the entry count at O and the entries it counts lie within the file, an entry among them has tag 305 (Software; of several, the first), with field type ASCII (2) and a count of at least 15, its value lies within the file, and the value’s first 15 bytes are PerkinElmer-QPI. Otherwise it is a TIFF (tiff.md §7). This test never rejects; the IFD at O is then read as the first IFD of the main chain, with every check of tiff.md §7.1.

Reading. The IFDs, limits and checks of tiff.md §7.1 apply (the main chain, its SubIFDs to depth 4, at most 100000 IFDs; the field type, count and place of every tag of the table in every IFD read, XPosition and YPosition being RATIONAL tags). These values are read (tiff.md §7.1, Values read):

of

every main-chain IFD

every tag of the table but the tile and strip tables (TileOffsets, TileByteCounts, StripOffsets, StripByteCounts), and its ImageDescription when its field type is ASCII (2), for the QPI description (the convention §2)

every IFD of every level

its tile tables, or its strip tables

Each value read of an integer type MUST be at most 2^53 − 1. Nothing else is read for the layout.

Rejection. The input is rejected when a check fails, and when the convention gives it no layout: wherever the convention says that the input is rejected, or that something MUST hold and it does not (the convention §2–§4). The input is rejected with the reason the profile meets first, in this order: the baseline (the convention §3: IFD 0’s description and kind, a late FullResolution image, the samples per pixel of several channels), IFD 0’s predictor, the count of ReducedResolution images, then level by level (each IFD’s size, format, samples and tiling, the level’s uniformity and size), then the data type and codecs, then each level’s tiles or strips (their tables’ counts, each tile within the file), then the padding of each level in strips (a last strip that does not decode to its size; level 0 of a compression that cannot be padded), then the translation.

A short last strip thus has, when uncompressed, the ranges [(0, offset[k], n), Z], and when LZW, the ranges [(0, offset[k], p), T]; any other tile or strip but a JPEG one has the single range (0, offset[k], n). The sources are numbered by §1.2’s order of first use, over the references in the order of their keys. Besides the references and the root’s and the arrays’ zarr.json, the archive’s entries are those of the source metadata node refkv_source, the file’s IR mirror (the convention §5, conventions §8).

7.1 The description¶

This section is not part of the convention. The parser returns, beside the IR, a description of the file as spec/zarrify/tiff.md §7.6 specifies a TIFF’s, with the tags of §2’s table (the position tags with them), and none of the structures of a first IFD’s ImageDescription. Each IFD’s qpi holds its ImageDescription’s QPI elements as §3 reads them: image_type, name, color and slide_id, the root’s direct children ImageType, Name, Color and SlideID (the first of each, references decoded and white space trimmed, null where absent); qpi is null where the ImageDescription is not a QPI description. The channels, levels, scales and position are the projection’s.
