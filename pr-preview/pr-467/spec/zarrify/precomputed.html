Neuroglancer precomputed¶

The Zarr v3 layout of a Neuroglancer precomputed volume, and its info document. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store from a listed store is the precomputed profile, Part 2 below. The format is the one Neuroglancer’s precomputed documentation defines, cited here as “the format”, with its sharded format and its compressed segmentation format.

Convention version: 0 (until release, conventions §1) · UUID: c499987a-9518-4b2b-a804-a70a8de1a911 · Schema: schema.json

Changes: changes/precomputed/, one file per change.

Added 2026-11-03.

This document has two parts (conventions §11.1).

Part 1. The convention¶

This convention gives a layout only to the volumes that meet its requirements. Where it says that “the input is rejected”, a store that fails has no layout under this convention, and the profile rejects it. A scale it cannot present does not reject the store: the scale is recorded, with its reason, and its objects are kept (§3.3).

A precomputed volume is a store with an info document at its root and one directory per scale. Each scale is a 3-D grid of chunks along x, y and z, with channels as a fourth dimension inside each chunk. A scale stores its chunks in one of two ways:

  • unsharded: one object per chunk, named for the voxels it holds;

  • sharded: many chunks in one shard object, found through the shard’s own two-level index.

Connectomics volumes hold very many chunks. BANC has 690 million, 518 million of them in its finest scale, so a layout with a reference per chunk would be a store of billions of bytes that takes hundreds of thousands of requests to build. This layout has one reference per object instead, and reads a shard’s index when a chunk is read, as Neuroglancer does. A shard is one Zarr chunk, read by the codec refkv.precomputed (§6). The output comes from info and the store’s listing alone: the profile reads no chunk and no shard.

3.1 The array¶

With (sx, sy, sz) the size, (cx, cy, cz) the first chunk size, C the num_channels and (kx, ky, kz) the chunks a Zarr chunk holds (1 each for an unsharded scale, its box for a sharded one, §4.2), the array’s axes run from the slowest to the fastest as the format stores them, so that no codec has to transpose a raw chunk. The channel axis is left out of a volume of one channel.

3.2 Chunk objects¶

An unsharded scale’s chunk at position (i, j, k) on the grid is the object at <key>/<x0>-<x1>_<y0>-<y1>_<z0>-<z1>, where x0 = voxel_offset_x + i × cx, and x1 is the lesser of x0 + cx and voxel_offset_x + sx, likewise for y and z. Each bound is a decimal without leading zeros, with a leading - for a negative value. The name may end in a suffix that names its content coding, .gz, .br or .zstd, which §6.3 does not rely on. A name whose bounds are not exactly those of a chunk of the grid is not a chunk object: it is an other object (§8), as are the objects of a second chunk size. When two objects name one chunk (x and x.gz), the first by its key’s UTF-8 bytes is the chunk, and the second is an other object. An object of size 0 is not used (spec/zarrify.md §1.4), so that chunk reads as the fill value.

4.2 A shard is a box of chunks¶

A chunk’s id is its compressed Morton code: with the grid (gx, gy, gz), each axis has ceil(log2(g)) bits, and the id takes their bits from the lowest, x, then y, then z, in turn, leaving out an axis whose bits are used up. With the identity hash, the format places a chunk by its id alone:

  • its minishard is (id >> preshift_bits) & (2^minishard_bits − 1);

  • its shard is (id >> (preshift_bits + minishard_bits)) & (2^shard_bits − 1).

So the id’s lowest L = preshift_bits + minishard_bits bits say where a chunk lies in its shard, and the bits past them say which shard it is in. The lowest L bits of a compressed Morton code are ax bits of x, ay of y and az of z, whatever the other bits are, so every shard holds the chunks of one box of (kx, ky, kz) = (2^ax, 2^ay, 2^az) chunks, aligned to that box’s size on the grid. That box, the shard’s own, is the Zarr chunk: a box that runs past the grid is a Zarr chunk that runs past the array, and every scale of a volume has one. Shards a writer sizes for a scale holding 8 192 chunks are boxes of 32 × 16 × 16.

A shard’s number s gives its box (bx, by, bz) through those same bits: bit j of s is bit L + j of the id, which goes to the axis and the bit that the id’s order gives it, counted from past that axis’s ax, ay or az. A set bit of s past the id’s bits names no box.

4.3 Shards as Zarr chunks¶

A shard object is at <key>/<h>.shard, <h> the shard’s number in lowercase hexadecimal with ceil(shard_bits / 4) digits (0 when shard_bits is 0). Its Zarr chunk is at the box’s coordinates: <n>/c/<bz>/<by>/<bx>, with 0/ first when C > 1. An object of that directory whose name is not of that form, is not canonical, or whose number names no box within the grid is an other object (§8). A shard the store does not have has no entry, and reads as the fill value, like a chunk its shard does not hold.

5. The image¶

The presented scales are the levels of one OME-NGFF image, at <n> in ascending order of the product of resolution’s members in binary64, scales of one product in the order of scales. A level’s resolution is along z, y, x, with 1 for c.

A voxel i covers [i, i + 1) × resolution in the format, and OME-NGFF places a voxel’s center. So a level’s translation along an axis is (voxel_offset + 0.5) × resolution, in binary64, and 0 for c: the first voxel of a level downsampled by 2 lies over the first two of the level before.

PrecomputedRoot, the root’s zarr.json, a GroupDocument whose attributes are a Declaration, and ome, a PrecomputedOme, when any scale is presented. A root with no presented scale is a plain group.

6. The codec refkv.precomputed¶

An array-to-bytes codec, which reads a Zarr chunk that is one object of the volume. No other codec fits: the format’s edge chunks are clipped, in a shape only their position gives; its JPEG chunks hold a volume as one image; and a shard’s chunks are found through an index no Zarr sharding codec reads (§10).

A Zarr codec is not told where its chunk lies, and a clipped chunk’s shape depends on it, as does a chunk’s id. The position makes each value self-describing, in 12 bytes that no read needs a request for, as FITS’s tile parameters do (fits §3.3).

6.2 Decoding¶

The decoder reads the position, and for each chunk the selection touches:

  1. Finds its bytes. In an unsharded array, they are the object. In a sharded one, with m the minishard_bits: the first 16 × 2^m bytes of the object are the shard index, for each minishard two little-endian uint64, the start and the end of its minishard index, relative to the end of the shard index. A minishard index, inflated if minishard_index_encoding is gzip, is n little-endian uint64 three times: the chunks’ ids, delta coded; their offsets, each relative to the end of the chunk before it (to the end of the shard index for the first); and their sizes. A chunk whose id is not in its minishard reads as the fill value. Its bytes are inflated if data_encoding is gzip.

  2. Takes off a content coding, as §6.3 says.

  3. Decodes the voxels of a chunk of its clipped shape, x = min(cx, sx − i × cx) and so on, i its position on the grid:

    • raw: little-endian values, x fastest, then y, z and the channel. A raw chunk of the whole chunk size, from a writer that pads its edge chunks, is accepted too, cut back to the clipped shape.

    • jpeg, png, jxl: one image of width x and height y × z, its samples the channels, its rows the volume’s in the same order.

    • compressed_segmentation: the stream the format defines, with a block grid of the clipped shape.

    • compresso, crackle: a stream of that format, its own header giving x, y and z and its voxels’ width, x fastest.

    • fpzip: an fpzip stream of 4 dimensions, x, y, z and the channel, x fastest.

    • zfpc: a zfpc stream of dimensions as for fpzip: a header of 23 bytes, whose byte 5’s low 3 bits are the data type, 1 to 4 for int32, int64, float32 and float64, whose 4 little-endian uint32s from byte 6 are the dimensions, and whose byte 22 has bit a set when dimension a is correlated; then a little-endian uint64, the offset of the first stream, and one the size of each stream; then the ZFP streams, each with its header, one per position along the dimensions not correlated, the first of them fastest.

    • kempressed: an fpzip stream of dimensions x, y, the channel and z, each value 2 more than the voxel’s, as cloud-volume writes it.

    An encoded shape or data type other than the clipped shape and the array’s is an error.

  4. Fills the rest of the chunk with the fill value, past the volume’s end.

These encodings need decoders that only a reader of those chunks needs: the profile reads no chunk (§11.1), so a hierarchy is the same with or without one.

A reader of one chunk of a shard makes at most three requests: the shard index, one minishard index and the chunk. Chunks read together from a minishard may be one request when they lie near each other in the shard.

6.3 Content codings¶

An unsharded chunk object may be coded as a whole, which its name may say and an HTTP header usually does: a store of the format serves an object with Content-Encoding: gzip or br, and Neuroglancer reads it through a browser that undoes the coding. The listing does not tell, and the profile reads no chunk, so the decoder finds the coding from the bytes, one object at a time:

A reader follows spec/refkv.md §5.2 to read such an object: a 206 whose total is the object’s size pin gives the stored bytes.

7.3 Equivalence¶

Hierarchies of one store are compared entry for entry, refkv_source included (conventions §11.4).

8. Other objects¶

An other object is an object of the store whose size is not 0 and that is neither info nor a chunk object of a presented scale (§3.2) nor a shard of one (§4.3): provenance, meshes, skeletons, segment properties, the objects of a scale that is not presented, and anything else. Each has a reference refkv_source/objects/<k> to the whole object, <k> its key with ~ appended to a last segment that a Zarr reader would open, as the Zarr v2 convention §5 says. No listed object is dropped: an empty one is in the mirror’s listing.

9. Example¶

Harris15 (kharris15/oblique/em, inspected 2026-11-03), a raw uint8 volume of 3 scales with chunks of 512 × 512 × 16, is unsharded and served with Content-Encoding: br. The finest scale is 2.0_2.0_50.0, of size 8192 × 8192 × 91, and has 550 chunk objects. The hierarchy has, among others:

zarr.json                               the root: its ome, and info in its source metadata
0/zarr.json                             shape [91, 8192, 8192], chunk shape [16, 512, 512]
0/c/5/0/0                               [0, 0, 5] as 3 uint32, then 2.0_2.0_50.0/0-512_0-512_80-91
2/zarr.json                             of 8.0_8.0_50.0, shape [91, 2048, 2048]
refkv_source/objects/provenance         the object, whole

The chunk at 0/c/5/0/0 is clipped along z: its stream inflates to 512 × 512 × 11 bytes, which the codec places in the first 11 of 16 slices. The archive is 135 836 bytes for 766 chunks, and takes 1.4 s to write.

BANC (bates_phelps_kim_yang2025/banc/em, inspected 2026-11-03) is JPEG in shards, 7 scales in 87 767 objects. Its finest scale 8_8_45 has size 131072 × 147456 × 7010 and chunks of 128 × 128 × 16. With preshift_bits 11, minishard_bits 2 and shard_bits 17, each shard is a box of 32 × 16 × 16 chunks, so the array’s chunk shape is [256, 2048, 4096], and 64 512 of its 2^17 shard numbers have a box within the grid, each with its object. At the coarsest scale, 512_512_45, of size 2048 × 2304 × 7010 and shard_bits 5, the box is 16 × 32 × 16 chunks, and runs past the 18 chunks the volume has along y: tensorstore gives that scale the same shape as its write chunk, (2048, 2304, 256). The archive is 14 731 923 bytes for 690 million chunks, and took 23.6 s to write. Reading a few chunks takes about a second, and the values equal tensorstore’s.

10. What the layout does not express, and what was weighed¶

This section is informative.

Not expressed. Encodings the codec has no decoder for are kept but not presented, as is a jxl scale of 3 channels: cloud-volume, the writer these encodings have, writes 3 gray frames that its own reader does not read back in order, and one RGB image is another layout of the same bytes, which a reader that does not see the frames, as Neuroglancer’s does not, would take for it. A scale whose hash is murmurhash3_x86_128, whose shards are no boxes, is kept but not presented: all 8 sharded volumes of the 13 surveyed (hemibrain, FAFB, FlyWire, H01, MICrONS and BANC among them, inspected 2026-11-03) have identity, and none wraps. A later layout could present such a scale with a reference per chunk, read from every minishard index, at the cost below. Chunk sizes after the first add no voxels, and meshes, skeletons and annotations stay objects, though a convention of their own could present them.

The cost of this layout is the codec. A reader without it opens the hierarchy and cannot decode a chunk, where the first row would serve one for an unclipped chunk. The cost of a read is the format’s own: a reader finds a chunk through the shard’s index, each read, where the first row has the offset in the reference.

Position in a literal, or a rectilinear grid. A rectilinear grid would say a clipped chunk’s shape without a header. It breaks the consumers that docs/adding-a-format.md lists, and does not give a shard’s position, which a chunk’s id needs.

Why not read a content coding from the header. A profile that asked for each object’s Content-Encoding would make a request per chunk, which is what the layout is built to avoid, and one object’s header says nothing of the next’s. The bytes say it, for no request.

Part 2. The profile¶

11. Neuroglancer precomputed profile¶

Choosing the profile. A store whose root has the key info, and none of the keys spec/zarrify.md §1.4 tests first. Neuroglancer’s precomputed:// and |neuroglancer-precomputed: spellings are not store URLs: give the URL they wrap, ending in /.

11.1 Reading¶

The profile lists the store (spec/zarrify.md §1.5) and reads one object, info, whole, in one request. It reads nothing else, however many chunks the volume has.

Nothing about a scale rejects the input (§3.3). A store of a volume with no scale it can present has a root with no ome, and all its objects are other objects.

11.3 Chunks and other objects¶

Every chunk object, shard and other object has one reference, whole, its source a url source with a size pin, its listed size. The url sources are one per object some reference uses, in the order of first use, the references in ascending order of their keys’ UTF-8 bytes, as for SAFE (safe.md §8.8). A chunk’s reference is a Concat of the literal position and that range (§6.1); an other object’s is that range alone. No other entry is a reference, and the output has no data sources.

11.4 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the store: what it found of the source, for a projection to read with the IR. Its JSON Schema is precomputed/description.json. The parser describes no stored array (spec/stored-array.md §7): the chunks are the listing’s objects, whose names §3.2 and §4.2 place. The description holds none of an output’s decisions: which scales are presented and why the others are not (§3.3), their order, each array’s zarr.json (§3.1), the image (§5), the source metadata (§7) and which objects are chunks (§8) are the projection’s, which makes them from the description and the listing. It is a JSON object with these members:

member

value

info

the info document as parsed, as text (its integers and strings as written, its members in order), which passed §11.2’s checks

documents

the keys of the documents the IR holds: ["info"]

ignored

the keys the listing ignored, where there are any

11.5 Summary¶

The summary line holds arrays (presented scales), notPresented, sharded (the arrays with shards), chunks (the references to chunk objects and shards), emptyChunks, objects and otherObjects, then what every store’s holds (conventions §8.9).
