Stored arrays in the IR¶

A stored array is one structure that a source itself declares as an array, described as the source stores it, at the byte level: its shape, the size of its elements in bits and how they pack, how the source cuts it into units and whether it may leave a unit out, the codecs that decode a unit to the elements’ bytes, the fill value of a unit it leaves out, where the source declares what its elements are, and a map of the units the source holds. Parsers build the descriptions and the map into the IR (conventions §8); projections and profiles read them, together with the source’s own declarations, and decide everything about the output, starting with the data type. This document is not a convention: nothing it specifies is written in an output, and the IR mirror does not record it.

Added 2026-11-08. The design is design/proposals/ir-array-model.md (d-v-b/refkv#289); where the two differ, this document governs.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119.

1. Stored arrays¶

The IR describes the source; a projection decides the output. A description holds what the source holds, as found, and no concept tied to an output encoding: not which arrays are presented or how they are assembled, not output chunking, shards or padding, not data types, byte order names or default values, and no byte the source does not hold. Where the IR cannot or need not interpret something, it falls back to a more general representation: bytes, or where the source holds them (§2.2); the source’s own id and parameters (the codec source, §3.2); an array whose storage it does not model (a description with no grid, §2.3).

Every array a parser reaches has a description, whether or not its profile presents it. A format whose parser describes its arrays has a paragraph in §7, which lists the structures that are its stored arrays and what each of their declarations is, and says what of the format is described and what is not yet; the parser of a format with no paragraph there describes nothing.

These rules are of the descriptions. An element’s form (conventions §8.5) is older, and still gives a format’s own geometry of a unit, a data type’s name among it.

2. The description¶

A description has these members (the Rust type StoredArray of rust/refkv-ir/src/array.rs):

A description stops at the elements’ bytes as they come out of a chain. Which data type those bytes are, in which byte order, how a structure’s members lie, how a string or reference is presented, and what the values mean (a scale, a blank, dimension names) are the profile’s: it reads them from the declarations, or, where a codec makes the elements, from the codec’s entry (§3.2).

2.1 Keys¶

A description is keyed by the IR element that declares the array. For a kind of element that may declare several arrays, the key always adds the array’s index among them, in the source’s order, however many it declares; the format’s paragraph of §7 names those kinds. So (element, index) is one array’s alone, and on each element either no description has an index or every one has, as 0 to n − 1. Within a run, the id is what is computed on; the JSON form also gives the element’s path (§2.5).

Each format’s paragraph of §7 says how a profile finds, from the facts its parser gives, the key of each array’s description: the declaring element’s id, and the index where the format’s kind of element carries one. A profile so matches what its facts say of an array to the array’s description, presented or not. A graft does not touch the facts: a format whose files a store grafts renumbers the ids its facts give in its store code, as the HDF5 store’s placed() renumbers its store.element ids. The declaring element is in no run’s subtree (§5.1), so its id names one element, which an unfold leaves where it is.

2.2 Places and parameters¶

A place is bytes of the source:

  • an IR element (element), with member, for an element in a run’s subtree, the position j of the run’s member it is in, and range, an (offset, length) within the element’s extent (its bytes in its own space); or

  • where no element holds them, a range of an object by its key (object; none for the parsed source itself), the offset counted from the object’s start, and its length. In a store IR, an object is one of the store’s objects, and an external file of a file IR is named by the sibling key the run resolves for it, its key in the store.

An element’s bytes, for a place, are its extent: as many as its extent’s length, in its space. A place lies within what it names: a range within its element’s extent, and an object’s range within the object where its size is known (the parsed source’s in a file IR, any object’s in a store IR).

A parameter of a codec, or a given fill value (§2.4), is a value ({"value": …}) or a place whose bytes the codec makes it from ({"source": place}). It is tagged, so that a value that is an object cannot be read as a place.

2.3 The grid¶

A grid has an entry for each axis, Each(n) or a List, an edge, and sparse (§2.4):

  • Each(n): the axis’s units are all n elements long, but for a last one the axis’s end cuts.

  • List: each unit’s length in order, a run of c equal lengths n kept as [n, c].

  • edge: how a unit past an Each axis’s end is stored, as the source declares its layout: full, at the full unit length, the part past the end filled (HDF5’s chunks, TIFF’s tiles), or short, cut to the axis (a TIFF last strip).

A grid is in canonical form:

  • an axis is Each(n) when all its units are n long, and, under short, also when all but a shorter last one are, which the axis’s end cuts; otherwise it is a List (under full, units of one length but a shorter last one stay a List: Each would say the last is stored full);

  • under short, n is the declared length clamped to the axis’s length (a TIFF’s RowsPerStrip above ImageLength, often 2^32 − 1, is one strip of the image’s rows); under full, n is the declared length, which may exceed it;

  • a List sums to the axis’s length, and its adjacent equal lengths form one run: [n, c] with c at least 2, or n alone;

  • lengths are at least 1. An axis of length 0 has no units: it is Each of the declared length, or an empty List where the source declares none.

An array whose storage the IR does not model (an HDF5 virtual dataset, a NumPy object array) has no grid, no chains and no chunk map rows: its element, shape, declarations and whatever else its parser knows. The profile reads the declaring structure for the rest, or leaves the array out.

2.4 Sparse grids and the fill value¶

A grid is dense where the source’s layout stores every unit (a NIfTI’s voxels, a FITS image, a FLAC’s frames): the chunk map has a row for each of its units, and it has no fill value. A grid is sparse where the layout may leave a unit out (an HDF5 chunk index, a TIFF entry of no bytes): the map has a row for each unit the source holds, and a unit it leaves out holds the fill value, where the source gives one. Sparse says what the layout allows, not what the file does: a sparse grid whose source holds every unit stays sparse, its fill kept.

A sparse grid’s fill is absent where the source defines none (HDF5’s “undefined”, and a format that has no fill value), or defines one the IR cannot express, whose place is then among the description’s declarations (the general fallback); a profile tells the two apart through the format’s list of declaration places. Otherwise it is one of:

  • format_default: the source says its format’s default (HDF5’s “default”, which the HDF5 specification defines as zero bytes);

  • given: one decoded element’s bytes, ceil(item_bits / 8) of them, as a parameter (§2.2): a value, the bytes as a base64 string (RFC 4648 §4, with padding), or the place that holds them (a range, an extent, or an element’s whole extent). An element of fewer bits than whole bytes takes the first bits of its bytes, packed as the array packs them.

2.5 The JSON form¶

The descriptions cross the bindings as one JSON document, {"chains": [...], "arrays": [...], "undescribed": …}: the chain table, each chain a list of codecs {"name": …, "parameters": {name: parameter}}; the descriptions in the IR’s order; and the mark of a source that kept no descriptions at all at the descriptions’ limit (§6), in a file IR true or false, in a store IR a list of the keys of the objects whose arrays kept none, empty where none is marked. A description has every member of §2, null where it is absent, and path, its element’s path in the IR (null for an element the IR does not hold, which no checked IR has); a description has no fill, which is its grid’s. A place is {"element": e, "member": j, "range": [offset, length]} (member and range may be null) or {"object": key, "offset": o, "length": n} (object null for the parsed source). A grid is {"axes": [...], "edge": "full" | "short", "sparse": …}, each axis {"each": n} or {"list": [...]}, each run of a list n or [n, c], and sparse null for a dense grid, else {"fill": …}, the fill null where the source gives none, else "format_default" or {"given": parameter}. A unit parameter is {"chain": c, "codec": k, "name": …}. The JSON Schema stored-array.json gives the document, and, under $defs, the description (stored_array), which each format’s description schema refers to for its arrays. Integers are written exactly, at any size.

3. Codecs¶

3.1 Chains¶

A chain lists every step the source encodes a unit with, in encoding order. Decoding runs it from last to first, on the unit’s bytes as its element or ranges give them (§4), and ends with the elements’ bytes:

  • as the source stores them, in its byte order, packed as item_bits and pad_from say, with bits most significant first within a byte; or

  • as a codec makes them: a codec that makes the elements rather than restoring them (JPEG’s decoding, GRIB’s unpacking) states in its entry the bytes it makes.

Every codec takes bytes to bytes. An array stored as is has one empty chain.

The IR holds one table of distinct chains, and a description names its chains by their positions in it, each once. A unit’s chain is the description’s first, chains[0], unless its row gives another position in the description’s chains (§4); every chain of an array ends in the same element bytes.

A unit parameter names parameter name of the codec at position codec of the description’s chain chain (a position in its chains), and a description lists each once; each unit of that chain that does not skip the codec gives its value in the chunk map’s column p.<codec name>.<name>. A parameter is given either in its codec or as a column, never both; a codec whose parameter is a column appears once in its chain; and a codec sees a unit’s bytes, its parameters, and the unit’s decoded shape (its grid unit, cut at the array’s end under short and whole under full) with the array’s item_bits and pad_from, never its coordinates, so a parameter that depends on the unit’s position other than through its shape is a column its parser computes. (TIFF’s LZW decodes up to the unit’s size, and its predictor sums along the unit’s rows.)

Streams. A codec whose entry says its units are a stream does not decode a unit apart: a video picture is predicted from pictures decoded before it. Its units decode in the order of the array’s first axis, which is the source’s decode order, each with the state of a decoder that has decoded the units before it. A unit still decodes to its own elements, one picture: a decoder gives its pictures in another order than it takes their units, and keeps which is which. The codec’s unit parameter sync says where a decoder may start with no state: at a unit whose sync is 1. Started there, it makes that unit’s elements, and those of the units after it, as a decoder of the whole stream does, but for a unit after it that the source presents before it (a leading picture of an open group), which may be predicted from units before the sync unit: a decoder started at the sync unit before that one makes it. When a unit is presented is the profile’s, which reads the source’s tables; the IR does not model it.

Configuration the source defines once, apart from the units, is a parameter given as a place, so that the description says where it is rather than copying it. Parameters only an encoder needs (a zlib level, a block size) are not recorded.

3.2 The list¶

A codec’s name is one of this list. Each entry gives:

  • the exact byte format its decoding takes, its framing included: a header, a trailer, a block layout or a checksum the source writes around the encoded bytes (HDF5’s LZ4 filter writes its own block layout, not an LZ4 frame; LZF has no header; zlib is RFC 1950, with its header and Adler-32, not raw deflate). A name never covers two framings, unless a parameter of its entry chooses between them (HDF5’s bitshuffle filter, whose compression parameter frames its blocks with LZ4 or leaves them bare, would be one entry), or the encoding’s own first bytes tell them apart (a JPEG 2000 codestream and a JP2 file that holds one); otherwise an encoding the sources frame two ways is two entries. An encoding HDF5 frames its own way is named with the prefix h5_ (h5_lz4, h5_szip, h5_bitshuffle);

  • its parameters, which of them a unit may give as a column and the column’s Arrow type;

  • what its decoding makes;

  • for a parameter given as a place, how the parameter is made from those bytes.

A chain’s codec has only its entry’s parameters.

4. The chunk map¶

4.2 Rows¶

  • Rows are grouped by array, in order, and within an array are in row-major order of coords; a parser adds them in any order, and the IR sorts them.

  • Exactly one of element and ranges is set in each row. range is set only with element, where the unit is part of it (a FITS tile within its heap element), is at least one byte long, lies within the element’s bytes, and, where the element’s recipe is the identity (§5.2), is not all of them: such a whole element names the element alone, so that a unit has one spelling. With any other recipe the element alone gives the recipe’s bytes, and a range of its whole extent is the one way to name the raw bytes (a TIFF JPEG tile whose recipe splices in its tables). A unit inside a derived space is an element or a range of one, since ranges address only objects. A row’s ranges are at least one, each at least one byte long, and lie within their objects as a place’s do (§2.2).

  • Null is the only way to write the first chain and “skips nothing”.

  • A parameter column is set exactly on the rows whose array lists it in unit_parameters for the row’s chain and that do not skip its codec; null elsewhere.

  • A rank-0 array has at most one row.

5. Checks¶

Both checks run when a parser adds its descriptions and chunk map to its finished IR, and in the check::finish of a store after its grafts and unfolds (a file IR’s own check::finish runs before its descriptions are built, so has none to check). A description or a row they refuse is a bug in its parser: an internal error naming the array’s element.

They also check the undescribed mark (§6): a file IR lists no keys, and one marked true has no descriptions, chains or rows; a store IR is not marked true itself, and its list names its objects, once each, none of which holds a description’s key or a row’s element (another object’s rows may read its bytes).

5.1 Each description¶

  • Its element and places. Its element, and every element its places, its fill’s and its chains’ parameters name, is an element of the IR; its own element is in no run’s subtree (an unfold would leave the key behind); a place’s member is set exactly when its element is in a run’s subtree, and is below the run’s count; an object key is any key or none in a file IR (an external file’s key is checked in the store’s IR, once the file is grafted), and in a store IR is never none and names one of the store’s objects; a place lies within what it names (§2.2), its end below 2^64.

  • No extent. A description without a shape has no grid, no axes and no pad_from.

  • The grid. Its rank is the array’s rank, and it is in canonical form (§2.3).

  • Chains. At least one when grid is set, none when it is not; each a position in the chain table, and none twice. The chain table holds no chain twice, and every codec of it is one of the list (§3.2), with only its entry’s parameters.

  • axes. When given, a permutation of the rank other than the identity.

  • item_bits, pad_from and the fill. item_bits is set when its grid’s fill is given, and when grid is, unless every chain of the array begins with source; it is at least 1. pad_from is below the rank, given only when item_bits is set and is not a multiple of 8. A given fill value is ceil(item_bits / 8) bytes: a base64 string of that many, or a place of that length (a range’s or an extent’s length, else its element’s).

  • unit_parameters. None is listed twice. Each names a chain of the description, a codec of that chain that appears once there, a parameter the codec’s entry allows as a column, and no parameter the codec gives itself.

  • Keys. (element, index) is unique among the IR’s descriptions, and on each element index is either absent from every description or set on every one, as 0 to n − 1.

5.2 The chunk map¶

  • its columns match the schema: each of the IR’s length, the list offsets their values’, and each parameter column one whose name is p.<codec name>.<name> of an entry of the list and a parameter the entry allows as a column, of the entry’s type;

  • rows are only for arrays the IR describes that have a grid;

  • coordinates are of the array’s rank, inside its grid, grouped and ordered as §4.2 says, with no repeats;

  • an array whose grid is dense has a row for each of its units (§2.4);

  • exactly one of element and ranges is set in each row, and a row’s ranges are at least one, each at least one byte long;

  • member is set exactly when element is set and is in a run’s subtree, and is below the run’s count;

  • range is set only with element, at least one byte long, its end within the element’s bytes and below 2^64, and not the element’s whole extent where the element’s recipe is the identity: the element has no form, or its form no recipe ("recipe": null is none), or a recipe, by the grammar of conventions §8.5, of only ["src", o, n] parts (n null or left out: to the element’s end) and ["rows", o, s, n, c] parts that, read as ranges of the element’s extent, cover all of it in order with no gap or overlap ([["src", 0]], [["src", 0, null]], src parts end to end, rows runs of n bytes each n apart, or a single run of any stride, that make up its length). A part of no bytes covers none, and is skipped before its offset and stride are looked at; a part with fields the grammar does not give it, or a src part of null length whose offset is past the element’s end, is not the identity;

  • the first chain and no skips are written as null;

  • chain is a position in the array’s chains, and skips names only codecs of the unit’s chain;

  • each parameter column is set exactly on the rows whose array lists it for the row’s chain and that do not skip its codec;

  • every element is an element of the IR;

  • every range is checked as a place’s is (§5.1): its key, and its bounds.

6. In the IR¶

Built at finish. A parser keeps what it learns about its arrays to itself while it reads. When its IR is finished (after its last fold and rollback, and after check::finish), it builds a description for each array it reaches and the chunk map’s rows from the finished IR, and adds them to the IR, which, in order: sorts the descriptions by (element, index), so that which arrays fall back follows from the source alone; fits the map to its limit (below); drops from the chain table the chains no description names, keeping the others’ order, and renumbers the descriptions’ positions in it; fits the descriptions to their limit (below), which falls back the same way and drops the chains it leaves unnamed; sorts the rows; and checks them (§5). They are not in the facts a projection reads, which keep their arrays until each format’s projection reads the descriptions. NumPy’s does: its parser returns no facts of an array but its header’s text and its description’s key, and its projection takes the array’s shape, order and data from the description and the chunk map.

Only two things change ids afterwards.

  • A graft carries a file IR’s descriptions and rows into the store it joins, in order:

    • it fits the file’s arrays, in the file’s order, to the store’s chunk map limit as it stands then (below), which counts every object the store has listed, grafted or not; a graft does not grow it. A store has the 2^22 once, where each file had it, so an array that kept its rows in its file may fall back in the store, depending on what was grafted before it;

    • it carries into the store’s chain table only the chains the file’s remaining descriptions name, each with its places’ element ids renumbered and then found in the table by its value: a chain the table has keeps its position, and a new one is appended, in the order the file’s descriptions first name them. The table’s existing chains and positions are untouched. Two chains of one array that the renumbering makes equal become one, which the array’s rows and unit parameters then name; the two give the same unit parameters, or the graft fails;

    • it fits the file’s descriptions, last, to what remains of the store’s descriptions’ limit, as describe does (below): where even their fallen-back descriptions do not fit, the file joins the store with none, its key added to the store’s undescribed list, as is the key of a file marked undescribed at its own describe. A graft that fails on the IR’s room adds nothing to the store.

    element, every place’s element and the element column take their new ids; array takes the description’s new position, after the store’s; parameter columns of one name join; and the parsed source’s null key, in every place and in ranges, becomes the file’s key in the store.

  • An unfold of a run (a store’s own check::finish may unfold one) gives its members after the first new ids: each row’s and place’s element in member j’s subtree moves to member j’s copy, and member is cleared on every element that was in the run.

The mirror’s canonical form (conventions §8.8) leaves the descriptions and the chunk map out before it unfolds the runs, so its unfolds renumber none.

Limits. The IR’s budget counts the descriptions’ entries and the chunk map’s in fields of its own, each against a limit of its own, never against the IR’s room (its records and elements). The descriptions’ entries are each description, each axis of its shape, each run of a listed axis (an Each axis has none), each of its places (its declarations, and its grid’s fill given at a place), each of its chains and each unit parameter; and of the chain table, each chain, each codec and each place a codec’s parameter names. The chunk map’s are each row, each of its coordinates, each of its ranges items and each unit-parameter value it sets (a row’s range is part of it, and is none). The descriptions’ limit is 2^22 + floor(Z / 4) entries for a source of Z bytes, and the chunk map’s 2^22 + 4 × Z. A store’s are 2^22 + floor(Z / 4) + 4 × o and 2^22 + 4 × Z + 4 × o, for its o objects of Z bytes in all: a file’s of Z bytes, and 4 more for each object, as the limit of its table’s rows is (conventions §8.9). The floor is of the total, not of each object’s size. A store’s limits grow as it lists its objects, and not when a file is grafted. Every unit in space 0 has at least one byte of its own (an HDF5 chunk of an implicit index may be a single byte), or an index entry of several, so where no two units share bytes or index entries, a map fits where each row’s rank, plus the unit-parameter values it sets, is at most 3 for a unit held by an element of space 0 (with or without a range), or at most 2 for a unit in ranges into the parsed source. Nothing else has that guarantee: a unit in a derived space can cost far less than a byte of the source; a unit in ranges into another object (an HDF5 external file) costs entries only the parsed source’s size pays for, so its array can fall back at any rank; and a source whose structures share bytes or index entries (two HDF5 object headers on one chunk index, TIFF IFDs sharing a StripOffsets array) can pass the limit.

The chunk map’s limit never rejects a run, and never cuts an array’s rows short, which a profile would read as units the source does not hold. Arrays are tried in the order of the IR’s descriptions: a file IR’s, and a store parser’s own, are in (element, index) order, which describe sorts them into; in a store, each graft’s arrays keep their relative order and follow those already there, so a store’s arrays are in graft order (not in key order: a description keyed by a file’s root is keyed, in the store, by the file’s object element, whose id can be below the earlier grafts’ ids). One whose rows do not fit in what remains of the limit keeps none of them, and falls back: its description has no grid, no chains and no unit parameters, and the map neither a row of it, nor a parameter column only its description listed, nor an object key only its rows named. Later arrays are still tried, and the run goes on. In a file IR, which arrays fall back follows from the source alone; in a store, from its files in graft order.

The descriptions’ limit never rejects a run either. Where the descriptions and the chain table pass what remains of it, two passes follow the map’s fit. First every array is charged its fallen-back description’s cost; where that total passes the limit, the source keeps no descriptions, chains or rows at all and is marked undescribed (§2.5), which a profile reads as a source to take as its bytes, never as one with no arrays. Otherwise, in the same order, each array keeps its full description (its grid, chains and unit parameters, and the chains it is the first kept description to name) while what remains allows, and falls back as at the map’s limit otherwise; an array that fell back at the map’s limit stays fallen back. A fallen-back array’s rows and the columns and chains only it named are dropped, so a later array that names a chain it shared pays for that chain. A store parser that describes its own objects’ arrays itself, not by graft, keys each of them in one of its objects, and where it keeps none lists the key of every object whose arrays it described.

As the map is built, a row holds about 93 bytes of memory, a coordinate 8 and a ranges item 24; the worst case, rank-1 rows of elements over a shared index at four entries per byte, is about 200 bytes per byte of the source. A parameter column holds about 16 bytes a row, null or not, for every row of the map; the list allows few columns (a video codec’s sync). Descriptions a check refuses, and those a fallback drops, spend none of either limit.

Bindings. Python’s refkv._core.Ir gives the descriptions as the JSON document of §2.5 (stored_arrays(), read by refkv.ir.stored) and the chunk map as an object of the Arrow PyCapsule interface (chunk_map()); pyarrow, polars or nanoarrow read it without a copy, and refkv itself depends on none of them. The WebAssembly module carries neither, and compiles no Arrow code.

CZI: stored arrays¶

What the CZI parser describes as stored arrays (stored-array.md), part of the CZI profile.

Every subblock the parser reads is a stored array, whether or not the profile places it: the ZISRAWSUBBLOCK segment an entry of the subblock directory names, or, in a part with no directory, one that the part’s walk finds (czi.md §7.9). A subblock is the one structure of a CZI file that declares an array: a rectangle of pixels of its own stored size, pixel type and compression. The file declares no array above it. A scene, a mosaic and a pyramid level are regions of one pixel frame, in which each subblock’s entry gives its place (the Start and Size of its dimension entries), and there subblocks overlap, leave gaps, and differ in scale and in encoding: the source cuts nothing into a grid of them. Assembling subblocks into images and levels is the profile’s (czi.md §3), which reads each subblock’s place from its declarations. An array is keyed by its segment’s struct (subblocks/<i>), with no index; a segment that several entries name is one array, keyed by the struct of the first of them, of which the others are aliases (czi.md §5.3). The facts give the keys: declared_by lists, for each entry in order, the id of its subblock’s struct, null for an entry of a subblock in another file, which that file’s entries list again; and each level’s and each tile array’s declared_by lists the ids of its subblocks’ structs in the order of its cells or its members. Each file of an image across files describes its subblocks in its own IR, and the CZI store, which grafts them, renumbers the ids its facts give (stored-array.md §2.1).

  • Declarations. The subblock’s own copy of its entry: subblocks/<i>/entry, its 32 bytes, which hold the PixelType and the Compression, then subblocks/<i>/dimensions, its dimension entries, which hold the stored size and the subblock’s place among the others, where the copy has any. The directory’s entry of the subblock, where the file’s directory has one (directory/entries/<j> and directory/dimensions/<j>, j a position of the key in declared_by), holds the same bytes wherever the array has a shape, but for the FilePart of an entry of or in a part.

  • shape is the stored height (the StoredSize of the Y dimension entry), then the stored width (that of X), then the samples of a pixel type of several: 3 for Bgr24, Bgr48, Bgr96Float and Bgr192ComplexFloat, and 4 for Bgra32. Such a pixel type has the axis in every encoding, whether the encoding stores a pixel’s samples together or a codec makes them. axes is absent: an entry names its dimensions by letter, and lists them in no order. The entry’s other dimensions (C, Z, T, S, M and the rest) are no axes of the array: they say where the subblock lies.

  • item_bits is the bits of one sample of the PixelType: 8, 16, 32 or 64.

  • The grid is one unit, the whole subblock: each axis Each of its length, under short. Its row is the subblock’s data, the data element: of uncompressed data its first bytes, as many as the array’s (bytes after them are no part of the unit), and of any other all of it. The data of a Zstd1 subblock is two elements, its header and its frame, so its row is ranges of the file, all the data’s bytes; so is the row of a subblock whose data element the finished IR made an alias, its bytes lying in an earlier element’s, and a declaration that became one is the range of the file likewise.

  • The chain is one, by the Compression: empty for 0; tiff_lzw for 2; jpegxr for 4; zstd for 5; czi_zstd1 for 6; and jpeg for 1 (JpgFile) and 3 (lossless JPEG), whose streams’ precisions, which the grid’s conditions bound, are at most the samples’ bits.

  • A grid only where the data is what the entry says, as far as the parser reads without decoding it (czi.md §7.4): uncompressed data of at least the array’s bytes; a Zstandard frame (after a Zstd1 header of either form) that names no dictionary and declares, where it declares one, a content size of the array’s bytes, with hi-lo packing only on samples of 16 bits; an LZW stream that starts with the Clear code; a JPEG XR file whose container gives a pixel format the PixelType admits; and a JPEG stream whose frame header has the pixel type’s samples as its components and a precision that its samples hold: for a lossless stream (SOF3), 2 to 8 with samples of 8 bits and 9 to 16 with samples of 16, and for a DCT stream (SOF0 to SOF2), under JpgFile alone, 8 with samples of 8 bits and 12 with samples of 16. These are the profile’s conditions for a coded size (czi.md §3.2), but for two, which the profile leaves unplaced for reasons of its own, and whose row is the data value that keeps their bytes (ranges of the file, for Zstd1). A lossless stream of three components under JpgFile is described, in a jpeg chain, which makes the components in the frame’s order: the profile does not place it because nothing says which component is which, a question the description does not ask. And a Zstandard frame that declares no content size is described: the profile does not place it because only decoding it says how many bytes it holds, and, as of any stream the parser does not decode, one that holds other than the array’s bytes is not detected. Any other subblock has its shape and item_bits and no grid: the IR cannot say what its bytes are. (czifile 2026.8.16 reads some of them, as other arrays than the entry declares: data or a frame of fewer bytes as an array of fewer rows, an 8-bit JPEG or JPEG XR stream under Gray16 as 8-bit samples, and a Zstd1 frame of 8-bit samples whose header says hi-lo packing as the frame’s content.)

  • A stream of another size. A JPEG or JPEG XR stream may be of another size than its entry’s stored size, as some writers leave a pyramid’s edge (czi.md §3.2): the description gives the entry’s, and the stream decodes to its own, which is what czifile reads.

  • No shape either, nor item_bits, for a subblock whose copy of its entry does not agree with the entry that names it (czi.md §2.4): the file declares it twice, differently, and a reader follows one or the other (czifile follows the directory’s entry where it comes to the subblock from the directory, and the subblock’s own where it walks the segments).

  • Not described: a ZISRAWSUBBLOCK segment that no entry names in a file with a directory, of which the parser reads the segment header alone; a subblock’s attachment (a valid-pixel mask); and the attachments that hold images (a JPG thumbnail, an embedded CZI label or preview), which the parser keeps as bytes and reads nothing of.

  • The grid is dense: CZI has no fill value.

DICOM: stored arrays¶

What the DICOM parser describes as stored arrays (stored-array.md), part of the DICOM profile.

A DICOM file’s stored arrays are its Pixel Data (7FE0,0010), each lookup table of a PALETTE COLOR image, and each Pixel Data in an item of a sequence the parser walks (an icon image’s), whether or not the profile presents them. The facts give the keys: declared_by is the id of the top-level Pixel Data’s element; palette.declared_by lists the ids of the red, green and blue tables’ elements, where the tables are arrays; and nested lists each element that keys the Pixel Data of its items, by its id (declared_by), with how many it keys (count). A series’ store form is composed of its files’ outputs, and has no descriptions of its own. Below, an attribute is the first element of its tag in the Pixel Data’s own dataset, absent where its value is empty (and, of an item’s, where its VR in explicit VR is not the one dicom.md §2.2 gives it, or the IR does not hold its value); N is Number of Frames (0028,0008), 1 without the attribute, and S is Samples per Pixel (0028,0002).

  • The top-level Pixel Data is keyed by its element (dataset/7FE00010), with no index.

  • Declarations. The element of the Transfer Syntax UID (meta/00020010), which gives the byte order of native samples and names the frames’ encoding; then each of these elements of the dataset that has a value, a data element whole (its header, with its VR in explicit VR, and its value): Photometric Interpretation (0028,0004), Bits Allocated (0028,0100), Bits Stored (0028,0101), High Bit (0028,0102), Pixel Representation (0028,0103), Pixel Padding Value (0028,0120), Pixel Padding Range Limit (0028,0121), and the palette’s descriptors (0028,1101)–(0028,1103), tables (0028,1201)–(0028,1203) and segmented tables (0028,1221)–(0028,1223).

  • shape is N, where the dataset has a Number of Frames (an axis of 1 for a value of 1, and no axis without the attribute); then Rows (0028,0010) and Columns (0028,0011); and, for S above 1, S: after Columns where a pixel’s samples are stored together, and before Rows where each sample is a plane (native data of Planar Configuration (0028,0006) 1, and RLE data, whose codec makes planes). A whole-slide image’s frames are its tiles, and the array is the frames: placing them in the total pixel matrix is the profile’s. axes is absent: DICOM names its dimensions by tag, and lists them in no order.

  • item_bits is Bits Allocated.

  • The grid is a frame a unit: Each(1) on the frames’ axis and Each of its length on every other, under short. Native frames of Bits Allocated 1 follow each other with no padding (dicom.md §7.5): where N is above 1 and Rows × Columns is no multiple of 8 they are one unit together, Each(N) on the frames’ axis.

  • Rows. A native frame is the frames/<f> element: a member of the run the frames fold into (frames/0, with member f), or frames/0 alone where the file holds one unit. The bytes of the value past the frames are no unit’s. An encapsulated frame is the data of those of its fragments (dicom.md §7.5) that are not empty: the fragments/<j> element where one fragment holds it (with an Extended Offset Table, frame f’s is fragments/<f>), and ranges of the source, a fragment’s data each, in order, where several do.

  • The chain is one, by the transfer syntax (dicom.md §2.1): empty for native data, or lsb_first with bits 1 for Bits Allocated 1, in every byte order; jpeg, with no tables, for JPEG Baseline (1.2.840.10008.1.2.4.50), of Bits Allocated 8, and for lossless JPEG (.4.57 and .4.70), whose Bits Allocated the parser takes as 8 or 16, every frame’s precision, which it reads, at most that; jpegls for JPEG-LS (.4.80 and .4.81); jpeg2k for JPEG 2000 (.4.90 and .4.91); dicom_rle for RLE Lossless (1.2.840.10008.1.2.5); and source, with format dicom and id the Transfer Syntax UID, for HTJ2K (.4.201 to .4.203), which the list has no entry for. The description follows the attributes: a stream’s own frame header is compared with them only where the profile does (dicom.md §7.5), and a stream decodes to its own. A JPEG stream of three samples is described as the file holds it, without the marker the profile writes before it.

  • No grid for JPEG 2000 frames of Photometric Interpretation YBR_FULL_422, which the parser accepts only with chroma components of half the width: a frame’s samples are then not an array of the image’s shape, and what a decoder makes of them is not the stream’s samples (OpenJPEG upsamples the chroma and converts to RGB). The parser refuses what the profile does not read (another transfer syntax, Float Pixel Data, a sparse tiling), and builds no IR of it.

  • A lookup table of a PALETTE COLOR image whose tables the profile reads (dicom.md §4.1: none segmented) is keyed by its own element (dataset/00281201, dataset/00281202, dataset/00281203), with no index. Its declarations are the Transfer Syntax UID’s element and its descriptor’s (dataset/00281101 to dataset/00281103); shape is its entries, the descriptor’s first value (65536 for 0); item_bits is 16 where the table’s value holds two bytes an entry, else 8; and it is one unit in an empty chain, Each of its entries under short: the range of the table’s element that holds the entries, after its header, the bytes of the value past them left out. Entries of one byte in a table of VR OW under Explicit VR Big Endian, whose 16-bit words that syntax swaps, have no grid. The tables beside a segmented one are not arrays: they are among the Pixel Data’s declarations.

  • A Pixel Data in an item is keyed by the element of the top-level dataset its items lie in (the sequence dataset/<tag>, whatever the depth of the item), a kind of element that may declare several arrays: its index is its position among the Pixel Data of that element’s items, in the order of the file, each member of a run of items counted. Its declarations, shape and item_bits are as the top-level one’s, read of its own item’s attributes, the declaring elements with member where the items are a run; shape is absent where Rows, Columns or S is absent or 0, where S is above 1 and Planar Configuration is neither 0 nor 1, and where Number of Frames is not an integer of at least 1, and item_bits where Bits Allocated is absent or 0. A value of defined length is native, whatever the transfer syntax (PS3.5 A.4), and has the grid and the chain of native frames, each unit a range of the Pixel Data’s element, after its header (with member in a run), where the profile’s rules for the top-level one hold of it (dicom.md §3): Bits Allocated 8, 16 or 32, or 1 with S 1; S 1, or 3 with a Photometric Interpretation of RGB or YBR_FULL; and a value that holds the frames. It has no grid otherwise, nor where its item’s byte order is not the transfer syntax’s, nor, under Explicit VR Big Endian, for Bits Allocated 1 or 8, whose bytes a VR of OW swaps. A value of undefined length, a fragment sequence the parser does not read as frames, has no grid.

  • The grid is dense: DICOM has no fill value, and Pixel Padding Value is a declaration.

ENVI: stored arrays¶

What the ENVI parser describes as stored arrays (stored-array.md), part of the ENVI profile.

An ENVI raster is one stored array, the one its header declares, in the store IR the profile’s run builds of the header file and the data file beside it. It is keyed by the header file’s object (the header has no element of its own), with no index. The facts give the key: array.declared_by is the id of that object.

  • Declarations. The line of the data type field, then the lines of the byte order and interleave fields where the header has them: each the element lines/<i> of the line where the field starts, which holds its name, its value and its line end.

  • shape is the data’s, outermost first, as the interleave orders bands, lines and samples (envi.md §4.1). axes gives each storage axis’s place in the list samples, lines, bands: [2, 1, 0] for bsq, [1, 2, 0] for bil, [1, 0, 2] for bip.

  • item_bits is eight times the bytes of one element of the data type field’s type (envi.md §3); a complex element is its two parts.

  • The grid is one unit of the whole array: each axis Each of its size, under short. Its row is the data element of the data file, another object of the store: for a raw file, the array’s bytes after the header offset’s; for a gzip file, the whole file.

  • The chain is one: empty for a raw file; gzip for a gzip file; and skip, then gzip, for a gzip file with a header offset above 0, which GDAL counts within the inflated bytes. skip’s length is the value of the header offset field, a range of the field’s line. The byte order is a declaration, not a codec.

  • The stream is not inflated, as the profile reads none of the data: one that inflates to other than the header offset’s bytes and the array’s is not detected.

  • No grid for no input: the profile rejects what it does not read (other file types, framed data, a raw data file of another size), and builds no IR of it.

  • The grid is dense: ENVI has no fill value. The header’s data ignore value marks pixels to ignore, and is recorded, not made a fill value.

FITS: stored arrays¶

What the FITS parser describes as stored arrays (stored-array.md), part of the FITS profile.

Every HDU with an axis (NAXIS above 0) has descriptions, whether or not the profile presents them, keyed by its header element (hdus/<i>/header), a kind of element that may declare several arrays: each of an HDU’s has an index. An image (the primary HDU, or an IMAGE extension) has one array, index 0; a table (TABLE or BINTABLE) two, its rows (0) and its heap (1); a tile-compressed image (a BINTABLE with ZIMAGE = T) three, its image (0) and its table’s rows (1) and heap (2). The parser’s description gives the key: each HDU’s elements has its header’s id, which keys its arrays unless it is of no axes, and so holds none (fits.md §9.6). In a compressed file (fits.md §2.1) the headers and the units’ elements are in the stream element’s space: a unit’s bytes are the decoded file’s.

  • Declarations. The header’s element: its cards give the array’s axes and what its elements are (BITPIX, BSCALE, BZERO and BLANK; a table’s TFORMn; a tile-compressed image’s Z cards). A tile-compressed image whose table has a ZSCALE, ZZERO or ZBLANK column, which gives each tile’s scale, zero or blank value, has a second, the table’s rows (the table element), each tile’s values in its row, at the places the header’s TFORMn give the columns. A parameter given as a place of a card is the card’s 80 bytes, a range of the header’s element, and is the card’s value (FITS Standard 4.0 section 4.2), an integer or a string.

  • An image. shape is NAXISn to NAXIS1, the slowest first, and for two or more axes axes is their reverse, since the header lists NAXIS1 first. item_bits is |BITPIX|. It is one unit in an empty chain: each axis Each of its length, or an empty List for an axis of length 0, under short. Its row is the HDU’s data element, or, where the HDU’s data is longer than the image (an IMAGE extension whose PCOUNT is not 0, or whose GCOUNT is not 1), the range of that element that holds the image, its first bytes, as astropy reads it; an image of no elements has no row. The elements are as stored, big-endian: BSCALE and BZERO are the profile’s.

  • A table’s rows are an array of shape [NAXIS2], a row an element: item_bits is 8 × NAXIS1. It is one unit, the rows element, in an empty chain, gridded as an image, with no row where the rows have no bytes. What a row’s bytes are (its columns’ fields, an ASCII table’s text) is the profile’s, from the header’s TFORMn and TBCOLn. Rows of no bytes (NAXIS1 of 0) have no item_bits and no grid; nor have a binary table’s rows where its TFORMn are not all forms the profile reads (fits.md §4.1) or their fields’ bytes are not NAXIS1 in all, since readers do not agree on where such a row is: the standard’s rows are NAXIS1 bytes each, as the profile cuts them, and astropy’s the fields’ bytes, one row after another. An ASCII table’s row is NAXIS1 characters, which its fields need not fill.

  • A table’s heap is the H bytes from THEAP to the end of the data (fits.md §4.3), of shape [H] and item_bits 8: one unit, the heap element, in an empty chain. An empty heap is described too, with no row; an ASCII table’s is empty unless its PCOUNT is not 0. Which of its bytes a row’s descriptor names is the profile’s.

  • A tile-compressed image’s image has shape ZNAXISn to ZNAXIS1, axes as an image’s, and item_bits |ZBITPIX|, or, where it is quantized (below), 32. Its grid is its tiles: Each of ZTILEn to ZTILE1 (with the defaults of fits.md §3.3), under short, an edge tile cut to the image. Each row of its table that holds a tile is a row of the chunk map, at the tile’s coordinates (the table’s rows are the tiles in storage order, ZNAXIS1’s fastest): the tile’s bytes in the heap, a range of the element of its chunk of the heap (hdus/<i>/heap/<j>, fits.md §6.1), or that element alone where the tile is all of it. A table row with both descriptors empty holds no tile, and has no row.

    • The first chain is that of a tile in COMPRESSED_DATA, by ZCMPTYPE: fits_rice for RICE_1 and RICE_ONE, its block_size and byte_pix the places of the ZVALi cards of the parameters BLOCKSIZE and BYTEPIX (fits.md §3.3), each absent where the header has no such card; gzip for GZIP_1; shuffle, then gzip, for GZIP_2, the shuffle’s element_size a value, the bytes of an element (4 under quantization), for which the header has no card; and no codec for NOCOMPRESS.

    • Quantization. A float image (ZBITPIX below 0) whose table has the columns ZSCALE and ZZERO is quantized (FITS Standard 4.0 section 10.2): its elements are the integers its tiles store, each 4 bytes, big-endian, two’s complement, which the codecs above code, and its description stops at them. The profile makes the image’s floats of them with what the declarations give: the dither’s name, the ZQUANTIZ card’s value (NO_DITHER, SUBTRACTIVE_DITHER_1 or SUBTRACTIVE_DITHER_2; without the card, NO_DITHER); the tile’s scale and zero, its row’s ZSCALE and ZZERO; and the integer of a pixel of no value, its row’s ZBLANK where the table has that column, else the header’s ZBLANK card, else its BLANK card, as astropy reads it, else none. An integer I is then NaN where it is that blank; else 0 where it is −2147483646 under SUBTRACTIVE_DITHER_2; else I × scale + zero without a dither, and (I − R + 0.5) × scale + zero under one, computed in binary64, each operation rounded, in that order, then rounded to |ZBITPIX| bits. R is the dither’s next random number, of the 10,000 cfitsio’s fits_init_randoms makes (from s = 1, s ← 16807 × s mod (2^31 − 1) each time, the number s / (2^31 − 1) as a binary32). The source stores no seed of a tile’s dither: it is computed, the tile’s index in the table (from 0, the tiles in storage order) plus ZDITHER0. A tile starts at the number at floor(500 × N), N the number at (seed − 1) mod 10000, and takes one for each pixel, whatever its integer; after the last number it takes up the N after its own (after the last, the first) and goes on from floor(500 × N).

    • The second chain. A tile in GZIP_COMPRESSED_DATA is a gzip stream of its elements as an image stores them, never quantized. Where the table has that column, the image is not quantized and the first chain is not gzip alone, the description has a second chain, gzip, which those tiles’ rows name; where the first chain is gzip alone, they are in it. A quantized image has no second chain: such a tile holds its floats, not the integers of its other tiles (below).

    • source. A RICE_1 image whose BYTEPIX (4 where absent) is not the bytes of an element (not 4, where quantized), or whose elements are floats that are not quantized, has the one codec source as its first chain, with format fits and id the ZCMPTYPE card’s string: fits_rice makes integers of BYTEPIX bytes, which are then not the image’s elements. astropy converts their values to the image’s type; the profile’s codec does not.

    • A tile’s width. A GZIP_1, GZIP_2 or NOCOMPRESS tile, and one in GZIP_COMPRESSED_DATA, is described as holding its elements at their own size (4-byte integers under quantization), as the profile reads it. astropy takes the size of a tile’s values from its decoded length, and converts those of a tile stored at another size: the parser reads no tile, so no description tells such a tile from the others.

    • No grid for an image that readers do not agree on, which keeps its shape, item_bits and declarations: an integer image whose table has the columns ZSCALE and ZZERO (astropy scales its values where there is no dither and refuses it where there is one; the profile reads them as stored); a float image without those columns whose header has a ZSCALE or a ZZERO card (cfitsio takes the cards as every tile’s and dequantizes; astropy and the profile read the values as stored) or a ZBLANK or a BLANK card (astropy makes a stored value equal to it NaN; the profile reads it as stored); an image that is not quantized whose table has a ZBLANK column; a quantized image with neither that column nor a ZBLANK card whose BLANK card is no integer; a quantized image of which a tile is in GZIP_COMPRESSED_DATA, whose units would hold two kinds of elements, its floats and its integers; and an image whose table’s rows are not its columns’ fields (as a table’s, above), whose descriptors are then not where the parser read them.

    • Its table’s rows and heap are described as a binary table’s: the rows one unit, the table element; the heap one unit, the range of the HDU’s element (hdus/<i>) that holds it, since its bytes are in the elements of its tiles’ chunks.

  • The grid is dense, but a tile-compressed image’s, which is sparse, a table row whose descriptors are both empty leaving its tile out: FITS has no fill value. BLANK, the stored value of a pixel with none, is a declaration.

FLAC: stored arrays¶

What the FLAC parser describes as stored arrays (stored-array.md), part of the FLAC profile.

A FLAC file’s samples are one stored array, keyed by its STREAMINFO block, the value metadata/0/streaminfo, with no index. The facts give the key: info_value is that element’s id.

  • Declarations. One: the STREAMINFO block, whose fields give the sample rate, the channels, the bit depth, the samples in all and the MD5 of the decoded samples.

  • shape is the samples, then the channels: the frames’ samples in all, which the parser checks are STREAMINFO’s total where it records one, 0 meaning unknown (flac.md §8.1), and STREAMINFO’s channels. A sample’s channels are together, last, as the codec makes them.

  • item_bits is the bit depth rounded up to whole bytes: 8, 16, 24 or 32. These are the bytes STREAMINFO’s MD5 is of (RFC 9639 §8.2): each sample little-endian, sign-extended.

  • The grid is the frames: Each of the first frame’s block size, then Each of the channels, under short. The profile accepts a stream of one block size, whose last frame alone may hold fewer samples. Each frame is a row, the element frames/<j>, whole.

  • The chain is one, flac, its setup the STREAMINFO block. A frame decodes alone: FLAC has no state from frame to frame, so the codec is not a stream (stored-array.md §3.1).

  • The grid is dense: FLAC has no fill value.

GRIB: stored arrays¶

What the GRIB parser describes as stored arrays (stored-array.md), part of the GRIB profile.

Every message of a GRIB edition 2 file has descriptions, whether or not the profile presents its fields, keyed by its element (messages/<i>), a kind of element that may declare several arrays: each bitmap one of its sections 6 holds (indicator 0) and each of its fields (a section 7, with the sections 3, 5 and 6 in effect at it) is an array, indexed in the order of their sections, a bitmap before its field. The file’s store parser describes them itself (stored-array.md §6). A field’s array is the values its section 7 codes, in the file’s order: how fields stack into a variable, where on its grid a bitmap puts a field’s values, and which way a grid’s rows run are the profile’s. The facts give the keys: each entry of fields has declared_by, the id of its message’s element, array, the index of its values’ array, and mask, the index of the bitmap that says which points its values are (its own, or, under indicator 254, the message’s last one before it), or null. Below, an octet is numbered from 1 in its section, a section is the element messages/<i>/sections/<j>, and n is section 5’s number of values (octets 6–9).

  • Declarations. A field’s: its section 3 (the grid’s number of points, its template, Ni, Nj and the scanning mode); its section 5 (n, the data representation template and its octets: the reference value R at octets 12–15, the binary scale factor E at 16–17 and the decimal scale factor D at 18–19, the type of the original values, complex packing’s missing value management at octet 23 and its substitutes for missing values at 24–31); the first 6 octets of its section 6, which end with the bitmap indicator (the section’s element, or the header element of a section that holds more); and, where a bitmap says which points its values are, that bitmap’s bits (the bitmap element of its section 6). A bitmap’s: the section 3 in effect, and the first 6 octets of its section 6, likewise.

  • A bitmap is a bit for each point of the grid, in the file’s order, 1 where the point has a value: shape is section 3’s number of points (octets 7–10), one axis, and item_bits is 1. It is one unit in an empty chain, Each of the points (an empty List for none) under short, and its row is the section’s bitmap element, the octets after the first 6, or the range of its first octets that hold the points’ bits where it holds more. A bitmap whose section holds fewer bits than the grid has points has no grid.

  • A field’s shape. Where every point has a value (indicator 255, and n the grid’s number of points) and the grid is one whose rows the parser reads (template 3.0, 3.1, 3.10, 3.20, 3.30 or 3.40, defined by its template, with no list of the points of each row, and Ni × Nj its number of points), shape is Nj, then Ni, with axes [1, 0], since section 3 gives Ni first; or, where the scanning mode’s bit 3 (0x20) says that consecutive points run along a column, Ni, then Nj, with no axes. Rows that alternate in direction (bit 4, 0x10) are as the file stores them. Every other field is one axis of its n coded values, in order: one on a reduced grid, on a 3.101 grid or on a grid the parser does not read; one whose n is not the grid’s number of points; and one with a bitmap, of any indicator. A field with a bitmap is the values of the points the bitmap keeps, and no value is made for a point it leaves out: the bitmap’s own array, or for a predefined bitmap (indicator 1–253) the indicator, says which they are.

  • Units. A field is one unit: each axis Each of its length, or an empty List for an axis of length 0, under short. Its row is its section 7’s element with the range of the octets that hold its values, which start after the section’s first 5; a field of no values, and one whose values no octet codes, has no row.

  • IEEE floats (template 5.4, of the precision 1 or 2 at octet 12) are stored as they are: item_bits is 32 or 64, the elements big-endian, the chain empty, and the row’s range the n values’ octets.

  • A constant field codes no value: simple packing, JPEG 2000, PNG or CCSDS packing (5.0, 5.40, 5.41, 5.42) of a bit width of 0 (octet 20), and complex packing (5.2, 5.3) of no groups (octets 32–35). Every value is the reference value R, an IEEE binary32, big-endian: item_bits is 32, the chain is empty, and the grid is sparse, with no row, its fill given: the place of R (section 5’s octets 12–15). ecCodes and NCEP’s g2c read R itself whatever the decimal scale factor D is, as their encoders write it, where FM 92’s regulation 92.9.4 would give R × 10^−D.

  • A field in simple packing (5.0) is its integers as section 7 stores them: item_bits is the bit width (octet 20), whatever it is, the chain empty, and the row’s range the octets that hold n integers.

  • A packed field is the integers its packing codes, in the codec of the integers, each parameter a range of section 5 (stored-array.md §3.2): grib_complex for 5.2 and for 5.3, with differencing (missing value management 0; widths of at most 64 bits; an order of 1 or 2, and descriptors of at most 8 octets), item_bits 64; jpeg2k for 5.40, whose codestream’s samples, in the image’s order whatever its rows, are the unit’s integers, item_bits the bit width in the whole octets that hold it (8 × ⌈bits / 8⌉); grib_png for 5.41 and grib_ccsds for 5.42 (unsigned samples of at most 32 bits), item_bits the bit width. The row’s range is all of section 7 after its first 5 octets. The parser reads no octet of section 7 after them, so a stream that is not its codec’s, or holds other than n integers, or a PNG image of other pixels than the bit width’s, is not detected.

  • Values. The description stops at the integers X, which the profile makes the field’s values of with R, E and D, its declarations: FM 92’s regulation 92.9.4 gives (X × 2^E + R) × 10^−D. ecCodes computes it in binary64, X and R converted first, each operation rounded, in that order, with 2^E 1 multiplied by 2 as many times as E’s magnitude (divided, for a negative E), and 10^−D 1 divided by 10 as many times as D’s magnitude (multiplied, for a negative D); R is an IEEE binary32, big-endian, and E and D are each an integer whose first bit is its sign and whose other 15, the most significant first, are its magnitude.

  • source, with format grib, id the data representation template’s number and parameters the place of section 5’s octets after it (from octet 12), for any other template (the spectral 5.50 and 5.51, 5.61, 5.200), and for one of those above with parameters its codec does not take (IEEE floats of another precision, complex packing of other options, signed CCSDS samples, a section 5 shorter than its template’s octets). Complex packing with groups and missing value management 1 or 2 is source too: a coded value whose bits are all 1 (in a group of width 0, a group’s reference whose bits are all 1) is a missing value, and under 2 so is one that is 1 less, for which the field codes no integer, so that an element would have to be made for it. The field then has no item_bits, and its row’s range is section 7 after its first 5 octets.

  • No grid for a field whose section 7 holds fewer octets than its IEEE floats or its simple packing’s integers take, and for one of another packing, named or source, with values to code and a section 7 of 5 octets: no unit of no bytes is named.

  • The grid is dense, but a constant field’s: GRIB has no fill value.

H5J: stored arrays¶

What the H5J parser describes as stored arrays (stored-array.md), part of the H5J profile.

An H5J file is described as the two formats it is made of. Its datasets are described as HDF5’s (hdf5/stored-arrays.md), by the same code: a channel’s dataset is an array of one dimension of 8-bit elements, the bytes of its MP4 file, whose one row is the struct that holds that file in the IR (h5j.md §5.3). Each channel the profile zarrifies (h5j.md §8.2) also has its MP4 file’s tracks described as MP4’s (mp4/stored-arrays.md), keyed by each track’s trak box in that struct, every element and range renumbered to the H5J file’s IR and bytes: a track of 4:0:0 pictures is one array, the luma plane, in an hevc chain. A channel the profile records keeps its dataset’s description alone: its bytes, as an MP4 file, are not described.

HDF4: stored arrays¶

What the HDF4 parser describes as stored arrays (stored-array.md), part of the HDF4 profile.

Every dataset of the SD interface the parser reaches is a stored array, whether or not the profile presents it: each Var0.0 Vgroup of the file’s CDF0.0 Vgroup (hdf4.md §3). It is keyed by that Vgroup’s element (elements/1965/<ref>), with no index. The facts give the key: each presented dataset’s array.declared_by is that element’s id. The writer’s Vdatas (tables) and the datasets’ attributes are not described yet.

  • Declarations. The number type’s element (elements/106/<ref>), whose type code and width say what an element is and whose class byte gives the byte order (4: little-endian; else big-endian), then the dimension record’s (elements/701/<ref>), where the Vgroup names them; then, of a _FillValue the description does not give (below), its Vdata header.

  • shape is the dimension record’s sizes, in its order: HDF4 stores an array in its declared order, so axes is absent. An unlimited first dimension’s size is the records the data holds, its bytes divided by a record’s, as the SD interface reads it: the dimension record keeps the size at its creation, and no place holds the records.

  • item_bits is the bits of the type the number type’s code names: 8, 16, 32 or 64; of text (char8), 8.

  • Data stored whole (as one element, in linked blocks, or compressed whole) is one unit, each axis Each of its length, or an empty List for an axis of length 0, under short. Its row is the one element that holds its bytes (the data element, the compressed stream’s, or a linked block’s), with the range of them where the element holds more; or, where several linked blocks hold them, ranges of the file, the blocks’ bytes in order. The chain is empty, zlib for data compressed with deflate (method 4, which HDF4 writes as a zlib stream), or source for another method, with format hdf4 and id the method’s code; its row is then the compressed stream. A dataset with no data, or whose compressed data decodes to no bytes, has no row: every element is the fill value.

  • A chunked dataset has the grid of its chunk lengths, Each on every axis, under full: the library stores every chunk at the full chunk size. Each chunk the chunk table lists is a row, at the coordinates the table gives, as a dataset stored whole is (above), in the chain of its own method: the array has a chain for each method its chunks use, the empty one first. A chunk of an unlimited dimension past the records lies outside the array, and has no row; a chunk the table does not list has none.

  • No grid for data the parser does not locate: in an external file, in a special element of another kind, of a compression model other than 0, or in linked blocks one of which was never written, which the library reads as zeros and no place holds. Nor where the data holds fewer bytes than the dataset, or the number type or the dimension record does not read. Such a dataset still has its shape and item_bits, but for an unlimited first dimension, whose size only the data gives: it has no shape, unless the parser located its data.

  • The grid is sparse, whole or chunked: a dataset may hold no data, and a chunk table need not list every chunk. Its fill value is given: a chunked dataset’s chunk header’s (its bytes after the header’s dimensions), where it is one element long; else the _FillValue attribute’s first element, its place in the attribute’s Vdata, where it is of the dataset’s number type and byte order (of text, its first byte). A _FillValue of the dataset’s type in another byte order leaves none, its Vdata header among the declarations. With neither, it is format_default, the SD interface’s: netCDF’s default of the number type’s netCDF type, as NC_arrayfill writes it (char 0, of char8 and uchar8; byte −127, short −32767 and long −2147483647, as bytes of the number type, so 129, 32769 and 2147483649 of the unsigned types; and float and double 9.9692099683868690e36), which a _FillValue of another type does not change.

HDF5: stored arrays¶

What the HDF5 parser describes as stored arrays (stored-array.md), part of the HDF5 profile.

Every object the parser reads whose header has a data layout message, and neither a symbol table nor a link info message, is a stored array, whether or not a path reaches it or the profile presents it: a dataset. It is keyed by its object’s element (objects/<i>), with no index: i is the dataset’s position among the description’s objects (hdf5.md §8.7), whose storage gives its storage element, which the store’s placed() renumbers (stored-array.md §2.1). An attribute’s value is not described yet.

  • Declarations. The first is the data of the dataset’s datatype message, or, where that message is shared, of the committed datatype’s datatype message it names; a header with no one datatype message gives none. Of a dataset the parser did not read, it is the shared message’s own data: the description reads no byte the parser did not, so it is the same however the file’s bytes were fetched. After it come the fill value messages whose value the description cannot give (below). A message is the element the IR made of its data (messages/<k>/data), or, where the IR had no room for one, a range of the source.

  • shape is the dataspace’s current dimensions, absent for a null dataspace and for one that does not read. axes is absent: HDF5 stores an array in its declared order.

  • item_bits is eight times the datatype’s size, the bytes of one stored element (for a variable-length type, of its heap reference); absent where the datatype does not read or its size is 0, and for a dataset the parser did not read whose datatype message is shared.

  • A chunked dataset whose chunk index and filter pipeline the parser read has the grid of its chunk shape, Each on every axis, under full, and one chain: its filter pipeline’s codecs (stored-array.md §3.2), in the pipeline’s order. A filter the list has no name for, or whose client data are fewer than its entry’s parameters, is source, with format hdf5, its id, its name where the message gives one, and parameters, a place of all its client data, where it has any. Each chunk the index holds is a row: its element; or, where the chunks of an implicit index are one data element, its range of that element (no range where the chunk is all of the element); or, where the IR had no room for its element, its range of the source. skips is the chunk’s filter mask, less the bits past the pipeline; an edge chunk the dataset stores unfiltered skips every codec. A chunk the index does not hold has no row.

  • A contiguous or compact dataset is one unit in an empty chain: each axis Each of its length, or an empty List for an axis of length 0, under short. The row’s bytes are the dataset’s data element, or the range of its layout message’s data that holds a compact dataset’s (a range of the source where the IR had no room for the element); a dataset of no bytes, and a contiguous one with no address, has no row. A dataset whose stored bytes are not as many as its elements’, and a contiguous one whose data runs past the end of the file, has no grid.

  • A dataset in external files is one unit likewise, its row’s ranges the files’ ranges in order, each by the sibling key the run resolved for the file. It has a grid only where a store run found every file it reads, each as long as its part; in a file run, which looks for no sibling, it has none.

  • No grid also for a virtual dataset, a null dataspace, a chunked dataset whose index the parser did not read, and a dataset of which it did not read the dataspace, the datatype, the layout, the filter pipeline message or the fill value message.

  • Sparse and dense. A chunked dataset’s grid is sparse (its index may leave a chunk out), and so is a contiguous one’s (a dataset of no address holds no unit); a compact dataset’s, and one in external files, is dense.

  • The fill value of a sparse grid has HDF5’s three states, as the library’s H5Pfill_value_defined gives them for the dataset: none where it is undefined (the message says so, or the header has no fill value message of either type), format_default (a fill value is defined and the message holds none: zeros), or given, the place of the value’s bytes in the message, which are an element as the datatype stores one. The new message (type 5) is read where a header has both. A shared message, several messages of the type read, a message that does not read, or a value whose length is not the datatype’s size, leaves none, with those messages among the declarations, whatever the grid.

LIF: stored arrays¶

What the LIF parser describes as stored arrays (stored-array.md), part of the LIF profile.

Every image of a LIF, LOF or LIFEXT file (lif.md §2.3) is a stored array, keyed by the element that holds the XML that declares it, a kind of element that may declare several arrays: header/xml, or, of a LOF, description/xml, with the image’s index among that XML’s images, in document order. The facts give the key: each image’s declared_by is that element’s id and the index, a pair. Below, a dimension’s N and s are its NumberOfElements and BytesInc, e is the bytes of a sample, and o the channels’ BytesInc in ascending order (lif.md §3.2): the sample of channel c at the index i of each dimension lies o_c + Σ i × s bytes into the image’s bytes, which start with the data of its memory block.

  • A LAS X project (lif.md §8) is a store whose LOFs’ IRs are grafted, each with its descriptions (stored-array.md §6): an image is its LOF’s, keyed by description/xml under the LOF’s object, and the store’s parser renumbers the id in declared_by. Its bytes start at the Offset of the document’s Block, counted in the block’s data. An image the project holds in other files than one LOF is not read (lif.md §8.4), and has no description; the image of a LOF that a document that is no image names is read, and is described, though the profile presents none of it.

  • Declarations. One: the key’s element, the XML’s whole text, in UTF-16, whose DimensionDescription and ChannelDescription elements say what the image’s samples are (DataType, Resolution) and what its axes are (DimID); no range of the text is given. In a project it is the LOF’s XML, which the parser reads the layout from, not the document that names the LOF.

  • shape and axes. The axes are the image’s dimensions, each one, a dimension of one element too, and, of an image of more than one channel, its channels, which take the position after the last dimension in the source’s list. Storage order is read off the byte increments: the axes by their bytes a step (a dimension’s s; the channels’, the least difference of two of o), the largest first, and, of two of one step, the one the source lists later before the other (LAS X lists the fastest dimension first, and gives each the bytes of those before it). An axis of one element steps nowhere, and is placed by its BytesInc all the same. So X, Y and Z with three channels between Y and Z have shape [N_Z, 3, N_Y, N_X] and axes [2, 3, 1, 0], and interleaved channels are the last axis. Along the channels’ axis the elements are the channels in ascending order of BytesInc, which need not be the XML’s. (liffile 2026.10.14 orders two dimensions of one BytesInc the other way; only dimensions of one element can be so in an image with a grid.)

  • item_bits is 8 × e: the channels’ Resolution, rounded up to 8, 16, 32 or 64 (lif.md §3.1). The parser refuses an image whose channels differ.

  • The grid. From the fastest axis on, the span of the axes so far is the bytes from their first sample to the end of their last: e before any, and with each axis the place of its last element more. An axis of more than one element packs when it steps by exactly the span of the faster ones, the channels evenly so. The axes that pack, from the fastest up to the first that does not, are within a unit, Each of their length; every slower axis is Each(1); the edge is short. So an image whose every axis packs is one unit, as LAS X writes most; one whose rows have bytes between them (stride-aligned RGB rows) has a unit a row; and one whose planes or channels lie apart has a unit for each. A unit is a row of the map: the data element of the image’s memory block (blocks/<i>/data) with the range of the unit’s bytes, or that element alone where the unit is all of it. Bytes of the block before, between or after the units are no part of the array. (liffile 2026.10.14 reads an image’s samples end to end from the start of its block, whatever bytes the increments leave before or between them, but for stride-aligned rows of interleaved samples; and it reads a project’s LOF from the start of its block whatever the Offset.)

  • The chain is one, empty: the samples are stored as they are.

  • No grid for an image whose axes do not nest: one with an axis of more than one element that steps by fewer bytes than the faster axes span. Its samples then share bytes, and are no array of distinct elements (a BytesInc of 0 repeats a plane, and a smaller one than the plane’s bytes overlaps it), or lie in an order that no order of the axes gives (channels unevenly apart, with a dimension’s steps between them). The profile presents such an image plane by plane all the same. And no grid for an image whose units’ rows alone would pass the file’s chunk map limit (stored-array.md §6), which are not built. Either image has its shape, axes and item_bits. What the parser refuses (bit-packed samples, channels of two types, channels neither planar nor interleaved, rows that overlap) has no IR.

  • The grid is dense: LIF has no fill value.

MP4: stored arrays¶

What the MP4 parser describes as stored arrays (stored-array.md), part of the MP4 profile.

Every track whose handler is vide or soun has descriptions, whether or not the profile zarrifies it, keyed by its trak box, a kind of element that may declare several arrays: each of a track’s has an index. The facts give the key: each such track’s declared_by is the id of its trak box. A track’s samples are its tables’, then its track fragments’, in decode order (mp4.md §3), each the element samples/<T>/<j>.

  • Declarations. The fields value of the track’s first sample entry (its data value, of a sample entry the convention does not parse), then the data value of each of its child boxes, in order: a video codec’s configuration is among them. A track with no sample entry has none.

  • A video track of H.264, HEVC, AV1 or VP9 (the sample entries avc1; hvc1 and hev1; av01; vp09), of one sample description, whose configuration box (avcC, hvcC, av1C, vpcC) the parser reads as pictures of three planes of one bit depth, from 8 to 16 (4:2:0, 4:2:2 or 4:4:4), or of a luma plane alone of such a depth (4:0:0), has three arrays, the planes of its pictures: index 0 the luma plane, 1 and 2 the chroma planes; of 4:0:0, the luma plane’s alone.

    • shape is the samples, then the plane’s height and width: the sample entry’s height and width for the luma plane, and for a chroma plane those halved, rounded up, as the format subsamples (both for 4:2:0, the width for 4:2:2, neither for 4:4:4). The first axis is the samples in decode order, not the pictures in presentation order: when a sample is presented is the profile’s, from the track’s tables. A stream whose pictures are of another size than the sample entry’s decodes to the stream’s.

    • item_bits is 8 for a bit depth of 8, else 16.

    • The grid is a sample a unit: Each(1), then Each of the plane’s height and of its width, under short.

    • The chain is the codec (h264, hevc, av1 or vp9): its setup the configuration box’s data value, its plane the array’s index, and sync a unit parameter, 1 for a sync sample (mp4.md §3) and 0 for any other.

    • Each sample is a row of each of the track’s arrays: its element.

  • A Motion JPEG track (jpeg, mjpa, dmb1, or mp4v of object type indication 0x6C), of one sample description, whose first sample’s frame header the parser read, of the sample entry’s width and height, 8 bits and 1 or 3 components, has one array, index 0: shape the samples, the height, the width and, for 3 components, the components; item_bits 8; a sample a unit, in decode order, in a jpeg chain with no tables.

  • Any other track of one sample description has one array, index 0, of its samples as the sample entry encodes them, by the general fallback (stored-array.md §1): an audio track, whose decoded samples are not described yet; a video track of another codec, of a sample entry of width or height 0, or whose configuration the parser does not read as above (pictures of chroma planes of another bit depth than luma’s); and a Motion JPEG track of another frame (a picture’s fields, 12 bits, streams with no markers). shape is the track’s sample elements, one axis; there is no item_bits, since the IR does not say what a sample decodes to; the grid is Each(1) under short; and the chain is source, with format mp4 and id the sample entry’s type, its four characters as a string. Each sample element is a row, in decode order: a sample, or, of a PCM track of one sample size, a chunk’s samples together (mp4.md §5.3).

  • No grid, and neither shape nor item_bits, in one description of index 0, for a track whose samples are not one array: a track with no samples, with more than one sample description, or with its sample sizes in an stz2 box; and a PCM track with a sample that its tables size as no whole number of frames, which readers do not agree on (ffmpeg reads its frames by the sample entry’s size).

  • The grid is dense: MP4 has no fill value.

MRC: stored arrays¶

What the MRC parser describes as stored arrays (stored-array.md), part of the MRC profile.

An MRC file’s data is one stored array, keyed by the file’s header element, with no index. The facts give the key: declared_by is that element’s id. The dataset layout (spec/zarrify/mrc-dataset.md) is a second layout of the same file, and has no description of its own.

  • Declarations. Ranges of the header element, in this order: machst, (212, 4), whose first byte gives the byte order of the header’s fields and of the values; mode, (12, 4); and, of a mode 0 file, whose values’ sign they decide (mrc.md §3), nversion, (108, 4), IMOD’s stamp, (152, 4), and IMOD’s flags, (156, 4).

  • shape is nz, ny and nx, the sections, the rows and the columns, whatever the kind of file (mrc.md §4.1): an image is one section, and a volume stack’s sections are those of all its volumes, which the profile cuts by mz. axes is [2, 1, 0]: the header gives nx first. The axis map (mapc, mapr, maps) names the axes and reorders no value, so it changes neither.

  • item_bits is the mode’s: 8 for mode 0; 16 for modes 1, 6 and 12; 32 for mode 2, and for mode 3, whose element is a pair of 16-bit integers; 64 for mode 4, a pair of 32-bit floats; and 4 for mode 101, with pad_from 2, the columns’ axis: each row ends on a whole byte.

  • The grid is one unit, the whole array: each axis Each of its length, under short. Its row is the data element. The profile’s checks (mrc.md §8.1) leave no axis of length 0, and no data that is not whole in the file, so no array of an MRC file lacks a grid but by the limits of stored-array.md §6.

  • The chain is empty, but for mode 101’s, lsb_first with bits 4: a row’s first value is the low half of its first byte. A row of an odd nx ends on half a byte of padding, the high half of its last byte, which decodes to the low half, after the row’s last value, as pad_from says.

  • A file gzipped whole (mrc.md §8.4) has no header element: its bytes are the stream, which holds the header. Its array is keyed by its data element, the stream, as declared_by says, and that element is its one unit. It has no declarations: the header is the first 1024 bytes the stream inflates to, which no place names: the parser gives the inflated bytes no derived space yet. Its shape, item_bits and pad_from are those of the header the parser inflated. Its chain ends with skip, then gzip: the values are what the stream inflates to, after the header and the extended header. skip’s length, 1024 plus nsymbt, is a value, since no place holds nsymbt either.

  • The grid is dense: MRC has no fill value.

ND2: stored arrays¶

What the ND2 parser describes as stored arrays (stored-array.md), part of the ND2 profile.

An ND2 file’s frames are one stored array, and a frame is a unit of it, not an array of its own: the source names the frames as one sequence (the chunks ImageDataSeq|<f>!), declares one layout for all of them (ImageAttributesLV!) and none in a frame’s own chunk, and counts them by its experiment’s loops. A frame is found by its number in the chunk map, as an HDF5 chunk is by its index, and a frame the map does not name is a unit the source does not hold. The array is keyed by the ImageAttributesLV! chunk’s element (chunks/ImageAttributesLV!), with no index, in every file, whichever frames it holds. Each frame chunk the map names at or past the loops’ count (a frames/<f> of the IR), which the image leaves out (nd2.md §4.1), is an array of one frame, keyed by the frames element, a kind of element that may declare several arrays: its index is its position among those chunks, in the order of their numbers. The facts give the keys: declared_by is the id of the ImageAttributesLV! chunk’s element, and unplaced has declared_by, the id of frames, and count, the arrays it keys.

  • Declarations. The lv element of the ImageAttributesLV! chunk (its data: a lite variant, or the compressed record of one), then that of ImageMetadataSeqLV|0! where the file has one with data: the attributes give a sample’s size and a pixel’s components, and the picture’s planes say what each component is. The experiment, which says what a frame’s number means, declares nothing of a sample: the profile reads it.

  • shape is the frames the loops count, N (the product of the loops’ counts as nd2.md §3 flattens the experiment, 1 with no loops), then uiHeight, uiWidth and, where uiComp is more than 1, uiComp, a pixel’s components being stored together. The array of a frame past the count has no first axis. axes is absent: ND2 names its dimensions by member, and lists them in no order.

  • item_bits is uiBpcInMemory: 8, 16 or 32.

  • The grid is under short. Where a frame’s rows are stored end to end (uiWidthBytes is the bytes of a row’s samples), or the frames are compressed, a frame is a unit: Each(1) on the first axis, and Each of its length on every other. Where uiWidthBytes is more, each row’s samples are followed by bytes that are no sample, and a row is a unit, Each(1) on the rows’ axis too: the source holds one row’s samples together and no two rows’, so a unit of several rows would either hold bytes that are no element or be bytes a recipe joins (stored-array.md §1).

  • Rows. Frame f below N, where the map names it, is at f on the first axis: its frames/<f>/pixels element, which starts after the frame’s 8-byte timestamp, with member where the frames are a run. Of padded rows, row r is the range (r × uiWidthBytes, the bytes of a row’s samples) of that element, taken before its recipe, which joins the rows (stored-array.md §4.2); one row whose samples end the file is the element alone. A frame past N is a range of its frames/<f>/data element, which holds the timestamp too: the rows’ bytes from 8, or the stream, from 8 to the data’s end; or, of padded rows, each row’s samples from 8 + r × uiWidthBytes.

  • The chain is one for the file: empty, or zlib where eCompression is 0. The parser inflates no frame: a stream that does not inflate to the frame’s bytes is described as one that does.

  • No grid for a frame chunk past N that holds no frame as the attributes say: one whose header is no chunk header within the file; one whose header gives fewer bytes of data than the timestamp and uiHeight rows of uiWidthBytes (of compressed frames, no byte after the timestamp); and one whose rows’ samples, or whose stream, the file does not hold to their end. Its description keeps its shape and item_bits. Below N the profile rejects such a file. An array whose rows would pass the chunk map’s limit (stored-array.md §6) falls back before they are made: frames of padded rows that share their bytes have a row for each row of each.

  • Where readers differ. A frame’s bytes follow its chunk’s name, of the length the chunk’s header gives, as the nd2 library’s chunk reader reads a chunk; nd2’s frame reader takes every frame’s name to be 4072 bytes, as NIS-Elements writes it, whatever the header says, and reads the same bytes only of such a file. The header’s is the format’s own declaration, so the frame keeps its grid. nd2 also counts the loops of some experiments otherwise (it reads a time loop whose periods have no validity list as no period, and the convention as every period), which moves no frame: N says only which frames the first array holds. And nd2 takes as a frame’s number whatever Python’s int reads after ImageDataSeq|, where the convention (nd2.md §4.1) takes a decimal number without leading zeros: in a file that names both ImageDataSeq|0! and ImageDataSeq|00!, nd2 reads the second as frame 0, and the description, with the profile, the first. The description follows the convention there, and no file a writer is known to make has such a name.

  • The grid of the frames the loops count is sparse, a frame the chunk map does not name being a unit the source does not hold, and that of a frame past them dense: ND2 has no fill value.

NDPI: stored arrays¶

What the NDPI parser describes as stored arrays (stored-array.md), part of the NDPI profile.

An NDPI is read by the TIFF parser in NDPI’s layout, and every IFD that declares a size is described as a TIFF’s (tiff/stored-arrays.md), keyed likewise, the macro image and the slide map too, with the differences below. The facts give the keys: each level’s declared_by lists, in the order of its planes, the id of each plane’s IFD.

  • A JPEG strip that McuStarts cuts. An image of Compression 7 in one strip (interleaved samples of 8 bits, with neither JPEGTables nor a tile size), with McuStarts (65426), whose strip’s header the parser read (zarrify/ndpi.md §7 reads those of the IFDs of positive Magnification), is cut into the strip’s restart intervals, as tifffile reads it. The grid is Each of the MCU’s height, Each of an interval’s width (its MCUs times the MCU’s width) and Each of the samples, under full. Each interval is a row: the strip’s element, with the range from the interval’s McuStarts value (with McuStartsHighBytes) to 2 bytes before the next one’s, or before the strip’s end, which leaves out the restart marker or EOI after it. The chain is jpeg_restart_interval, its header the range of the strip’s element before the first interval.

  • A JPEG strip read whole. The image is one strip in a jpeg chain, as a TIFF’s, without McuStarts, and also where the parser did not read the strip’s header (an IFD of no positive Magnification), where the header is not one the profile reads, where its frame’s components are not the image’s samples, where McuStarts and McuStartsHighBytes do not fit one another, and where McuStarts are not the offsets of the intervals the image’s size needs: as many, increasing, within the strip, each interval of at least one byte. A strip’s frame may give another size than the image’s fields (ndpi.md §4): the description gives the fields’, and the stream decodes to the frame’s.

  • JPEG XR (Compression 22610). The fields do not say what the streams hold: Hamamatsu writes 8-bit YCbCr of 3 samples whatever they are (zarrify/ndpi.md §3). Where the parser read the header of the image’s first stream (its first tile that holds bytes, or its strip), its pixel format is one the profile reads and its size is the unit’s, the image’s samples are the stream’s: shape has the pixel format’s samples last, or none for one sample; item_bits is the pixel format’s, 8 or 16; and the chain is jpegxr. The declarations are the fields’ all the same. Any other JPEG XR image (an IFD of no positive Magnification, whose stream the parser does not read) is as its fields say, in a source chain.

  • source has format ndpi in an NDPI.

netCDF3: stored arrays¶

What the netCDF3 parser describes as stored arrays (stored-array.md), part of the netCDF3 profile.

Every variable of the header is a stored array, whether or not the profile presents it, keyed by the file’s header element, a kind of element that may declare several arrays: a variable’s index is its position in the header’s variable list. The parser’s description gives the key: its elements has the header element’s id, and the variable at position k of its variables is the array of index k (netcdf3.md §7.7).

  • Declarations. The range of the header that holds the variable’s nc_type, 4 bytes, which names its type (netcdf3.md §3.1). The format fixes the byte order (big-endian) and the order of the elements (the last index varying fastest), which no place declares.

  • shape is the lengths of the variable’s dimensions, in order, a record variable’s first the record count (netcdf3.md §7.3), which no place holds for a streaming file; empty for a scalar. axes is absent.

  • item_bits is the bits of the type: 8, 16, 32 or 64. There is no pad_from.

  • The grid. A fixed-size variable is one unit, each axis Each of its length, under short; its row is its data’s element, variables/<k>. A record variable is a unit per record: Each(1) along the record axis and Each of its length along each other, under short; the row of record r is the records element, with the range of its slice, r × recsize past the variable’s own offset in a record. A record variable of no records has no row.

  • The grid is dense: the file stores every unit, a fixed-size variable’s data and each of the records it counts, so the grid has no fill value. A netCDF-C file written without fill holds bytes in every unit all the same, whatever they are.

  • The chain is empty: the format stores every value as it is.

NIfTI: stored arrays¶

What the NIfTI parser describes as stored arrays (stored-array.md), part of the NIfTI profile.

A NIfTI file’s voxels are one stored array, of a single file, of a file gzipped whole and of a header-and-image pair alike, as nibabel reads them. The facts give its key: declared_by is the id of the element that declares it. Below, n is the header’s dim[0], and v its vox_offset.

  • A single file’s array is keyed by its header element, with no index. That element is its one declaration: the header, whose sizeof_hdr gives the file’s byte order, with its dim, its datatype and bitpix, and what else a profile reads of the voxels (scl_slope, scl_inter).

  • shape is dim[n] to dim[1]: the header lists its dimensions the fastest-varying first, so axes is n − 1 down to 0 for an n of 2 or more, and absent for 1. Each of the n dimensions is an axis, the sixth and the seventh too, which the parser accepts only at 1; the values of dim past dim[n] are not read.

  • item_bits is the bits of a voxel of the header’s datatype, which bitpix repeats (the parser refuses a header where the two differ). A voxel is one element: an RGB24 or RGBA32 voxel of 24 or 32 bits, a complex one of 64 or 128.

  • The grid is one unit: every axis Each of its length, under short. Its row is the voxels element, the voxels’ bytes from v, in an empty chain.

  • A pair’s array is the single file’s, described by the pair’s store parser itself (stored-array.md §6): its key and its declaration are the header element of the header file, and its row the voxels element of the image file, where v counts.

  • A gzipped file’s array has the single file’s shape, axes, item_bits and grid, but its header lies in its stream, where no element holds it. It is keyed by the file’s one element, voxels, the whole file, and has no declarations: a profile reads the header from the facts’ gzip.head, the stream’s first bytes as the parser inflated them. Its row is that element, in the chain skip, gzip: the stream inflates to the header, the extender and the extensions, then the voxels, and skip’s length is v, a value, since no place holds the field. The parser inflates the start of the stream alone, and accepts the file only where the size its trailer records is v plus the voxels’ bytes, modulo 2^32.

  • No grid for no file the parser accepts: it refuses one whose voxels it does not read as one array (a datatype it has no size for, a dimension below 1, a sixth or seventh dimension above 1, voxels the file does not hold).

  • The grid is dense: NIfTI has no fill value.

NumPy: stored arrays¶

What the NumPy parser describes as stored arrays (stored-array.md), part of the NumPy profile.

A .npy file’s array, and each stored (method 0) or deflated (method 8) .npz member’s whose header was read, is a stored array, keyed by its header element, with no index; that element is its one declaration (its descr, fortran_order and shape). Its key is found by its path: a .npy file’s header element, or a .npz member’s entries/<i>/data/header, i the member’s position in the archive’s central directory, which is its position among the source metadata’s members, presented or not; a member with no description (one whose header was not read) has no such element. For an array the profile presents, the parser’s description gives the key too: its entry of arrays holds stored, the header element’s id, beside its path and its header’s text. shape is the header’s, reversed for a Fortran-order array of two or more axes, whose axes then give the header’s order; item_bits is eight times the size of an element of its descr as NumPy lays it out, whether or not the profile presents the array: a type string (with its one-character codes, such as <h or ?; a subarray, (2,3)<f4; fields joined by commas, <f8,<i4) or a structure (with its padding fields, fields of shape, fields whose type is a (type, shape) tuple, and fields of no bytes, such as |S0, which add none). It is absent for a descr of no size: an object array’s; one of 0 bytes; one whose size is the machine’s (l, L, g, G, p, P), which a header does not give; and a structure with two fields of one name, which NumPy refuses. A presented array is one unit, its data element, in an empty chain: each axis is Each of its length, or an empty List for an axis of length 0 (which has no unit, and no row), under short, dense: NumPy defines no fill value. An array whose data is not presented (its descr has no data type, or its data does not fit) has no grid, nor, by the general fallback (stored-array.md §1), has one whose element’s bits would pass 2^64 (an array of no elements may be of such a type), whose item_bits is then absent too. A deflated member’s header and data elements lie in a derived space, what its deflate stream inflates to (npy.md §5.3): its unit is its data element there, in the same empty chain, since inflating the stream is the IR’s transform of the derived element and no codec of the array. No range of the file holds such a unit; a projection references the derived element’s own bytes, the stream, and decodes them.

NRRD: stored arrays¶

What the NRRD parser describes as stored arrays (stored-array.md), part of the NRRD profile.

A NRRD input is one stored array, the one its header declares, in the store IR the profile’s run builds of the header file and, for a detached header, its data file. It is keyed by the header file’s object (the header has no element of its own), with no index. The facts give the key: array.declared_by is the id of that object. Below, the NRRD definition is Teem’s, which zarrify/nrrd.md cites.

  • Declarations. The line of the type field, then the line of the endian field where the header has one: each the element lines/<i>, which holds the field’s identifier, its descriptor and its line end.

  • shape is the values of the sizes field, reversed: the data holds the header’s last axis outermost. axes gives the header’s order, the storage axes reversed ([2, 1, 0] for three axes).

  • item_bits is eight times the bytes of one element of the type field’s type (nrrd.md §3).

  • The grid is one unit of the whole array: each axis Each of its size, under short. Its row is the data element of the data’s file, whole: the header file for an attached header, and for a detached one the data file, another object of the store. For the raw encoding the element is the array’s bytes, after the lines and bytes that line skip and byte skip pass over, or, with a byte skip of −1, those that end the file; bytes of the file after them are no part of the unit, as the NRRD definition says (pynrrd 1.1.3, which reads a file it is given by its path to its end, refuses one that has any). For the gzip encoding the element is the stream: from after the lines line skip passes over to the end of the file.

  • The chain is one: empty for the raw encoding; gzip for the gzip encoding; and skip, then gzip, for the gzip encoding with a byte skip above 0, which the NRRD definition counts within the inflated bytes. skip’s length is the descriptor of the byte skip field, a range of the field’s line. (pynrrd 1.1.3 skips those inflated bytes too, but first seeks as many bytes into the file, so it reads no such file that follows the definition.)

  • The stream is not inflated, as the profile reads none of the data: the description is the same whatever the stream holds, and one that inflates to other than the skipped bytes and the array’s is not detected. The array’s bytes are the first the chain makes: the NRRD definition leaves what follows the data unread. (pynrrd 1.1.3 refuses a stream that inflates to more, and inflates the first member alone of a stream of several, which the gunzip program the NRRD definition names reads whole.)

  • No grid for no input: the profile rejects what it does not read (the text, hex and bzip2 encodings, the type block, several data files), and builds no IR of it.

  • The grid is dense: NRRD has no fill value.

SAFE: stored arrays¶

What the SAFE parser describes as stored arrays (stored-array.md), part of the SAFE profile.

Each band file of a Sentinel-2 product, a JP2 file, holds one image, a stored array, in both forms of the product: in the directory form’s store IR, whose parser describes its objects’ arrays itself (stored-array.md §6), and in the zip form’s file IR. It is keyed by the band file’s codestream struct (boxes/<i>/codestream, under the band file’s object or under its zip entry’s data), with no index. The facts give the key: each band’s declared_by is the id of that struct. The profile presents every band file. The product’s other images (the quality masks, the preview image, the cloud and snow probabilities, a mirror’s quicklook) are in objects the parser does not read (safe.md §2.1), and have no description.

  • Declarations. The siz value, the codestream’s SIZ marker segment, whose component triples give a sample’s precision and sign; then the contents of each jp2h box before the codestream, the JP2 header, which holds the color specification. The parser parses the first, and holds the second as bytes.

  • shape is Ysiz, then Xsiz, then, for an image of three components, 3: a pixel’s components are together, last. axes is [1, 0], or [1, 0, 2]: SIZ gives Xsiz before Ysiz, and Csiz is a count, after the extents it lists.

  • item_bits is the size of the samples the codec makes: 8 for a precision of at most 8 bits, else 16. The precision itself (15 bits of a reflectance band) is SIZ’s.

  • The grid is the codestream’s tiles: Each of YTsiz and of XTsiz, each at most its axis’s length, then Each(3) for three components, under short: a tile at the image’s right or bottom edge is cut to the image. (A tile size above the image’s is SIZ’s alone, where the profile reads its chunk shape.) A tile is a unit, and not the image one unit in a jpeg2k chain, because the parser locates every tile: it walks the codestream’s tile-parts by their SOT markers, and accepts only a codestream of one tile-part a tile, in raster order (safe.md §8.3). Each tile is a row, the element tiles/<k>, whole: its tile-part, from its SOT marker through its packets. Every tile has a row. (GDAL reads a band file in blocks of its own choosing, the codestream’s tiles or the whole image: the grid is SIZ’s.)

  • The chain is one, jpeg2k_tile, its header the range of the codestream struct from its start to the first SOT: the main header. A chain’s header is its own file’s, so each band file has a chain of its own.

  • No codestream is made. A tile’s bytes are no codestream without the main header, and the description holds none the source does not: the SIZ of its own that the profile gives each chunk, and the empty tiles that fill a chunk at an edge (safe.md §8.6), are the profile’s.

  • No grid for no band file: the parser rejects a product with a band file it does not walk to its end (a TLM, PLM or PPM marker, several tile-parts for a tile, an image or tile origin other than 0, components that are signed, subsampled or of unlike precisions), and builds no IR of it.

  • The grid is dense: JPEG 2000 has no fill value.

safetensors: stored arrays¶

What the safetensors parser describes as stored arrays (stored-array.md), part of the safetensors profile.

Every tensor of a header that passes the profile’s checks (safetensors.md §8.2) is a stored array, whether or not the profile presents it, keyed by the file’s header element, a kind of element that may declare several arrays: a tensor’s index is its position among the header’s tensors, in the order the header writes them (__metadata__ is none of them). The facts give the key: declared_by is the id of the header element, and a tensor’s index is its position in the facts’ own.tensors, which a presented tensor’s entry of the facts’ arrays gives as index.

  • The store form (safetensors.md §9) describes each shard’s tensors itself, not by graft. A presented shard, described in place, has a file’s elements and facts (its entry of the store’s facts’ shards holds them as facts), and its tensors are keyed by its own header. A shard that is not presented for its key, whose header passed the checks, has no element but its object: its tensors are keyed by that object, also a kind of element that may declare several arrays, with the same indexes, and their places are ranges of it. A shard whose header fails a check has no descriptions. The store’s facts’ declared_by lists, in the order of own.files, the id of the element that keys each shard’s descriptions, null for a shard with none.

  • Declarations. One: the range of the header that holds the entry’s dtype value, a JSON string as the header writes it, with its quotes and any escapes (of a shard keyed by its object, the same bytes as a range of the object). The format fixes the elements’ byte order (little-endian) and their order (the last index varying fastest), which no place declares.

  • shape is the entry’s shape, empty for a scalar. axes is absent: a tensor is stored in the order of its shape.

  • item_bits is the bits of one element of the dtype (safetensors.md §3), from 4 to 64; a complex number is one element. There is no pad_from: a tensor’s elements pack unbroken into whole bytes.

  • The grid. A tensor is one unit: each axis is Each of its length, or an empty List for an axis of length 0, under short. Its row is its data’s element, tensors/<i>, or, of a shard keyed by its object, the data’s range of the object. A tensor with an axis of length 0 holds no bytes, and has no unit and no row.

  • The chain is empty for elements of whole bytes. Elements of 4 or 6 bits (F4, F6_E2M3 and F6_E3M2) are in lsb_first, its bits their size: the buffer packs them from each byte’s least significant bit (safetensors.md §3.2). The library reads a tensor’s bytes and none of its elements, so this order rests on that section: for F4 it is the order of PyTorch’s float4_e2m1fn_x2, which the library writes, and for the 6-bit types, of which no writer was found, the same order by analogy.

  • The grid is dense: safetensors has no fill value.

  • No grid for no tensor of a checked header, but at the descriptions’ limit’s fallback (stored-array.md §6): the checks leave no tensor whose storage the IR does not model, and the chunk map’s limit has room for the row of any tensor that holds a byte. A header reaches the descriptions’ limit only where its tensors’ shapes have more than 2^23 axes in all, each a description’s entry and two bytes of the header: tensors then fall back, or the file keeps no descriptions.

TIFF: stored arrays¶

What the TIFF parser describes as stored arrays (stored-array.md), part of the TIFF profile.

Every IFD the parser reads (of the main chain, a SubIFD, or one another pointer tag leads to) whose ImageWidth (256) and ImageLength (257) are unsigned values it holds declares an image, a stored array, whether or not the profile presents it, keyed by the IFD’s element, with no index. The planes of an OME-TIFF and the levels of a pyramid are each an array: how they assemble is the profile’s. The facts give the keys: each level’s declared_by lists, in the order of its planes, the id of each plane’s IFD, null for a plane no file of the run holds, and a set’s store renumbers them as it does planes (stored-array.md §2.1). Below, a field’s value is the first of its values, and a field the IFD lacks has TIFF 6.0’s default.

Each plane after the first of an ImageJ stack in one IFD (tiff.md §4.1), which IFD 0 and its ImageDescription declare together, is a stored array too, keyed by its imagej/planes/<p> element, with no index, which declared_by gives for it. Its description is IFD 0’s, whatever that is, with the value element of IFD 0’s ImageDescription (270) as one more declaration, the last; where it has a grid, its rows are the plane’s own strips, imagej/planes/<p>/strips/<j>.

  • Declarations. The header’s byte_order, then the value element of each of these fields the IFD has with a value inside the file: BitsPerSample (258), PhotometricInterpretation (262), ColorMap (320), ExtraSamples (338), SampleFormat (339), YCbCrCoefficients (529), YCbCrSubSampling (530) and ReferenceBlackWhite (532).

  • shape is ImageLength, then ImageWidth; with SamplesPerPixel (277) other than 1, the samples come last, or first where PlanarConfiguration (284) is 2. An ImageDepth (32997) other than 1 comes before ImageLength. axes is absent: TIFF names its dimensions by tag, and lists them in no order.

  • item_bits is BitsPerSample, where every sample has the same; absent otherwise. Where it is not a multiple of 8 and the image has a grid, pad_from is the columns’ axis (1, or 2 with the samples first): a unit’s rows each end on a whole byte. An image the IR does not model (No grid, below) has none; one that falls back at the limits of stored-array.md §6 keeps it.

  • The grid. An IFD with TileWidth (322) and TileLength (323) is cut into tiles, Each of TileLength and of TileWidth, under full, as libtiff and tifffile read it; its tables are TileOffsets (324) and TileByteCounts (325), or, where it has not both, StripOffsets (273) and StripByteCounts (279). Another is cut into strips, Each of RowsPerStrip (278), at most ImageLength, and of ImageWidth, under short, its tables the strips’. Interleaved samples are a last axis of one unit; with the samples first, each is a unit of its own, and the tables list the first sample’s units, then the next’s. Each entry of the tables that holds bytes is a row, its element the entry’s data element (tiles/<j> or strips/<j>, of the IFD the tables are first met in); a JPEG tile or strip whose element’s recipe is not the identity (it splices in a marker, or the tables) is that element with a range of all its extent (stored-array.md §4.2). An entry of no bytes at offset 0, as a sparse file’s writer leaves a unit out, has no row.

  • The chain is one, by Compression (259): empty for 1; tiff_lzw for 5, zlib for 8 and 32946, xz for 34925 and zstd for 50000, each after tiff_predictor where Predictor (317) is 2 or 3; packbits for 32773; ccitt_t6 for 4 (one sample of 1 bit); jpeg for 7 (samples of 8 bits), with tables where the IFD has JPEGTables (347); jpeg2k for 33003, 33004, 33005 and 34712 (8 or 16 bits); jpegxl for 50002 and 52546 (8, 16 or 32 bits); webp for 50001 (8 bits); lerc for 34887 (8, 16, 32 or 64 bits), before zlib or zstd where the second value of LercParameters (50674) is 1 or 2; eer for 65000 and 65001 (one sample of 1 bit), with their fixed bit counts as values, and for 65002, with the places of those of the fields 65007, 65008 and 65009 the IFD has with unsigned values. The streams of jpeg, jpeg2k, jpegxl, webp and eer use no predictor, and libtiff and tifffile pass a Predictor over under them, as the chain does. Any other compression, one of these with samples of another size, and LERC whose LercParameters are not unsigned integers with a second value of 0, 1 or 2, is source with format tiff and id the Compression: the profile then reads the IFD for the rest.

  • No grid for an image the IR does not model: BitsPerSample that differ; FillOrder (266) other than 1; a Predictor other than 1 under a compression that is neither LZW, Deflate, LZMA or zstd nor one of those five, such as none, PackBits, CCITT and LERC (libtiff applies a predictor only within those four coders, and tifffile applies one to whatever it does not decode as an image, so readers disagree); under those four, a Predictor other than 1, 2 and 3, Predictor 2 with samples that are not integers of 8, 16, 32 or 64 bits, and Predictor 3 with samples that are not floats of 32 or 64 bits (by SampleFormat, which every sample must share); PhotometricInterpretation 6 with a YCbCrSubSampling other than (1, 1) under a compression that restores the stored bytes (1, 5, 8, 32773, 32946, 34925, 50000), whose samples are then not an array of the image’s shape; an ImageDepth other than 1; a PlanarConfiguration other than 1 and 2 with more than one sample; a width, a length, a sample count, a tile size or a RowsPerStrip of 0; an IFD without both of its units’ tables, as unsigned values the parser holds; tables that do not list as many units as the grid has, or that differ in length; an entry of no bytes at an offset other than 0, which readers do not agree on (libtiff sizes a lone strip from the image and refuses one among others, and tifffile reads it as absent); and an entry whose bytes do not lie in the file, so that a file cut short does not read as an image with units its source does not hold.

  • More bytes than the unit’s. A tile or strip may hold, or decode to, more bytes than its unit’s elements take (a tile stored at a larger sample size than its fields give): the unit’s are the first, as libtiff and tifffile read them.

  • The grid is sparse, an entry of no bytes at offset 0 leaving its unit out, and has no fill value: TIFF has none. NDPI’s grid of restart intervals (below) is dense.

VSI: stored arrays¶

What the VSI parser describes as stored arrays (stored-array.md), part of the VSI profile.

A VSI slide’s arrays are described by its store parser itself (stored-array.md §6), in the store IR of the .vsi file and its tile files: each tile file’s levels, and the images of the .vsi file’s IFDs, whether or not the profile presents them. The facts give the keys: each image’s declared_by is the id of the element that declares its arrays, a pyramid’s tile file’s ets element or an IFD image’s IFD; and the facts’ declared_by lists, by its index in the chain, the id of each IFD whose image is described, null for an IFD with no description, so that what names an IFD by that index (a stack’s coarse_ifd, an entry of not_presented) finds its image’s.

  • A tile file’s arrays (vsi.md §3) are its levels, one array a level, from 0 to the greatest level coordinate among its tiles (level 0 alone without use_pyramid, and in a file of no tiles). They are keyed by the file’s ets element, the ETS header, a kind of element that may declare several arrays: a level’s index is the level. That element is their one declaration: its pixel_type, channels, colorspace, compression, background and component_order.

  • shape. A tile’s record lists its coordinates: the column’s, the row’s, then the others. Storage order is their reverse, without the level’s: the coordinates after the row’s, the last first, then the rows and the columns; and, where channels is above 1, that many samples last, which a tile interleaves. axes gives the records’ order: of n axes before the samples, n − 1 down to 0, and then n for the samples, which the header counts apart. A coordinate after the row’s has the size dimension_sizes gives it, or 1 where the header’s dimensions do not reach it. Level 0 has the stack’s width and height, which the slide declares in the .vsi file’s tree (its Image boundary), and which Bio-Formats reads. A later level declares no size: it is as large as its tiles reach, as many tile heights as its greatest row coordinate plus one, and as many tile widths as its greatest column coordinate plus one. (Bio-Formats halves the level before, and stops at that extent, vsi.md §4.1: that crop is the profile’s.)

  • item_bits is eight times the bytes of a sample of the header’s pixel_type.

  • The grid is a tile a unit: Each(1) on every axis before the rows, then Each of tile_height, of tile_width and, where there are samples, of channels, under full (a tile at the right or bottom edge is a whole tile). Each record of the directory whose tile lies in its level’s grid is a row: its tiles/<k> element. A tile of level 0 past the stack’s width or height is no unit of the array the slide declares, and has no row (Bio-Formats does not read it either); every tile of a later level lies in its grid.

  • The chain is one for every level of a file, by the header’s compression: empty for 0 (the samples little-endian); jpeg, with no tables, for 2 (JPEG) and for 5 (lossless JPEG, a stream of the same standard), and jpeg2k for 3, where a sample is one or two bytes. Any other is source with format vsi and id the compression: 8 (PNG) and 9 (BMP), which the list has no codec for, and JPEG or JPEG 2000 of larger samples, which those codecs’ entries do not cover. The parser reads no tile, so a stream that holds other samples than the header says is not detected.

  • The grid is sparse: a tile the directory does not list is the background. The fill value is given, as the place of the background’s first sample in the ets element (a sample’s bytes at offset 108), where the tiles are uncompressed and the background’s samples are all the same. Otherwise there is none, the background being in the declaration: an element is one sample, and what a codec’s decoding makes (a JPEG stream’s components, before any color conversion) need not be in the background’s color space.

  • No grid, and no shape, for a level after 0 that holds no tile, below one that holds some: the file declares no extent for it.

  • An IFD’s image (vsi.md §2.3). Every IFD of the .vsi file’s chain that lies in a TIFF region of the tree, and declares a size, is described as a TIFF’s (tiff/stored-arrays.md), by the same code, keyed by its struct (ifds/<j>), with no index: the macro image, a stack’s default sample IFD, and each stack’s coarse thumbnail. The byte order’s declaration is the first two bytes of the file’s header element; a field’s unsigned values are those of the types BYTE, SHORT, LONG and IFD; and source has format vsi. A JPEG strip whose element’s recipe splices in a marker and the tables is that element with a range of all its extent (stored-array.md §4.2).

  • Not described. An IFD that lies in no TIFF region has no element, so its image has no key and is not described yet; an EXIF IFD declares no image.

Zarr v2: stored arrays¶

What the Zarr v2 parser describes as stored arrays (stored-array.md), part of the Zarr v2 profile.

Every array node of the store (zarr2.md §2) whose .zarray the parser reads, as a JSON document whose shape is a list of at most 32 nonnegative integers, is a stored array, whether or not the profile presents it (zarr2.md §3.4): the store declares an array there, and nothing above it. It is keyed by the object of its .zarray, with no index, which a profile finds by the document’s key. A store parser describes its own arrays, each in that object (stored-array.md §6). The same parser reads an OME-Zarr store, whose arrays it describes alike.

  • Declarations. The .zarray object, whole: its dtype, fill_value, filters and compressor say what the elements are; the description reads them only as far as this paragraph says.

  • shape is the document’s shape, reversed for an order of F and two or more axes, whose axes then give the document’s order: Zarr v2 stores each chunk in its array’s order, and its chunk keys name the chunks in the document’s order of the axes.

  • item_bits is eight times the size of an element of dtype as NumPy lays it out, read as a NumPy header’s descr is (as npy/stored-arrays.md says), a structure’s fields given as lists: absent for |O, an object array’s, and for any type of no size NumPy knows.

  • The grid is the document’s chunks, each axis Each of its chunk length, under full: Zarr v2 stores a chunk past an axis’s end whole. A unit is a chunk object of the array that is not empty, its row ranges, the whole object by its key: the key below the array’s path, its indexes canonical and below each axis’s count of chunks, joined by dimension_separator (. when absent or null), 0 for an array of no axes (zarr2.md §3.2). An empty object holds no unit: a reader cannot decode it, and the profile references none.

  • The chain is one: a codec for each filter, in order, then one for the compressor. A codec whose encoding the list names is that entry: zlib, gzip, bz2 (as bzip2), zstd, blosc, lzma of format 1 or none (an .xz stream, as xz) and shuffle, its element_size the filter’s elementsize, a value. Any other is source, with format zarr2, id the codec’s id, and parameters its other members as written, where it has any (numcodecs’ lz4, which frames its block with its length, and the filters that take the array’s elements: delta, fixedscaleoffset, quantize, vlen-utf8 and the rest). An array of no item_bits has a grid only where its chain begins with source, which makes its elements (vlen-utf8, of an object array’s strings).

  • The fill value. The grid is sparse: a store may leave a chunk out. Its fill is absent for a null fill_value, which Zarr v2 reads as none; otherwise it is given, a value, the bytes NumPy makes of it in dtype, in its byte order: a boolean; an integer in the type’s range; a float as a number (rounded to the type, never past its largest), NaN, Infinity or -Infinity; a complex number as a pair of those, or one, its imaginary part 0; a datetime or timedelta as an integer or NaT; a U type’s string as UTF-32, padded with zeros; and base64 of a bytes, void or structured type’s bytes, padded with zeros to the element. A value this does not read as the type’s gives no fill: the .zarray among the declarations holds it.

  • No grid for an array whose .zarray has no order of C or F, no chunks of positive integers as many as its axes, a dimension_separator other than . or /, filters that are not null or a list of objects with an id, or a compressor that is not null or one.

  • Not described: a node whose .zarray is empty, too large to read, not JSON, or has no shape as above. A group declares no array.

Zarr v3: stored arrays¶

What the Zarr v3 parser describes as stored arrays (stored-array.md), part of the Zarr v3 profile.

Every candidate of the store (zarr3.md §2) that is below no other described array, and whose zarr.json the parser reads, as a JSON object whose node_type is array and whose shape is a list of at most 32 nonnegative integers, is a stored array, whether or not the profile presents it (zarr3.md §3.3). Listed, it is keyed by the object of its zarr.json; in the zip form (zarr3.md §7.4) by the entry of its zarr.json (entries/<i>); with no index either way, which a profile finds by the document’s key. A store parser describes its own arrays, each in that object (stored-array.md §6).

  • Declarations. The zarr.json: listed, its object, whole; zipped, its entry’s data element, as the IR holds it: the document’s text, or, deflated, the stream, a derived element; but a document the IR does not hold as a node’s (one below a node the profile leaves out, zarr3.md §3.3) is its bytes as the zip file stores them, of a deflated one the stream as bytes. Its data_type, fill_value and codecs (the bytes codec’s endian) say what the elements are.

  • shape is the document’s shape, in the order its leading transpose codecs give, whose axes then give the document’s order: storage axis j is the document’s axis order[j] after each in turn. Any transpose after another codec is a codec of the chain.

  • item_bits is the bits of a data type of Zarr v3’s core: 8 for bool, int8 and uint8; 16, 32 and 64 for the integers and floats of those sizes; 64 and 128 for complex64 and complex128; N for r<N>. Any other data type (an extension’s, such as string) gives none.

  • The grid is the document’s chunk_grid, under full: regular, each axis Each of its chunk_shape; rectilinear of the inline kind, an axis given as one size Each of it, and an axis given as a list the chunks it needs to cover the axis (each run cut there), Each where they are of one size and a List of them otherwise. A unit is a chunk object of the array that is not empty, by the chunk key encoding (zarr3.md §3.1): listed, its row ranges, the whole object by its key; zipped, its row the data element of its entry, which the zip file stores (method 0).

  • The chain is one: a codec for each of the document’s codecs after the leading transposes, but bytes, which lays the elements out as they are in the order its endian declares. gzip, zstd and blosc, and the numcodecs. codecs whose encodings the list names (as for Zarr v2, zarr2/stored-arrays.md: numcodecs.zlib, numcodecs.gzip, numcodecs.bz2, numcodecs.zstd, numcodecs.blosc, numcodecs.lzma of format 1 or none, and numcodecs.shuffle), are those entries. Any other is source, with format zarr3, id the codec’s name, and parameters its configuration, where it has one: crc32c, vlen-utf8, and sharding_indexed, whose units are its shards. An array of no item_bits has a grid only where its chain begins with source.

  • The fill value. The grid is sparse: a store may leave a chunk out. Its fill is given, a value, the bytes of the document’s fill_value for a core data type: a boolean; an integer in the type’s range; a float as a number (rounded to the type, never past its largest), NaN, Infinity, -Infinity, or 0x and the hex digits of its bits; a complex number as a pair of those; r<N>’s bytes as a list of byte values. An element of more than one byte takes the order of the codec that lays the elements out: the bytes codec after the leading transposes, or the first of a leading sharding_indexed codec’s inner codecs, after their transposes. A value this does not read, a data type outside the core, and an order no codec declares give no fill: the document among the declarations holds it.

  • No grid for an array whose document has another chunk grid or one whose configuration is not the grid’s, a rectilinear axis whose chunks pass its end and are not all of one size (its last chunk is stored whole, which a List does not say), a chunk key encoding other than default and v2 with a separator . or /, storage_transformers, or codecs that are not a nonempty list of codecs each named; and, zipped, an array of which the zip file compresses a chunk: its unit is no bytes of the file as its chain takes them.

  • Not described: a candidate whose zarr.json is empty, too large to read, not JSON, not an array’s, or has no shape as above, or is below a described array. A group declares no array.
