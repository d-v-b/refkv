Hamamatsu NDPI¶

refkv turns an image file into an OME-Zarr dataset by writing a small archive of references to the file’s bytes, without copying the pixels (overview). This page is about Hamamatsu NDPI slides.

Who this is for¶

Hamamatsu NanoZoomer scanners write whole-slide images as .ndpi files, often several gigabytes each, onto the scanner’s PC or a pathology lab’s file server; public examples are on OpenSlide’s test-data server and on Zenodo (for example QuPath’s tutorial slides). Pathologists and image analysts want to view such a slide in an OME-Zarr viewer, or tile it for analysis in Python, without converting every slide first.

NDPI is a TIFF variant that most Zarr tooling cannot read as tiles: each pyramid level is a single JPEG strip, which can be tens of thousands of pixels wide. refkv cuts each strip into chunks of about 1024 × 1024 pixels at the JPEG restart markers the scanner wrote, and makes every chunk a complete JPEG stream out of byte ranges of the file and the strip’s shared header. The 198 MB CMU-1.ndpi became a 5.5 MB archive in about 15 s (at spec/zarrify.md revision 16, before the archive kept every tag on refkv_source).

Newer NanoZoomers (such as the C13210) write JPEG XR instead, in tiles or single strips. Fluorescence slides hold 16-bit grayscale in those streams, though their tags say 8-bit YCbCr. refkv makes each tile or strip a chunk as it is, and takes the data type from the JPEG XR stream header.

What you get¶

One OME-Zarr 0.5 image at the archive root, with one array per level.

  • Axes: c, y, x: uint8 RGB for JPEG levels. For JPEG XR levels, what the streams hold: uint16 with one channel for a fluorescence slide, or uint8 or uint16, gray or RGB. A slide with focal planes has c, z, y, x.

  • Levels: one per magnification, full resolution first; the macro image and slide map are left out.

  • Focal planes: the images of one magnification are the planes of that level, along z, by their focal offset (tag 65424, in nanometers), each with chunks of its own. z has a scale and a translation in micrometers when the offsets are evenly spaced, and otherwise scale 1 and no unit. The offsets are always in the root’s FocalOffsets. Every level of the hierarchy has the same offsets, which is what makes it a valid multiscale. A coarse level with fewer planes, often only one, is left out, so that every plane of the finer levels is kept. More exactly, the offsets kept are those whose levels hold the most pixels. An image left out is listed in the root’s LeftOut with its reason.

  • Chunks: with restart offsets (McuStarts), a level is cut into chunks of whole restart intervals, about 1024 pixels on a side (2048 × 1024 at CMU-1’s level 0, where one interval is 2048 pixels wide). A level without them, usually the smallest, is one chunk. Some older scanners write such a level’s JPEG a row short of its tagged size; its chunk then carries the tagged size in the JPEG’s frame header, which the stream’s last row of 8 × 8 or 16 × 16 blocks already covers, so it decodes at the level’s size. A level whose JPEG would need more blocks is left out (the file is rejected when that is the full-resolution level). A JPEG XR level’s chunks are its tiles (896 × 896 at a C13210’s full resolution), or its single strip.

  • Codecs: transpose, then imagecodecs_jpeg. Each chunk is decoded as one JPEG stream. JPEG XR levels have imagecodecs_jpegxr, after transpose when RGB.

  • Data sources: the parts of each level’s JPEG header (quantization and Huffman tables; restart interval and scan header) are stored once in the archive as data sources, and each chunk’s height and width are a literal. Reading a chunk reads only its own intervals from the file.

  • Scale: from the TIFF resolution tags, in micrometers, when they give a pixel under 25.4 µm.

  • Translation: from the slide-center offsets the scanner records.

  • Channels: omero.channels labels the samples R, G, B, in red, green and blue, each with the window 0 to 255. A single channel is labeled with the slide’s fluorescence filter (TxRed), with its type’s whole range as its window.

  • Metadata: the file’s IR mirror on refkv_source (since revision 26): every IFD, tag, high word, strip and tile, from which the file is rebuilt byte for byte, shown as JSON under refkv_source/tree. The root holds a fluorescence slide’s filter, emission wavelength and exposure time (Fluorescence, Wavelength, ExposureTime), and nothing for a brightfield one of a single focal plane.

Try it¶

example.py zarrifies a public file and plots it with matplotlib. Its dependencies are in its header (PEP 723), so it runs on its own, with refkv from PyPI:

uv run docs/zarrify/ndpi/example.py

OpenSlide’s CMU-1.ndpi (198 MB, CC0), from corpus_tiff.txt:

uv run refkv zarrify https://openslide.cs.cmu.edu/download/openslide-testdata/Hamamatsu/CMU-1.ndpi CMU-1.vzip

{"format": "ndpi", "axes": ["c", "y", "x"], "levels": [[3, 38144, 51200], [3, 9536, 12800], [3, 2384, 3200], [3, 596, 800]], "references": 1093, "codec": "imagecodecs_jpeg", ...}

This took 14 s (openslide.cs.cmu.edu answers each request in about half a second) and wrote a 5.5 MB archive, at revision 16 (overview); the archive now also keeps the file’s tags, so it is larger.

import zarr
import refkv.zarr

g = zarr.open_group(refkv.zarr.open("CMU-1.vzip"), mode="r")
ms = g.attrs["ome"]["multiscales"][0]
for d in ms["datasets"]:
    a = g[d["path"]]
    print(d["path"], a.shape, a.chunks, d["coordinateTransformations"][0]["scale"])
print(ms["datasets"][0]["coordinateTransformations"][1])
img = g["3"][:]
print(img.shape, img.dtype, img.mean(axis=(1, 2)).round(1))

Viewing¶

The Neuroglancer fork (https://github.com/d-v-b/neuroglancer, branch vzip) displays NDPI archives: it decodes imagecodecs_jpeg for uint8, and reads data sources. Its imagecodecs_jpegxr decodes the gray and RGB JPEG XR streams of uint8 and uint16 that JPEG XR levels hold. The Zenodo slide above renders through the live demo. Expect slow panning at full resolution on hosts without HTTP/2 or multi-range support (below).

Supported and not supported¶

Supported:

  • NDPI files of any size, including over 4 GB (64-bit offsets).

  • Every level with a positive magnification, each a single JPEG strip, with or without restart offsets.

  • Slides with several focal planes, such as SR1274-908A.ndpi of OME’s sample images (5.8 GB, 3 planes of 7 levels, 0.1 µm apart by its tags). It zarrifies in 2 to 3 minutes over HTTPS, on a host that closes connections under load, so a read may need retrying.

  • JPEG XR levels, tiled or in a single strip, of 8- or 16-bit gray or RGB, with tile offsets above 4 GiB (their high bytes). For example, the two NanoZoomer C13210 slides of OME’s sample images (in corpus_tiff.txt) zarrify in about 3 s over HTTPS.

Rejected:

  • Levels that are neither one baseline JPEG strip of 8-bit YCbCr nor JPEG XR, levels of both kinds in one slide, or levels that do not get strictly smaller.

  • JPEG XR streams of another pixel format (such as 32-bit float), or of another format in different levels.

  • A strip header without exactly one SOF0 segment and a restart interval, or restart offsets that do not match the strip.

In the browser¶

The browser code (js/) reads Hamamatsu NDPI:

  • Pyramids of single JPEG strips, including in files over 4 GB: each level’s strip is cut at its restart markers into chunks of about 1024 × 1024 pixels, each a JPEG stream rebuilt from byte ranges of the file and the strip’s header, held once in the archive as data sources.

  • Pyramids of JPEG XR tiles or strips, each a chunk.

  • Focal planes, along z. The Neuroglancer fork’s decoders were not checked on chunks with a z axis.

Performance¶

The layout makes reading costly, and nothing in the archive can fix that. A chunk is about 128 pieces of the file, one per row of JPEG blocks (MCUs), and consecutive pieces are a whole strip row apart. The NDPI access study (branch research/ndpi-access) measured what that costs:

  • Over-read or many requests. Today’s readers merge the ranges of a chunk when they are at most their policy’s coalescing gap apart (max_coalesce_gap, 64 KiB by default). Where a strip row is smaller than that (all of CMU-1), every chunk read fetches the full strip width: reading 4 × 4 chunks of CMU-1’s level 0 reads 89 MB for 1.4 MB of chunk data. Where a row is larger (the 6.9 GB Hamamatsu-1, levels 0–3), a chunk costs 128 requests.

  • The floor. Any reader that fetches only the bytes it needs makes at least one request per row of the view (135 to 270 for a 1080-pixel-high view). Chunk shape cannot change that; only multi-range requests, HTTP/2, or reading the bytes between rows can make those requests cheap.

  • What helps. Planning all of a view’s chunk reads together (a batch window), choosing the gap to merge by a cost model of round-trip time and bandwidth, and caching the fetched gaps (which the next pan uses). Over 55 modeled views of CMU-1 at 20 ms and 50 Mbit/s, the study’s prototype takes the total from 41 s to 14 s, and the Rust core’s read planner, used per view, to 18 s (15 s with a cache of the fetched spans). Neither is the default reader yet: the readers of archives merge the reads of chunks read at the same time (spec §6.3), but with a fixed gap, no cost model and no cache. (design/IR_NOTES.md has the table.)

  • The header is free. Since spec/zarrify.md revision 14 the JPEG header is a data source in the archive, so a chunk read is one request (or one merged request) to the file instead of two. Reading all 130 chunks of CMU-1’s level 1 went from 247 requests to 130.

The hosts matter as much as the reader: openslide.cs.cmu.edu takes about 0.5 s per request at 5–7 Mbit/s and supports neither HTTP/2 nor multi-range requests.

How it’s verified¶

js/test/ndpi/verify.py zarrifies the synthetic NDPI files (including inputs to reject) with the browser code, reads every level back through python/src/refkv and zarr-python, compares the pixels with tifffile, and rebuilds each file from its mirror. compare.py checks that the Python and browser outputs are the same, and equivalent to the frozen reference’s outside refkv_source, on those files and on the 3 NDPI slides of corpus_tiff.txt, among them the 6.9 GB Hamamatsu-1.ndpi.

  • Profile: spec/zarrify/ndpi.md, which builds on spec/zarrify/tiff.md

  • Rust core (Python and the browser): rust/refkv-ir/src/tiff.rs (its NDPI variant), rust/refkv-ir/src/ndpi.rs, rust/refkv-ir/src/project/ndpi.rs

  • Frozen reference (revision 25): conformance/zarrify/reference/

  • Fixtures: fixtures/ndpi/
