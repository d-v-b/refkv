NIfTI¶

The Zarr layout of a NIfTI-1 or NIfTI-2 single file (.nii), gzipped or not (.nii.gz), or header-and-image pair (.hdr and .img), and the translation of its header into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the NIfTI profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 06e5809d-4d54-4b72-afd0-6bf61a7b4c85 · Schema: schema.json

Changes: changes/nifti/, one file per change.

Changes before 2026-10-22 are recorded in the revision log of VIRTUALIZE.md, this document’s earlier name, up to revision 29.

This document has two parts (conventions §11.1).

RGB24 and RGBA32 are the color data types: each voxel is its samples (red, green, blue and, for RGBA32, alpha) in consecutive bytes. COMPLEX64 and COMPLEX128 are the complex data types: a voxel is its real part, then its imaginary part, each a binary32 or a binary64 in the file’s byte order. The file’s voxel data is X × Y × Z × T × C × b bytes at offset v, x varying fastest, then y, z, t and k, the index along dimension 5.

4. The image¶

The hierarchy is one image at the root (conventions §4), without a name, with one array at path "0": the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A}, where A has ome (M, below), zarr_conventions and refkv_zarrified (§1).

4.1 The array¶

Stored order. The file holds the voxels as a row-major array V whose axes are, outermost first: c (dimension 5) if n ≥ 5; t if n ≥ 4; z if n ≥ 3; y; x; and, for a color type, c (the samples). Its sizes are those of the array’s axes, and its elements are b bytes, or 1 byte (a sample) for a color type. The axes of V are the array’s, in another order when n ≥ 5 (dimension 5 is stored outside dimension 4) or the data type is a color type (the samples are stored innermost). V is cut as conventions §7 cuts contiguous values, with the chunk limit L = 131072 (2^17) bytes, which gives a chunk shape for V (1 along its axes before the cut axis, whole along those after) and the bytes of each chunk.

Chunks: every chunk is present. For example, a 64 × 64 × 33 × 200 int16 series (n = 4) has slices of 8192 bytes and volumes of 270336, over L, so the cut axis is z: k =   ceil(33 / floor(131072 / 8192)) = 3 chunks of 11 slices each, the chunk shape [1, 11, 64, 64]. A single voxel’s series of 100000 float32 values is cut along t into 4 chunks of 25000.

The array holds the voxels’ raw values. NIfTI’s value scaling is not applied; it is recorded in the source metadata (§5).

4.2 Value scaling¶

For a data type that is not a color type, the scaling applies when scl_slope is finite and not 0; its slope s is scl_slope, and its intercept i is scl_inter if that is finite, else 0. (A color type, or a scl_slope of 0, ±∞ or NaN, has no scaling.) The scaling is nontrivial when s ≠ 1 or i ≠ 0. The scaled value of a voxel is s × raw + i.

Affine. The image’s affine is the sform if sform_code > 0, else the qform if qform_code > 0, else there is none. (A code of 0 or less is unset. A set sform is used even when it is not representable; the qform is then not considered.) OME-NGFF 0.5 places an image only by a scale and a translation per axis, so an affine is used only when it is representable: an axis-aligned map with a positive diagonal.

  • The sform is representable when its 12 values are finite, the six values srow_x[1], srow_x[2], srow_y[0], srow_y[2], srow_z[0] and srow_z[1] are 0, and srow_x[0], srow_y[1] and srow_z[2] are positive. Its diagonal is (srow_x[0], srow_y[1], srow_z[2]) and its offset (srow_x[3], srow_y[3], srow_z[3]).

  • The qform is representable when quatern_b, quatern_c and quatern_d are all 0 (the rotation is the identity), pixdim[0] is not negative (qfac is 1; a NaN pixdim[0] is not negative), pixdim[1], pixdim[2] and pixdim[3] are finite and positive, and qoffset_x, qoffset_y and qoffset_z are finite. Its diagonal is (pixdim[1], pixdim[2], pixdim[3]) and its offset (qoffset_x, qoffset_y, qoffset_z).

An affine that flips or rotates an axis, such as the common radiological sform with a negative srow_x[0], is not representable: the image then has no translation, and its scales come from pixdim. The affine itself is always in the source metadata (§5).

A complex value has no order, so it has no window. The window in raw values is lo = cal_min and hi = cal_max; when the scaling applies (§4.2), lo and hi are instead the smaller and the larger of (cal_min − i) / s and (cal_max − i) / s. One of these is not finite only when the arithmetic overflows binary64, which only NIfTI-2’s binary64 fields can make it do. With more than 64 channels M has no "omero" member: the window is the header’s cal_min and cal_max, and a window per channel would make the root grow with C.

5.2 The IR mirror¶

refkv_source is the file’s IR mirror (conventions §11.3). The IR’s elements (the NIfTI source model) are below; nothing is left out: the header, the extender, the extensions, the voxel data, and every byte between and after them.

The chain. The first extension starts at q = L + 4; while q + 8 ≤ v, the extension at q has esize (i32) at q and ecode (i32) at q + 4, both in the file’s byte order, and the next starts at q + esize. The chain stops, without the extension at q, when esize < 8 or q + esize > v. (The standard’s rule that esize is a multiple of 16 is not checked.)

A file gzipped whole (§7.4) has one element beside the root: voxels, of extent (0, size), the gzip stream, its codec {"encoding": "gzip", "endian": "little" \| "big", "skip": v}. The file’s bytes do not show the header, so NiftiRoot is all that holds it.

A pair’s IR is a store’s (conventions §8.9): these elements lie in its objects, as §7.5 says.

The view (conventions §8.7) shows the header, the extender and each extension of at most 1024 bytes; a text extension’s data is shown as its text up to the first NUL, with the bytes from the NUL on when they are not all NUL.

5.4 Equivalence¶

Hierarchies of one file are compared entry for entry, refkv_source included (conventions §11.4).

Part 2. The profile¶

The NIfTI profile of spec/zarrify.md is §7 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

7. NIfTI profile¶

7.1 Header¶

The input is a NIfTI-1 or NIfTI-2 single file (.nii), which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/nifti.json) chose: bytes 0–3 of H are the 32-bit integer 348 in either byte order and bytes 344–347 are 6E 2B 31 00 (n+1), NIfTI-1; or bytes 0–3 are the 32-bit integer 540 in either byte order and bytes 4–11 are 6E 2B 32 00 0D 0A 1A 0A (n+2), NIfTI-2. Its header is the first L bytes of the file (the convention §2); a file shorter than L bytes is rejected. The file is little-endian if bytes 0–3, read as a little-endian 32-bit integer, are L, and big-endian otherwise (§1.2 has checked that one of the two holds). Every field is read in that byte order, at the offset and with the type that the convention §2 gives it.

Checks. The input is rejected unless all of these hold:

  • Dimensions: n = dim[0] is from 1 to 7, and dim[i] is from 1 to 2^53 − 1 for every 1 ≤ i ≤ n. The values dim[i] for i > n are not checked. If n ≥ 6, dim[6] MUST be 1, and if n = 7, dim[7] MUST be 1 (the layout has no axis for dimensions 6 and 7, so CIFTI-2 files, whose data runs along them, are rejected).

  • Data type: datatype is in the table of the convention §3, and bitpix is 8 times its bytes per voxel b.

  • Color: a color data type has n ≤ 4.

  • Offset: vox_offset is an integer v with L + 4 ≤ v ≤ 2^53 − 1. For NIfTI-1, vox_offset is a binary32 number, which MUST be finite and have an integral value. (The voxel data never starts inside the header or its 4-byte extender. The NIfTI-1 standard’s advice that vox_offset be a multiple of 16 is not checked, and a vox_offset of 0, which some readers take to mean 352, is rejected.)

  • Data size: with X, Y, Z, T, C the sizes of the convention §2, the size of the voxel data, B = X × Y × Z × T × C × b computed exactly, is at most 2^53 − 1, and v + B is at most the file’s size.

Every check applies whatever the other fields hold. No other field is checked: the values the layout uses (the convention §4) only change the output as the convention says, and never reject the input. (A display window whose scaling overflows binary64 is left out, by the convention §4.4, rather than rejected by §1.3; no other number the layout computes can overflow.)

Extensions. The 4 extender bytes at offset L and the extension chain when the first of them is not 0 (the convention §5.3) are read to make the source metadata. They never reject the input, and never change where the voxel data starts: it starts at v whatever they hold. A gzipped file is read as §7.4 says, and a header-and-image pair as §7.5 says.

7.2 Chunks¶

The voxel data is B contiguous bytes at offset v, x varying fastest: the voxel with indices (x, y, z, t, k) along dimensions 1 to 5 starts at byte v + ((((k × T + t) × Z + z) × Y + y) × X + x) × b. It is the array V of the convention §4.1, row-major at offset v.

Every chunk of the convention’s array is present. The chunk with coords (t, k, z, j, i) (each only for the axes present), at 0/c/<coords>, is the chunk of V with those coords along the same axes, and is referenced as conventions §7 references a chunk of contiguous values (with the chunk limit 2^17 bytes): one range of source 0, the chunk’s bytes in the file, followed for an edge chunk by its zero padding. Where conventions §7 makes that padding a literal range, it is instead the range (1, 0, p) of the output’s zero data source (§1.2), p the padding’s bytes: the source holds as many zero bytes as the most padding any reference of the output holds. Where conventions §7 copies the chunk (when its reference, with the padding as a literal range, would not fit in a payload), the chunk is copied, with its padding. The ranges lie within the file (by the data size check). The output’s source table is source 0, followed by the zero data source when a reference is padded; it has no other data source.

NiftiChunk, the chunk of V that starts o bytes into the voxel data and holds l of its bytes, padded with p zero bytes (by conventions §7, for the chunk at (i_0, …, i_{a−1}, q, 0, …, 0), o is the offset it gives the chunk’s bytes, l = m × s_a and p = (c − m) × s_a, which is 0 but for an edge chunk along the cut axis):

7.4 Gzipped files¶

A file gzipped whole is one gzip member (RFC 1952) that holds a NIfTI file, as gzip and dcm2niix write .nii.gz. This profile reads it (spec/zarrify.md §1.2, Choosing the profile: the signature of §7.1 holds of what the file’s first bytes inflate to). S is the stream, those bytes the member holds. Every check of §7.1 is made of S as of a file, but that nothing bounds v + B but the trailer’s check below, and a file is too short when S is. A stream that holds a pair’s header file (§7.5) matches no signature, and is rejected by spec/zarrify.md §1.2.

Reads. The file’s first bytes, doubling from 64 KiB up to 16 MiB until they inflate to as much of S as is wanted, and the last 4 bytes of the file, its trailer’s ISIZE. What is wanted is the first 552 bytes of S, and when the extender’s first byte is not 0, the extension chain, from L + 4 up to 1 MiB of it, or to v. A stream whose start holds less than that is taken to end where it stops. No other byte is inflated.

The trailer. The input is rejected when S ends before L + 4 bytes (the gzip stream ends or breaks in the header's first <L + 4> bytes), or when ISIZE, the stream’s size modulo 2^32, is not (v + B) mod 2^32: the gzip trailer records a stream of <ISIZE> bytes modulo 2^32, not the <v + B> of the header and the voxel data: bytes after the voxel data, or a file of several gzip members, which a chunk cannot decode. A bytes codec refuses a chunk of another length than the array’s, and several members are what bgzip writes: its last trailer records its last block’s size.

The array is V as §4.1 says, in one chunk of the whole array: its chunk shape is the array’s shape, and its codecs are those of §4.1, then:

The cost is reads. Nothing is copied and every value is exact, but the chunk is coarse: a gzip stream has no index, so a reader inflates the whole stream to read any value, even one slice, holds the whole array in memory to do so, and reads it with no concurrency. Zarrifying stays cheap, since only the start of the stream is inflated. A reader that needs random access to a large volume should decompress the file once and zarrify that, which gives chunks of at most 128 KiB.

7.5 Header-and-image pairs¶

A NIfTI file may be two files: a header file .hdr, whose header has the magic ni1 or ni2, and an image file .img beside it, which holds the voxels. The input is the header file. An .img file has no signature, so it cannot be named. A file with the magic n+1 or n+2 is a single file whatever its name.

Signature. This profile’s signature (§7.1) also holds of a file with bytes 0–3 the 32-bit integer 348 in either byte order and bytes 344–347 6E 69 31 00 (ni1), NIfTI-1; or bytes 0–3 the integer 540 and bytes 4–11 6E 69 32 00 0D 0A 1A 0A (ni2), NIfTI-2. A header without either magic, such as ANALYZE 7.5’s, matches no signature and is rejected.

Siblings (spec/zarrify.md §1.9):

7.6 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the input: what it found of the file’s known structures, in NIfTI’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7). Its JSON Schema is nifti/description.json. It holds none of an output’s decisions: the data type of a datatype code (§3), the axes and their order, the scaling, the scales, units, affine and position (§4), the chunks (§7.2) and the root’s source metadata (§5) are the projection’s.

It is a JSON object with these members:

member

value

version

1 or 2, as the signature selects it (§7.1)

byte_order

little or big: the order in which the header’s first field is its length

header

every field of the header of the version, as the root’s header gives it (§5.1)

extender

the 4 bytes after the header, as integers; null for a pair’s header file that ends at its header (§7.5)

voxels

the voxel data’s range: offset, v, and bytes, its size B (§7.1); of a gzipped file (§7.4), in the stream; of a pair, in the image file

gzip

of a gzipped file only: skip, v; head, the header’s bytes in the stream, as lowercase hexadecimal; and extensions, each extension of the chain the stream’s start holds, its esize and ecode, and the data of a text code’s of at most 1024 bytes as a text value (conventions §6)

elements

the ids of its IR elements (§5.3) by name: voxels, and of a file that is not gzipped, header, extender (when there is one) and extensions, the chain’s in its order

header_key, data_key

of a pair only: the header file’s and the image file’s keys

The voxels’ stored description is keyed by header, or of a gzipped file by voxels, the stream (spec/stored-array.md §7). The projection reads the header from the IR’s header value, or a gzipped file’s from gzip.head, and makes every decision of §3, §4, §5 and §7.2 from it. A pair’s store run also reads the edge chunks the projection copies (§7.5), which it returns beside the description.

The parser still makes one decision of the output: the voxels element’s form names the data type of §3 (§5.3).
