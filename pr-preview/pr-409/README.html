refkv: reference-aware key-value storage¶

refkv presents image files and chunked array stores in about two dozen formats as Zarr hierarchies whose chunks are references to the original bytes, without copying them. It zarrifies a TIFF slide, an ND2 or CZI file, an HDF5 file or an N5 store from Python or in the browser, and saves the result as one small archive.

[!CAUTION] This project is almost entirely vibe-coded. It is intended for personal use, and as a proof of concept. If you need virtual Zarr datasets, use Icechunk or kerchunk. refkv is released on PyPI as 0.x versions, with no support; until 1.0 the specification and the zarrified layouts can change without regard for existing archives.

The current goal of this package is capability demonstration, not code quality. Do not expect the internals to express anything except the minimum needed to satisfy the design requirements. If this package demonstrates real utility, then the design practice will transition from pure velocity to a slower, more methodical pace.

If this package looks like it could be useful to you, let us know with a GitHub star or an issue expressing features you use / need. That’s an actionable signal we can use to re-orient development.

Zarrify a file¶

pip install "refkv[images]"   # or refkv[media] for MP3, FLAC and MP4

import zarr
import refkv.zarr
from refkv.zarrify import zarrify

store = zarrify("https://openslide.cs.cmu.edu/download/openslide-testdata/Aperio/CMU-1-Small-Region.svs")
image = zarr.open_group(refkv.zarr.store(store), mode="r")["0"]  # the full-resolution level
image.shape                   # (3, 2967, 2220)
tile = image[:, :512, :512]   # reads and decodes only the JPEG tiles it covers
store.save_vzip("slide.vzip") # the hierarchy as one vzip archive, about 30 KB

zarrify reads the file’s structure (its headers and indexes), not its data. A Rust core does the work, natively from Python and as WebAssembly in the browser. docs/zarrify/ has a page per format: what you get, how to run it, and what is not supported.

Try the live demo: paste the URL of a remote image file or store, and the browser zarrifies it and shows it in Neuroglancer (or, for a Sentinel-2 product, on a map).

Virtual datasets¶

For netCDF, HDF5 and the other files VirtualiZarr reads, refkv.ReferenceStore.from_virtualizarr(vds) turns a virtual dataset into a store that xarray opens, through refkv.zarr with the zarr extra (docs/virtual-datasets.md has a runnable example).

The model¶

Underneath, the repository defines a value type, and two implementations of it, at different levels of abstraction:

refkv is a reference value type for key-value storage: a value is either bytes or a reference to byte ranges of other objects, such as the chunks inside HDF5, netCDF or TIFF files. The model is specified without a backend (spec/refkv.md), so any key-value store that can tell bytes from references can hold such a store.

vzip is refkv’s binding to a plain ZIP archive (spec/bindings/vzip.md). A vzip archive holds regular files and refkv references, which can point to byte ranges in external objects, and a vzip reader resolves those references before returning bytes. Every zarrified hierarchy above is saved as one.

phkv is a second implementation of refkv, in draft (spec/bindings/phkv.md): a refkv store kept in one file with a perfect hash of its keys, so that a lookup reads a few ranges of it however many keys it holds. It can also sit inside a vzip archive, which keeps the archive readable by ZIP tools.

The sizes and request counts are the reference writers’ and readers’ on the same store (spec §16.3, benchmarks). Write vzip for the widest compatibility, and when ZIP tools or vzip-only readers will read it. Write phkv for the smallest file and the fewest requests per lookup, when every reader knows phkv; the hybrid keeps both kinds of reader working, at the largest size.

The code in this repository exercises the model by writing vzip archives, and phkv stores from Python and Rust.

Documentation¶

docs/ is for users: installing, the live demos, and a page per format. python/README.md lists the extras and the platforms with wheels, and js/README.md covers the browser code.

The documentation site, https://d-v-b.github.io/refkv/, renders docs/ and spec/ with the pages that list every format, which are made from the profile registry when the site is built (just docs, docs-site/conf.py).

Layout¶

Specifications, documentation and design notes are organized by component; code is organized by language.

directory

holds

spec/

the specifications: the reference value type (refkv.md), its ZIP binding (bindings/vzip.md), and the draft perfect-hash binding (bindings/phkv.md), zarrification (zarrify.md), the conventions every zarrified hierarchy shares (conventions.md), how the IR describes the arrays a source stores (stored-array.md), one document per format with its Zarr convention and its profile (zarrify/, each <format>.md beside <format>/schema.json), the wire schema (proto/), and earlier revisions (history/)

docs/

user documentation: virtual datasets with xarray, combining stores, a stack of TIFF files, and a page per format in docs/zarrify/

design/

design notes and studies: ARCHITECTURE.md, FINDINGS.md, PITCH.md, COMPARISON.md, THIRD_PARTY_READERS.md (third-party readers as format parsers), the IR notes (IR_NOTES.md), the conformance rounds’ notes and proposals, and the experiment scripts the notes cite

python/

the Python distribution refkv (pyproject.toml): the package (python/src/refkv, with the ZIP binding in refkv.vzip), its tests (python/tests) and its release process; the root pyproject.toml is a uv workspace over it, with the repository’s development tools

js/

the TypeScript library (js/src) and its Node tests

demo/

the browser demo, which just js::build bundles with the library and demo/pages.sh publishes to https://d-v-b.github.io/refkv-demo/

rust/refkv-ir

the Rust core: the format parsers, the IR, the projections and the read planner, built for Python (through the bindings in rust/refkv-python) and for the browser (wasm32)

rust/refkv-python

the core’s Python bindings, which the refkv wheel builds in as the module refkv._core (manifest-path in python/pyproject.toml)

fixtures/

the synthetic test inputs every implementation shares, one directory per format, and their generators (fixtures/generators/)

conformance/

the conformance harnesses: vzip/ for the vzip binding, phkv/ for the draft phkv binding (just conformance-phkv), zarrify/ for zarrification (with the frozen reference implementations, Python and TypeScript), and the agent-written independent implementations (impls/)

just lists the recipes: just test (Python), just python::build (a wheel), just js::test (Node), just ir-test (Rust), just compare and just compare-mutants (the zarrifiers against the frozen reference), just conformance (the vzip binding’s independent implementations).
