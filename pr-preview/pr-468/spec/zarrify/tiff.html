TIFF¶

The Zarr layout of a TIFF or BigTIFF file, including OME-TIFF and JPEG-tiled slides such as Aperio SVS, and the translation of its tags into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store is the TIFF profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 48e9ac4e-1156-4a62-955e-20467d9c2700 · Schema: schema.json

Changes: changes/tiff/, one file per change.

Changes before 2026-10-22 are recorded in the revision log of VIRTUALIZE.md, this document’s earlier name, up to revision 29.

This document has two parts (conventions §11.1).

Part 1. The convention¶

This convention gives a layout only to the files that meet its requirements. Where it says that “the input is rejected”, or that something MUST hold, a file that fails has no layout under this convention, and the profile rejects it.

2. The source¶

The file is a TIFF (magic 42) or BigTIFF (magic 43), in either byte order. Its IFDs are the image file directories of its main chain, which starts at the header’s first-IFD offset and ends at a next-IFD offset of 0, and, for each of them, its SubIFDs: the IFDs whose offsets its SubIFDs tag (330) lists, in order, and theirs in turn. Main-chain IFDs are at depth 0 and the SubIFDs of an IFD at depth d at depth d + 1; the SubIFDs of an IFD at depth 4 are not read. (A SubIFD’s next IFD is not part of the source.) The main chain MUST have at least one IFD. IFD 0 is the first IFD of the main chain. Of duplicate tags in an IFD, the first is used.

Format. An IFD’s format is the tuple (BitsPerSample, SamplesPerPixel, SampleFormat, PlanarConfiguration, Compression, Predictor). Computing it requires:

  • BitsPerSample, when the tag is present with at least one value, all equal and at least 1;

  • SamplesPerPixel at least 1;

  • SampleFormat values all equal (when the tag is present it MUST have at least one value).

When SamplesPerPixel is 1, PlanarConfiguration is taken as 1. Otherwise it MUST be 1 or 2. When Compression is 7, the format also includes PhotometricInterpretation (absent counts as a value of its own). Counts of BitsPerSample and SampleFormat are not otherwise checked. If any of these fails, the input is rejected. Formats are computed for IFD 0 (always, even when it is not a plane), for every IFD that becomes a plane or a level (§4.1, §4.2), and for every candidate of the level scan (§4.2).

Size. An IFD that becomes a plane or a level, or is a candidate of the level scan, MUST have ImageWidth and ImageLength, and both MUST be at least

  1. An IFD is tiled if it has TileWidth and TileLength, the size of a tile. Its tile tables are its TileOffsets and TileByteCounts, or, in an IFD with neither, its StripOffsets and StripByteCounts: some writers list a tiled image’s tiles under the strips’ tags, and libtiff and tifffile read them there. A tiled one (§4.2) MUST have both of its tile tables (so one with TileOffsets or TileByteCounts and not the other is rejected, whatever StripOffsets and StripByteCounts it has), with TileWidth and TileLength at least 1. An IFD that is not tiled is in strips, whatever TileOffsets and TileByteCounts it has, and MUST have StripOffsets and StripByteCounts and a RowsPerStrip of at least 1 when it becomes a plane or a level (§4.5).

3. OME-XML¶

If IFD 0’s ImageDescription has field type ASCII (2), let D be its bytes up to the first NUL. If D is valid UTF-8 and the tag scan below finds a start tag named OME in it, D is the OME-XML, and X is its text.

Tag scan. X is read as a sequence of tags, not as a validated XML document, in one left-to-right scan: at each <, a skipped section (1) if one starts there, else a tag (2) if the grammar matches, else text; the scan continues after whichever was found. So a <!-- inside a tag’s attribute value is part of the value, not a comment.

  1. Skipped sections: scanning from the start, the first of these to begin at each point is skipped, up to and including its end:

    the next -->

    CDATA section

    the next ]]>

    the next ?>

    the next >

    The search for the end starts after the whole start marker (so <!--> does not end itself). A section without an end runs to the end of X.

  2. Tags: outside skipped sections, a tag is a match of this grammar starting at a < (whitespace and digits as in spec/zarrify.md §1.3):

    tag    = "<" ["/"] qname *(ws1 attr) [ws] ["/"] ">"
qname  = [name ":"] name
name   = 1*(ASCII letter / digit / "_" / "." / "-")
attr   = aname [ws] "=" [ws] ( DQUOTE *(not DQUOTE) DQUOTE / "'" *(not "'") "'" )
aname  = 1*(any character except whitespace, "=", "/", ">", DQUOTE, "'", "<")
ws     = 1*whitespace ; ws1 is the same

    A < where the grammar does not match is text. Scanning continues after the end of each tag.

  3. A tag is a start tag if it does not begin with </, and an end tag if it does. It is self-closing if it ends with />. Its name is the last name of its qname, without the namespace prefix. Attribute names are compared exactly. Of duplicate attribute names in a tag, the first is used.

  4. Attribute values have references decoded: the five XML predefined entities (&lt; &gt; &amp; &quot; &apos;), and numeric character references (&# digits ; or &#x hex digits ;) that denote a Unicode scalar value other than U+0000. Anything else, including other entity references and references to U+0000, surrogates or values above U+10FFFF, is left as it is. Whitespace is not normalized.

4. The image¶

4.1 Planes¶

Let spp be IFD 0’s SamplesPerPixel. Without OME-XML there is one plane, IFD 0, except that IFD 0 of EER (Compression 65000, 65001 or 65002) has one plane per main-chain IFD of its width, length, tiling and format, in chain order, along t (SizeT is their count): an EER file is a stack of frames; and except that an ImageJ hyperstack has the planes its description gives, below. With OME-XML:

  • SizeZ and SizeT default to 1; SizeC defaults to spp.

  • If spp > 1: SizeC 1 is read as spp; any other SizeC ≠ spp is rejected (several RGB channels are not supported). Channels are then the samples, and there is one plane per (z, t).

  • If spp = 1, there is one plane per (z, c, t).

Let Cp be 1 if spp > 1, else SizeC. Planes have positions (z, c, t) with z < SizeZ, c < Cp, t < SizeT; the plane count is SizeZ × Cp × SizeT, which MUST be at most 100000. Planes are mapped to main-chain IFDs (by their index in the main chain, IFD 0 being index 0) by the TiffData elements, in document order (with one implicit TiffData without attributes if there are none):

  • Multi-file datasets: a TiffData with a UUID names the file identified by the UUID’s FileName if it has one, else by its text (two identifiers are the same file only if they are equal strings). If the TiffData elements name more than one distinct file, their planes lie in those files (§7.4). Otherwise UUIDs are ignored, so a file that names itself is accepted, and a TiffData without a UUID names no file.

  • Coverage: a TiffData starts at position (FirstZ, FirstC, FirstT) (each default 0, and each MUST be less than SizeZ, Cp, SizeT respectively, else the input is rejected) and IFD index IFD (default 0). It covers PlaneCount planes. PlaneCount defaults to the plane count when it is the only TiffData and has no IFD attribute, and to 1 otherwise.

  • Stepping: successive planes step through positions in DimensionOrder (default XYZCT; the letters after XY are fastest first, with sizes SizeZ, Cp, SizeT) and through consecutive IFD indices. Planes past the last position are ignored: with P the plane count and L the start position’s index in that order (`L = a + A × (b

    • B × c)for the letters afterXYwith positionsa, b, cand sizesA, B), a TiffDatacoversmin(PlaneCount, P − L)` planes.

  • Cost: the planes covered, summed over all TiffData elements, MUST be at most 4 × P + 1000, else the input is rejected (so that a short document cannot step through many more planes than the image has).

  • A plane mapped twice takes the later mapping.

After all TiffData elements are applied, every plane MUST be mapped to an existing main-chain IFD, else the input is rejected. (An index past the chain that a later mapping replaces is not an error.)

ImageJ hyperstacks. Without OME-XML, an IFD 0 whose ImageDescription (§2) starts with ImageJ= and has a line images=N, N > 1, makes the file an ImageJ hyperstack of N planes (a Micro-Manager stack file, §7.5, is read as one whatever its description says). The description’s lines frames=, channels= and slices= (each an integer; 1 without its line, but slices is N when none of the three has a line) are SizeT, SizeC and SizeZ, and MUST multiply to N; with spp > 1 the channels are the samples, so channels MUST be 1 (an RGB stack ImageJ writes has no channels line). N MUST be at most 100000. ImageJ orders its planes channels first, then slices, then frames: the plane at (z, c, t) is ImageJ’s plane p = (t × SizeZ + z) × Cp + c. The planes lie in one of two layouts, and any other main-chain length is rejected:

  • One IFD a plane: the main chain has N IFDs, and plane p is main-chain IFD p (each MUST have IFD 0’s size, tiling and format, §4.2).

  • One IFD: the main chain has one IFD, and the planes after the first follow its strips, with no IFD of their own, as ImageJ writes a stack of more than 4 GB (and tifffile one with truncate). IFD 0 MUST have no SubIFDs, be in strips with Compression 1, and its strips MUST each hold exactly their rows (rows × B bytes, §4.5) and each start where the one before it ends. With P the bytes of its strips in all, strip k of plane p is the StripByteCounts[k] bytes at StripOffsets[k] + p × P, and StripOffsets[0] + N × P MUST be at most the file’s size. Every plane has IFD 0’s strips, joined and padded as IFD 0’s are (§4.5).

4.2 Pyramid levels¶

  • If IFD 0 has SubIFDs, there are 1 + s levels, where s is IFD 0’s SubIFD count: level 0 is the planes’ IFDs, and level k ≥ 1 is, for every plane, its IFD’s k-th SubIFD. A plane IFD with fewer than s SubIFDs rejects the input.

  • Otherwise level 0 is the planes. Without OME-XML, the later main-chain IFDs are scanned in order. An IFD that is tiled is a candidate: its format and size are checked as §2 says (a failure rejects the input). A candidate becomes the next level if it has IFD 0’s format and is strictly smaller in both width and length than the last level. Other IFDs, and other candidates, are skipped. This finds the pyramids of Aperio SVS files, whose stripped thumbnails, labels and macros are skipped. (A tiled image of the right format that is not part of the pyramid would be taken as a level.)

Within a level, all planes MUST have the same width, length, tiling (tiled with the same tile size, or in strips with the same rows per strip, §4.5) and format. Every image of every level MUST have IFD 0’s format. (The level scan above takes tiled images only; planes and SubIFD levels may be in strips.) Without OME-XML and SubIFDs, when IFD 0 is in strips, a later main-chain IFD that is not a level and has IFD 0’s width, length and format (a stack of pages without an ImageJ description, §4.1) rejects the input: its planes have no mapping, and the image would show only the first. (A later IFD whose format cannot be computed, or whose values do not load, does not have IFD 0’s. A tiled IFD 0 keeps the rule it had before images in strips had a layout: its later pages of its size are not read as planes.)

Packed samples. Packed samples have {"name": "imagecodecs_packints", "configuration": {"bitspersample": BitsPerSample, "runlen": n}} in the place of bytes, n the samples of a chunk’s row: its width, times SamplesPerPixel when interleaved. Their bits run most significant first and a row starts on a whole byte, in either byte order (TIFF 6.0 and libtiff, for whichever byte order the file has), so the codec has no endian, and the chunk’s bytes are ceil(n × BitsPerSample / 8) bytes a row. A sample of 1 bit decodes to 0 or 1, what it holds, PhotometricInterpretation (0, WhiteIsZero, or 1, BlackIsZero) telling which is white. They MUST be uncompressed, LZW, Deflate, zstd or PackBits (and CCITT and EER, which are their own codecs below), with Predictor 1, which libtiff does not apply to them. refkv.tiff_lzw then takes a chunk’s size in samples for the size it decodes up to, which is more than the stream holds, so it reads the whole stream.

PackBits, TIFF 6.0 §9’s run-length coding (imagecodecs_packbits, not the zarr-extensions codec packbits, which packs bits), is one stream a tile or strip, with no predictor.

CCITT. Compression 4 is one T.6 stream a tile or strip, which requires BitsPerSample 1 and SamplesPerPixel 1. It decodes to a sample of 1 for a coded black run and 0 for a white one, as an uncompressed bilevel image holds them. Compression 2 and 3 are rejected.

EER, Electron Event Representation, requires BitsPerSample 1 and SamplesPerPixel 1, of s, a and b bits: 8, 2, 2 for Compression 65000; 7, 2, 2 for 65001; and tags 65007, 65008 and 65009 for 65002. [h, w] is the level’s chunk’s rows and columns, one shape for every chunk, so a level in strips whose last is short is rejected, and every IFD of every level MUST have IFD 0’s bits. It decodes a frame’s events to one bit a pixel, and has no super-resolution (superres is left out, as 0).

LERC is one LERC stream a tile or strip, which holds its own type and shape; a stream in Deflate or zstd, as LercParameters (tag 50674) records, is one the codec finds without being told. Pixels a stream’s mask leaves out decode to the codec’s values, as tifffile reads them. LERC has no 64-bit integers, which are rejected. LZMA is an xz stream of the bytes. WebP requires BitsPerSample 8, SampleFormat 1, PlanarConfiguration 1, and SamplesPerPixel 3 or 4; h is true for 4, since a WebP stream may leave out an alpha channel that is all opaque, and would otherwise decode to 3 samples, and false for 3. JPEG XL requires SampleFormat 1 with BitsPerSample 8 or 16, or SampleFormat 3 with BitsPerSample 32. Otherwise the input is rejected.

{"name": "refkv.tiff_lzw"}, refkv’s own codec (imagecodecs-zarr’s imagecodecs_lzw reads the whole stream, which the next sentences rule out), has no configuration: each chunk is one TIFF LZW stream (TIFF 6.0 §13: codes packed most significant bit first, with the “early change” every TIFF writer uses), which decodes to the chunk’s bytes as bytes reads them. A decoder reads the stream until its output reaches the chunk’s size and no further, as TIFF readers decode a tile into a buffer of its size: some scanners write a tile’s end-of-information code one bit too narrow (a reader at the right width sees code 514, one more table entry, or an invalid code), so a decoder that reads the whole stream overruns the tile by a few bytes or fails; a chunk whose stream ends before the chunk’s size is malformed.

Predictor. Predictor 2, horizontal differencing (TIFF 6.0 §14), with an integer data type (SampleFormat 1 or 2) puts {"name": "imagecodecs_delta", "configuration": {"axis": a, "dist": 1}} (conventions §3) before bytes, a being the index of x in stored order: n − 1 for an array of n axes, or n − 2 when transpose comes first. Within each row of a tile or strip, the writer stored each sample less the same sample of the pixel before it, in the data type’s arithmetic (modulo 2^BitsPerSample), so that the decompressed bytes are differences, and the codec sums them back along x, each sample apart. GDAL, libtiff and tifffile write it with LZW, Deflate, zstd and LZMA.

Predictor 3, the floating-point predictor (Adobe’s TIFF Technical Note 3), with a float data type (SampleFormat 3) puts {"name": "imagecodecs_floatpred", "configuration": {"axis": a, "dist": 1}} (conventions §3) in place of bytes, a being the index of x in stored order, as above. Within each row of a tile or strip, the writer gathered the most significant bytes of the row’s values, then their next bytes and so on, and stored each byte less the same byte of the sample before it along x, modulo 256. These bytes do not depend on the file’s byte order, so the codec has no endian. Interleaved samples have dist 1 too: the codec takes the axis after a for a pixel’s samples and differences each with the same sample of the pixel before. (A dist of the sample count is not what they need, and imagecodecs refuses one of 3.) GDAL, libtiff and tifffile write it with LZW, Deflate, zstd and LZMA.

Any other Predictor rejects the input, but for JPEG 2000, whose streams do not use it, and so do:

  • Predictor 2 with a float data type, whose values a writer differences as integers of their bits (libtiff does), which no codec of conventions §3 sums back, and Predictor 3 with an integer data type, which libtiff does not write;

  • Predictor 2 or 3 with Compression 1, which libtiff stores without differencing (it applies a predictor only inside a compression’s coder) and tifffile does not write, so that readers disagree on what the bytes hold;

  • Predictor 2 or 3 with JPEG (Compression 7), whose stream does not use it.

The codecs read the bytes of a tile as they are, filled from each byte’s most significant bit (FillOrder 1), and decode samples at full resolution. So, for every IFD that is a plane or a level:

  • when Compression is 1, 4, 5, 8, 32773, 32946, 34887, 34925, 50000, 50001, 50002, 65000, 65001 or 65002, FillOrder MUST be 1;

  • when PhotometricInterpretation is 6 (YCbCr) and Compression is neither 7 nor JPEG 2000 (whose streams hold their own sampling), YCbCrSubsampling MUST be present and exactly [1, 1] (absent, it is TIFF 6.0’s default [2, 2]).

Otherwise the input is rejected. bytes has endian from the TIFF’s byte order (when the data type is larger than 1 byte). When spp > 1 and PlanarConfiguration is 1 (interleaved), transpose comes first, for every compression including JPEG 2000.

A chunk is present when its byte count is more than 0, and absent (the fill value) otherwise. Its bytes are the tile’s or strip’s (or strips’), encoded as the codecs say (a short last chunk’s, with its padding, §4.5); for JPEG, a JPEG tile is made a complete stream with the IFD’s JPEGTables and an explicit color transform for its PhotometricInterpretation (2: RGB as stored; 6: YCbCr). For JPEG, JPEGTables, when present, MUST be at least 4 bytes long, start with FF D8 and end with FF D9, and every present tile or strip MUST be more than 2 bytes long. Its reference is a TiffChunk (§7.3). Of a level that shards its strips (§4.5), these chunks are the array’s inner chunks.

4.5 Strips¶

An IFD in strips (§2) that becomes a plane or a level has its rows per strip R = min(RowsPerStrip, ImageLength), and S = ceil(ImageLength / R) strips per sample plane, the last holding the remaining rows. Let B be the bytes of one row of a strip: ceil(ImageWidth × BitsPerSample / 8), with ImageWidth times SamplesPerPixel when the samples are interleaved. A level in strips has chunks of R′ rows by the level’s width (§4.4), m strips each, which are R′ = R and m = 1 unless it joins them.

Joined strips. An uncompressed strip is its rows’ bytes, nothing around them, so consecutive strips are the rows of a larger chunk without decoding anything. Let M = min(floor(2^20 / (R × B)), 2^10), the most strips a chunk holds. A level joins its strips when Compression is 1, S and M are at least 2, and every strip of every sample plane of every IFD of the level holds exactly its rows, rows × B bytes. Then

  • m = ceil(S / ceil(S / M)), the fewest chunks those limits allow, as even as whole strips allow;

  • R′ = min(m × R, ImageLength).

The strips of a chunk need not meet in the file (§7.3). The limit of 2^20 bytes is the one contiguous source values have (conventions §7), and it bounds what a partial read costs, since a reader of a chunk reads all of it: one row of a plane of n chunks costs 1 / n of the plane, at most 2^20 bytes. The limit of 2^10 strips keeps a chunk whose strips are all apart within the reads a reader allows a value by default (refkv §6.7, rule 5).

Shards of compressed strips. A strip of LZW, Deflate or zstd is a stream of its own, which the codecs of §4.3 decode one at a time, so it stays one chunk, and its level gathers those chunks in shards instead (zarrify §2.1). Let M = min(floor(2^30 / (R × B)), 2^10), the most strips a shard holds. A level shards its strips when Compression is 5, 8, 32946 or 50000, S and M are at least 2, and, of Deflate and zstd, ImageLength is a multiple of R. Its array is then a ShardedArray of the array this document describes:

  • the inner chunks are that array’s chunks, of R rows by the level’s width, one strip each, and the inner codecs its codecs;

  • a shard holds K = ceil(S / ceil(S / M)) inner chunks along y, the fewest shards those limits allow, as even as whole strips allow, and 1 along every other axis, so that each sample plane of each plane has its own shards. The shard’s rows, K × R, may be more than ImageLength.

Each shard’s index is written from StripOffsets and StripByteCounts, with no strip read (but a short LZW strip’s, below), and a strip with no bytes is an inner chunk the shard does not hold. The limits are not the joined strips’, because they answer another question: a reader of a few rows of a shard reads only those strips, so 2^20 bytes would bound nothing a partial read costs. The limit of 2^10 strips is the one a joined chunk has, and also keeps a shard’s reference within the payload limit (§1.2) however far apart its strips are, at 16 bytes of index and at most 20 bytes of range a strip. The limit of 2^30 bytes bounds what a reader that reads a whole shard as one value holds at once. A level of one strip has nothing to gather.

Whether a reader makes fewer requests depends on the reader, which zarrify §2.1 describes. A strip of JPEG, JPEG 2000, LERC, LZMA, WebP, JPEG XL, PackBits, CCITT or EER keeps a chunk a strip, and so does a level of any compression but LZW whose last strip is short and not uncompressed, as below. So has a level of uncompressed strips with a strip that does not hold exactly its rows: a strip with no bytes, which is the fill value, or with more or fewer bytes than its rows, whose rows the concatenation would misplace.

When its last chunk is short (the level has more than one chunk and ImageLength is not a multiple of R′), it is padded to R′ rows, so that every chunk decodes to the chunk shape (a Zarr reader then needs no irregular chunk grid): the bytes of its strips are followed by the bytes that make the rows missing zero, which depend on the compression (rows being the chunk’s rows, and of a level that does not join, the strip’s):

5.3 Values¶

An entry’s value is an element when it lies within the file. Part 2. The profile¶

The TIFF profile of spec/zarrify.md is §7 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

7. TIFF profile¶

Signature (spec/zarrify.md §1.2, tested at the precedence of profiles/tiff.json): bytes 0–3 of H are 49 49 2A 00, 4D 4D 00 2A, 49 49 2B 00 or 4D 4D 00 2B. A file this signature chose is read by the NDPI profile instead when it passes that profile’s detection test (ndpi.md §7), and by the QPTIFF profile when it passes that one’s (qptiff.md §7); a VSI file, whose signature is tested first, is read by the VSI profile (vsi.md §9).

7.1 Reading¶

The input is a TIFF (magic 42) or BigTIFF (magic 43, offset size 8 and reserved word 0), in either byte order. An NDPI file is read with the changes given in the NDPI profile (ndpi.md §7, ndpi.md).

  • IFDs: the zarrifier reads the chain of image file directories (IFDs) from the header (the main chain, which ends at a next-IFD offset of 0; it MUST have at least one IFD). Then, for every main-chain IFD in order, it reads the IFDs whose offsets that IFD’s SubIFDs tag (330) lists, in order, and after them, each of their SubIFDs in turn (depth first), down to depth 4: the SubIFDs of a SubIFD at depth 4 (main-chain IFDs being at depth 0) are not read. A SubIFD’s next-IFD offset field MUST lie within the file but its value is not used or checked. (A main-chain next-IFD offset is an offset, so it MUST be at most 2^53 − 1.) A SubIFDs tag with no values means no SubIFDs.

  • Limits: every IFD offset read (main chain or SubIFD) MUST be at least 8 (16 for BigTIFF) and MUST differ from every other IFD offset read, so a cycle, or a SubIFD shared by two IFDs, rejects the input. At most 100000 IFDs are read; reading the 100001st rejects the input. (The IFDs that other pointer tags lead to are read for the source metadata only, and never reject the input: the convention §5.)

  • Tags: the tags that the convention’s layout uses (the table of the convention §2) are checked below. Every other tag is read only for the source metadata (the convention §5), which never rejects the input: its field type and value are not checked. Of duplicate tags in an IFD, the first is used and the others are not checked (the source metadata keeps them).

Checks on every IFD read. For every tag of the convention’s table present in an IFD read (whether or not that IFD is used), without reading its value:

  • Field type: each tag’s field type is one of these. Any other type rejects.

    field types

    ImageDescription

    may be any field type that TIFF 6.0 or BigTIFF defines (1–12, 16–18), or 13 (IFD)

    JPEGTables

    MUST be BYTE (1) or UNDEFINED (7); its value is its bytes

    XResolution, YResolution

    MUST be RATIONAL (5)

    every other tag

    MUST be an unsigned integer type: BYTE (1), SHORT (3), LONG (4), IFD (13), LONG8 (16) or IFD8 (18), in either TIFF variant

  • Count: a scalar tag MUST have at least one value. An array tag may have any count; BitsPerSample and SampleFormat with no values reject when they are used.

  • Place: its value MUST lie within the file (a value of more than 4 bytes, 8 for BigTIFF: its offset plus its size is at most the file’s size).

Values read. A tag’s values are read only where the layout uses them (an IFD’s tables are often shared by many IFDs, and most IFDs are not used): of a scalar tag, its first value (the only one used); of an array tag, every value; of ImageDescription and JPEGTables, their bytes. They are read for:

Sampled chunks. After the IFDs, the zarrifier reads the bytes of each sampled chunk of the omero windows (the convention §4.4), the source ranges its reference names, and decodes them. These reads and their decoding never reject the input: a chunk that does not decode is not sampled.

7.2 Rejection¶

The input is rejected when a check of §7.1 fails, and when the convention gives it no layout: wherever the convention says that the input is rejected, or that something MUST hold and it does not (the convention §2–§4).

7.3 Chunks¶

Every chunk that the convention says is present (the convention §4.4) is the entry <level>/c/<coords>, but for a level that shards its strips (the convention §4.5), whose entries are its shards (zarrify §2.1), each a Shard whose inner chunks’ ranges are their references here. Tile (strip) k, with TileByteCounts (StripByteCounts) n > 0, has the single range (0, TileOffsets[k], n) (StripOffsets[k]; for JPEG, for a short last strip, and for strips that a level joins, see below; of plane p of an ImageJ stack in one IFD, the convention §4.1, StripOffsets[k] + p × P). Here and below, a tiled IFD’s TileOffsets and TileByteCounts are its tile tables (the convention §2): its StripOffsets and StripByteCounts, where it has neither. The sources are numbered by §1.2’s order of first use, over the references in the order of their keys. Besides the references and the root’s and the arrays’ zarr.json, the archive’s entries are those of the source metadata node refkv_source, the file’s IR mirror (the convention §5, conventions §8): its table’s arrays, whose chunks hold copied bytes, and its view’s groups.

7.4 Several files¶

An image’s planes may lie in several files: those its OME-XML’s TiffData elements name (§4.1), and those of a Micro-Manager stack (§7.5). The rules are those of spec/zarrify.md §1.9, and this is the profile’s sibling table:

it says

on demand. A file that names one file, or none, is a file input with a file IR

probes

the document’s files, all in one batch, in the order the TiffData elements first name them, each required: the file "<key>" does not exist. A Micro-Manager stack’s, one at a time, from n = 1, while its index maps hold fewer planes than its summary says, ending at the first absent

OME-XML: a UUID’s text and the UUID attribute of the OME element of the file it names, when both are there, MUST be equal. A sibling with no OME-XML records nothing to compare. Micro-Manager: every file’s summary MUST have the first’s UUID. Else: the file "<key>" is not part of this image

order

first use (zarrify §1.2: the references in the order of their keys)

reads and mirror

each file as §7.1 reads a TIFF, its main chain and the tags of its IFDs, and the mirror describes each in place at its key, under its object as a file IR describes the file (§5)

A UUID with a FileName names the file by that name, which is a written name: one that is not a key below the file’s directory is rejected, the TiffData's file name "<name>" is not a path below the file's directory. A UUID with no FileName can name only the named file, when its text is the OME element’s UUID; any other is rejected, since nothing says where that file is: a TiffData names a file by its UUID alone (<text>), with no FileName.

The planes are as §4.1 maps them, each with its file: a TiffData’s IFD is an index in the main chain of the file it names. Every plane’s IFD MUST exist in that file. Every IFD of a plane in another file has the size and the format the named file’s first plane has (§4.2), else: a file of the image holds planes of another size or format.

An image across files, and a Micro-Manager stack in any number of files:

  • has one level. IFD 0 with SubIFDs is rejected: an image across files with SubIFD levels is not supported;

  • has one strip a chunk: strips are neither joined nor sharded (§4.5), and a level in strips whose last strip is short is rejected: an image across files whose strips leave a short last strip is not supported.

Its source.url is the named file’s object URL, whichever files hold the planes. Its omero windows are sampled as a single file’s are (§4.4), from the chunks in whichever files hold them.

7.5 Micro-Manager stacks¶

A Micro-Manager stack is what Micro-Manager’s “image stack” format writes, usually as <name>_MMStack_Pos0.ome.tif. Despite the name, such a file holds no OME-XML, and its planes are not described by any TIFF tag: its own header describes them (Micro-Manager file formats). When no OME-XML was found, a little-endian classic TIFF whose bytes 8–39 are these little-endian u32s is one:

bytes

field

8–11

54773648

12–15

the index map’s offset M

16–31

the display settings’ and comments’ headers and offsets, not read

32–35

2355492

36–39

the summary’s length L, at most 2^24

The summary is the L bytes at 40, which MUST be a JSON object. The index map at M is the u32s 3453623 and N, with N at least 1, and N entries of 5 u32s: channel, slice, frame, position and an IFD’s offset. A file that is not all of this, whatever its bytes 8–11, is a TIFF like any other. The profile reads each IFD an index map names ahead of walking the main chain, a batch of ranges rather than an IFD a request: every IFD’s elements are as the chain gives them.

The array’s axes are as §4.4 gives them, of sizes SizeT, SizeC and SizeZ, the greatest frame, channel and slice of the index maps of all the files, plus 1. Each entry’s plane is the IFD at its offset, which MUST be in that file’s main chain, else a Micro-Manager index map names an IFD that is not in the main chain. Every entry of a file MUST have the position of its file’s first entry, else a Micro-Manager file of several positions is not supported: Micro-Manager’s default writes a file for each position, and each is an input. A plane no entry names has no chunk, since an acquisition may be stopped or skip planes.

The stack’s expected planes are the product of the summary’s Frames, Slices and Channels, each 1 when it is absent. When the named file’s N is at least that, the input is a file input. Otherwise it names siblings, and its later files are probed as §7.4 says; a stopped acquisition, whose first later file is absent, therefore costs one probe. A key of the form <s>_<n>.ome.tif, with <n> digits and <s> holding _MMStack, whose expected planes the file does not cover, is a later file named as the input, and is rejected: <key> is a later file of a Micro-Manager stack: zarrify <s>.ome.tif.

The summary’s PixelSize_um and z-step_um, when they are numbers other than 0, are the scale of x and y and of z, in micrometers (their absolute values), in place of the resolution tags (§4.4). The summary’s ChNames name the channels of the omero as the OME-XML’s Channel names do. The whole summary is the root’s micromanager member (§5).

7.6 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the file: what it found of the file’s known structures, in TIFF’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7). Its JSON Schema is tiff/description.json. It holds none of an output’s decisions: which IFDs are the levels and planes (§4.1, §4.2), the axes, sizes, data type and codecs (§4.3, §4.4), how strips are joined, padded and sharded (§4.5), the scales and position (§4.4), the omero and the root’s source metadata (§5) are the projection’s. Those decisions are refkv’s plan of the file, made from the description alone by the function the convention’s projection calls; a layout that wants another image makes its own from the description. A QPTIFF’s description is a TIFF’s, with each IFD’s QPI description and without the structures of the first IFD’s ImageDescription (spec/zarrify/qptiff.md §7.1); an NDPI’s is its own (spec/zarrify/ndpi.md §7.1). Of an image across files (§7.4), it is the named file’s, with named_key, the named file’s key, and files, each other file’s key and description, every element of each the store IR’s.

Attribute values have their references decoded.

A short last LZW strip is the last strip of a sample plane of an IFD in strips under compression 5 whose rows are fewer than RowsPerStrip, at most max_padding bytes short of a strip of RowsPerStrip rows, of at least a byte, within the file, and read to at most 3 × its decoded size + 64 bytes, at most eager_decode (§4.5); with the strips past the file’s size in such reads left out, in tree order. What the projection makes from it, and the parser still decides:

  • The IR’s planes of an ImageJ stack in one IFD (imagej/planes/<p>) follow the hyperstack the parser found, as the elements of the source model do.

  • The parser checks the source model (the header, the IFDs and their values, §7.1), and the files an image across files names (§7.4), whose sizes and formats the plan checks. The checks of the image (§7.2) are the plan’s: an input the parser accepts is rejected where the convention’s projection makes its plan.

  • The IR holds no planes of the OME-XML: which IFD holds which plane is the plan’s.
