Zarr v2¶

The Zarr v3 layout of a Zarr v2 hierarchy, and its attributes. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store from a listed store is the Zarr v2 profile, Part 2 below. The OME-Zarr convention builds on this one.

Convention version: 0 (until release, conventions §1) · UUID: 8e792619-d671-4687-ab51-752885dd3ee6 · Schema: schema.json

Changes: changes/zarr2/, one file per change.

Changes before 2026-10-22 are recorded in the revision log of VIRTUALIZE.md, this document’s earlier name, up to revision 29.

This document has two parts (conventions §11.1).

Part 1. The convention¶

This convention gives a layout only to the hierarchies that meet its requirements. Where it says that “the input is rejected”, or that something MUST hold, a hierarchy that fails has no layout under this convention, and the profile rejects it. An array below a root group that fails §3 is the one exception: it is left out, and the rest of the hierarchy has its layout (§3.4).

A Zarr v2 hierarchy (the Zarr storage specification, version 2) is a tree of groups and arrays: a group has a .zgroup document, an array a .zarray document, and either may have a .zattrs document of user attributes. An array’s chunks are objects at keys <array>/<chunk key>. The output is a Zarr v3 hierarchy with a node at the path of every Zarr v2 node; each array’s chunks are its chunk objects, referenced whole, under the same keys (the Zarr v3 v2 chunk key encoding produces exactly the Zarr v2 keys). Each node’s attributes, and the members of its documents that the Zarr v3 metadata does not reproduce, are its source metadata (§4); the store’s listing and every document read, byte for byte, are its IR mirror on refkv_source (§4.1). Every other object of the store, but consolidated metadata, is kept whole (§5).

2. Nodes¶

The candidates are the directories D (the root included) for which the store has an object D/.zarray or D/.zgroup. A candidate with both rejects the input. Candidates are classified from the root down (in order of their number of segments):

  • a candidate inside an array (a proper descendant of a directory that is an array) is not a node, and none of its documents is read or checked;

  • otherwise, a candidate with .zarray is an array, whether or not it is presented (§3.4), and one with .zgroup an explicit group.

Every directory that is a proper ancestor of an array or an explicit group, and is not one itself, is an implicit group. No other directory is a node.

A node’s documents are read as JSON (spec/zarrify.md §1.6):

Consolidated metadata. A .zmetadata object (consolidated metadata) is never read: nodes come from the listing and documents from their own objects, so stale consolidated metadata cannot change the output. (Chunks must come from the listing anyway, since .zmetadata does not list them.) It is kept as an other object (§5), so that consolidated metadata that differs from the documents is not lost.

3.2 Chunks¶

Chunks. The chunk keys of an array at path D are D/ (nothing at the root) followed by: 0 when n = 0; otherwise i0, i1, …, i(n−1) joined by s, where each ik is the decimal form of an integer with 0 ≤ ik < ceil(shape[k] / chunks[k]), without leading zeros. An array with a zero in shape has no chunk keys. The chunk objects of the array are the store’s objects with these keys, whatever their size. A chunk is present when its chunk object is not empty: its bytes are the whole object, the chunk as Zarr v2 stored it. A chunk without an object reads as the fill value, as in Zarr v2. An empty chunk object is one of §5’s empty objects: its chunk is absent too, and reads as the fill value, and the mirror lists it (§4.1). (Zarr v2 readers fail on an empty chunk object, which an interrupted write can leave behind, rather than read the fill value; the mirror records that the object was there.) Every other object under D is one of §5’s other objects.

A trailing axis has one chunk, and its index adds to the Zarr v3 chunk key: a present chunk’s entry is its chunk object’s key followed by s and 0, but for n = 0, whose entry stays 0, the v2 key of the one chunk of a one-dimensional array. Its bytes are still the whole object.

Zarr2Object, a present chunk, or an other object (§5): the whole of an object of the store, of size s > 0:

What the filter is applied to is the array’s dtype for the first, and the astype of the one before for any other. 3.4 Arrays that are not presented¶

An array that fails a rule of §3, whose .zarray is not JSON (spec/zarrify.md §1.6), or whose .zarray or .zattrs is too large or empty to read, or whose .zattrs is not an object or not JSON, is not presented, when it is not the root: it has no zarr.json, and its reason, the rule it failed first, is in the root’s source metadata (Zarr2Node’s not_presented), in order of the arrays’ paths. It is still an array of §2: a candidate inside it is not a node, and its ancestors are groups. Its documents are read and held in the mirror (§4.1) (a document that is not JSON as one gap), but for one too large to read, which is an other object. Its chunk objects are other objects (§5), so the hierarchy keeps every byte of it.

A root array that fails is the whole store, and the input is rejected, with its reason. Nothing else of a store is left out in this way: a .zgroup that fails §2, a group’s .zattrs that is not an object, or a candidate with both documents, rejects the input.

What S leaves out, the Zarr v3 metadata holds: zarr_format, shape, chunks, the data type, order, the fill value, the compressor’s id and the members its codec carries, the filters, each id included, and the separator. Members are copied as spec/zarrify.md §1.6 reads them, except that a number written as an integer (a JSON number with no fraction and no exponent) is kept exactly, every digit, beyond 2^53 − 1 too, and is written back so. Any other number is its binary64 value, and a number whose binary64 value is infinite still rejects the input. Where §3 uses a number (a size, a fill value, a level), it uses its binary64 value.

4.1 Elements¶

Everything else the store holds that the hierarchy does not reference is on refkv_source, which is the store’s IR mirror (conventions §8, as a store’s IR, conventions §8.9): its table, from which the listing and every document read are rebuilt byte for byte, and its view, refkv_source/tree. This section is the Zarr v2 source model: the elements of a Zarr v2 store’s IR.

Paths are relative to the IR’s root, whose path is ""; <d>, <k> are a directory’s and an object’s key segments, named by conventions §8.9 (so a chunk key’s trailing digits are its name index). Types are those of conventions §8.6.

The view shows each member’s text of at most 1024 bytes as a string (conventions §8.7); a member past that is the spill form, its bytes in refkv_source/ir/held. The mirror lists every object of the store, documents nested under arrays, .zmetadata and empty objects included, with its size; the hierarchy references the chunk objects and the other objects (§5), and the mirror rebuilds the rest.

Equivalence. Hierarchies of one store are compared entry for entry, refkv_source included (conventions §11.4).

5. Other objects¶

An other object is an object of the store (spec/zarrify.md §1.4) whose size is not 0 and which is none of these:

  • a document that §2 reads: the .zgroup of an explicit group, the .zarray of an array, and the .zattrs of either;

  • a chunk object of an array that is presented (§3.2), whatever its size.

Among them are READMEs and other files a writer put next to the data, OME-XML outside the place that the OME-Zarr convention §7 gives it, a .zattrs of a directory that is not a node, documents nested under an array (the .zgroup or .zarray of a candidate inside an array), the objects under an array that are not chunk keys, and all the objects of an array that is not presented (§3.4) but for the documents the mirror holds. Each is kept whole: the hierarchy has the key refkv_source/objects/<k>, where k is the object’s key, escaped, and its bytes are the object’s. (An empty object holds nothing, and has no key; the mirror lists it, below.)

Escaping. A last segment that a Zarr reader would take for a node’s document must not end a key under refkv_source/objects/: when the last segment of k is zarr.json, .zarray or .zgroup followed by any number (zero included) of ~, one ~ is appended to it. So zarr.json is kept at refkv_source/objects/zarr.json~, a/.zgroup at refkv_source/objects/a/.zgroup~, and zarr.json~ at refkv_source/objects/zarr.json~~. The escape is one to one: a key whose last segment is one of these names followed by at least one ~ is the object’s key with one ~ removed, and every other key is the object’s. No Zarr v3 or Zarr v2 reader then opens a node under refkv_source/objects/.

Empty objects and ignored keys. The empty objects are the store’s objects of size 0, the empty chunk objects (§3.2) among them: they have no entry, and the mirror lists them, each an object of the IR of size 0 (§4.1). The ignored keys are the relative keys of the listed objects that spec/zarrify.md §1.4 ignores and records, which are not objects of the IR. When there is at least one, refkv_source’s source metadata has, beside the mirror’s description ir, the member "ignored": I, I the ignored keys in ascending order of their UTF-8 bytes; otherwise it has no such member.

The group refkv_source. The hierarchy has the group refkv_source, a child of the root (the source metadata node of conventions §2), whose zarr.json declares the convention with the source metadata {"ir": D, "ignored": I} (D the mirror’s description, conventions §8.2; ignored as above), and the mirror’s arrays and view groups below it. The directories between it and the other objects are not nodes and have no zarr.json. A hierarchy that has a node (§2), an implicit group included, at the path refkv_source, or below it, is rejected, since its keys would mix with these. When the root is an array, which can have no children, the mirror’s keys (refkv_source/zarr.json among them) and the objects’ keys under refkv_source/objects/ are plain keys of the archive, which Zarr readers do not read as nodes.

Part 2. The profile¶

The Zarr v2 profile of spec/zarrify.md is §7 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

7. Zarr v2 profile¶

The profile was chosen because the store’s root has a .zarray or a .zgroup and the store does not declare OME-NGFF 0.4 (§1.4); a store that does is read by the OME-Zarr profile (ome-zarr.md §11, ome-zarr.md), which builds on this one. The store is listed (§1.5), and the documents that the convention §2 reads are read as JSON (§1.6).

Consolidated metadata. A .zmetadata object (consolidated metadata) is never read: nodes come from the listing and documents from their own objects, so stale consolidated metadata cannot change the output. (Chunks must come from the listing anyway, since .zmetadata does not list them.)

Numbers. The documents’ integer literals are kept exactly where the convention copies them (its §4), beyond 2^53 − 1 too, in place of §1.6’s last paragraph; every number the convention uses is its binary64 value, as §1.6 says.

7.1 Rejection¶

The input is rejected when a rule of §1.4–§1.6 fails, and when the convention gives it no layout: wherever it says that the input is rejected, or that something MUST hold and it does not. An array below a root group that fails its rules is left out instead (the convention §3.4).

7.2 Chunks and other objects¶

Every chunk that the convention says is present (the convention §3.2) is an entry under its own key, referencing the whole chunk object through its own url source (§1.4). A chunk object of size 0 has no entry: it is one of the convention §5’s empty objects, which the mirror lists.

Every other object of the convention §5 is referenced whole in the same way, by an entry under the key refkv_source/objects/<k> (with a ~ appended when the convention §5 escapes k’s last segment) whose url source is the URL of the object k (§1.4). (This is the one place where an entry’s key is not its object’s key; §1.4’s rules otherwise apply: the sources are in ascending order of their entries’ keys, each entry referencing its object’s whole range.) The ignored keys are the member ignored of refkv_source’s source metadata (the convention §5). The documents under refkv_source/ (the mirror) are deflated and, like the chunks, not among the documents a reader fetches when it opens the archive (conventions §2).

Reading. The store is listed, then every document that the convention §2 reads, which the listing names, is read whole in one round, concurrently (conventions §8.9), each once; then the documents are checked in path order. So a document that cannot be read is a failure even when another document read in the same round would reject the input. No other object is read.

7.3 The description¶

This section is not part of the convention: nothing it specifies is written in an output. The parser returns, beside the IR, a description of the store: what it found of the source, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7), which give each array’s chunks. It holds none of an output’s decisions: which arrays are presented and why the others are not (the convention §3.4), each array’s zarr.json (its data type, codecs, fill value and chunk grid, §3), the source metadata (§4), and the OME-Zarr profile’s layer are the projection’s, which makes them from the description, and rejects the input where §7.1 says. It is a JSON object with these members:

member

value

profile

zarr2, or ome-zarr where the root declares OME-NGFF 0.4 (§1.4)

nodes

each node (the convention §2) in ascending order of its path, then each implicit group: path, kind (array, group or implicit), and, for an explicit node, document, its .zarray or .zgroup, and attributes, its .zattrs, where the listing has one

documents

the keys of the documents the parser read, which the IR holds (the convention §4.1), in the order it holds them: each node’s, in the order of nodes, its own document first

ignored

the keys the listing ignored, where there are any (the convention §5)

A document is key, its key, and one of: json, its JSON as parsed, as text (its integers and strings as written, its members in order, a repeated key kept); error, why it does not parse; or unread, why it was not read: an array’s document that is empty or too large, whose array is left out (a group’s or the root’s rejects the input before the description).
