TIFF, OME-TIFF and Aperio SVS¶

refkv turns an image file into an OME-Zarr dataset by writing a small archive of references to the file’s bytes, without copying the pixels (overview). This page is about TIFF files, tiled or in strips.

Who this is for¶

Microscopy and pathology labs keep a great deal of their data as tiled TIFF: OME-TIFF from Bio-Formats, scanners and acquisition software, plain tiled TIFFs and BigTIFFs from image-processing pipelines, and Aperio SVS slides from whole-slide scanners. The files sit on a lab server, in the IDR (whose idr0096 study alone has 205 OME-TIFFs on ftp.ebi.ac.uk), on Zenodo, or on OpenSlide’s test-data server. The people who use them want to open a slide in an OME-Zarr viewer, or slice it with zarr-python or dask, without running a conversion that duplicates hundreds of gigabytes.

refkv reads the TIFF’s image file directories and, for OME-TIFF, its OME-XML, and writes an archive in which every Zarr chunk is one tile of the file. A 487 MB, 9-level OME-TIFF from the IDR became a 624 KB archive in a few seconds (at spec/zarrify.md revision 16, before the archive held the file’s IR mirror); the tiles are read from the IDR’s server only when a reader asks for them.

TIFF files are zarrified by refkv’s Rust core, rust/refkv-ir, the same code in Python and (built for WebAssembly) in the browser: it parses the file into an intermediate representation (IR), plans the range requests, and projects the IR onto the TIFF convention. Installing refkv builds it, which needs a Rust toolchain (overview).

What you get¶

One OME-Zarr 0.5 image at the archive root, with one array per pyramid level, 0 the full resolution.

  • Axes: a subsequence of t, c, z, y, x: t, c and z only when the image has more than one time point, channel or z-plane.

  • Levels: OME-TIFF SubIFDs; without OME-XML, the later tiled images of the same format that get strictly smaller (how SVS stores its pyramid, so its label, macro and thumbnail images are skipped).

  • Chunks: one TIFF tile per chunk, for each plane and sample plane, or, for an image in JPEG or JPEG 2000 strips, one strip per chunk (its rows by the image’s width). LZW, DEFLATE and zstd strips are the inner chunks of sharding_indexed shards of up to 1024 strips, one key per plane for most files, so a read of one row costs that row’s bytes and a read of a whole plane through zarr-python one request (zarrita and Neuroglancer still read a strip at a time). Uncompressed strips are joined, without copying, into chunks of up to 1 MiB (2^20 bytes) and 1024 strips, so a file of one row per strip does not get a key per row; a reader of a chunk reads all of it, so reading one row then costs up to 1 MiB (tiff.md §4.5). A short last chunk is padded to the others’ rows, so that the chunk grid stays regular: with zeros when uncompressed, and with a few literal bytes that continue its stream when LZW; a short last strip of DEFLATE, zstd, JPEG or JPEG 2000 cannot be padded, so its level has the rectilinear chunk grid, a chunk a strip, unsharded. Interleaved RGB keeps its samples in one chunk, behind a transpose codec.

  • Codecs: none, LZW (refkv.tiff_lzw), DEFLATE (numcodecs.zlib), zstd, JPEG 2000 (imagecodecs_jpeg2k) and JPEG (imagecodecs_jpeg), the tiles and strips as stored.

  • Scale: from the OME-XML physical sizes, else Aperio’s MPP, else the TIFF resolution tags when they give a pixel under 25.4 µm (72, 96 or 300 dpi is a document resolution, not a pixel size); each level’s scale grows with its downsampling.

  • Translation: the stage position of the first plane (OME-XML), or the slide position of an Aperio scan (Left, Top).

  • Name: the OME Image name.

  • Channels: omero.channels labels RGB samples (an SVS slide’s, for example) R, G, B in red, green and blue, and an OME-TIFF’s channels by their OME-XML Channel names and colors (else C0, C1, …, in white). The file records no display range, so each channel’s window is sampled from the middle chunk of the coarsest level: the 5th to 99.9th percentile of its values, leaving out zeros, for uncompressed, LZW and Deflate data. RGB samples, and tiles refkv does not decode (JPEG, JPEG 2000, zstd), get the data type’s whole range (0 to 255 for 8-bit data). A float image whose windows cannot be sampled, or one with more than 64 channels, has no omero.

  • Metadata: the root’s refkv_zarrified.tiff holds the byte order and whether the file is BigTIFF. Everything else is on refkv_source, the file’s IR mirror (conventions §8): a table under refkv_source/ir/ that accounts for every byte of the file (every tag of every IFD, SubIFDs and EXIF IFDs included, every tile, and the gaps between them), so that the file can be rebuilt from it and the file’s bytes, and a JSON view of it under refkv_source/tree, where the tags are at ifds/<i>/tags/<tag>. A value of more than 1024 bytes, such as most OME-XML documents or a long Aperio description (tag 270), is not copied into the view: the view points to it in the file.

JPEG-tiled slides (Aperio SVS)¶

SVS tiles are JPEG streams with their tables missing: the tables are in the TIFF’s JPEGTables tag, and the color transform in a separate tag. refkv makes each chunk a complete JPEG stream by inserting, through the chunk’s reference, an Adobe color marker and the tables after the tile’s start-of-image marker. That prefix is the same for every tile of a level (often of every level), so it is held once in the archive as a data source, and reading a tile still reads only the tile from the file. SVS slides with JPEG 2000 tiles (compression 33003 and 33005) need nothing of the kind.

Try it¶

example.py zarrifies a public file and plots it with matplotlib. Its dependencies are in its header (PEP 723), so it runs on its own, with refkv from PyPI:

uv run docs/zarrify/tiff/example.py

The outputs below were recorded at spec/zarrify.md revision 16 (overview). The summary line now also has the members planner (the read planner’s counts of batches, ranges and requests), elements (the size of the file’s IR) and folded (how the mirror’s table was folded), shown as … here: their values were not measured again.

In the browser. The live demo zarrifies the same OME-TIFF and opens it in Neuroglancer: https://d-v-b.github.io/refkv-demo/image-to-zarr/?url=https%3A%2F%2Fftp.ebi.ac.uk%2Fpub%2Fdatabases%2FIDR%2Fidr0096-tratwal-marrowquant%2F20210609-ftp-ome-tiffs%2F4000_d11_m5_LT_2%2520(20x_01).ome.tiff. It was ready in about 1 s, from 17 range requests (before the read planner; the count differs now). The OpenSlide SVS files do not work there: openslide.cs.cmu.edu sends no CORS headers, so the browser cannot read them (“500: Failed to fetch”). The demo’s own SVS example, a TCGA slide on Zenodo with JPEG 2000 tiles, does work.

Viewing¶

The Neuroglancer fork (https://github.com/d-v-b/neuroglancer, branch vzip) displays these archives: it decodes imagecodecs_jpeg (8-bit), imagecodecs_jpeg2k (8- and 16-bit integers), zstd, numcodecs.zlib, refkv.tiff_lzw and imagecodecs_delta; the idr0096 OME-TIFF above, whose tiles are JPEG 2000, renders through the live demo. It has no int64 or float64 data types, so a TIFF with 64-bit integer or float samples cannot be shown there (zarr-python reads it).

Supported and not supported¶

Supported:

  • TIFF and BigTIFF, either byte order, with tiled images or images in strips.

  • Pyramids as SubIFDs (OME-TIFF), or as a sequence of smaller tiled images (SVS).

  • OME-TIFF planes over Z, C and T in any DimensionOrder, single-file.

  • ImageJ hyperstacks (an ImageJ= description with images=N): one IFD a plane, or the one-IFD layout ImageJ writes for stacks of more than 4 GB, whose later planes follow IFD 0’s strips with no IFD of their own, as planes over T, C and Z (§4.1).

  • Unsigned and signed integers of 8 to 64 bits, float32 and float64, unsigned samples of 1 and 12 bits (imagecodecs_packints, read as uint8 and uint16, and a file without BitsPerSample as 1 bit), planar or interleaved samples.

  • Compression: none, LZW, DEFLATE, zstd, LZMA, PackBits, CCITT Group 4 (1 bit), EER (a stack of frames along t), JPEG 2000, LERC (as GDAL’s COG driver writes for LINZ’s elevation), WebP (3 or 4 samples of 8 bits, as for LINZ’s imagery), JPEG XL, and JPEG (8-bit, gray or RGB or YCbCr) with or without JPEGTables.

  • The horizontal predictor (Predictor 2), as GDAL, libtiff and tifffile write it with LZW, DEFLATE or zstd, of integer samples: imagecodecs-zarr’s imagecodecs_delta codec sums the differences back (zarr-python reads it with refkv[images]).

  • The floating-point predictor (Predictor 3), as GDAL writes for Copernicus DEM and USGS 3DEP tiles, with LZW, DEFLATE or zstd, of float samples: imagecodecs-zarr’s imagecodecs_floatpred codec undoes it, in the place of bytes.

Rejected:

  • Images in strips whose last strip is shorter than the others, when they would need more than 4 MiB (2^22 bytes) of zeros, or a short last LZW strip of more than 16 MiB (2^24 bytes), which is read to pad it.

  • Old-style JPEG (compression 6).

  • Predictor 2 of float samples (whose bits are differenced as integers), Predictor 3 of integer samples, either without compression (libtiff stores such a file undifferenced) or with JPEG: no codec of refkv’s conventions undoes these.

  • An image across files with SubIFD levels, or whose strips leave a short last strip (§7.4).

  • An OME-TIFF with several RGB channels (SizeC other than 1 or the samples per pixel).

  • More than 100000 IFDs or planes.

  • An ImageJ hyperstack whose description’s frames, channels and slices do not multiply to its images, or whose IFD count is neither 1 nor its images; one in one IFD that is tiled, compressed, or whose strips are not contiguous; and one whose channels have several samples each.

  • Planes or levels whose bits are filled least significant first (FillOrder 2) when uncompressed, DEFLATE or zstd, and subsampled YCbCr that is not JPEG or JPEG 2000 (the codecs decode samples at full resolution).

A file that is none of the formats refkv reads is rejected with not a file of any supported format (exit status 3).

In the browser¶

The browser code (js/) reads TIFF:

  • TIFF and BigTIFF, either byte order, tiled or in strips (the same layout as above: the browser runs the same core).

  • Pyramids as SubIFDs (OME-TIFF), or, without OME-XML, as later tiled images of decreasing size (as in SVS).

  • OME-TIFF planes over Z, C and T in any DimensionOrder, with physical pixel sizes and units.

  • Samples per pixel stored planar (one chunk per channel) or interleaved (through a transpose codec).

  • Compression: none, LZW (refkv.tiff_lzw), DEFLATE (numcodecs.zlib), zstd, LZMA (imagecodecs_lzma), PackBits (imagecodecs_packbits), CCITT Group 4 (imagecodecs_ccittfax4), EER (imagecodecs_eer), JPEG 2000 (imagecodecs_jpeg2k), LERC (imagecodecs_lerc), WebP (imagecodecs_webp), JPEG XL (imagecodecs_jpegxl), and JPEG (imagecodecs_jpeg), and Predictors 2 (imagecodecs_delta) and 3 (imagecodecs_floatpred). JPEG tiles that keep their tables in JPEGTables, as in Aperio SVS, become complete JPEG streams through references that prepend the tables and a color marker, held once in the archive as a data source.

Not supported, and refused with HTTP 422: what the profile rejects (above), such as old-style JPEG.

Several files¶

An OME-TIFF whose TiffData elements name other files is read with them, as is a Micro-Manager stack, which holds no OME-XML and keeps its planes in numbered files of up to 4 GB (§7.4, §7.5). Name the first file:

uv run refkv zarrify "https://downloads.openmicroscopy.org/images/Micro-Manager/1.4.22/sebastien/Test_Dataset_MultiPosition_Stack_1_MMStack_Pos0.ome.tif" stack.vzip

Each position of a Micro-Manager acquisition is its own input. This one is 140 frames of 3 channels and 21 slices across two files, 4.7 GB, read with 26 MB of requests.

Performance¶

  • Zarrifying reads only the IFDs, the tag values the layout uses and the OME-XML (and, for the source metadata, the tag values the view shows). The read planner batches these reads, runs up to 8 requests at a time in Python (--connections) and packs ranges into multi-range requests where the server supports them. A file of at most 1 MiB is read whole, in two requests. (At revision 16, before the planner, the 487 MB idr0096 file took 17 range requests in the browser.)

  • Reading a chunk is one range request for one tile. For JPEG tiles the shared header is in the archive, so it costs no request.

  • The archive grows with the number of tiles: CMU-1.svs (24,813 tiles, 178 MB) gave a 3.4 MB archive, in 10 s, at revision 16. The IR mirror stores long runs of tiles as one row of its table, whose offsets and byte counts it reads from the TIFF’s own TileOffsets and TileByteCounts.

How it’s verified¶

js/test/tiff/verify.py zarrifies each synthetic file with the browser code (the Rust core as WebAssembly), reads every level back through python/src/refkv and zarr-python, and compares it with tifffile; it also rebuilds each file from its archive’s IR mirror and checks that it is the file, byte for byte. compare.py compares three zarrifiers (overview) on the 73 synthetic files (including inputs to reject), the 205 OME-TIFFs of idr0096 and the 4 SVS slides of corpus_tiff.txt: the Python and browser hosts of the core must write the same archive, refkv_source included, and both must match, outside refkv_source, the frozen reference: the Python TIFF profile refkv shipped before the core.

  • Profile: spec/zarrify/tiff.md; convention: spec/zarrify/tiff.md

  • Rust core: rust/refkv-ir/src/tiff.rs (the parser) and rust/refkv-ir/src/project/tiff.rs (the projection)

  • Python host: python/src/refkv/ir/; browser host: js/src/zarrify/ir/

  • Frozen reference: conformance/zarrify/reference/refkv_reference/tiff/ and conformance/zarrify/reference/ts/tiff/

  • Fixtures: fixtures/tiff/
