NRRD¶

The Zarr layout of a NRRD input (Teem’s “nearly raw raster data”: a .nrrd file whose text header is followed by its data, or a detached header, .nhdr, and the data file it names), and the translation of its header into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, which files it reads and which inputs it rejects, is the NRRD profile, Part 2 below. The format is Teem’s Definition of NRRD File Format, cited here as “the NRRD definition”.

Convention version: 0 (until release, conventions §1) · UUID: 23e0c600-8da6-40f1-81e7-ab246e948e88 · Schema: schema.json

Changes: changes/nrrd/, one file per change.

Added 2026-10-25.

This document has two parts (conventions §11.1).

2. The header¶

A NRRD input is one array. Its header is text: lines, each ended by a LF (0A), a CR (0D) before the LF being part of the line end. A line’s text is its bytes without its line end; the last line of a file may end at the file’s end, without a LF, its text all of it. The first line is the magic, NRRD0001 to NRRD0005. Each later line is, in this order of tests (the first row that matches it applies):

4. The image¶

The hierarchy is one image at the root (conventions §4), without a name, with one array at path "0": the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A} (an ImageGroup), where A has ome (M, below, an OmeImage), zarr_conventions and refkv_zarrified (§1).

The profile accepts 2 or 3 axes of the role space, at most one of time and at most one of channel (§8.2). The axes of the role space are, in the header’s order, x, y and z; the axis of the role time is t and that of the role channel c. The array’s axes are t, c, z, y, x, each only when present, in that order (conventions §4), and the root’s source metadata records each header axis’s image axis (§5.1).

4.2 The gzip encoding¶

A gzip-encoded NRRD’s data is one deflate stream of the whole array, as the gzip program writes it. A deflate stream has no index: its blocks start at bit offsets that only decoding finds, and each block may refer to the 32 KiB of output before it, so no part of the stream can be decoded without decoding the stream up to it. The layout could therefore only cut the array into chunks at block boundaries by decompressing the data (which a zarrifier must not read, spec/zarrify.md §1.2, “Structure only”), and then would need a codec that starts mid-stream from a given window. It takes the one form that keeps the stream as it is: one chunk of the whole array, a reference to the stream, which Zarr’s gzip codec decodes.

The cost is reads: nothing is copied and every value is exact, but the chunk is coarse. A reader decompresses the whole stream to read any value, holds the whole array in memory to do so, and reads it with no concurrency. This suits the inputs gzip NRRDs usually are (volumes of a few hundred megabytes at most, such as the IMPC’s embryo scans); a reader that needs random access to a large volume should decompress it once and store it chunked. The profile does not decompress the stream, so a stream that does not decode to exactly B bytes (a damaged file, or one with other bytes after its gzip members, or whose byte skip is wrong) is not detected: reading its chunk fails.

The bzip2 encoding is rejected for the same reason and one more: bzip2’s blocks are independent, but they too start at bit offsets that only a scan of the compressed data finds, and Zarr v3 has no bzip2 codec that both of refkv’s readers decode (zarr-python has none of its own; numcodecs’ numcodecs.bz2 has no counterpart in the browser).

4.3 Scales, units and position¶

A number is valid if it is finite and positive. The NRRD definition places an image in a space by space directions (a vector per axis: the step in space from one sample to the next along it) and space origin (the first sample’s position), and otherwise by spacings. OME-NGFF 0.5 places an image only by a scale and a translation per axis, so the orientation is applied only when it is axis-aligned: when the header has space directions, every axis of the role space has a vector, and the vector of the axis x, y or z (the j-th, from 0) has a component j (the space has more than j coordinates), which is valid, and every other component 0. (A space of more coordinates than spatial axes, such as a 2-D image in a 3-D space, or a space with a time coordinate, is axis-aligned when those components are 0.)

5.2 The IR mirror¶

refkv_source is the input’s IR mirror (conventions §8), a store IR (conventions §8.9) whose objects are the files the profile read. Its leaves partition each object. A file the chunks reference is described in place: its bytes stay in the file, which is a source of the archive (§8.5), and the table holds none of them. A file no chunk references, and so no source names, is held: the table holds its bytes (refkv_source/ir/held), as a store’s documents are held (conventions §8.9), so that the mirror alone rebuilds it.

its key

described in place

a detached header’s file

its key

held

a detached header’s data file

its key below the header’s directory (§8.3)

described in place

The view, refkv_source/tree, shows the header’s lines; the data and the gaps are not shown.

The elements are determined by the files. Hierarchies of one input are compared entry for entry, refkv_source included (conventions §11.4).

7. What the layout does not express¶

  • Several data files. A detached header whose data file field is a list (LIST) or a pattern (slice%03d.raw 1 60 1) splits the array across files, one slab per file, each with its own line and byte skips. Each could be a run of chunks of its own file, but a gzip slab is a chunk only when the slabs cut the array along chunk boundaries, and the profile’s store run would probe a file per slab; the profile reads one data file.

  • Text and hex data, which no chunk can reference as binary values, and bzip2 (§4.2).

  • Block data (type: block), opaque records of no data type.

  • Axes OME-NGFF cannot place: one spatial axis or more than three, two time axes, or two channel axes (a list axis beside a color axis, a matrix stored as two axes). Such inputs are rejected rather than given a layout of their own.

  • Oblique orientations, which are recorded but not applied (§4.3).

Part 2. The profile¶

The NRRD profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles. The input is the header file and, for a detached header, its data file, and the profile also says which of them are read.

8. NRRD profile¶

The input is a file input that names the header file (a URL, or a local path), which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/nrrd.json) chose: bytes 0–6 of H are NRRD000 (4E 52 52 44 30 30 30), byte 7 is a digit from 1 to 5, and byte 8 is a LF or a CR. (The magic of 1998’s files, NRRD00.01, does not match.) The profile reads the input as a file read as a store (spec/zarrify.md §1.8): the store URL is the header file’s directory, its objects are the header file, at its key, and a detached header’s data file, which the profile probes for (§8.3), and the root’s source.url is the header file’s object URL.

8.1 The header¶

The header file is read from its start: its first min(size, 65536) bytes, then, while the bytes read hold no blank line after the magic and do not reach the file’s end, as many bytes again as are held (each read doubling them), up to 2^24 bytes in all. A detached header’s file, which the mirror holds (the convention §5.2), is read whole: by its first read when it is at most 65536 bytes, by the reads of its header when they reach its end, else in one request in the run’s last batch. The header (§2) is the bytes through the blank line that ends it, or, when none does, the whole file. The input is rejected when:

  • its first line is not NRRD0001 to NRRD0005 (the file’s first line is checked as soon as it is read, or its first 8 bytes when the line is longer): not a NRRD header: its first line is not NRRD0001 to NRRD0005;

  • 2^24 bytes do not hold a blank line and the file is longer: no blank line ends the NRRD header within its first 16777216 bytes;

  • a line is none of a comment, a key/value pair and a field; a key/value pair’s key is empty; a field’s identifier is not followed by a space or the line’s end, is not a field’s of §2 in any case, or names a field the header has given already: line <n> of the header: ..., <n> the line’s number, the magic’s 1;

  • the header has no data file field and no blank line ends it: the header ends at the end of the file, without the blank line before the data.

The lines after a data file field whose descriptor’s first word is LIST are the names of the data files (the NRRD definition’s third form, which ends the header), not fields: they are not read as lines of the header, and §8.3 rejects the input.

8.2 The fields¶

The fields are checked in this order, each only by what the layout reads of it; the descriptor is read without the spaces and tabs around it where one value is read. A field the header lacks is not checked, unless it is required.

  • dimension is required, an integer from 1 to 16: n.

  • type is required, in the table of §3 (in lower case); block is rejected: the NRRD type block is not supported: its blocks are opaque, of no data type.

  • encoding is required, raw, gz or gzip (in lower case). ascii, text, txt and hex are rejected (their values or bytes are text, which no chunk can reference as binary), and so are bz2 and bzip2 (§4.2): the NRRD encoding <e> is not supported: <why>.

  • endian, when present, is little or big (in lower case); it is required when the data type is larger than 1 byte.

  • sizes is required: n integers from 1 to 2^53 − 1.

  • line skip is an integer from 0 to 2^53 − 1, and byte skip from −1 to 2^53 − 1. With the gzip encoding, byte skip MUST NOT be −1: it counts back from the data’s end, which only decompressing can find.

  • data file: §8.3.

  • space and space dimension are not both present. space is one of the NRRD definition’s spaces (in lower case: right-anterior-superior or RAS, …, 3D-left-handed-time), whose dimension is d; space dimension is an integer from 1 to 16, d. space directions, space origin, space units and measurement frame are present only with one of them.

  • space directions: n vectors and none, each vector of d numbers. space origin: one vector of d numbers. space units: d quoted strings.

  • spacings: n numbers. units: n quoted strings. kinds: n kinds of the NRRD definition (in lower case: domain, space, time, list, …, ???, none).

  • The axes’ roles (§4.1): 2 or 3 of the role space, at most one of time and at most one of channel.

A value that is not as these require is rejected: the <field> field "<descriptor>" .... min and max are read as numbers when they are (§4.4) and are never rejected; no other field is checked: content, block size, old min, old max, number, sample units, thicknesses, axis mins, axis maxs, centers, labels and measurement frame’s vectors are recorded as written (§5.1).

8.3 The data file¶

A detached header’s data file descriptor names its one data file: a path relative to the header file’s directory. Its key is the descriptor’s segments (the parts between /) without the segments ., joined by /. The input is rejected when:

  • the descriptor’s words (separated by spaces and tabs) are LIST and any others, or are 4 or 5 words of which the first holds % and the others are integers: the data file field "<descriptor>" names several data files, which the profile does not read;

  • the descriptor is not UTF-8, starts with /, has no segment but ., or has an empty segment, a segment .., or a segment that holds \ or : (a Windows path, a drive, a URL’s scheme, which could name a file outside the directory): the data file "<descriptor>" is not a path below the header's directory;

  • the key is the header file’s: the data file "<descriptor>" is the header's own file.

The data file is then probed, as the VSI profile probes a tile file (vsi.md §9.2): the host says whether the object at its key exists, and its size (a local file that is there, or an HTTP object whose response to the first request is not a 404; a 404 is absent, any other failure a failure, not a rejection). An absent data file rejects the input: the data file "<key>" does not exist.

8.4 The data¶

The data’s file is the header file for an attached header and the data file for a detached one; its start is the header’s end for an attached header, and 0 for a detached one.

Line skip. When line skip is L > 0 and byte skip is not −1, the file is read in windows of 65536 bytes from the start, and the start moves past the L-th LF. The input is rejected when the file ends first (line skip <L> passes the end of <file>), or when 2^24 bytes are read first.

Byte skip. The data starts at D: the start plus byte skip, or, for byte skip −1, at size − B of its file, B the raw data’s bytes (§3), so that the data ends at the file’s end. For the gzip encoding, D is the start: byte skip counts bytes of the decompressed data, which the refkv.skip codec passes over (§4.1). The input is rejected unless all of these hold:

  • B is at most 2^53 − 1;

  • for the raw encoding, D + B is at most the file’s size;

  • D is at least the start (the data does not begin inside the header or the skipped lines);

  • for the gzip encoding, the stream, the size − D bytes from D to the file’s end, is at least 18 bytes (a gzip member’s header and trailer), and its first three bytes are 1F 8B 08 (a gzip member of deflate data). The stream is not otherwise read: the output does not depend on the pixel data (spec/zarrify.md §1.2).

Bytes of the file after the data are not read, as the NRRD definition says.

8.5 Chunks¶

Every chunk of the convention’s array (§4.1) is present, at 0/c/<coords>, and references the data’s file; the output copies no data, but an edge chunk below.

  • Raw: the chunk is referenced as conventions §7 references a chunk of contiguous values of V at D (with the chunk limit 2^17 bytes): one range of the data’s file, followed for an edge chunk by its zero padding. Where conventions §7 makes that padding a literal range, it is instead the range (1, 0, p) of the output’s zero data source (spec/zarrify.md §1.2), p the padding’s bytes: the source holds as many zero bytes as the most padding any reference of the output holds. Where that section copies the chunk (when its reference, with the padding as a literal range, would not fit in a payload), the chunk is copied, with its padding (its bytes are read in the run’s last batch).

  • Gzip: the one chunk, 0/c/0/.../0, is one range of the data’s file: (D, size − D).
