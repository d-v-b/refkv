Imaris IMS¶

refkv turns an image file into an OME-Zarr dataset by writing a small archive of references to the file’s bytes, without copying the pixels (overview). This page is about Imaris .ims files.

Who this is for¶

Imaris files come from Oxford Instruments’ Imaris and its file converter, and directly from Andor’s Fusion software (for example on Dragonfly spinning-disk systems). They hold multi-resolution, multi-channel time-lapses, often tens or hundreds of gigabytes, on facility storage, and are shared on Zenodo and the OME sample-image server. A .ims file is HDF5, which most web-based viewers and Zarr tools cannot read without the HDF5 library and a local copy.

refkv reads the file’s HDF5 structure itself (superblock, groups, attributes and chunk B-trees, never the pixels) and writes an archive in which every Zarr chunk is one HDF5 chunk of the file. Imaris’s own resolution pyramid becomes the OME-Zarr levels.

What you get¶

One OME-Zarr 0.5 image at the archive root, with one array per Imaris resolution level.

  • Axes: t (more than one time point), c (more than one channel), z (more than one plane, or z-chunks deeper than 1), y, x.

  • Data types: uint8, uint16, uint32, int8, int16, int32, float32.

  • Chunks: the HDF5 chunks as stored (Imaris pads the dataset to whole chunks; chunks wholly in the padding are left out).

  • Codecs: bytes, or bytes then numcodecs.zlib for deflate-compressed files.

  • Scale and translation: from the image extents (ExtMin, ExtMax), so each level’s voxel size is the extent over its size, and the translation is the extents’ corner; the unit from Unit (micrometers by default).

  • Time step: the mean interval between the first and last time points’ timestamps.

  • Name and omero: the image name, and each channel’s name, color and contrast range.

  • Metadata: the rest of the HDF5 file (every group’s attributes, which hold the extents, units, channels, acquisition settings and time points; the histograms; the thumbnail; DataSetTimes; the Scene objects), kept by refkv_source, the file’s IR mirror: a table that rebuilds the file byte for byte, and a JSON view under refkv_source/tree of every object header, message, attribute, link, heap and chunk index the walk reads (spec/zarrify/ims.md §5).

Try it¶

example.py zarrifies a public file and plots it with matplotlib. Its dependencies are in its header (PEP 723), so it runs on its own, with refkv from PyPI:

uv run docs/zarrify/ims/example.py

retina_large.ims from the OME sample images (47 MB, 4 levels, 2 channels, deflate; CC BY 4.0), from corpus_ims.txt:

uv run refkv zarrify https://downloads.openmicroscopy.org/images/Imaris-IMS/eliana/retina_large.ims retina.vzip

{"format": "ims", "levels": 4, "sizes": {"t": 1, "c": 2, "z": 64, "y": 1567, "x": 2048}, "dataType": "uint8", "chunkShape": [16, 256, 256], "compressed": [true, true, true, true], "channels": ["CollagenIV (TxRed)", "GFAP (FITC)"], "chunks": 612, ...}

This took 6 s and wrote an 80 KB archive, at spec/zarrify.md revision 16 (overview); the archive now also mirrors the HDF5 file’s other objects, so it is larger.

import zarr
import refkv.zarr

g = zarr.open_group(refkv.zarr.open("retina.vzip"), mode="r")
ms = g.attrs["ome"]["multiscales"][0]
print([(a["name"], a.get("unit")) for a in ms["axes"]])
for d in ms["datasets"]:
    print(d["path"], g[d["path"]].shape, g[d["path"]].chunks, d["coordinateTransformations"])
print([(c["label"], c["color"]) for c in g.attrs["ome"]["omero"]["channels"]])
print(g["3"].metadata.codecs)
print(g["3"][:, 4, 100, 120:126])

In the browser. Not on the live demo yet: it zarrifies only TIFF, NDPI and ND2. downloads.openmicroscopy.org sends no CORS headers, so the OME sample files work only from the command line. Files on Zenodo do work in a local build of the demo (see the overview): it zarrified HeLa_H2BmCherry_GFPtubulin_Mitotracker.ims (Zenodo 4449687, 8 MB, 10 time points, 3 channels) in about 5 s and showed it in Neuroglancer.

Viewing¶

The Neuroglancer fork (https://github.com/d-v-b/neuroglancer, branch vzip) reads every data type and codec this profile writes; the HeLa time-lapse above renders through a local build of the demo, as one layer with a color and a contrast control per channel (the fork assembles each of its chunks from the file’s chunks of every channel, as Imaris stores one channel per chunk). It reads the chunks from the file’s host, so that host must allow cross-origin reads.

Supported and not supported¶

Supported:

  • Files from Imaris 5.5 to 10, ImarisWriter, ImarisFileConverter and Andor Fusion: HDF5 superblock versions 0 to 3, compact, dense and symbol-table groups, soft links (Imaris 10), and chunks under any of HDF5’s chunk indexes (version 1 and 2 B-trees, fixed and extensible arrays, implicit, single chunk).

  • Uncompressed, deflate or LZ4 chunks, after byte shuffling or not, with a Fletcher32 checksum or not (which stays in the source).

Rejected, with the message the command prints:

  • Other HDF5 filters: unsupported HDF5 filters [32001].

  • HDF5 files that are not Imaris images, including Imaris scene files without image data: not an Imaris file (no DataSet group).

  • Image datasets that are compact or contiguous, and data types other than those above.

  • More than 64 resolution levels, or more than 100000 datasets.

In the browser¶

The browser code (js/) reads Imaris IMS (HDF5):

  • Files from Imaris 5.5 to 10 and its converters: every resolution level, time point and channel, with extents, units, time step, channel names, colors and contrast ranges.

  • Chunks as stored, uncompressed, deflate (numcodecs.zlib) or LZ4 (imagecodecs_lz4h5), after byte shuffling (numcodecs.shuffle) or not.

Not supported, and refused with HTTP 422: other filters, and HDF5 features Imaris files do not use.

Performance¶

  • Zarrifying reads the HDF5 metadata only (groups, attributes and chunk indexes), so its cost grows with the number of datasets and chunks, not with the file size: 6 s for this 47 MB file, 11 s for the 8 MB HeLa time-lapse on Zenodo.

  • Reading a chunk is one range request.

  • Imaris chunks are often deep in z (16 planes here), so reading one z-plane decodes 16.

How it’s verified¶

IMS is zarrified by refkv’s Rust core, natively in Python and as WebAssembly in the browser. js/test/ims/verify.py zarrifies the synthetic IMS files (including inputs to reject) with the browser code, reads them back through python/src/refkv and zarr-python, and compares the pixels with h5py (cropped to the image size), and rebuilds each file byte for byte from its archive’s mirror. compare.py checks that the Python and browser outputs are identical, and equivalent outside refkv_source to the frozen reference (the Python profile of revision 25), on those files and on the 21 public files of corpus_ims.txt, one of which must be rejected (a scene file).
