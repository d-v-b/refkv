MRC¶

The Zarr layout of an MRC2014 file (.mrc, .mrcs, .map, .rec, .st), gzipped or not (.map.gz, .mrc.gz), and the translation of its header into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the MRC profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 2aacd010-2ed1-4748-bc3c-5dd5e840bbce · Schema: schema.json

Changes: changes/mrc/, one file per change.

Changes before 2026-10-22 are recorded in the revision log of VIRTUALIZE.md, this document’s earlier name, up to revision 29.

This document has two parts (conventions §11.1).

1. Declaration¶

The root and refkv_source declare the convention (conventions §11.2), the root with its source metadata of §5.1 as the member "mrc". Its CMO is:

  "uuid": "2aacd010-2ed1-4748-bc3c-5dd5e840bbce",
  "schema_url": "https://raw.githubusercontent.com/d-v-b/refkv/refs/heads/main/spec/zarrify/mrc/schema.json",
  "spec_url": "https://github.com/d-v-b/refkv/blob/main/spec/zarrify/mrc.md",
  "name": "refkv_zarrified",
  "description": "The Zarr layout of a MRC source zarrified by refkv, and the source's metadata"
}

The array has no attributes.

The hierarchy also holds the file as a dataset: the group dataset, which declares the MRC dataset convention (mrc-dataset.md, conventions §9) and which xarray opens with named dimensions and coordinates in angstroms. The root’s property names it: "layouts": {"dataset": "dataset"}, after source. A zarrifier told to write the image layout alone (spec/zarrify.md §1.7) writes no group dataset, and the root’s property has no layouts.

Mode 0 is int8, as the MRC2014 standard says, except in an IMOD file whose bytes are unsigned. When mode is 0 and the i32 at byte 152 (in the file’s byte order; the 41st byte of extra2) is 1146047817 (IMOD’s stamp, IMOD as a little-endian integer), the data type is int8 when either says the bytes are signed: bit 0 of the i32 at byte 156 (IMOD’s flags) is set (“1 = bytes are stored as signed (the default as of IMOD 4.9)”), or nversion is from 20140 up to, not including, 21000 (“the best way to indicate that a byte file is signed is simply to conform with the standard and set the NVERSION field”; both from IMOD’s MRC format). Otherwise the bytes are unsigned (IMOD’s default before 4.9), and the data type is uint8, b = 1. Reading such a file as int8 would make every value over 127 negative. IMOD’s own test ends nversion at the current year plus 2; a fixed end keeps the output the same whenever a file is zarrified. (The other flag bits do not change the data type, and neither does the flag without the stamp; bit 2 is the origin’s sign, §4.2.) A complex64 value is its real part, then its imaginary part, each a binary32 in the file’s byte order.

A mode 3 value is its real part, then its imaginary part, each an int16 in the file’s byte order. Zarr has no complex integer type, so the array’s data type is zarr-extensions’ struct with the fields real and imag.

A mode 101 value is 4 bits, unsigned: a row’s first value is the low nibble of its first byte, its second the high nibble, and so on. A row of odd nx ends on a padding nibble, so that every row starts on a byte and has ⌈nx / 2⌉ bytes, and B = ⌈nx / 2⌉ × ny × nz (§8.1). The order is zarr-extensions’ packbits, which is bit packing, not TIFF’s run-length PackBits; the array decodes to one uint8 a value, from 0 to 15. SerialEM writes this mode for K2 and K3 frames.

4. The image¶

The hierarchy is one image at the root (conventions §4), without a name, with one array at path "0": the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A}, where A has ome (M, below), zarr_conventions and refkv_zarrified (§1).

4.1 The array¶

Kind. The file is, by ispg and nz:

kind

volume stack

ispg ≥ 401 (the profile has checked that mz divides nz, §8.1): nz / mz volumes of mz sections

ispg = 0 and nz = 1

ispg = 0 and nz > 1

otherwise (any other ispg, negative or over 230 included)

The axis map. The sections, rows and columns run along the axes maps, mapr and mapc name: 1 is x, 2 is y and 3 is z. The map is applied when the three values are a permutation of 1, 2 and 3; then the sections’ axis is named by maps, the rows’ by mapr and the columns’ by mapc. Otherwise (a 0, a value out of range, or a value repeated) the sections’ axis is z, the rows’ y and the columns’ x. The data is never reordered: the array’s axes are the file’s dimensions in stored order, however they are named. (With the standard map mapc = 1, mapr = 2, maps = 3, the array is z, y, x.)

Axes. For an image, the rows’ axis then the columns’; for an image stack or a volume, the sections’ axis, the rows’ and the columns’; for a volume stack, t, then those three. (t is the volume’s index in the stack, of type time; it is not the acquisition time.)

Chunks (conventions §7, contiguous values): the data is the row-major array V of the array’s shape, with elements of b bytes, at offset 1024 + nsymbt. It is cut as contiguous values with the chunk limit L = 2^20 bytes (1 MiB): blocks of whole volumes or sections when they are small, else blocks of rows of a section, else runs of a row. The chunk grid, the chunk shape and each chunk’s bytes are those conventions §7 gives; an edge chunk along the cut axis is followed by zero bytes up to the whole chunk.

For example, a 256 × 128 int16 stack of 20 sections (the fixture mrc_chunk_sections.mrc) has sections of 65536 bytes, so k = ceil(20 / floor(2^20 / 65536)) = 2 chunks of 10 sections each, the chunk shape [10, 128, 256]. A 1000 × 1100 int8 image of 1100000 bytes, over L, is cut along its rows into 2 chunks of 550 rows, [550, 1000].

Chunks of mode 101. The values are cut with elements of one byte, the same limit, as the safetensors profile cuts a packed tensor (safetensors.md §8.3): when nx is even and each chunk’s first value is the first of a byte, each chunk of values [s, s + m) is the bytes [v + s / 2, v + (s + m) / 2), padded with zero bytes to the whole chunk’s. Otherwise, as for an odd nx, whose rows are not one run of bits, there is one chunk per row, its chunk shape 1 along every axis but the columns’, each the row’s ⌈nx / 2⌉ bytes.

Translation. For a volume or a volume stack (ispg not 0), when the three origin values are finite and at least one is not 0, the image has a translation (conventions §5): the position of the first value, p[0] for x, p[1] for y, p[2] for z, and 0 for t (each only for the axes present). Otherwise it has none: an image’s or an image stack’s origin is a phase origin in pixels, not a position, and nxstart, nystart and nzstart, which crystallographic writers use to place a map in its unit cell, are not applied (§7); all are in header.

The origin’s sign. The position p is origin, each 0 written 0 and not -0, except in a file whose origin has IMOD’s sign, where it is -origin. A file’s origin has IMOD’s sign when all of these hold:

  • the i32 at byte 152 is IMOD’s stamp (§3);

  • bit 2 (the value 4) of the i32 at byte 156, IMOD’s flags, is clear;

  • nversion is not a standard version, from 20140 up to, not including, 21000 (§3).

MRC2014 (note 10) gives the position of a subvolume’s first pixel in its parent: origin is 100, 120 for a subvolume cut 100 and 120 in. IMOD defines it the other way, as the position of the parent’s origin relative to the first pixel, so that a subvolume has negative values, and bit 2 says a file is stored with that sign inverted (IMOD’s MRC format). The first three rows are what IMOD’s own reader does, in mrc_head_read. It reads a standard nversion with bit 2 clear as the standard’s, since IMOD writes that version only with bit 2 set. The last row departs from IMOD’s reader, which gives a file without the stamp and without a standard version IMOD’s sign. That file may be from any writer, and UCSF ChimeraX, like MRC2014, reads it as stored.

4.3 Channels¶

M has an "omero" member, an Omero, when the data type is not complex64 or a mode 3 struct, and dmin and dmax are finite with dmax > dmin, and in no other case: {"channels": [{"label": "C0", "color": "FFFFFF", "active": true, "window": {"min": dmin, "max": dmax, "start": dmin, "end": dmax}}]}, one channel (an OmeroChannel) whatever the kind of file.

5.2 The IR mirror¶

refkv_source is the file’s IR mirror (conventions §11.3). The IR’s elements (the MRC source model) are below; nothing is left out: the header, the extended header, the data, and every byte after them.

The view (conventions §8.7) shows the header; the extended header, opaque bytes, is not shown, and a zarrifier never reads it.

5.4 Equivalence¶

Hierarchies of one file are compared entry for entry, refkv_source included (conventions §11.4).

6. Example¶

7. What the layout does not express¶

This section is informative. OME-NGFF 0.5 places an image by a scale and a translation per axis, names its axes as space, time or channel, and has no per-index coordinates, so several things an MRC header or extended header says have no expression in the layout. They are all kept in header (§5.1) or in the mirror (§5.2), and a reader that needs them must read them there.

  • The unit cell’s angles (cellb). Angles other than 90° make the grid non-orthogonal: a shear, which a scale and a translation cannot express. The layout uses cella and the grid for the scales as if the cell were orthogonal; a map of a monoclinic or triclinic crystal is shown skewed.

  • The space group (ispg from 1 to 230) and the symmetry operators of a CCP4 extended header: crystallographic symmetry and the periodicity of the map. The layout has no notion of either; ispg serves it only to tell a volume from a stack.

  • Where a sub-volume sits. nxstart, nystart and nzstart place the map’s first voxel in the unit-cell grid, in grid units, and origin places it in angstroms. Writers differ on which they set, and how, and a hierarchy has one translation; the layout applies origin for volumes only (§4.2), as MRC2014 directs for EM data, and applies the starts never. A map that an older writer placed by its starts alone is shown at the origin. A file IMOD wrote before it had a stamp, whose origin has IMOD’s sign and nothing to say so, is placed on the other side of its first pixel (§4.2).

  • What a stack’s index means. The sections of an image stack (ispg 0) are independent images, such as micrographs, a tilt series or particles, and the volumes of a volume stack are independent volumes; the layout names the one z (a space axis) and the other t (a time axis) because the OME-NGFF axis types offer nothing closer. kind says which it is.

  • Per-section metadata. FEI1, FEI2, SERI and AGAR extended headers hold a record per section (tilt angle, stage position, dose, defocus, the pixel size of each frame); the layout does not decode them, and OME-NGFF has no place for a value per index anyway.

  • An image’s phase origin (origin with ispg 0), in pixels: not a position.

  • The statistics dmean and rms, the labels, the format version nversion (except that it can decide a mode 0 file’s data type, §3, and the origin’s sign, §4.2), and the extra space (IMOD’s own fields among them, except the signed-byte flag, §3, and the origin’s sign, §4.2).

  • Half-complex transforms. A mode 4 file is usually a Fourier transform of a real volume holding half the spectrum (nx = N / 2 + 1); the layout gives the data type, complex64, not the meaning.

Part 2. The profile¶

The MRC profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

8. MRC profile¶

8.1 Header¶

The input is an MRC2014 file, which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/mrc.json) chose: bytes 208–210 of H are 4D 41 50 (MAP). Its header is the first 1024 bytes of the file (the convention §2); a file shorter than 1024 bytes is rejected. The file is little-endian if byte 212 (the first byte of machst) is 44, and big-endian if it is 11; any other value is rejected. Every field is read in that byte order, at the offset and with the type that the convention §2 gives it. (The second stamp byte, 44 or 41 for little-endian data in different writers, and the fourth byte of map, a space or a NUL, are not checked.)

Checks. The input is rejected unless all of these hold, checked in this order:

  • Dimensions: nx, ny and nz are each at least 1.

  • Mode: mode is in the table of the convention §3; any other value is unknown.

  • Extended header: nsymbt is not negative, and 1024 + nsymbt is at most the file’s size.

  • Volume stack: if ispg ≥ 401, mz is at least 1 and divides nz.

  • Data size: B = nx × ny × nz × b (for mode 101, ⌈nx / 2⌉ × ny × nz) computed exactly is at most 2^53 − 1, and 1024 + nsymbt + B is at most the file’s size.

Every check applies whatever the other fields hold. No other field is checked: the values the layout uses (the convention §4) only change the output as the convention says, and never reject the input. A file whose map field is not MAP, and a file shorter than 212 bytes, are rejected by §1.2. A gzipped map is read as §8.4 says.

The extended header is described (the convention §5.3) and never read: the data starts at 1024 + nsymbt whatever it holds.

8.2 Chunks¶

The data is B contiguous bytes at offset v = 1024 + nsymbt, the column index varying fastest: the value at column i, row j and section k starts at byte v + ((k × ny + j) × nx + i) × b. It is the array V of the convention §4.1, row-major at offset v.

Every chunk of the convention’s array is present. The chunk with coords c (in the array’s axis order), at 0/c/<coords>, is the chunk of V with those coords, and is referenced as conventions §7 references a chunk of contiguous values (with the chunk limit 2^20 bytes): one range of source 0, the chunk’s bytes in the file, followed for an edge chunk by its zero padding. Where conventions §7 makes that padding a literal range, it is instead the range (1, 0, p) of the output’s zero data source (§1.2), p the padding’s bytes: the source holds as many zero bytes as the most padding any reference of the output holds. Where conventions §7 copies the chunk (when its reference, with the padding as a literal range, would not fit in a payload), the chunk is copied, with its padding. The ranges lie within the file (by the data size check). The output’s source table is source 0, followed by the zero data source when a reference is padded; it has no other data source.

MrcChunk, the chunk of V that starts o bytes into the data and holds l of its bytes, padded with p zero bytes (by conventions §7, for the chunk at (i_0, …, i_{a−1}, q, 0, …, 0), o is the offset it gives the chunk’s bytes, l = m × s_a and p = (c − m) × s_a, which is 0 but for an edge chunk along the cut axis):

Where conventions §7 copies the chunk, it is instead bytes: the l bytes and the p zero bytes.

refkv_source is the IR mirror (the convention §5.2). The dataset layout (mrc-dataset.md) is written from the same read: its data variable’s chunks are these chunks again, entry for entry, and its coordinates are deflated index chunks, bytes entries. The archive has no other entries than the root’s and the array’s zarr.json, the array’s chunks, the dataset’s documents and chunks, and the mirror’s.

8.4 Gzipped files¶

A file gzipped whole is one gzip member (RFC 1952) that holds an MRC file, as the EMDB distributes its maps (.map.gz). This profile reads it (spec/zarrify.md §1.2, Choosing the profile: the signature of §8.1 holds of what the file’s first bytes inflate to). S is the stream, those bytes the member holds. Every check of §8.1 is made of S as of a file, but that nothing bounds 1024 + nsymbt + B but the trailer’s check below, and a file is too short when S is.

Reads. The file’s first bytes, doubling from 64 KiB up to 16 MiB until they inflate to the first 1024 bytes of S, and the last 4 bytes of the file, its trailer’s ISIZE. A stream whose start holds less than that is taken to end where it stops. No other byte is inflated: the extended header is not read, as §5.3 says.

The trailer. The input is rejected when ISIZE, the stream’s size modulo 2^32, is not (1024 + nsymbt + B) mod 2^32: the gzip trailer records a stream of <ISIZE> bytes modulo 2^32, not the <1024 + nsymbt + B> of the header and the data: bytes after the data, or a file of several gzip members, which a chunk cannot decode. A bytes codec refuses a chunk of another length than the array’s, and several members are what bgzip writes: its last trailer records its last block’s size.

A packed mode. The input is rejected when the mode is packed (§3) and nx × bits is not a multiple of 8: a gzipped file of <bits>-bit values and odd nx = <nx>, whose rows each start on a byte, which one chunk cannot decode. The rows of such a file are not one run of bits, and the stream cannot be cut into the rows §4.1 would give it.

The array is V as §4.1 says, in one chunk of the whole array: its chunk shape is the array’s shape, and its codecs are bytes (packbits for a packed mode, §4.1), then:

The cost is reads. Nothing is copied and every value is exact, but the chunk is coarse: a gzip stream has no index, so a reader inflates the whole stream to read any value, even one slice, holds the whole array in memory to do so, and reads it with no concurrency. Zarrifying stays cheap, since only the start of the stream is inflated. A reader that needs random access to a large volume should decompress the file once and zarrify that, which gives chunks of at most 1 MiB.

8.5 The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser returns a description of the file: what it found of the file’s known structures, in MRC’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7). Its JSON Schema is mrc/description.json. It holds none of an output’s decisions: the data type of a mode (§3), the kind of file, its axes and their order, the voxel size and the position (§4), the chunks (§8.2) and the root’s source metadata (§5) are the projection’s.

It is a JSON object with these members:

member

value

byte_order

little or big, as the machine stamp gives it (§8.1)

header

every field of the header, as MrcHeader gives it

data

the data’s range: offset, 1024 + nsymbt, and bytes, its size B (§8.1); of a gzipped file (§8.4), in the stream S

gzip

of a gzipped file only: skip, 1024 + nsymbt, and head, the first 1024 bytes of S, the header, as lowercase hexadecimal

elements

the ids of its IR elements (§5.3) by name: data, and of a file that is not gzipped, header and, when nsymbt > 0, extended

The array’s stored description is keyed by header, or of a gzipped file by data, the stream (spec/stored-array.md §7). The projection reads the header from the IR’s header value, or a gzipped file’s from gzip.head, and makes every decision of §3, §4, §5 and §8.2 from it.

The parser still makes one decision of the output: the data element’s form names the data type of §3 (§5.3).
