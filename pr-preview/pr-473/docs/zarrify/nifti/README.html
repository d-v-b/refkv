NIfTI¶

refkv turns an image file into an OME-Zarr dataset by writing a small archive of references to the file’s bytes, without copying the pixels (overview). This page is about NIfTI volumes.

Who this is for¶

NIfTI (.nii) is the working format of neuroimaging: anatomical and functional MRI, diffusion data, templates and atlases. It comes out of dcm2niix, SPM, FSL and AFNI, and is shared through OpenNeuro, GitHub repositories of tools and test data, and lab servers. Someone who wants to look at a volume in an OME-Zarr viewer next to microscopy data, or read one slice of a large 4-D series lazily, has to convert it today.

A NIfTI file is a header followed by one block of voxels, so refkv reads the header (348 or 540 bytes) and writes an archive in which every Zarr chunk is a run of at most 128 KiB of that block: several z-slices, one slice, or some rows of a large slice. The SPM avg152T1.nii template became a 12 KB archive in under 4 s (at spec/zarrify.md revision 16).

Gzipped files¶

A .nii.gz is read as it is, with nothing decompressed but its first bytes: one chunk references the whole file, with the codecs bytes, refkv.skip (the header’s length) and gzip. The cost is reads: a gzip stream has no index, so reading one slice inflates the whole stream, and holds the whole array in memory. To slice a large volume repeatedly, decompress it once and zarrify the .nii. A .nii.gz of more than 2 GiB is past a reader’s default bytes per get (refkv §6.7 rule 5): raise max_get_bytes to read it.

Header-and-image pairs¶

Give the .hdr file. refkv finds the .img file beside it, by its name, and the chunks reference the .img file. Each chunk is a range of it, as in a single .nii file. A file of this kind has the magic ni1 or ni2; a .hdr file with neither, such as ANALYZE 7.5’s, is not read.

What you get¶

One OME-Zarr 0.5 image at the archive root, with one array, 0.

  • Axes: t (4-D and up), c (5-D, or RGB/RGBA voxels), z (3-D and up), y, x. NIfTI’s first dimension, which varies fastest, is x.

  • Data types: every NIfTI integer and float type (uint8 to uint64, int8 to int64, float32, float64), COMPLEX64 and COMPLEX128 as complex64 and complex128, and RGB24 or RGBA32 as uint8 with a c axis. The Neuroglancer fork has no complex data type, so zarr-python reads a complex array and the browser demo does not show one.

  • Chunks: the voxels as the file stores them, cut into equal runs of at most 128 KiB along the outermost axis that allows it: whole volumes or blocks of slices when they are small, else blocks of rows of a slice (13 slices per chunk for the template below).

  • Codecs: bytes in the file’s byte order (transpose first for color voxels and 5-D files). No compression: the file has none.

  • Scale: from the sform or qform when it is axis-aligned with a positive diagonal, else from pixdim; units from xyzt_units (meters, millimeters, micrometers; seconds, milliseconds and microseconds).

  • Translation: the affine’s offset, only when the affine is axis-aligned. A rotated or flipped affine, such as the common radiological sform with a negative x step, gives no translation.

  • Intensity scaling: the raw values are stored. A nontrivial scl_slope/scl_inter is recorded in the root’s source metadata (the refkv_zarrified convention) as "nifti": {..., "scaling": {"slope": s, "inter": i}}; compute s × raw + i.

  • Header: every field of the NIfTI header and its affine, under refkv_zarrified.nifti. The whole file (the header, its extensions, the voxels and every byte between) is described on refkv_source by the Rust core’s IR mirror, from which it is rebuilt byte for byte; its view refkv_source/tree shows the header, the extender and each extension of at most 1024 bytes (since revision 26).

  • omero: a display window from cal_min/cal_max, or R, G, B (A) channels for color voxels.

Try it¶

example.py zarrifies a public file and plots it with matplotlib. Its dependencies are in its header (PEP 723), so it runs on its own, with refkv from PyPI:

uv run docs/zarrify/nifti/example.py

SPM’s avg152T1.nii template (903 KB, GPL-2.0), from corpus_nifti.txt:

uv run refkv zarrify https://raw.githubusercontent.com/spm/spm/main/canonical/avg152T1.nii avg152T1.vzip

print(g.attrs["ome"]["multiscales"][0]["datasets"])
print(g.attrs["refkv_zarrified"]["nifti"]["scaling"])
a = g["0"]
print(a.shape, a.dtype, a.chunks)
print(a[45, 50, 40:48])

Viewing¶

The Neuroglancer fork (https://github.com/d-v-b/neuroglancer, branch vzip) displays NIfTI archives of uint8, int8, uint16, int16, uint32, int32, uint64 and float32 data; avg152T1.nii renders through a local build of the demo, with millimeter scales. It has no int64 or float64 data type, so float64 volumes (which some pipelines write) cannot be shown there; zarr-python reads them. Neuroglancer shows the raw values: apply the nifti scaling yourself where it matters.

Supported and not supported¶

Supported:

  • NIfTI-1 and NIfTI-2 single files (.nii), either byte order, up to five dimensions.

  • Extensions after the header are kept in the source metadata; they do not change where the voxels start.

Rejected:

  • A gzipped file with bytes after the voxels, or of several gzip members (bgzip): a chunk could not decode it. Decompress the file first.

  • A header-and-image pair whose .img file is missing or too short, or whose header file is not named .hdr. NIfTI records nothing that ties the two files together, so an .img of the right length from another image would not be noticed.

  • COMPLEX256, binary and FLOAT128 types.

  • Data along dimensions 6 and 7, such as CIFTI-2 files.

  • A vox_offset inside the header, or voxel data past the end of the file.

In the browser¶

The browser code (js/) reads NIfTI (NIfTI-1 and NIfTI-2 single files):

  • Up to five dimensions (t, c, z, y, x), either byte order, all integer and float types, and RGB/RGBA voxels.

  • Chunks of as many whole slices as fit in 128 KiB, or of row blocks when a slice is over it.

  • Pixel size and units as scale; an axis-aligned qform or sform as translation; the whole header, and its intensity scaling, recorded under refkv_zarrified.

Not supported, and refused with HTTP 422: COMPLEX256, and dimensions 6 and 7 (CIFTI).

Performance¶

  • Zarrifying reads the first 552 bytes of the file: one range request, after one request for the file’s size.

  • Reading a chunk is one range request of at most 128 KiB.

  • The archive has one entry per chunk, 7 for this template, beside its 7 documents and the mirror’s 2 chunks.

How it’s verified¶

js/test/nifti/verify.py zarrifies 88 synthetic NIfTI files (including inputs to reject) with the browser code, reads them back through python/src/refkv and zarr-python, and compares the values with nibabel’s unscaled data. compare.py checks that the Python and browser outputs are equivalent on those files and on the 12 public files of corpus_nifti.txt (nibabel’s and NiiVue’s test data, SPM templates and dcm2niix regression data).

  • Profile: spec/zarrify/nifti.md

  • Rust core: rust/refkv-ir/src/nifti.rs (the parser) and rust/refkv-ir/src/project/nifti.rs (the projection)

  • Python host: python/src/refkv/ir/; browser host: js/src/zarrify/ir/

  • Frozen reference: conformance/zarrify/reference/refkv_reference/nifti/ and conformance/zarrify/reference/ts/nifti/

  • Fixtures: fixtures/nifti/
