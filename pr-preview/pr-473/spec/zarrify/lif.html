LIF¶

The Zarr layout of a Leica LIF file (the Leica Image File that LAS X and LAS AF write, versions 1 and 2), of a Leica object file (LOF), of a LIF extension file (LIFEXT) and of a LAS X project of XLEF, XLCF, XLIF and XLLF documents (§8), and the translation of their XML into JSON. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store is the LIF profile, Part 2 below, cited as “the profile §n”.

Convention version: 0 (until release, conventions §1) · UUID: b099ab1f-f9d4-4276-9006-9ff1193a34b2 · Schema: schema.json

Changes: changes/lif/, one file per change.

Added 2026-10-25.

This document has two parts (conventions §11.1).

Part 1. The convention¶

This convention gives a layout only to the files that meet its requirements. Where it says that “the input is rejected”, or that something MUST hold, a file that fails has no layout under this convention, and the profile rejects it.

Every convention is held to reconstruction and efficiency (conventions, introduction). For LIF this means: every block the file holds (the XML header, every memory block with its ID and data, those of no image included) and the bytes after the last block can be rebuilt from the hierarchy, byte for byte (its IR mirror, §5.3); each image’s elements of the XML, its dimensions and channels, are on its group as JSON; and no document grows with the number of planes: an image’s documents grow with its dimensions and channels only, which the profile bounds (the profile §7.3).

2. The source¶

All integers are little-endian, u8, u32 and u64 unsigned. Offsets are from the start of the file.

2.1 Blocks¶

A LIF file is a sequence of blocks. The first, at offset 0, is the header block:

Memory block i is the i-th the walk finds (the profile §7.2), from 0, in file order. Bytes after the last block are the tail.

2.2 The XML header¶

The XML header’s bytes MUST be well-formed UTF-16LE (a code unit of an unpaired surrogate rejects the input); its text is read by the tag scan of the TIFF convention §3 (skipped sections, tags, and attribute values with their references decoded), and its tags nest into elements as the CZI convention §2.7 says: an element’s children are those opened while it is the innermost open one, and the root is the first element at depth 0, self-closing or not. Elements are named by their local name. A path A/B names an element’s first child A and that child’s first child B.

The root MUST be named LMSDataContainerHeader, or LMSDataContainerEnhancedHeader in a LIFEXT file (§2.6), and its attribute Version MUST be an integer, 1 or 2: the file’s version, which gives the width of the memory blocks’ data sizes. An XML header whose text is LMS_Object_File is a Leica object file’s (LOF): its XML is elsewhere (§2.5).

An attribute’s integer is its value with whitespace removed from both ends, one or more digits of a value at most 2^53 − 1; its decimal is that value when it matches the decimal of the CZI convention §2.7 and is finite.

2.3 Images¶

The elements are the elements named Element in the root’s subtree, in document order: the file’s own, its folders, and its images. An image is an element with a path Data/Image; the images are numbered k from 0 in document order. An element with no image, such as a folder, or FLIM data (Data/SingleMoleculeDetection), has no layout: its memory block is kept as bytes (§5.4).

An image’s path is the attribute Name of each element from the file’s own element to the image, in that order (an element without one: null). Its memory block is named by the attribute MemoryBlockID of its first child Memory, which MUST be present: the memory block whose ID’s code units are the attribute value’s (§2.1). Exactly one memory block MUST have that ID, and two images MUST NOT name one block. (LAS X gives elements without data, such as folders, IDs it writes no block for, or the ID of one block of size 0; they name no image’s block.)

2.4 Dimensions and channels¶

2.5 Leica object files¶

A LOF holds one memory block, of one element, and its XML after the data. Its header block (§2.1) has the XML text LMS_Object_File (15 characters), so that what follows it, from offset h = 13 + 2 × 15 = 43, is:

The magic bytes and the test value MUST be these, and the XML MUST lie within the file. The bytes after the XML are the tail. The memory block has no ID. Its data is the data of the file’s image, if it has one, whatever its XML’s MemoryBlockID says, and the file has at most one image.

The XML is read as §2.2 says, with §2.3 and §2.4 for its image, but for two things. An image need not have a Memory element. XML that starts with <Data>, as an older writer’s does, is read as if it were <LMSDataContainerHeader Version="2"><Element> followed by that XML and the end tags of those elements, so its image’s path is [null], and it has no Name or UniqueID.

A LOF of no image is accepted. LAS X writes one beside a frame image, of a SimpleListInMemory: its output is the root and refkv_source.

2.6 LIFEXT files¶

A LIFEXT file holds optional data that LAS X writes beside a LIF file: pyramid levels and histograms of the LIF file’s images. It is a LIF file (§2.1) but for two things. The root of its XML header is LMSDataContainerEnhancedHeader, its elements under children of the root named ChildrenOf. And the data size of each of its memory blocks is a u64, also in the files of Version 1 that LAS X writes. A ChildrenOf has an attribute MemoryBlockID, the ID of a memory block in the LIF file, whose image the elements under it belong to.

The images of a LIFEXT file are read as a LIF file’s are (§2.3) and each is an image of its output. The profile reads the LIFEXT file alone: it presents the images the file holds, records the MemoryBlockID each belongs to as its parent (§5.2), and does not look for the LIF file, which the LIFEXT file does not name. Nor does a LIF file name its LIFEXT file, so §7.2 reads none for a LIF file (for the reason of zarrify §1.9, Probing): to present a file’s LIFEXT images, zarrify the LIFEXT file.

3.2 Channels¶

An image’s channels are taken in ascending order of their BytesInc (two channels of one BytesInc reject the input): channel c, from 0, has the c-th, o_c. The image MUST have a dimension of DimID 1: its X is the used one, else the first, of BytesInc s_x, and its channels are:

The sample of channel c at the index i_d along each dimension d is at o_c + Σ i_d × s_d bytes into the data of the image’s memory block, s_d the dimension’s BytesInc. The image’s extent is O + Σ (N_d − 1) × s_d + e over its dimensions (N_d its NumberOfElements, O the largest o_c), computed exactly, which MUST be at most its block’s data size D.

3.3 Axes and fields¶

The image’s axes (conventions §3) are t when its dimension of DimID 4 is used, c when it has more than one channel, z when its dimension of DimID 3 is used, then y and x. Its shape is N_T, the number of channels, N_Z, N_Y and N_X (each for its axis present; N_Y is 1 when the image has no used dimension of DimID 2, as a line scan over time, x and t, has none). Each number of the shape MUST be at most 2^31.

Its field dimensions are its used dimensions of any other DimID, in document order, d_1, …, d_q, and its fields the combinations of their indexes: field f = i_1 + N_1 × (i_2 + N_2 × (…)) (the first fastest) has the offset Σ i_j × s_j; there are F = N_1 × … × N_q of them, one when q is 0, at most 65536. The image’s planes are N_T × n' × N_Z × F (n' the number of channels, or 1 when they are interleaved: a band of each is a chunk), at most the references a run makes, 2^22 + 4 × the file’s size: a dimension whose BytesInc is 0 repeats a plane without growing the extent. Each field is an image of the output (§4.2): OME-NGFF 0.5 has no axis for a mosaic’s tile, a wavelength or a rotation.

3.4 Rows and bands¶

A row is R = N_X × s_x bytes. When Y is used, its BytesInc s_y MUST be at least R; the rows are packed when it is R, or Y unused, and padded otherwise (stride-aligned RGB rows), the bytes between them in no chunk.

A chunk holds a band of b rows of one plane. b is the largest divisor of N_Y such that b × R ≤ 2^24 and, for padded rows, a band of b rows (b ranges of R bytes, s_y apart) starting at the farthest band’s offset (the profile §7.4: the last band of the plane of the last time, channel, depth and field) has a reference payload of at most 65519 bytes (spec/zarrify.md §1.2); at least 1. So every chunk is one range of its block, or for padded rows the ranges of its rows, and holds at most 16 MiB (or one row).

4.4 Mosaics¶

A tile scan is an image with a used dimension of DimID 10, one element per tile, whose Data/Image has an Attachment named TileScanInfo with a child Tile per tile (its FieldX, FieldY and stage position PosX, PosY, PosZ). Tiles overlap: the stage moves less than a field of view between them, and LAS X stitches them into a merged image, which it writes as an image of its own. Each tile is a series of the output, as a CZI tile is an array of its own (the CZI convention §4.4): its pixels as the file holds them, its place in §5.2’s tile and tile_scan, and nothing stitched. The tiles have no translation: the stage frame’s direction and origin (FlipX, FlipY, SwapXY and the objective’s) are not in the image’s own frame, so a viewer places them from the source metadata, or shows the merged image.

Part 2. The profile¶

The LIF profile of spec/zarrify.md is §7 of this document. (Conformance is spec/zarrify.md’s Appendix A.) What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

7. LIF profile¶

7.1 Detection¶

Signature (spec/zarrify.md §1.2, tested at the precedence of profiles/lif.json), either of two:

  1. Bytes 0–3 of H are 70 00 00 00 (the test value) and byte 8 is 2A (the magic byte). No other profile’s signature matches these bytes: a NIfTI file starts with a header size of 348 or 540, the others with a magic number of their own. A LOF or a LIFEXT file starts with the same bytes, and its XML says which it is (§2.2).

  2. H starts with the UTF-8 byte order mark EF BB BF or with <?xml, and holds the bytes LMSDataContainerHeader: a LAS X document, an input of §8. No other signature tests for XML, so nothing else claims these bytes, and a LIF file’s XML is UTF-16 at byte 13. LAS X writes the root within the first 100 bytes.

7.2 Reading¶

The zarrifier reads, in any order (spec/zarrify.md §1.2, evaluation order):

  1. the header block’s fixed part, its first 13 bytes, which MUST lie within the file, and the XML header;

  2. the walk. From o = 13 + 2c: if o is the file’s size, the walk ends with an empty tail. Otherwise the H bytes at o are a memory block’s fixed part when they lie within the file, their test value is 0x70 and both magic bytes 0x2A, its ID ends within the file, its D is at most 2^53 − 1 and its data ends within the file; the walk then continues at the end of its data. When they are not, or after 2^20 blocks, the walk ends and the tail is the bytes from o to the end of the file. The walk never rejects: a block that cannot be read ends it, and an image whose block lies after it names a block the file does not hold (§7.3).

A LOF has no walk. After step 1 it is read in order: the 19 bytes of its version fields and memory block’s fixed part, and its XML block’s fixed part and XML (§2.5).

Nothing else is read: no byte of a block’s data. (The implementations read the first 64 KiB, then the rest of the XML header when it is longer, then the blocks’ fixed parts and IDs in batches at the offsets the XML’s Memory elements predict: the first one’s (the file’s own element’s), then those with a Size above 0, each ID once, in document order, since LAS X writes no block for its folders’ empty and repeated IDs. A file whose blocks follow its elements is walked in one round of requests, and each block the prediction misses costs another. The prediction decides only what is read ahead, never the output. A LOF’s XML is read, with its fixed part, in a read of at most 1 MiB from the end of the data, then of the rest of the XML when it is longer.)

7.3 Rejection¶

The input is rejected when a read of §7.2 step 1 lies outside the file, when a rule of this profile fails, and wherever the convention says the input is rejected or that something MUST hold: the header block (§2.1: test value, magic byte, the XML within the file), the XML header (§2.2: UTF-16, the root, the version), a LOF’s parts (§2.5: their magic bytes and test value, the XML within the file, at most one image), each image (§2.3: its Memory, its memory block found once and named by it alone; §2.4: its dimensions and channels and their attributes; §3: its data type, channels, X, rows, extent, shape and planes), the images in document order. The walk (§7.2 step 2) never rejects, and neither does what only the source metadata reads.

7.6 Decisions¶

  • Hierarchy. A file holds a tree of elements (folders and images), each image with its own memory block. The output is a bioformats2raw collection of the images in document order, as the CZI and ND2 profiles collect their scenes and positions, with each image’s path in the tree on its group (§5.2). A field dimension (a mosaic’s tiles, a lambda scan’s wavelengths) selects an image, as ND2’s positions and CZI’s scene, illumination and view dimensions do: OME-NGFF 0.5 has room for one time axis, one channel axis and space.

  • Axes and chunks. The axes come from DimID, not from the order of the dimensions: LAS X usually stores channels between Y and Z (or outside T), and the BytesInc of each dimension and channel places every plane, so a chunk is a band of one plane whatever the order of the others. Bands follow the CZI profile’s row bands, bounded at 2^24 bytes.

  • Channels. Planar channels are chunks of their own; interleaved channels (RGB) are one chunk with c inside it and the transpose codec, as the TIFF profile reads interleaved samples. The channel order is the bytes’ order (BytesInc): BGR data stays BGR, labeled by ChannelTag’s colors, as the CZI convention keeps its subblocks’ B, G, R order.

  • Mosaics. Not stitched; each tile is an image with its stage position in its source metadata (§4.4), as CZI keeps each overlapping tile.

  • Metadata. Nothing is lost: the XML header and every block are in the mirror, byte for byte, and each image’s element, memory, dimensions and channels are on its group as text, as the XML writes them, so that no number changes in a translation.

  • LIFEXT files of several parents. A LIFEXT file has a ChildrenOf for each image of the LIF file it adds to, as public files do, and each gives images here. liffile reads only the first.

  • LOF and LIFEXT. A LOF is an image of one block and a LIFEXT file a LIF file’s images in another root, so each has the layout a LIF file’s images have: the same series, array and source metadata. A LIFEXT file is not joined to its LIF file: neither names the other. So it has its own output, with each image’s parent, and a LIF file’s output does not depend on a file beside it.

  • Signature. Precedence 55, after CZI’s: the test value and magic byte are five fixed bytes that no other signature reads.

  • Data types. Every bit depth the XML can describe in whole bytes: 1 to 64 bits, as uint8 to uint64, and float16 to float64; the Resolution is kept as the window’s range. Bit-packed data (BitInc other than 0), other data types, channels of two types, and channels that are neither planar nor interleaved cannot be referenced as chunks, and are rejected.

  • LAS X documents. A project’s documents describe the images a LIF file’s XML header describes, so its output has the layout of a LIF file’s, and its images their paths in the same tree. The documents are read whole and kept in the mirror. A LOF gives what its document does, and LAS X writes both the same; the profile reads a LOF’s for the layout, so that a project and a LOF of it give one image. §8.2 lists the rest.

8. LAS X documents¶

LAS X can save a project as many files instead of one LIF file: documents, which are XML, name one another and name the files that hold the images. An XLEF is the experiment, an XLCF a collection, an XLIF an image or another element, and an XLLF a folder view. Images are held in LOFs (§2.5), or in TIFF, JPEG, PNG or BMP files, one per plane or per image.

Such an input is a file read as a store (zarrify §1.8), and its output has the layout of §4: a bioformats2raw collection of the images, each with its path in the tree of elements.

8.1 The documents¶

A document is UTF-8, usually after a byte order mark, and is read by the tag scan of §2.2. Its bytes MUST be valid UTF-8, its root MUST be named LMSDataContainerHeader, with a Version of 1 or 2, and the root MUST have a child Element: the document’s element. So a document holds one element, and:

A Memory of exactly one entry, a Block whose File ends in .lof in ASCII lower case, names a LOF. It MUST have an integer Offset and an integer Size (§2.2), for an element that is an image or not. Any other entries name nothing the profile reads (§8.4).

8.4 The images¶

The documents are walked from the named file, a document before the ones it names, and these in the order of its References, each document once. The walk gives the images in order, so that k and the series (§4.1) number the input’s images as a LIF file’s do, and each image’s path (§2.3) is the Name of each document’s element on the way to it.

An image element with a LOF is presented. Its LOF MUST be a LOF (§2.5, the LOF "<key>" is not a LOF file), MUST have an image (the LOF "<key>" that "<document>" names holds no image), and that image is the one the output has: its dimensions and channels are its LOF’s, which LAS X writes the same as its document’s, and its checks are §7.3’s, whose message then starts with the LOF "<key>": . Its Offset plus its Size MUST be at most the LOF’s data size D, and the image’s extent (§3.2) at most its Size: its plane offset (§7.4) counts from B plus its Offset. LAS X writes an Offset of 0 and a Size of D.

Any other image element is not presented, and is recorded on the root (§5.1) with its reason. That is an image in TIFF, JPEG, PNG or BMP Frames, an image of several Blocks, an image whose Block is not of a LOF, and one whose Memory names no file. Its document is still in the mirror, as is every other element, so nothing about it is lost but the reference to its pixels. A later version MAY present an uncompressed TIFF frame: a frame’s Size is the plane’s, and its Offset where the plane falls in the image, so it needs each TIFF’s strips read, and one file for each plane at worst.

The references of an image are ranges of its LOF’s object, named by object URL (zarrify §1.8).

9. The description¶

This section is not part of the convention: nothing it specifies is written in an output. Beside the IR, the parser of a LIF, LOF or LIFEXT file returns a description of the file: what it found of the file’s known structures, in Leica’s own terms, for a projection to read with the IR and its stored arrays (spec/stored-array.md §7).
