NumPy¶

The Zarr layout of a NumPy file: a .npy file, which holds one array, or a .npz archive, a ZIP file of .npy members such as np.savez and np.savez_compressed write. What all of refkv’s conventions share is in spec/conventions.md, cited here as “conventions §n”. How refkv produces this layout as a reference store, and which files it accepts, is the NumPy profile, Part 2 below.

Convention version: 0 (until release, conventions §1) · UUID: 62b1d1ba-8eb3-465c-a333-75e096fce519 · Schema: schema.json

Changes: changes/npy/, one file per change.

Added 2026-10-30.

This document has two parts (conventions §11.1).

Like MP3 and HDF5, NumPy’s arrays are not images: the hierarchy holds each array as a plain Zarr array, with no OME-NGFF metadata. The values stay in the file; each chunk is a range of it, or, for a member that np.savez_compressed deflated, the member’s deflate stream as a gzip member.

2. The NPY format¶

A .npy file, and each .npy member of a .npz archive, is the NPY format of NumPy’s NEP 1 (“A simple file format for NumPy arrays”), in one of its versions 1.0, 2.0 and 3.0. It is a preamble, then a header, then the data. All integers are little-endian.

The preamble is p bytes: 10 for version 1, 12 for versions 2 and 3. The header is the n bytes after it: text, in ISO 8859-1 for versions 1 and 2 and in UTF-8 for version 3, holding a Python dictionary literal. NumPy writes it as repr writes a dictionary of three members, descr, fortran_order and shape, followed by spaces and a newline that pad the preamble and header to a multiple of 64 bytes (16 in older versions of NumPy):

{'descr': '<f8', 'fortran_order': False, 'shape': (3, 4), }

The data is the B bytes after the header, at offset p + n: the array’s elements, each of e bytes, in C order (the last index varying fastest) when fortran_order is false, and in Fortran order (the first index varying fastest) when it is true. B is e times the product of shape (1 for the shape (), an array of rank 0).

The literal. The header’s text is read as this subset of Python’s literals, the one NumPy writes:

header  = ws "{" ws [entry {ws "," ws entry} [ws ","]] ws "}" ws
entry   = string ws ":" ws value
value   = string | integer | "True" | "False" | tuple | list
tuple   = "(" ws ")" | "(" ws value ws "," ws ")" | "(" ws value {ws "," ws value} [ws ","] ws ")"
list    = "[" ws [value {ws "," ws value} [ws ","]] ws "]"
integer = digit {digit} ["L"]
string  = "'" {char} "'" | '"' {char} '"'
ws      = {" " | "\t" | "\n" | "\r"}

An integer’s L is a Python 2 long, as files that Python 2 wrote have them ((2L,)); the integer is its digits. A char is any character but the quote that opens the string, a backslash and a line break, or an escape: \\, \', \", \n, \r, \t, \xHH, \uHHHH and \UHHHHHHHH (H a hexadecimal digit), the character they name. A tuple of one value needs its comma, as in Python: (3,).

The members. The dictionary has exactly the members descr, fortran_order and shape, each once, in any order:

  • fortran_order is True or False;

  • shape is a tuple of integers, the array’s size along each of its axes, at most 64 of them (NumPy’s limit);

  • descr is a type string (§3), or a list of fields, a structured data type: each field a tuple (name, descr), name a string and descr a type string or a list of fields.

E is < or >. A datetime’s or timedelta’s unit U is one of Y, M, W, D, h, m, s, ms, us, ns, ps, fs and as, and k, a positive integer, is 1 when it is not written. A structured data type’s F is its fields in order, each {"name": name, "data_type": D}, D the field’s Zarr data type: a field’s type string is one of the table’s rows above EU<n> (numbers, booleans, datetimes and timedeltas), or a list of fields of its own, a nested structure. A structure is presented only when its names are unique and not empty, and its fields of more than one byte all have one byte order, the codec’s (none when every field is one byte).

Any other type string or list is not presented: an object array (|O, whose data is a pickle), f16 and c32 (long doubles, which Zarr has no type for), a datetime or timedelta without a unit, a size of 0, a type string with =, and a structure with a field of shape ((name, descr, shape)), a padding field (an empty name), a string, bytes or void field, or two byte orders. (§7 lists what the layout does not express.)

The fill value is the data type’s zero: false for bool, 0 for a number (a float’s too), [0, 0] for a complex type, 0 for a datetime or timedelta, "" for fixed_length_utf32, and for a structure the object of its fields’ fill values, by name. No chunk of an array is missing, but those of an array of size 0.

4. The hierarchy¶

The hierarchy is a group at the root: the root zarr.json is {"zarr_format": 3, "node_type": "group", "attributes": A}, where A has zarr_conventions and refkv_zarrified (§1) and nothing else.

4.1 An NPY file¶

A .npy file’s array is the root’s one child, at path array (§4.3).

4.2 An NPZ archive¶

A .npz archive is a ZIP file (§8.3) whose members are its central directory’s entries, in its order. A member is presented, as an array at the path K, its name, when:

  • its file name ends with .npy, and K is the file name without it;

  • K is a Zarr node name: it is not empty, has no /, is not . or .., does not start with __, and is not zarr.json; and it is not refkv_source;

  • it is stored (method 0) or deflated (method 8), its preamble and header are those of §2, its data type is one of §3’s, and its data lies within its stored bytes; a deflated member’s preamble, header and data are its stream, the bytes its deflate data inflates to, and its data ends the stream.

A presented member’s array is what np.load gives for the key K: NumPy’s NpzFile names its arrays so. Every other member is not presented, with a reason (§5.1): it is in the root’s source metadata, and its bytes are in the mirror.

4.3 The arrays¶

An array’s stored shape is shape reversed when fortran_order is true and the rank r is at least 2, and shape otherwise: the shape whose C order is the data’s order. A data type with a trailing axis (|S<n> and |V<n>) adds n to the end of both: an element’s bytes are its last, fastest axis whatever the order.

4.4 The refkv.skip codec¶

refkv.skip is a bytes-to-bytes codec, configuration {"length": k}, or {"length": k, "keep": n}, k and n non-negative integers. Decoding drops the first k bytes of its input, which MUST have at least k, and, with keep, any after the n that follow them, which it MUST have too; encoding puts k zero bytes before its input. (A compressed FITS file’s arrays use keep, fits §2.1: what its stream decodes to goes on past the array.) A deflated member’s chunk is its stream as a gzip member (§8.4): gzip decodes it to the stream, the NPY preamble and header and then the data, and refkv.skip, with k the p + n bytes of the preamble and header, leaves the data, which bytes decodes. (No codec of zarr-python, numcodecs or imagecodecs drops a prefix of more than a checksum’s 4 bytes.)

5.2 The IR mirror¶

refkv_source is the file’s IR mirror (conventions §11.3). The IR’s elements (the NumPy source model) are below; nothing is left out: the preamble and header of every NPY array the profile read, every member (a deflated member’s preamble, header and data are in what its deflate data inflates to, and are elements of that space), the ZIP structures, and every byte between or after them.

5.4 Equivalence¶

Hierarchies of one file are compared entry for entry, refkv_source included (conventions §11.4).

A .npz archive of np.savez(f, image=a, labels=b) has the arrays image and labels. np.savez_compressed deflates its members: then each array is one chunk, the member’s deflate data between a gzip header and trailer, and its codecs end with refkv.skip and gzip (§4.4). ]

and its one chunk, fortran/c/0/0/0, is the literal 1F 8B 08 00 00 00 00 00 00 FF, the member’s 189 bytes of deflate data, and the member’s CRC-32 and size (248) as two u32s.

7. What the layout does not express¶

This section is informative.

  • Compressed archives. np.savez_compressed deflates each member, its NPY header and its data together, so no range of the file holds the array’s elements: a deflate stream can only be read from its start. Such a member is one chunk, however large, and reading any of its elements inflates all of it: a 1 GiB member is a 1 GiB chunk, which a reader holds in memory whole, and fetches whole over HTTP. A viewer that reads an array in tiles (Neuroglancer) reads it at most once at a time, but cannot show a part of it sooner. Members compressed with another method (bzip2, LZMA) are not presented (method).

  • Object arrays hold Python objects as a pickle, which is code, not data: an object array is not presented, and np.load reads one only with allow_pickle=True.

  • Long doubles (f16, c32, and f12 on some platforms) have no Zarr data type.

  • Structures with padding, fields of shape, or string fields have no struct of the zarr-extensions that holds them field for field; the record’s bytes are in the mirror.

  • Fixed-length bytes and voids (|S<n>, |V<n>) are uint8 with a trailing axis, as the HDF5 convention’s fixed-length strings are (hdf5.md §3.1): a reader that wants NumPy’s S<n> views the last axis as one element.

  • Field titles and the header’s other text. The header’s spacing, its member order, and anything a later NumPy writes beyond the three members are in the mirror (header), not in the layout.

Part 2. The profile¶

The NumPy profile of spec/zarrify.md is §8 of this document. What every profile’s Part 2 shares is in spec/zarrify.md, Profiles.

8. NumPy profile¶

8.1 Signature¶

The input is a .npy file or a .npz archive, which its signature (spec/zarrify.md §1.2, tested at the precedence of profiles/npy.json, before the SAFE profile’s) chose: bytes 0–5 of H are 93 4E 55 4D 50 59 (a .npy file); or bytes 0–3 are 50 4B 03 04, a ZIP local file header, whose file name (its length the u16 at byte 26, the name at byte 30, within H) ends with .npy (a .npz archive). A ZIP file whose first member is not a .npy member does not match.

8.2 An NPY file¶

The preamble is the file’s first bytes, and the header the n after it (the convention §2). The input is rejected unless all of these hold, checked in this order:

  • Preamble: the file has at least 10 bytes, and major is 1, 2 or 3 and minor 0, and, for versions 2 and 3, at least 12 bytes.

  • Header: p + n is at most the file’s size.

  • Text: a version 3 header is UTF-8.

  • Literal: the header is a literal of the convention §2, a dictionary of exactly the members descr, fortran_order and shape, each of its type.

  • Data type: descr is presented (the convention §3).

  • Data size: B computed exactly is at most 2^53 − 1, and p + n + B is at most the file’s size.

Bytes after the data are allowed (a gap).

8.3 The archive¶

The archive is read as safe.md §8.4 reads the zip form, for its end of central directory, its central directory and its local headers, with the same checks: the end records, ZIP64, the central directory’s entries (disk 0, not encrypted, a UTF-8 name), each local header’s signature, and the members’ ranges [lho, ds + cs) lying before the central directory and not overlapping. Every member’s local header is read, whatever its size. Besides:

  • Names: no two members have the same file name.

  • No product: the members are not a SAFE product: none of safe.md §8.4’s rules on names, directories and methods apply.

  • Stored members: a stored member (method 0) MUST have cs = us.

  • Members: a stored or deflated member whose file name ends with .npy has its preamble and header read from its data, at ds (a deflated member’s from its stream, which is inflated as far as its header ends), by §8.2’s checks, each of which makes the member not presented (the convention §4.2) instead of rejecting the input: the preamble and header (header), the data type (datatype), and the data size, p + n + B at most cs (size); a deflated member’s deflate data that ends, or is invalid, before its header does, or a header that ends past byte 2^20 of its stream, p + n > 2^20 (header: the profile inflates no more of a member than that to read its header); and a deflated member’s data that does not end its stream, p + n + B = us (size). A member that is neither stored nor deflated is not read (method).

  • Arrays: at least one member is presented; otherwise the input is rejected, with each member’s reason: no member can be presented: a.npy (method), b.txt (not_npy).

8.4 Chunks¶

A stored array’s data is B contiguous bytes at offset v, its elements in the order of its stored shape (the convention §4.3), C order. Every chunk of the array is present. The data is cut as conventions §7 cuts contiguous values of the stored shape (the trailing axis included, with the element its byte), with the chunk limit 2^20 bytes (1 MiB); the chunk shape along each axis is the cut’s, put in the array’s axis order. An array of rank 0 is one chunk, <name>/c, the range (0, v, e); an array with a size of 0 has none.

NpyChunk, the chunk that starts o bytes into the data and holds l of its bytes, padded with p zero bytes (conventions §7; p is 0 but for an edge chunk along the cut axis):

A deflated member’s array, of B > 0 bytes, is one chunk, <name>/c/0/…/0 (one 0 for each of its axes, a trailing axis included; <name>/c for rank 0): its deflate data, the cs bytes at ds, as a gzip member (RFC 1952), which inflates to its stream. Its reference is never copied: its literals are 18 bytes. With B = 0 it has none.

8.6 The description¶

This section is not part of the convention: nothing it specifies is written in an output. A NumPy parser returns, beside the IR, a description of the file: what it found of the source, for a projection to read with the IR’s stored arrays (spec/stored-array.md §7). It holds none of an output’s data types, codecs or chunks. It is a JSON object with two members:

member

value

own

the root’s source metadata (§5.1)

arrays

the arrays the profile presents, in the output’s order: a .npy file’s one, or a .npz archive’s presented members in its central directory’s order

and an entry of arrays has these:

member

value

path

the array’s path (§4)

header

its NPY header’s text, decoded as its version says (§2): the array’s declaration

stored

the id of the IR element that keys its stored array, its header element

deflate

a deflated member’s only: crc and size, its central directory entry’s CRC-32 and its uncompressed size (which a ZIP64 entry’s 32-bit fields do not hold)

The profile’s projection reads an array’s shape and its order from its stored array, its data from the chunk map (one unit, its data element), and its data type, byte order and fill value from header’s descr (§3). A deflated member’s header and data are in the space of the derived element that is its stream (§5.3): the stream is that element’s extent in the file, and the offset the refkv.skip codec skips to (§8.4) is its data element’s in that space (its header’s end, for an array of no elements). A stored array may have no grid, and so no unit, for an array the profile presents all the same: one of a type NumPy’s own layout gives no size, a<n>, which §3 reads as S<n>. The projection then reads the declaring structure for the rest (spec/stored-array.md §2.3): its data is the data element beside its header.

The parser still decides which members are presented and at which path (§8.3), and gives the data element a form that names its data type (§5.3): both are in the IR and the source metadata as before.
